# v2.0 实施计划 —— 插件 Provider 扩展点（最小可用）

> 依据：`docs/superpowers/specs/2026-10-28-插件provider扩展点-design.md`（含 D1–D4 四个已定决策）
> 目标：**一个 provider 插件能被安装、启用、出现在模型选择器、能真的用来生成文本**，
> 且剪裁 / 流式 / 统计 / 中断全部复用既有链路。
> 非目标（留 v2.1）：登录窗口、`paste-token`、`capabilities` 扩展端点、官方 WorkBuddy 插件。

---

## 0. 一条在写计划时才定下来的硬约束：**provider token 不落盘**

`providerConfigs` 会被持久化到项目/应用设置里（`src/lib/project-store.ts`）。
而 v2 的 D3 决策要求"凭证由插件持有，QMAI 只做内存中转"。

**矛盾点**：如果把 `providerToken` 写进 `providerConfigs[providerId].apiKey`，它就会被落盘。

**决定**：

| 字段 | 是否落盘 | 说明 |
|---|---|---|
| `label` / `baseUrl` / `savedModels` / `maxContextSize` / `maxOutputTokens` | ✅ 落盘 | 都是可公开的元数据，重启后仍能显示 |
| `apiKey`（= providerToken） | ❌ **不落盘** | 请求前由通用适配器通过命令 `plugins_provider_auth(providerId)` 现取 |

**验收方式**：安装并启用一个 provider 插件后，在设置文件里 `grep` 该 token → **必须搜不到**。

## 2. T1：清单与权限

### 2.1 `plugin.json` schema 2

在 `src-tauri/src/plugins/manifest.rs`：

- `schema` 从只接受 `1` 改为接受 `1 | 2`
- `schema == 2` 时允许 `contributes.providers`；`schema == 1` 时出现该字段 → `E_PROVIDER_REQUIRES_SCHEMA_2`
- 新增类型：

```rust
pub struct ProviderDecl {
    pub id: String,
    pub name: String,
    #[serde(default)] pub description: String,
    #[serde(rename = "authKind")] pub auth_kind: AuthKind,
    #[serde(default, rename = "settingsPagePath")] pub settings_page_path: Option<String>,
    #[serde(default, rename = "authDomains")] pub auth_domains: Vec<String>,
    #[serde(default)] pub capabilities: Vec<String>,
}

#[serde(rename_all = "kebab-case")]
pub enum AuthKind { None, BrowserLogin, PasteToken, ImportFile }
```

校验（错误码写进 4.2 的表）：
- `id`：`^[a-z][a-z0-9-]{1,31}$` 且不含 `/`
- 与内置 11 个 provider 冲突 → `E_PROVIDER_ID_CONFLICT`
- 与另一个已安装插件的 provider 冲突 → 同上
- 声明了 `providers` 但 `permissions` 无 `net:listen` → `E_PROVIDER_REQUIRES_NET_LISTEN`
- `capabilities` 白名单外 → `E_PROVIDER_CAPABILITY_UNKNOWN`

### 2.2 新权限

`KNOWN_PERMISSIONS` 加 `net:listen`（需用户勾选，危险度中）。

⚠️ 注意：`KNOWN_PERMISSIONS` 是"需用户勾选"列表，`AUTO_GRANTED_PERMISSIONS` 是自动授予。
`net:listen` 属于**必须勾选**（它会让 QMAI 开一个本机端口给插件用）。

### 2.3 测试

至少覆盖：schema 1 拒绝 providers / schema 2 通过 / provider id 与内置冲突 / 缺 net:listen 拒绝 / authKind 非法。

## 3. T2：provider 注册表与探活

新文件 `src-tauri/src/plugins/providers.rs`：

```rust
pub struct PluginProvider {
    pub plugin_id: String,
    pub provider_id: String,
    pub name: String,
    pub base_url: String,
    pub token: String,            // 只在内存
    pub capabilities: Vec<String>,
    pub settings_page: Option<String>,
    pub models: Vec<ProviderModel>,
    pub ready: bool,
    pub last_error: Option<String>,
}

pub struct ProviderModel {
    pub id: String,
    pub name: String,
    pub max_input_tokens: i64,
    pub max_output_tokens: i64,
    pub supports_tool_call: bool,
    pub supports_vision: bool,
    pub credit_multiplier: Option<f64>,
}
```

流程（在 `start_plugin` 成功后）：

1. 宿主 bind `127.0.0.1:0` 拿端口 → 立刻关闭（把号给插件；见设计 D4）
2. 生成 `provider_token`（uuid v4）
3. `initialize` 的 `_qmai.provider = { port, token, baseUrl }`
4. 轮询 `GET /health`（最多 10s，间隔 250ms）→ 通了才 `ready = true`
5. `GET /v1/models` → 解析出 `Vec<ProviderModel>`
   - **缺 `maxInputTokens` 的模型被丢弃并记 warn**（设计 3.4：剪裁依赖它）
6. 存进 `PluginsState.providers: AsyncMutex<HashMap<String, PluginProvider>>`

新命令：

| 命令 | 返回 |
|---|---|
| `plugins_providers()` | `Vec<PluginProviderView>`（**不含 token**） |
| `plugins_provider_auth(providerId)` | `String`（token，供请求前现取；见 0 节） |
| `plugins_provider_refresh_models(providerId)` | 重新抓 `/v1/models` |

停用/卸载时：从 providers 表移除 + 收回端口。

## 4. T3：前端类型与通用适配器

### 4.1 打开类型

按设计 6.1 的表，只改类型声明，**内置的 case 一律不动**：

```ts
// 之前： provider: "openai" | "anthropic" | ... | "workbuddy"
// 之后：
export type LlmProviderId =
  | "openai" | "anthropic" | "google" | "azure" | "ollama" | "custom"
  | "minimax" | "claude-code" | "codex-cli" | "cursor-cli" | "antigravity-cli" | "workbuddy"
  | (string & {})   // 运行期注入的插件 provider；保留上面字面量的自动补全
```

涉及 4 处：`wiki-store.ts:236`、`settings-types.ts:15`、`settings-types.ts:42`、`llm-presets.ts:16-26`。

### 4.2 通用适配器

`src/lib/llm-providers.ts` 的 `switch (provider)` **加一个 default 分支**（不是重构成查表）：

```ts
default: {
  // 插件 provider：统一走 OpenAI 兼容 + 宿主分配的 baseUrl + 现取的 provider token
  return {
    url: `${baseUrl}/v1/chat/completions`,
    headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
    body: openAiCompatibleBody(model, messages, options),
  }
}
```

关键：**body 复用已有的 OpenAI 分支构造器**，不要复制一份（否则日后 OpenAI 那边改了这里不同步）。

需要新增：`ensurePluginProviderAuth(providerId)` —— 调 `plugins_provider_auth` 并缓存到内存（进程内有效，停用即清）。

## 5. T4：模型合并与界面

### 5.1 写入 `providerConfigs`

`plugins_providers()` 返回后（应用启动、插件启停、手动刷新时）：

```ts
providerConfigs[providerId] = {
  label: name,
  baseUrl,                          // http://127.0.0.1:<port>
  savedModels: models.map(m => ({ id: m.id, name: m.name, model: m.id, createdAt: 0 })),
  maxContextSize: maxInputTokens,
  maxOutputTokens,
  // apiKey 故意不写（见第 0 节）
}
```

> `savedModels` 的字段形状以 `getEffectiveSavedModels` 实际读取的为准，实现前先读该函数。

### 5.2 设置页运行期卡片

`LLM_PRESETS` 是静态数组，设置页按它渲染。新增：把插件 provider 转成同形状的 preset，**在运行时追加**到渲染列表（不改 `LLM_PRESETS` 本体）。

卡片上两个入口：`登录/设置`（v2.0 先只对 `authKind=none` 显示"无可用设置"，v2.1 接窗口）、`刷新模型`。

### 5.3 高危确认

启用 provider 插件时的确认层文案，用设计 §7 那段具体文字（不是泛泛的"可能联网"）。

## 6. T5：假 provider 插件与端到端

在 `tests/fixtures/plugins/fake-provider/` 造一个**零依赖 Node 脚本**：

- 实现 `/health`、`/v1/models`（3 个模型，其中一个**故意缺 `maxInputTokens`**）、`/v1/chat/completions`（SSE，回固定文本 + 带 usage）
- 同时实现 MCP stdio（`initialize` / `tools/list`），因为 v2 的握手仍走 MCP

验证清单（可自动化，写入 Rust 集成测试或前端测试）：

- [ ] 装 → `plugins_providers()` 有它，`ready=true`
- [ ] 缺 `maxInputTokens` 的模型**不在**返回列表里
- [ ] 不带 token 直接打端点 → 401
- [ ] 断掉健康检查（让脚本 `/health` 返 500）→ `ready=false` 且带 `last_error`
- [ ] 停用后 provider 从列表消失、端口被收回
- [ ] **token 不出现在任何设置文件里**（第 0 节）
- [ ] 前端：模型出现在选择器、能发请求、流式有多个 chunk、结束后 usage 非 0
