文风自进化实施计划

Goal

让「我的文风」在用户自己写的正文上自主迭代：每 3~5 个「打开日」自动跑一轮（同一天内多次打开只算 1 次），以用户 holdout 章节的确定性指标为标尺，把新画像与基线画像各生成一段探针文本比距离，更接近才保留。候选写成一份每轮唯一的文风预设，绝不自动启用、绝不改写用户正在用的那份；用户先看、再点启用。默认关闭。

Architecture

纯函数与 IO 彻底分离。节律（style-evolution-schedule）与指标折算（style-evolution-metrics）是两个零 IO 模块，所以「同日只算一次 / 跨天 +1 / 阈值浮动」与「归一化 + 距离 + ε」都能在一个测试里穷举。项目级状态只读写 <项目>/.qmai/style-evolution.json，走自己的通知、不进 bumpDataVersion()。编排引擎把读盘、调模型、取时间全部从参数注入，生产接线只在 App.tsx 的延迟 hydration 里挂一次 tick；模型调用走 callAnalysisModelText + resolveTaskLlmConfig，绝不直接调 streamChat。

十条硬约束
  1. 候选预设的 sourceBook 必须每轮唯一（带轮次号，例如 我的文风 · 自动进化 · 第 N 轮）。upsertWritingStylePreset 按 sourceBook 去重并原地覆盖 profile、保留 id（writing-style-store.ts:137-148），而 setEnabledWritingStyle（:166-174）不因 profile 变化而失效 —— 用固定来源的话，用户一旦启用候选，下一轮就会静默换掉他正在用的画像，而且此时「候选」与「在任」是同一个对象，回滚无从下手。见 Task 5。
  2. 回滚 = 删除本轮候选，且仅当它未被启用。removeWritingStylePresets（:186-201）删掉当前启用项时会把 enabledStyleId 置 null ⇒ 一次「回滚」会把项目的文风整个关掉。已被启用时面板必须拒绝删除并说明原因。见 Task 6。
  3. 分析失败不推进计数。达到阈值时只加计数、不归零；归零只由 completeRound() 做，它代表「一轮完整跑完」。写成「达到阈值就归零」会让一次失败的分析白吃掉 3~5 个打开日。见 Task 1、Task 5。
  4. 归一化不许除以目标值。纯中文小说里 latinCharRatio 恒为 0（style-metrics.ts:261），x/T 会得到 NaN，比较恒 false，判定静默退化且不报错。必须用固定的每项量纲 scale[i]；punctuationPerThousand 是 8 个子字段，必须摊平。见 Task 3。
  5. 同一个打开日最多尝试一次，靠 lastAttemptedOn；而且它必须在跑模型之前就落盘。否则在这一轮跑完（可能 40 秒以上）之前盘上还是旧值，而 hydrateDeferredProjectState 是 void（App.tsx:576，不 await、无锁），用户切书 A→B→A 就会再触发一轮。见 Task 7。
  6. 绊线名单是两张表，解析基准不同。analysis-model-call.guard.spec.ts:18-27 的 ANALYSIS_FILES 是裸文件名、按 book-analysis/ 解析；:76-79 的 ANALYSIS_COMPONENT_FILES 是 src/ 相对路径。新引擎在 src/lib/novel/，只能加进后者（字面量是 lib/novel/style-evolution-engine.ts，不带引号）；加进前者会 ENOENT，表现为「测试报错」而不是「断言失败」，极易被误读成守卫生效。见 Task 9。
  7. 「进备份」不是自动的。备份对 .qmai/ 是显式白名单：backup.rs:181-192 的 PROJECT_OWNED_FILES 里没有 style-evolution.json，不勾「拆书分析」时该文件直接被跳过 ⇒ 恢复后开关与打开日进度全丢。要改三处（常量 + 测试里的字面清单 + 那条一致性测试守着）。见 Task 2。
  8. 候选的 workbenchStyle 是规格与任务书冲突的一处，本计划按任务书做。任务书要求候选产出 workbenchStyle.styleFingerprint（复用 compileStyleFingerprint）；规格 00 节第 14 条却明确改成「不产出」。照任务书做的代价要认下来：writing-style-store.ts:356 的 if/else 一旦走结构化分支，constitution（:363）与 integratedDna（:367）都不再注入 —— 于是候选的 integratedDna 变成「存了但不参与注入」的字段。所以本计划额外钉死一条安全线：绝不允许空 rules 的 workbenchStyle（空 rules 会让注入内容缩成指纹的头几行，比不产出还糟）。见 Task 5 开头的冲突说明。
  9. 探针「跑偏」要按回滚处理并推进计数，不是 incomplete。规格 00 节第 8 条把两种失败分开：「无法判定」属于 reverted（该花的调用已经花完，结果就是不采纳），只有「没跑成」（调用抛错）才是 incomplete、才重试。写混这一格会得到一个反复重试、永远给不出结论还一直花钱的功能。latinCharRatio 与最短长度是两个现成的探测器。见 Task 5。
  10. 只缓存指标，绝不缓存距离；建立基线那一轮不跑探针。距离依赖目标 T，而 T 随笔者的正文增长而变化，缓存距离等于拿过期标尺量新候选。探针还必须多段（3~5 段 / 固定目标字数）：只有一段时 paragraphs === 1，oneSentenceParagraphRatio / dialogueParagraphRatio 只能取 0 或 1，距离会被「模型这次分了几段」这一随机事件主导。建立基线那轮没有可比对象，跑探针测不出任何东西 —— 规格 09 节的成本表是 1 / 2 / 3 次三种情形，写成「每轮都跑两次探针」会让首轮白烧一篇 token。见 Task 5。

四条与原始推测不同、下游必须照做的既成事实

  • advanceOpenDay 不接收 rng。它不抽阈值 —— 抽阈值只发生在 completeRound(state, today, rng) 里，因为只有「一轮完整跑完」才该换新节律。于是「阈值的随机源」只有一个入口，测试要固定阈值序列时注入点也只有一个。两者都是泛型 <T extends StyleEvolutionScheduleState>，返回的新状态保持调用方更宽的类型（例如 StyleEvolutionState），调用方不必做 as 断言。
  • resolveVerdict 返回对象而不是字符串：{ verdict: "kept" | "reverted", reason: "improved" | "not-improved" | "undecidable", delta: number | null }（delta 是 distanceBase - distanceCandidate，无法判定时为 null）。把「为什么」与「结论」分成两个字段，是为了让「无法判定」这条路径可以被单独断言，而不是混进「没有更近」里 —— 而它的归宿仍是 reverted（fail-closed，拿不到证据 ≠ 验证通过）。
  • 状态字段名是 probe.stylePresetId，轮次记录里的候选 id 字段是 stylePresetId（不是 candidateStyleId）。本轮记录还多带一个 sourceBook，面板与回滚都要按它定位预设。

/**
 * 「文风自进化」复核面板。
 *
 * 设计立场：这个功能**自动花钱、自动写盘**，所以面板必须让用户一眼看清
 * 「它攒到哪一步了 / 上一轮到底干了什么 / 现在拿来比的是哪一份」，并且
 * 把两个不可逆的动作（启用候选、回滚候选）分开、各自说清后果。
 *
 * ⚠️ 回滚**绝不**删除正在使用的那份候选：`removeWritingStylePreset` 删掉当前启用项时
 * 会把 `enabledStyleId` 置 null（`writing-style-store.ts:186-201`），
 * 也就是一次「回滚」会把项目的文风整个关掉。这里选择**拒绝并解释**，
 * 而不是照删不误 —— 用户想要的是撤销这次进化，不是关掉文风。
 *
 * ⚠️ 本面板订阅的是 `subscribeStyleEvolution`（本 store 自己的通道），
 * 不是 `dataVersion`：节律状态的写入刻意不进 `bumpDataVersion`（见 store 文件头），
 * 那会让写作统计、技能库、文风选择器整片重读，而这次变化只是「打开日 +1」。
 */
const VERDICT_LABELS: Record<StyleEvolutionRoundOutcome, string> = {
  bootstrap: "已建立基线（下一轮才开始比较）",
  kept: "已保留新候选（比基线更接近你的正文）",
  reverted: "已回滚（没有比基线更接近你的正文）",
  incomplete: "这一轮没跑成",
}

const HISTORY_LIMIT = 5

function percent(value: number | undefined): string {
  return typeof value === "number" && Number.isFinite(value) ? value.toFixed(4) : "—"
}

/** 两个 `YYYY-MM-DD` 之间差几天。按本地日期构造，不用 `Date.parse`（那会被当成 UTC）。 */
function daysBetween(from: string, to: string): number | null {
  const parse = (value: string): number | null => {
    const match = /^(\d{4})-(\d{2})-(\d{2})$/.exec(value)
    if (!match) return null
    return new Date(
      Number(match[1]),
      Number(match[2]) - 1,
      Number(match[3]),
    ).getTime()
  }
  const start = parse(from)
  const end = parse(to)
  if (start === null || end === null) return null
  return Math.max(0, Math.round((end - start) / 86_400_000))
}

/**
 * 基线回落链：**上一轮 keep 的候选 → 当前启用 → 都没有**（返回 `null`）。
 *
 * ⚠️ 引擎里有一份同样的判定（它要拿基线去跑探针），面板这份是**展示用**的 ——
 * 两边都按同一条链取值，所以面板显示的「当前基线」就是引擎实际用来比较的那一份。
 *
 * ⚠️ 已从文风库里被删掉的候选要跳过：`outcome` 记着它、盘上却没有它，
 * 这种「记录还在、预设没了」正是用户手动删除基线后的状态，按规格该回落到启用项。
 */
function resolveBaseline(
  rounds: StyleEvolutionRound[],
  presets: WritingStylePreset[],
  enabledStyleId: string | null,
): WritingStylePreset | null {
  for (let index = rounds.length - 1; index >= 0; index -= 1) {
    const record = rounds[index]
    if (!COMPLETED_ROUND_OUTCOMES.includes(record.outcome)) continue
    const id = record.stylePresetId
    if (!id) continue
    const found = presets.find((preset) => preset.id === id)
    if (found) return found
  }
  return presets.find((preset) => preset.id === enabledStyleId) ?? null
}

/**
 * 基线的括号说明。
 *
 * ⚠️「（上一轮保留的候选，未启用）」这一档是规格 07 节点名要求的：
 * 「keep 但不启用」之后，比较对象已经换成那条候选，而用户以为还是自己启用的那份 ——
 * 不写出来，面板显示的「当前基线」就会误导他判断这次进化值不值得启用。
 */
function baselineSuffix(baseline: WritingStylePreset, enabledStyleId: string | null): string {
  if (baseline.id === enabledStyleId) return "（正在使用）"
  return "（未启用）"
}

为什么标记不能写在 await 之后

为什么 in-flight 表必须放在模块级、而且必须同步占位。引擎里「先落盘 lastAttemptedOn 再跑模型」那道防线发生在读盘之后：两次并发调用会各自读到同一份旧状态，于是两次都认为自己该跑。Set.add 在任何 await 之前执行，第二次调用必然看到它 —— 这是唯一能挡住「void 调用 + 一天 4 个入口」这一格的写法。

反面写法（很容易写出来）：把 new Set() 放在每次调用里，或把 marker.add 放在第一个 await 之后 —— 两者都让守卫形同虚设，而「await 之后占位」在单线程测试里照样绿，只有并发用例能杀它。

/**
 * 同一个进程里，**每个项目一把**的 in-flight 标记。
 *
 * 为什么非要有它：`hydrateDeferredProjectState` 是 `void`（`App.tsx:576`，不 await、无锁），
 * 而打开项目一天有 4 个入口（`handleProjectOpened` 的 `:445`/`:582`/`:593`/`:624`）。
 * 用户在这几十秒里切书 A→B→A，两次调用会**各自读到同一份旧状态**——
 * 引擎里「先落盘 lastAttemptedOn 再跑模型」的那道防线发生在**读之后**，
 * 所以两次都会认为自己该跑。进程内的同步标记是唯一能挡住这一格的东西。
 *
 * `Set.add` 是同步的、在任何 `await` 之前，所以第二次调用必然看到它。
 */
const inFlight = new Set<string>()

/**
 * 生产环境的正文收集：用户自己项目的 `wiki/chapters/`。
 *
 * ⚠️ 刻意**不**复用拆书库的 `loadChapterList`：拆书库读的是导入的外部书、走的是它自己的
 * 分卷缓存与工作台版本管理（规格 01 节「为什么不能直接把拆书库那条链路接过来」）。
 * 用户自己的正文就是普通章节 md，剥掉 frontmatter 与章名后取正文。
 *
 * 任一章读失败都跳过而不抛错：一章坏了不该让整轮自进化作废。
 */
async function collectChapterBodies(projectPath: string): Promise<string[]> {
  let files: Array<{ name: string; path: string }>
  try {
    files = flattenMdFiles(await listDirectory(`${projectPath}/wiki/chapters`))
  } catch {
    // 还没有 `wiki/chapters` 目录 = 还没写正文。返回空数组，由引擎给出「样本不足」。
    return []
  }

  const bodies: string[] = []
  for (const file of files) {
    try {
      const raw = await readFile(file.path)
      // 正文里可能带 YAML frontmatter 与 `# 第 N 章` 标题行，两者都不该进文风指标。
      const { body } = splitChapterHeading(String(raw ?? ""))
      const text = body.replace(/^\s*---[\s\S]*?---\s*/, "").trim()
      if (text) bodies.push(text)
    } catch {
      // 跳过读不出来的那一章。
    }
  }
  return bodies
}

/**
 * 「文风自进化」的启动 tick —— **App 层唯一的调用入口**。
 *
 * 三件在这里做掉、不该散到调用点的事：
 *   1. 自建生产依赖（正文收集 + 模型调用）；调用方只给项目路径。
 *   2. 复用模块级 in-flight 表：同一次会话里切来切去也只会有一轮在跑。
 *   3. **吞掉异常**：这是后台行为，一次网络抖动或坏文件不该变成未处理拒绝，
 *      更不该弹给用户。`console.warn` 留痕即可。
 *
 * ⚠️ 返回结果只为测试与日志用；`App.tsx` 里是 `void` 调用它。
 */
export async function runStyleEvolutionTick(
  projectPath: string,
  deps: {
    callModel?: (prompt: string) => Promise<string>
    collectChapterBodies?: (projectPath: string) => Promise<string[]>
    now?: string
    rng?: () => number
    /** 测试注入用；生产走模块级的 `inFlight`。 */
    inFlight?: Set<string>
  } = {},
): Promise<StyleEvolutionRoundResult | null> {
  const marker = deps.inFlight ?? inFlight
  if (marker.has(projectPath)) {
    // 同一个项目已经有一轮在跑。**不**报错、**不**排队：这一轮该由正在跑的那次完成。
    return null
  }
  marker.add(projectPath)

  try {
    return await runStyleEvolutionRound(projectPath, {
      callModel: deps.callModel ?? createStyleEvolutionModelCaller(),
      collectChapterBodies: deps.collectChapterBodies
        ?? ((path: string) => collectChapterBodies(path)),
      now: deps.now,
      rng: deps.rng,
    })
  } catch (error) {
    console.warn("[文风自进化] 本轮未完成：", error)
    return null
  } finally {
    // 无论成功、失败还是抛错都必须释放，否则这个项目此后永不进化。
    marker.delete(projectPath)
  }
}

/**
 * 生产环境的模型调用：走拆书库的共享封装，**绝不**直接调 `streamChat`。
 *
 * 动态 `import()` 有两个理由：① 不让引擎进启动包；② 与 `App.tsx` 里那些
 * `await import("@/stores/…")` 的写法一致。
 *
 * 关思考重试等策略由 `callAnalysisModelText` 负责 —— 这也是绊线名单（Task 9）
 * 要盯着本文件的原因：绕过它就会丢掉思考-only 时的重试流。
 */
export function createStyleEvolutionModelCaller(
  modelKey?: string,
  signal?: AbortSignal,
): (prompt: string) => Promise<string> {
  return async (prompt: string) => {
    const [{ callAnalysisModelText }, { resolveTaskLlmConfig }] = await Promise.all([
      import("@/lib/novel/book-analysis/analysis-model-call"),
      import("@/lib/novel/book-analysis/analysis-model-resolver"),
    ])
    return callAnalysisModelText(
      resolveTaskLlmConfig({ modelKey }),
      [
        { role: "system", content: "你只输出被要求的内容，不写解释、前言或结尾寒暄。" },
        { role: "user", content: prompt },
      ],
      { signal, cancelMessage: "用户取消文风自进化" },
    )
  }
}
