# 插件平台 v3 —— 声明式优先的完整机制设计

> 基线：v2.0 已完成（`df71e28c`），当前机制见 `docs/plugins/current-mechanism-baseline.md`。
> 本文定义 v3：把插件按「是否执行第三方代码」分层，用同一份清单 / 同一个中心 / 同一套权限承载。
>
> 目标需求（产品已确认）：
> 1. **灵感类**：纯内容包，安装时装好，之后一直可用
> 2. **脑洞生成器**：声明式无代码（表单 + 提示词 + 输出映射）
> 3. **模型相关**：A 模型渠道（已完成）+ B 当前模型增强 + C 观测
> 4. 界面：**插件中心 + 有限固定插槽**，插槽里放**宿主渲染**的 UI（不是插件自己的 UI）

---

## 0. 一句话结论

**先把插件分成两层，再统一：**

| 层 | 跑第三方代码 | 覆盖需求 | 风险 |
|---|---|---|---|
| **Tier 1 声明式** | ❌ 不跑 | 灵感内容包、脑洞生成器、提示词/参数增强、观测 | **零执行风险** |
| **Tier 2 进程** | ✅ 子进程（MCP stdio） | 工具、模型渠道、代码型钩子 | 中（v1/v2 已有基础设施） |
| **Tier 3 UI 沙箱** | ✅ + 进宿主界面 | 自定义面板 | 高，**本期不做** |

已确认的产品需求里，**前两类完全落在 Tier 1**。

---

## 1. 为什么不做「一切皆插件」

DeepSeek Harness 的「一切皆插件」成立，是因为它**从第一行代码起就是容器架构**（其 `app.asar` 中 `cordis` 出现 3526 次、`__ModuleLoader__` 108 次、`plugin-loader` 118 次）。
QMAI 不是，**也不应该变成那样**：

| | DSH | QMAI |
|---|---|---|
| 产品定义 | 通用 agent 运行时 | **写作领域应用** |
| 价值在哪 | 运行时本身 | **写作能力本身**（章节生成、上下文工程、长篇一致性） |
| 正确形态 | 一切皆插件 | **内核 + 丰富贡献点** |

把「章节生成」「上下文裁剪」也变成可替换插件，等于自拆护城河。**正确的对标是 VS Code**（内核不是插件，但贡献点极丰富），不是 DSH。

因此 v3 的目标不是"把一切拆成插件"，而是：**在不重写内核的前提下，把贡献点做厚、把第三方代码的执行面做窄。**

## 2. 分层与包结构

### 2.1 清单 schema 3

```jsonc
{
  "schema": 3,
  "id": "idea-generator",
  "name": "脑洞生成器",
  "version": "1.0.0",
  "description": "根据灵感生成书名、标签、简介与人设",
  "author": { "name": "…", "url": "…" },
  "license": "MIT",
  "requires": { "qmai": ">=4.5.0" },

  // 本包用到了哪几层（决定是否 spawn 进程、是否需要高危确认）
  "kind": ["declarative"],

  "contributes": {
    "contentPacks": [],   // Tier 1 · 灵感素材
    "actions":      [],   // Tier 1 · 表单 + 提示词 + 输出映射
    "hooks":        [],   // Tier 1/2 · 请求、工作流、观测
    "tools":        [],   // Tier 2（v1 已有）
    "providers":    []    // Tier 2（v2 已有）
  },

  "slots": ["chapter-toolbar", "inspiration-browser"],

  "configSchema": { "type": "object", "properties": {} },

  // 免执行发现：仅用于商店/列表展示，不用来调用
  "preview": {
    "actions": [{ "id": "generate-titles", "title": "生成书名" }],
    "contentPacks": [{ "id": "scifi", "title": "科幻灵感包", "count": 120 }]
  }
}
```

`schema` 从 2 提到 **3**。清单仍是**封闭契约**（`deny_unknown_fields`），新增字段一律 bump。

### 2.2 目录

```
idea-generator/
├── plugin.json
├── content/inspirations.json      ← Tier 1 数据
├── prompts/*.md                   ← 提示词（便于多语言与长文本）
└── index.js                       ← Tier 2 入口（**可选**）
```

### 2.3 关键决策 D1：只有声明了 Tier 2 贡献才启动进程

- 纯 Tier 1 插件：`processState` 恒为 `"declarative"`，不 spawn、不占端口、不占内存
- 只要 `tools` 或 `providers` 非空，或存在 `impl: "process"` 的 hook，就必须有 `runtime`

> **为什么**：这是"用户敢装、我们敢上架"的根本。装 20 个灵感包不应带来任何进程开销。

## 3. 声明式动作（`actions`）—— 脑洞生成器的核心

一个 action = **表单 + 提示词 + 输出映射**。宿主渲染表单、宿主调模型、宿主按映射写回。**作者一行代码不写。**

### 3.1 完整示例

```jsonc
"actions": [{
  "id": "generate-titles",
  "title": "生成书名",
  "description": "根据题材和灵感生成多个书名备选",
  "slot": "chapter-toolbar",

  "form": {
    "fields": [
      { "key": "genre", "type": "select", "label": "题材", "required": true,
        "options": [{ "value": "xuanhuan", "label": "玄幻" },
                    { "value": "scifi",    "label": "科幻" }] },
      { "key": "idea", "type": "textarea", "label": "你的灵感", "required": true,
        "maxLength": 2000, "placeholder": "一句话说清核心设定" },
      { "key": "count", "type": "number", "label": "备选数量",
        "default": 5, "min": 1, "max": 10 }
    ]
  },

  "prompt": {
    "system": "你是中文网文书名策划，擅长短、狠、有钩子的书名。",
    "user": "题材：{{genre}}\n核心灵感：{{idea}}\n请给出 {{count}} 个书名，每行一个，不要编号、不要解释。"
  },

  "output": {
    "mode": "list",
    "schema": { "type": "array", "items": { "type": "string" }, "maxItems": 10 },
    "presentation": "chips",
    "targets": [
      { "kind": "project-field", "field": "bookTitle", "label": "设为书名", "confirm": true },
      { "kind": "insert-at-cursor", "label": "插入到光标处" },
      { "kind": "clipboard", "label": "复制" }
    ]
  },

  "model": { "strategy": "current", "minContextTokens": 8192 },
  "limits": { "timeoutMs": 60000, "maxOutputTokens": 2000 }
}]
```

### 3.2 表单字段类型（本期只做 6 种）

| type | 说明 | 额外约束字段 |
|---|---|---|
| `text` | 单行 | `maxLength` `placeholder` |
| `textarea` | 多行 | `maxLength` `rows` |
| `number` | 数字 | `min` `max` `step` `default` |
| `select` | 单选下拉 | `options[{value,label}]` |
| `multiselect` | 多选 | `options` `maxSelected` |
| `toggle` | 开关 | `default` |

未识别的 `type` → 运行时降级为 `text` 并在校验器里报 warning（不拒绝整包，避免我们加字段类型时卡住老插件）。

### 3.3 变量插值

| 命名空间 | 示例 | 来源 |
|---|---|---|
| 表单值 | `{{genre}}` | 用户填写 |
| 配置值 | `{{config.style}}` | `configSchema` 对应的用户配置 |
| 项目上下文 | `{{project.bookTitle}}` `{{chapter.title}}` `{{selection}}` | **需要项目读能力**（见第 7 章） |

**校验规则**：模板里引用了不存在的变量 → `qmai-plugin validate` 报错（安装时只警告，避免模板里有条件分支时误杀）。

**权限要求**：引用了 `{{project.*}}` / `{{chapter.*}}` / `{{selection}}` 的 action，其所属插件**必须声明并获批 `fs:project-read`**，否则该 action 在校验阶段就被拒绝（不是运行时才失败）。纯表单变量的 action 不需要任何权限。

### 3.4 关键决策 D2：输出目标是**枚举**，不是路径

`targets[].kind` 白名单：

| kind | 含义 | 约束 |
|---|---|---|
| `project-field` | 写入项目字段 | `field` 必须是枚举值（见第 7 章） |
| `insert-at-cursor` | 插入编辑器光标处 | 只在有打开的编辑器时可用 |
| `clipboard` | 复制到剪贴板 | — |
| `chapter-note` | 追加到当前章节备注 | 只追加，不改正文 |

**绝不提供"写任意文件"。**

> **为什么**：声明式插件虽不跑代码，但它驱动宿主写项目。若允许任意路径，等于给了它间接的完全写权限——正好抵消 Tier 1 的安全优势。枚举同时带来业务语义（"设为书名"而不是"写第 37 行"）。

### 3.5 关键决策 D3：解析失败必须可降级

`mode` 三选一：

| mode | 期望模型输出 | 解析失败时 |
|---|---|---|
| `list` | 每行一条 | 降级为 `text` 展示 + 允许手动复制 |
| `text` | 纯文本 | 不解析 |
| `json` | 严格 JSON | 降级为 `text` 展示原文 |

**永不因解析失败把错误抛给用户**——模型不听话是常态，不是用户的错。降级同时在日志记一条，便于作者改提示词。

### 3.6 执行流程

```
用户点插槽里的 action 按钮
  → 宿主渲染表单（若该 action 无表单，直接执行）
  → 校验必填 / 类型 / 长度
  → 插值生成 system + user 消息
  → 用「当前模型」（或 action.model 指定的策略）发起流式请求
  → 流式展示在结果面板（可中止）
  → 完成后按 mode 解析
  → 展示 targets 按钮，用户点哪个执行哪个（涉及覆盖的需二次确认）
```

## 4. 内容包（`contentPacks`）—— 灵感类

### 4.1 声明

```jsonc
"contentPacks": [{
  "id": "scifi-inspiration",
  "title": "科幻灵感包",
  "description": "120 条赛博 / 末世 / 星际的设定切入点",
  "slot": "inspiration-browser",
  "file": "content/inspirations.json",
  "maxItems": 5000,
  "actions": [
    { "kind": "insert-at-cursor", "label": "插入正文" },
    { "kind": "project-field", "field": "bookIntro", "label": "设为简介" },
    { "kind": "run-action", "actionId": "expand-idea", "label": "让 AI 扩写" }
  ]
}]
```

### 4.2 数据格式

```json
{
  "version": 1,
  "items": [
    { "id": "i001", "title": "最后一班地铁",
      "body": "末班车只有七个人，其中六个没有影子。",
      "tags": ["都市", "悬疑"] }
  ]
}
```

校验：`version` 必须为 1；`items` 为数组；每条必须有 `id`（唯一）、`title`、`body`；`tags` 可选。

### 4.3 使用流（全部宿主渲染）

```
插件中心 → 灵感库 → 卡片列表（搜索 + 标签筛选）
        → 选中某条 → 右侧操作按钮：插入正文 / 设为简介 / 让 AI 扩写
```

「让 AI 扩写」= 走 **action 执行器**（复用第 3 章），不另做机制。

**链式调用保护**：`run-action` 只能指向**同一插件内的 action**，且执行时维护一个调用栈——出现环（A→B→A）或深度 >3 直接拒绝并报错。**禁止跨插件 `run-action`**，否则会形成插件间的隐式依赖，卸载一个就会连带失效。

### 4.4 关键决策 D4：内容随包分发，不做运行时抓取

- 容量上限：**单包 5MB / 5000 条**，超限**拒绝安装**（不是运行时崩）
- 全部内容在安装时落到 `<插件根>/<id>/content/`，之后离线可用
- **零网络权限**——内容包不需要 `net:https`

> **为什么**：用户已确认"安装时装好，之后一直可用"。好处是离线可用、可审核、可按内容评分，且不需要任何权限。

## 5. 钩子机制（工作流 + 请求 + 模型增强 / 观测，一套）

### 5.1 四组作用域

| 组 | 事件 | 覆盖需求 | 失败策略 |
|---|---|---|---|
| **请求前** | `beforeLlmRequest` | 模型增强：注入系统提示词、参数预设、缓存键增强 | **fail-open**（用原请求） |
| **响应后** | `afterLlmResponse` | 模型增强：去 AI 味、格式规整 | **fail-open**（用原响应） |
| **工作流** | `beforeChapterDraft` `afterChapterDraft` `beforeReview` `afterReview` `beforePolish` `afterPolish` | 纯工作流 | **修改类 fail-open；门禁类 fail-closed** |
| **观测** | `onLlmUsage` `onChapterCompleted` | 模型观测：用量/成本、超预算提醒 | **fail-open**（纯通知） |

### 5.2 关键决策 D5：同一个 hook 支持两种实现

```jsonc
// Tier 1 · 声明式：去 AI 味不需要写代码
{ "on": "afterLlmResponse",
  "impl": "prompt",
  "template": "下面这段文字 AI 味太重，请改写得更自然，保持原意与长度：\n{{text}}" }

// Tier 2 · 代码型：复杂处理才需要
{ "on": "afterLlmResponse",
  "impl": "process",
  "tool": "rewrite_style" }
```

> **为什么**：让 80% 的钩子插件保持零代码。只有真正复杂的文本处理才升级到代码型。

### 5.3 关键决策 D6：超时必须**真取消**

- 独立预算：请求前/后 **8s**、工作流 **15s**、观测 **2s**
- 超时发 MCP `notifications/cancelled`，让插件真的停手
- 对照 DSH：它明确"超时 ≠ 取消，工作仍在跑"，靠插件作者自觉幂等。**我们不做这个妥协。**

### 5.4 关键决策 D7：同事件多插件**串行** + `priority`

串行保证可预测（并行会让"谁改了 prompt"无法复现）。每次 hook 之间 yield 事件循环，不阻塞 UI。

### 5.5 工作流钩子的落点（有现成接缝）

`src/lib/novel/deep-chapter-generation.ts:241` 的 `ChapterWorkflowProfile` 已有 5 个阶段开关（`runExecutionContractBuild` / `runAiReview` / `allowFinalIssueFix` / `runPostRevisionReview` / `runPostDraftPlanAudits`），且已有 `emitChapterWorkflowEvent` 事件通道。

**在这些既有 gate 点插入钩子调用即可，不需要把管线重构成状态机。**

### 5.6 钩子的 io 契约

```ts
interface HookContext {
  event: string
  project: { root: string; bookTitle: string } | null
  chapter?: { id: string; title: string; text: string }
  llm?: {
    provider: string
    model: string
    messages: ChatMessage[]        // 请求前：可改
    temperature?: number
    maxTokens?: number
  }
  response?: { text: string }      // 响应后：可改
  usage?: { promptTokens: number; completionTokens: number }
}

interface HookResult {
  // 只允许改声明过的字段；未声明即忽略
  patch?: Partial<Pick<HookContext, "llm" | "response">>
  block?: { reason: string }        // 仅门禁类事件有效
}
```

`impl: "prompt"` 的结果由宿主构造：把 `{{text}}` 替换为原文，调一次模型，返回的新文本作为 `patch.response.text`。

## 6. 插槽清单与配置引擎

### 6.1 插槽（先定 6 个，写进契约，不随便加）

| 插槽 | 位置 | 承载 |
|---|---|---|
| `chapter-toolbar` | 章节编辑页顶部工具栏 | `action` 按钮 |
| `inspiration-browser` | 右侧栏 / 抽屉 | `contentPack` 浏览 |
| `editor-context-menu` | 编辑器右键菜单 | `action` 快捷项 |
| `outline-toolbar` | 大纲页工具栏 | `action` 按钮 |
| `analysis-toolbar` | 拆书库工具栏 | `action` 按钮 |
| `plugin-center` | 插件中心内部 | 自述卡、灵感库入口 |

**只接受两种承载物**：`action`（按钮 + 宿主渲染表单）与 `contentPack`（宿主渲染浏览面板）。**不接受任意 UI。**

### 6.2 关键决策 D8：插槽带版本

```jsonc
"requiresSlot": { "chapter-toolbar": 1 }
```

我们升级插槽语义时 bump 版本；老插件继续按老版本渲染，或提示升级。**没有版本号的插槽不允许对外开放。**

> **为什么**：插槽是宿主与插件之间最脆弱的耦合面。没有版本，我们每次改 UI 都会静默打断线上插件。

### 6.3 配置引擎

```jsonc
"configSchema": {
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "defaultCount": { "type": "number", "title": "默认备选数量",
                      "default": 5, "minimum": 1, "maximum": 10 },
    "style":        { "type": "string", "title": "书名风格",
                      "enum": ["简洁", "爆点", "文艺"] },
    "apiKey":       { "type": "string", "title": "API Key",
                      "format": "password", "x-qmai-secret": true }
  },
  "required": ["apiKey"]
}
```

规则：
- 宿主按 schema **自动渲染设置表单**，与 `action.form` **共用同一个字段渲染器**（做一次，两处复用）
- `x-qmai-secret: true` → **不落明文**，走与 provider token 相同的内存策略
- 配置注入：环境变量 `QMAI_CONFIG`（JSON 字符串）；声明式里用 `{{config.style}}`
- 校验失败 → 拒绝启用并给出可读原因（不是静默用默认值）

## 7. 项目读写地基（Phase 1，必须先做）

### 7.1 现状是断的

`src-tauri/src/plugins/mod.rs:310` 写死 `project_root: None`，导致 `/host/project/read` 恒返回 `E_NO_PROJECT`。
于是**当前所有插件都拿不到用户正文**，「章节体检」只能靠人手动粘文本。

### 7.2 要补的接口

| 能力 | 形式 | 关键约束 |
|---|---|---|
| 读项目信息 | `GET /host/project/info` | `{root, bookTitle, tags, intro, chapterCount}` |
| 读章节 | `POST /host/project/read` | 限项目内（复用已有 lexical + canonical 双层校验） |
| **写字段** | `POST /host/project/field` | **字段名枚举**，不给任意路径 |
| 写章节备注 | `POST /host/project/chapter-note` | 只追加，不改正文 |
| 注册时机 | **打开/切换项目时**注册进插件会话 | 不是插件启动时 |

### 7.3 可写字段枚举（`project-field` 白名单）

```
bookTitle     书名
bookTags      标签（数组）
bookIntro     简介
protagonist   主角名
setting       核心设定
```

新增字段需改宿主并 bump `fieldApiVersion`。

### 7.4 关键决策 D9：写操作一律枚举，不给任意文件写入

正文是用户最珍贵的资产，一次 bug 就毁一本书。声明式动作的 `output.targets` 与 `POST /host/project/field` 用**同一套枚举**，保证两处一致。

## 8. 免执行发现（静态声明面）

`preview` 字段（可选）：

```jsonc
"preview": {
  "actions": [{ "id": "generate-titles", "title": "生成书名" }],
  "contentPacks": [{ "id": "scifi", "title": "科幻灵感包", "count": 120 }],
  "tools": [{ "name": "analyze_chapter_text", "description": "…" }],
  "providers": [{ "id": "fake-provider", "name": "假 Provider" }]
}
```

- **用途仅限展示与安装前预览**
- **调用真源仍是运行期**（`tools/list`、`/v1/models`）
- 两者不一致 → 记 warning，**以运行期为准**（保住 v2.0 的 D2 决策）

> **为什么需要**：当前"必须执行才知道插件提供什么"，导致商店无从渲染、坏插件装上后界面空着。静态声明让界面有东西可显示，同时不破坏"单一真源"。

## 9. SDK 与脚手架（Phase 4）

### 9.1 `@qmai/plugin-sdk`

| 模块 | 内容 |
|---|---|
| `declarative` | Tier 1 清单的类型定义（TypeScript 类型 + JSON Schema） |
| `runtime` | Tier 2 的 stdio 循环、`initialize`/`tools/list`/`tools/call` 分发、`isError` helper、日志走 stderr、优雅退出 |
| `provider` | health 端点、Bearer 校验中间件、SSE 分片与 usage、客户端断开即停上游 |
| `hooks` | 钩子函数的类型与注册助手 |

### 9.2 工具

- `qmai-plugin validate <dir>`：校验清单、内容包 schema、prompt 变量合法性、插槽版本、容量上限
- `create-qmai-plugin`：生成两种模板（`content-only` / `with-tools`），一条命令得到可跑骨架

### 9.3 为什么 SDK 是必需而非加分项

路线 1 会让 `plugin.json` 变重（6 字段 → 15+）。没有 SDK 与校验器，作者会被清单淹死，生态起不来。

## 10. 分期

| Phase | 内容 | 风险 | 依赖 |
|---|---|---|---|
| **1 地基** | 配置引擎 + 项目读写补通 + 静态声明面 + 修 4 个已知缺陷 | 低 | 无 |
| **2 Tier 1** | 内容包 + 声明式动作 + 6 个插槽（全宿主渲染） | 低 | Phase 1 |
| **3 钩子** | 请求前/后 + 工作流 + 观测（含真取消） | 中 | Phase 1 |
| **4 SDK** | `@qmai/plugin-sdk` + `validate` + `create-qmai-plugin` | 低 | Phase 1–3 |
| **5 Tier 2 收尾** | 登录窗口、余额/签到、模型能力字段扩展 | 中 | Phase 1 |
| **6（可选）** | Tier 3 UI 沙箱（iframe 面板） | 高 | Phase 2 |

**Phase 1 里的 4 个缺陷**（详见基线文档第 10 章）：
1. 工具调用持有全表锁 30 秒
2. 超时不取消
3. 崩溃不自愈
4. `requires.qmai` 不校验

> 先修它们，否则后面每个阶段都带着病。

### 10.1 本文是「设计总图」，不是一份实施计划

本文覆盖 6 个 Phase，体量远超单份实施计划。落地时按下面的切分**各自出独立计划**：

| 实施计划 | 覆盖 | 为什么这样切 |
|---|---|---|
| **计划 A** | Phase 1 + 2 | 地基 + Tier 1 是一条完整可用链路：装一个灵感包、点一个生成器、拿到结果。做完即可交付演示 |
| **计划 B** | Phase 3 | 钩子独立成计划，因为它要改请求/工作流主干，风险面与 A 完全不同 |
| **计划 C** | Phase 4 | SDK 依赖 A、B 的契约定型，必须最后做，否则会跟着改 |
| **计划 D** | Phase 5 | Tier 2 收尾，与 A/B/C 无耦合，可并行 |
| **计划 E** | Phase 6 | Tier 3，需单独立项评估 |

**下一步应产出「计划 A」**（Phase 1 + 2），而不是把 6 个 Phase 塞进一份计划。

## 11. 已知风险与未决问题

### 风险

1. **声明式动作的表达力边界**：极端需求（多轮交互、条件分支、外部数据）声明式做不了。缓解：留 `impl: "process"` 逃生舱 + `run-action` 链式调用。**不做**通用脚本语言（那等于变相执行任意代码）。
2. **提示词即产品**：声明式插件的质量几乎等于提示词质量。一个烂提示词会让用户觉得"插件没用"。缓解：`validate` 加提示词质量检查（长度、是否含变量、是否要求结构化输出），并在插件卡片显示作者与更新时间。
3. **插槽膨胀**：作者会不断要求"再加一个插槽"。缓解：契约里写明插槽清单是**受控资源**，新增需评审并 bump 版本。
4. **解析降级掩盖问题**：D3 的降级可能让作者长期不知道自己的提示词不稳。缓解：降级时在插件卡片显示"最近 7 天解析失败 N 次"。
5. **工作流钩子的可预测性**：多个插件改同一份上下文，结果难复现。缓解：串行 + priority + 记录每次 patch（可回放）。
6. **项目写字段的版本化**：新增字段要 bump `fieldApiVersion`，老插件不认识新字段是安全的（枚举外即拒绝），但用户会期待老插件支持新字段。

### 未决问题

1. **`selection` 变量的来源**：编辑器选区需要前端把当前选区传进 action 执行器。是否需要"无选区时禁用插入类 target"？倾向需要。
2. **多语言**：`prompts/*.md` 是否按语言分目录（`prompts/zh-CN/`）？倾向 v3 先只做单语言 + 清单里声明 `locale`，多语言留 v4。
3. **内容包的标签体系**：自由标签 vs 受控标签？倾向先自由（作者写），宿主做聚合与补全。
4. **观测数据存哪**：`onLlmUsage` 的统计数据落在插件自己的 `<id>.data/` 还是宿主统一看板？倾向**宿主统一**（否则用户装了 5 个观测插件就看到 5 份不同的账单）。

## 12. 与 v1 / v2 的关系

| 项 | v1 | v2.0 | v3 |
|---|---|---|---|
| `schema` | 1 | 2 | **3** |
| 贡献面 | tools（stages/panels 仅解析） | + providers | **+ contentPacks / actions / hooks**；stages→hooks 落地、panels→Tier 3 延后 |
| 执行 | 全部子进程 | 全部子进程 | **Tier 1 不执行，Tier 2 子进程** |
| 配置 | 无 | 无 | **`configSchema` + 宿主渲染** |
| 界面 | 无 | 设置页卡片 | **6 个固定插槽（宿主渲染）** |
| 项目访问 | 恒 `E_NO_PROJECT` | 同 | **接通读 + 受控写** |
| SDK | 无 | 无 | **有** |

**v1 与 v2.0 的插件在 v3 下继续可用**（清单 schema 1/2 仍被接受），不需要重写。
