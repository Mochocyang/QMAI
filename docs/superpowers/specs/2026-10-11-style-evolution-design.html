原始需求（用户原话，逐字保留）

https://github.com/alchaincyf/darwin-skill　这个处理之后，接下来你要做的就是对于这个“文风 skill”，让其能够自动分析用户写作的内容（比如小说的写作风格和文风）。

具体执行规则如下：
1. 触发机制：
当用户打开软件时，skill 会阅读用户曾经写过的小说内容，并不断完善对文风的分析。为了减少 skill 的分析压力以及 token 的消耗，我们不采用每次打开都分析的频率，而是设定为每打开 3 次、4 次或 5 次时，才进行一次自动分析。

2. 计数与时间限制：
次数的计算要遵循时间限制，不能在同一天内频繁触发。例如，如果用户一天内打开了 5 到 6 次，不能每天都分析，这样太浪费 token 了。我们将每天的打开行为定义为 1 次。比如第一天打开算作第 1 次，第二天打开算作第 2 次；如果第二天没有打开，隔了很长时间第三天再打开，依然算作第 2 次。

3. 进化目标：
也就是说，这个文风 skill 要以我发的“达尔文 skill”的方式，让 skill 实现自主的进化。

先说清机制。writing-style-store.ts:356 判 preset.profile.workbenchStyle?.styleFingerprint：有则 :359 加 【已启用文风画像】 前缀并走结构化注入；没有则走旧画像分支——不加前缀，constitution 被 clip(…, 800)（:363）、integratedDna 正文被 clip(…, 1800)（:371）。

v2 自审时发现原稿这条要求写错了，而且是会帮倒忙的那种错：

  1. compileStyleFingerprint(item: WorkbenchItem) 是消费者不是生产者——它读 item.styleFingerprint 与 item.rules 拼注入文本，本身不产生画像。原稿写「复用 compileStyleFingerprint 产出 styleFingerprint」是把方向搞反了。
  2. 真正的产出物是一个 WorkbenchItem：{ subject, summary, limitations, rules: WorkbenchRule[], styleFingerprint?: StyleFingerprint }。要让 compileStyleFingerprint 拼出有用的文本，必须有一组按 STYLE_FACETS 分维度的 rules，也就是让进化分析额外交付**整个拆书工作台的结构化产物**。
  3. 硬塞的代价是负的：两个分支是 if/else——一旦 workbenchStyle 存在，constitution（:363）与 integratedDna（:367）都不再注入。若用空 rules 凑一个 WorkbenchItem，注入内容会缩成 compileStyleFingerprint 的头几行 + positioning，等于把进化出来的正文全丢掉，比旧路径更糟。

决定：候选不产出 workbenchStyle，走旧画像路径（constitution ≤800 字 + integratedDna 正文 ≤1800 字 + 代表片段）。这是所有 v1 拆书画像共用的路径，不是为本次新开的降级口子。

代价要如实认下来：① 不加 【已启用文风画像】 前缀，故不受 context-engine.ts:1143 的 fail-closed 守卫保护；② writingStyle 在 trimContextPack 里排位靠后，预算紧张时会被整段裁掉且不报错——用户会看到「画像启用了但文风好像没生效」。这两条对所有旧式画像同样成立，不是本功能引入的回归。

代码里要挡住那个更糟的做法：加一条用例断言候选不会携带 rules 为空 / styleFingerprint 为空的 workbenchStyle。否则将来有人「顺手补上workbenchStyle」时，界面一切正常，注入内容却悄悄变空。

为什么不能直接把拆书库那条链路接过来跑

拆书库链路（style-analysis-adapter.ts / workbench-publish.ts）面向的是「一整本外部书」：它有分卷、章节指纹缓存、拆书库目录与工作台版本管理，输入是导入的书、产物是入库版本。用户的在写正文没有这些前提（章数不定、边写边变、不该占拆书库的目录），且它产出的画像没有「与上一版比谁更像作者」这一步。所以复用的是它的 prompt 组装与 profile 形状，不是它的编排。

04

计数与节律：逐条对照用户原话

这一节把用户第 1、2 条规则翻译成可执行判定，每条都标明对应的原话。

用户原话落成判定
「如果用户一天内打开了 5 到 6 次，不能每天都分析」
「我们将每天的打开行为定义为 1 次」		 today === lastOpenDate → 计数完全不动（不是 +0.5，也不是记一次“忽略”）。lastOpenDate 用本地日期 YYYY-MM-DD，不用 UTC（否则东八区晚上 8 点后就跨天了）
「第一天打开算作第 1 次，第二天打开算作第 2 次」 today !== lastOpenDate → openDayCount += 1，lastOpenDate = today
「如果第二天没有打开，隔了很长时间第三天再打开，依然算作第 2 次」 只比较是否同一天，不比较间隔天数。没有「漏一天扣一次」或「按日历天补算」的逻辑——中间空多少天都不影响计数
「每打开 3 次、4 次或 5 次时，才进行一次自动分析」 每轮开始时从 {3,4,5} 里取一个值作为本轮阈值；openDayCount >= nextThreshold → shouldAnalyze = true，随后计数归零并抽新阈值。即间隔在 3~5 之间浮动，而不是「第 3、4、5 次各分析一次」（后者会让第 4、5 次几乎立刻重复分析，与「减少消耗」的目标相反） 
advanceOpenDay(state, today):        // ⚠️ 不接 rng：它不再抽阈值，抽阈值只在 completeRound
  if today === state.lastOpenDate:
      // 同一天：计数完全不动（用户规则「一天内开 5~6 次只算 1 次」）。
      // 但**不**在这里重试：同一个打开日最多尝试一次，见边界③。
      return { state, shouldAnalyze: state.openDayCount >= state.nextThreshold
                                     && state.lastAttemptedOn !== today }
  count = state.openDayCount + 1
  if count >= state.nextThreshold:
      // ⚠️ 这里**不归零**：归零属于「一轮完整跑完」，只由 completeRound() 做。
      //    写成归零就会让一次**失败**的分析也消费掉这 3~5 天（违反边界①）。
      return { state: { ...state, lastOpenDate: today, openDayCount: count,
                        lastAttemptedOn: today },
               shouldAnalyze: true }
  return { state: { ...state, lastOpenDate: today, openDayCount: count },
           shouldAnalyze: false }

// 只有「一轮完整跑完」才调用它 —— 归零与成功解耦的关键
completeRound(state, today, rng):
  return { ...state,
           openDayCount: 0,
           nextThreshold: pickThreshold(rng),   // 3 / 4 / 5
           lastAnalyzedOn: today,
           lastAttemptedOn: today }
两个必须守住的边界

① 分析失败不推进计数：若本轮因模型未配置、章节不足、调用失败而没跑成，不能把计数当成「已消费」——那等于用户白等了 3~5 天却什么也没发生。所以「达到阈值」只置一个待办标记，真正归零发生在一轮成功结束之后。

② 阈值归零必须与成功绑定：实现方式是 advanceOpenDay 达到阈值时只加计数、不归零，归零交给单独的 completeRound()。两者分开，才不会出现「失败也清零」。既然计数保留在阈值之上，下一个打开日会自动再次判定为应分析——重试不需要额外标记。

③ 同一个打开日最多尝试一次（lastAttemptedOn）：只做到①②会漏掉一条真实的浪费路径——计数没推进 ⇒ shouldAnalyze 仍为真，而 hydrateDeferredProjectState 是 void（App.tsx:576，不 await、无 in-flight 锁），handleProjectOpened 又有一天的 4 个入口（启动 :445、打开/选择最近 :582/:593、外壳回调 :624）。于是用户切书 A→B→A、或重新打开同一本，就会再跑一次 tick，一天之内反复调用模型。这正是用户原话要避免的「同一天内频繁触发」。

所以「已尝试」与「已成功」必须分开记。而且 lastAttemptedOn 必须在开始跑模型之前就落盘——否则在那一轮跑完（可能 40 秒以上）之前，盘上仍是旧值，重入照样会发生：这是③真正生效的前提，不是实现细节。

🔴 一轮的结局必须是一个显式枚举（v2 新增；原稿这里两行互相打架）

原稿 07 节对「推进」的判据不一致：「模型报错」那行说不推进，而「探针生成跑偏」那行说推进（理由：「一轮已完整跑完」）——但全篇没有定义什么算「完整跑完」。分叉点很实际：分析成功但探针调用报错，算哪一类？写盘失败时轮次记录写不写？

修正：一轮只有三种结局，各自绑定计数行为与轮次记录：

结局含义计数轮次记录
incomplete前置不满足（样本不足、无 holdout）或任一模型调用失败/被取消/超时，或候选 profile 未通过校验不推进不写（只写一条界面提示）
kept探针与判定都跑完，且候选胜出归零并抽新阈值写，结论 kept
reverted探针与判定都跑完，但候选未胜出或无法判定归零并抽新阈值写，结论 reverted（含 reason）

关键区分：「无法判定」属于 reverted 而不是 incomplete——因为它已经把该花的调用花完了，结果就是「不采纳」；而 incomplete 是「这次没跑成」，必须让用户下次重试。这条区分正是原稿含糊之处的答案。

05

棘轮：靠什么判「进化了」

这是整个方案最关键的一处取舍，也是与达尔文 skill 差异最大的一处——不是照搬，而是照它踩过的坑绕开。

达尔文 skill 自己写下的教训（原文引用）

它 SKILL.md 第 8、62 行：

  • 「keep/revert 棘轮从「绝对分数 delta」改为「paired 同-judge 比较 + 奇数 N 多数决」（绝对分数 ±8 judge 噪音淹没保守编辑的真实增益、是 false-revert 源）」
  • 「绝对总分只用于 triage，绝不用于 keep/revert」。反例黑名单第 1b 条：「拿绝对分数 delta 当 keep/revert 棘轮 → 实测一支纯加标记的 skill 单评 −8.5、全是换尺」
  • 它的设计灵感节里更直接地点出病根：autoresearch 的 val_bpb 是确定性 loss（重跑同数），而 LLM-judge 分数是随机抽样；把后者当可重复的 metric 用是概念错误。

结论：达尔文 skill 的精髓是「棘轮 + 独立验证 + 人审」这套结构，而它自己已经证明「用 LLM 打分当棘轮」是错的。文风恰好有一条更好的路——本项目已经有确定性指标。

本方案的棘轮

目标 T  = computeStyleMetrics( 用户 holdout 章节 )        // 真实写法，确定性
基线 B  = 上一轮「保留」下来的候选；没有则取当前**启用**的预设     // 见下方「基线」
候选 C  = 本轮分析产出的 profile

探针文本：用固定提示词，喂 C.profile 与 B.profile 各生成一段（同一提示词、同长度约束）
candM   = computeStyleMetrics([ 用 C 生成的那段 ])
baseM   = computeStyleMetrics([ 用 B 生成的那段 ])       // 缓存的是**这份指标**

归一化用固定的每项量纲 scale[i]（为什么不能除以目标值：见 10 节反例 11）：
    norm_i(x) = x_i / scale[i]
distance(X) = mean_i( |norm_i(X) − norm_i(T)| )

保留条件：distance(candM) < distance(baseM) − ε        // ε = 最小改进阈值，防噪音抖动
否则：回滚（丢弃候选，保留 B）
🔴 首轮没有基线画像——这是一个必须单独定义的分支

若项目里没有任何生效的文风预设，就没有可比对象，距离比较无从谈起。不允许把它当成「距离 0、自动通过」（那等于把「没有证据」当「验证通过」）。

规则：此分支命名为建立基线，与「进化」严格区分：

  • 只跑 1 次分析调用（不跑探针——没有对手可比，跑了也无法判定，纯属浪费）；
  • 产物照常写成语料库里的候选预设，但轮次记录标记为 bootstrap，界面文案是「已建立基线（尚未验证）」，不声称「已进化」；
  • 从第二轮起才进入真正的棘轮（有基线可比），此时才可能出现「保留 / 回滚」。

基线的定义（v2 修订，原稿此处自相矛盾）：本规格 07 节原来写「在任 = 当前启用的那份」，而上面又承诺「从第二轮起就进入棘轮」——这两句只有当用户每次都启用候选时才同时成立。用户不启用时，第一句会让每一轮都停在「建立基线」，棘轮永不发生（与用户「让 skill 实现自主的进化」的要求相反）。故明确为：

  • 基线 B := 上一轮判定为 keep 的候选；若还没有 → 取当前启用的预设；若两者都没有 → 本轮走「建立基线」分支。
  • 这与达尔文 skill 的棘轮同构（候选击败在任者后接替成为在任者），也正是上面「第二轮起进入棘轮」能成立的前提。
  • 不违反「先给我看再启用」：允许候选接替基线，只是让它成为下一轮的比照对象；没有任何东西被自动启用，生成仍然只跟着用户启用的那份走。
  • 自我参照不会失控：判据始终是「离用户真实正文（T）更近」，T 是外部锚、不随候选漂移。

这样做的代价是首版画像没有经过验证；但它是用户可自行检查并决定是否启用的一份候选，而不是被静默塞进生成链路的成品——与用户选定的「先给我看再启用」一致。

要点为什么
指标项用 derived 里的比率与均值（句长均值、短/长句比、段长、一句一段比、对白段占比、标点密度、拉丁字符比） 这些是尺度无关的，可以跨文本长度比较；counts 里那些绝对计数（句数、字数）随文本长短变，不能直接比，只用于校验样本量够不够
先归一化再算差 句长均值是「字」量级（几十），比率是 0~1 量级。不归一化的话，句长均值会单方面主导距离，等于只看了一个指标
引入最小改进阈值 ε 生成有随机性，两次之间天然有抖动。没有 ε 就会出现「本轮略好一点点→保留、下轮略差一点点→回滚」的来回震荡，画像永远在抖而不会真正积累
holdout 章节不参与分析 这是达尔文 SkillOpt 那一路的「validation-gated」：拿被分析过的章节当目标，等于用训练集考试，必然「越改越像」。所以章节要分成 fit（给分析用）与 holdout（只用来算 T）
基线的探针指标缓存到 probe B 的探针文本在它被替换之前不会变，所以这份指标可复用，每轮只需生成候选那一次，调用数从 3 降到 2。
⚠️ 只能缓存指标，不能缓存距离：distance() 依赖目标 T，而 T 随用户继续写作而变化——缓存距离就等于拿过期的标尺比这一轮的候选，判定会失真。每轮必须用当前的 T 重算 distance(baseM) 与 distance(candM)。
由此推论：keep/revert 的结论只在同一轮内可比（两个距离用的是同一个 T），不跨轮比较距离数值。
🔴 归一化必须写成一张常量表，ε 才有依据（v2 新增；原稿只写了「先归一化再算差」）

原稿从未定义 归一化 是什么，却在 08 节要求「去掉 ε 会红」的变异——ε 未定义时这条测试根本写不出来。而最自然的那种实现（除以目标值 x_i / T_i）是错的：纯中文小说的 latinCharRatio 恒为 0（style-metrics.ts:261），除零得 NaN，比较恒为 false，判定会静默退化且不报错。

修正：用固定的每项量纲 scale[i]，norm_i(x) = x_i / scale[i]，不引入目标值做分母。量纲按指标的真实值域定，写死在代码里（不随数据变）：

指标来源scale理由
短句比 / 长句比 / 一句一段比 / 长段比 / 对白段比 / 拉丁字符比derived 比率1本身就是 0~1
句长均值avgSentenceChars60中文小说常见 10~60 字；取 60 使该维度落在 0~1
段长均值avgParagraphChars300同上，长段阈值 LONG_PARAGRAPH_MIN_CHARS=200
段均句数avgParagraphSentences8同上
标点密度（8 个子项）punctuationPerThousand.*100每千字次数，常见 0~100

两条实现要求：① punctuationPerThousand 是 8 个子字段构成的对象（:251-260），必须摊平成 8 个标量再进距离——对象做 Math.abs 得 NaN；② 只取 derived 里的比率与均值，counts 的绝对计数随文本长短变、不参与距离（原稿这一点是对的）。

ε 的取值依据：distance() 是「每项归一化差」的均值，量纲已在 0~1 附近，故 ε 取 0.01 量级（约为「平均每个指标改善 1%」）。它是一个常量，与 08 节测试里的固定随机源一起写死，使 keep/revert 在测试中完全可复现。

🔴 探针必须是多段，不能是「一段」（v2 新增）

原稿 09 节写「探针输出长度受控（一段，非整章）」，但距离里含段落级指标 oneSentenceParagraphRatio（:248）与 dialogueParagraphRatio（:250）。只有一段时 paragraphs === 1，这两个比率只能取 0 或 1：拿它和 holdout 多章算出的 T（例如 0.37）比，差值被量化成两个台阶，且完全由「模型这次分了几段」这一个随机事件决定——它会成为距离里的主导抖动项，正是 ε 想压却压不住的东西。avgParagraphChars 同理退化成「那一段有多长」。

修正：探针生成3~5 段 / 固定目标字数（提示词里明确要求分段），使段落级指标有统计意义；或把这些段落级指标排除出探针距离。推荐前者——它们是有信息量的风格特征，不该因为探针写得太短而丢掉。

一个额外好处

因为判据是「指标距离更小才保留」，「没有改进」是默认结果（候选被判回滚），而不是需要额外理由才能拒绝。这与本轮早些时候修章节徽章时定下的原则一致：拿不到证据就不采纳，绝不让「无证据」被当作「通过」。

🔴 候选预设的 sourceBook 必须每轮唯一（v2 重做：原稿的「固定合成来源」有个致命漏洞）

先看清约束。upsertWritingStylePreset 的去重键是 sourceBook：findIndex(s => s.sourceBook === input.sourceBook)（writing-style-store.ts:137），命中时原地覆盖 profile 并保留原 id（:139-148）。而 setEnabledWritingStyle（:166-174）只认 id、不因 profile 变化而失效，getEnabledWritingStyle（:217）拿的是 id 对应的当前 profile。

原稿的漏洞：原稿说用一个固定的合成来源（如 "我的文风 · 自动进化"），并声称「① 用户现有画像永不被碰；② 每轮候选覆盖上一轮候选」。这两条不可兼得，而且漏掉了主路径——用户启用了候选之后：

  1. 第 1 轮 bootstrap 写出候选 P1（固定 sourceBook，id = P1），未启用；
  2. 用户在文风库里点 P1 启用 ⇒ enabledStyleId = P1（这是文档设计的正常路径）；
  3. 第 2 轮判定 keep ⇒ 同 sourceBook 命中 :137 ⇒ 原地覆盖 P1.profile，id 不变；
  4. enabledStyleId 仍是 P1 ⇒ 用户一次都没点，正在用的画像已被换掉。

这正是用户明确否决的「静默替换」。更糟的是回滚无从下手：此时「候选」与「在任」是同一个预设，棘轮判 revert 时，「保留的」和「要删的」是同一个东西。

修正（两条一起才成立）：

  • 候选的 sourceBook 每轮唯一，带上轮次号，例如 "我的文风 · 自动进化 · 第 N 轮"。于是 upsert 每轮新增一条而不是覆盖，任何已启用的预设都不会被改写。
  • 清理上一轮候选时必须先检查它是否被启用：仅当 enabledStyleId !== 上一轮候选.id 时才删除它。
    于是盘上最多只会同时存在两条自动进化预设：用户启用的那条 + 本轮候选，不会堆积垃圾。
回滚的正确语义（v2 重做）

原稿错在：直接推荐 removeWritingStylePresetBySourceBook。而 removeWritingStylePresets（:186-201）在删掉当前启用项时会把 enabledStyleId 置为 null——若用户恰好启用了候选，一次「回滚」就会把项目的文风整个关掉（从「有文风」变成「完全没有文风」，静默降级）。

正确规则：回滚 = 删除本轮候选，且仅当它未被启用。若它已被启用，面板不得执行删除，而要如实说明：「这是你正在使用的文风，不能作为回滚目标；如需停用，请到文风库取消启用。」——宁可让用户多点一下，也不能悄悄把他的文风关掉。

为什么候选要写成「预设」而不是覆盖用户现有那一份

① 回滚变成「删掉候选预设」，不需要备份/还原 profile；② 用户可以在文风库里并排比较新旧两份，而不是只能信任一个被悄悄替换掉的东西；③ 与本轮刚实现的「点击文风卡片即启用」天然衔接——候选出现在库里，用户点它才生效。

v2 更正：原稿把③写成「回滚就是『不启用它、并删掉』」，漏了「用户已经启用它」这一格——那一格不允许删（会连带把 enabledStyleId 置 null），见上方回滚语义。

写入后同样会经过 saveWritingStyleStore，因此自动带上 bumpDataVersion()——文风库与写作区那个按钮会立刻看到候选。

🔴 面板必须同时跟随 dataVersion（v2 真机验证发现，测试曾漏掉）

原稿只写了「面板订阅 subscribeStyleEvolution」（那是为了节律状态，它刻意不进 bumpDataVersion，见 08 节），漏了另一半：面板就挂在文风画廊上面，用户完全可以先点下面的画廊把启用项换成别的文风，再回来点「回滚这份候选」。画廊是靠 dataVersion 刷新的（unified-skill-library-view.tsx:949/:1062），而面板若不跟，就会一直拿着打开时那份陈旧状态。

实测后果（本轮构建的真机上复现）：候选早已被切走，面板却仍认为「正在使用中」，于是错误地拒绝回滚并显示一条自相矛盾的红色提示 —— 而同一屏下方的画廊卡片已经正确标着「当前启用」是另一份。用户无法解释这个拒绝。

修正：面板的状态 effect 依赖 [reload, dataVersion]（不是只有 [reload]），并在每次刷新时清掉拒绝提示（它的前提刚被重新读过，前提没了就不该留着过期红字）。两条都加了用例，且都用变异验证过判别力。

成本与开关

  • 默认关闭（用户已选定）。关闭时：一次读文件、零次模型调用。
  • 开启后：每 3~5 个「打开日」触发一轮。调用次数按三种情形分别是：
    • 建立基线（上一轮没有 keep 候选，且项目里也没有生效的文风预设）：1 次（只做分析，不跑探针）
    • 棘轮·探针缓存已热（常规情形）：2 次（1 次分析 + 1 次候选探针；基线的探针指标命中缓存）
    • 棘轮·缓存未命中（基线刚换过、或缓存被作废）3 次（多一次基线探针；该结果随即写入缓存）
  • 分析输入是 fit 章节的抽样（按现有 analysis-chunk-planner 的预算思路控制总字数），不是全部正文；探针输出长度受控（一段，非整章）。
  • 界面必须显示：距离上次分析多少天、下次大约还需几次打开（以及约等于几天）、上一轮结论。不能让用户不知道它什么时候会花钱。v2 更正：原稿写「还需几天」，但节律计的是打开日——用户不打开就永远不会到阈值，「还需 N 次打开」才是准确说法。

#不要做为什么
1用 LLM 打分当保留/回滚的棘轮达尔文 skill 自己实测过：绝对分数 ±8 噪音，会把真实增益判成退步。本方案用确定性指标
2用被分析过的章节算目标指标训练集当考卷，必然「越改越像」，棘轮会一路假通过。必须留 holdout
3在没有 holdout / 判定不了时「当作通过」拿不到证据 ≠ 验证通过。判定不了就回滚
4自动启用新画像用户已明确选「改进后先给我看再启用」。且画像直接决定生成质量，静默替换不可接受
5分析失败也推进计数会让用户白等 3~5 天却什么都没发生（见 04 节边界①）
6用 UTC 判「同一天」东八区晚上 8 点后就跨天，用户会发现「同一天开了两次却算两次」
7在启动路径上同步等模型返回会卡住整个界面启动。必须空闲时异步、且失败不留痕
8把用户正文复制进拆书库目录往用户项目里塞一个假的「外部书」，语义错且会干扰拆书库的列表与缓存
8b候选预设沿用与用户现有画像相同的 sourceBookupsertWritingStylePreset 按 sourceBook 去重并原地覆盖（writing-style-store.ts:137-148）⇒ 会静默改掉用户正在用的画像、且无法回滚。必须用独立合成来源（见 06 节）
9不设最小改进阈值 ε生成有随机性，没有 ε 会导致画像在噪音里来回震荡、永不积累
10首轮就自动跑（不看开关）默认关闭是用户明确选择，涉及花钱
11归一化时除以目标值 x_i / T_i纯中文小说里 latinCharRatio 恒为 0，除以它得到 NaN；NaN 参与比较后 < 恒为 false，判定会静默退化成「永远回滚」或「永远保留」（取决于写法），且不报错。必须用固定量纲 scale[i]
12把 distance() 的结果缓存进 probe距离依赖目标 T，T 随笔者的正文增长而变化；缓存距离＝拿过期标尺量新候选。只缓存指标，每轮用当前 T 重算
13把 punctuationPerThousand 当作一个指标项它是 8 个子字段（dash / ellipsis / quote / exclamation / question / comma / semicolon / colon）构成的对象，对象Math.abs 得 NaN；必须先摊平成 8 个标量、或明确只取一个子集
14用裸文件名把新引擎加进 ANALYSIS_FILES那张表按 book-analysis/ 解析，跨目录会 ENOENT；见 03 节
15让进化状态写盘也调 bumpDataVersion()它会让文风库/写作区的刷新语义与「项目数据变了」混在一起；轮次历史变化的订阅由 store 自己的通知承担
16候选用固定 sourceBook用户一旦启用了候选，下一轮 upsert 就会原地覆盖正在生效的画像（writing-style-store.ts:137-148 + :166-174）；而且此时「候选」与「在任」是同一个，回滚无从下手。必须每轮唯一
17回滚时直接按 sourceBook 删候选removeWritingStylePresets（:186-201）在删掉当前启用项时会把 enabledStyleId 置 null ⇒ 一次「回滚」把用户的文风整个关掉。必须先判「是否被启用」，被启用则拒绝删除
18用「一段」当探针paragraphs === 1 时 oneSentenceParagraphRatio / dialogueParagraphRatio 只能是 0 或 1，距离被「模型这次分了几段」这一随机事件主导
19给候选硬塞一个空 rules 的 workbenchStyle（原稿就是这么要求的，方向反了）结构化分支与旧分支是 if/else：workbenchStyle 一旦存在，constitution（:363）与 integratedDna（:367）都不再注入，注入文本缩成 compileStyleFingerprint 的头几行 —— 反而不如老路径。正确做法是不产出，并在规格里认下代价

待确认点的结论（已销账）

设计过程中问过四个问题，此处保留问题与结论的对应关系，便于日后回溯为什么是这样。

  1. 「文风 skill」指哪个东西 → 用户选「就是 App「文风库」里的文风预设（.qmai/writing-style.json 里的一条）」。不新建 skills/SkillHub 下的 SKILL.md（那类 md 随软件发版，用户自己的写作数据改不了它）。
  2. 「3 次、4 次或 5 次」是哪种节律 → 用户选「间隔在 3~5 之间取一个值」，即每轮抽一个阈值，而非第 3、4、5 次各分析一次。
  3. 靠什么判定进化 → 用户选「确定性指标：用新画像生成文本 → 算指标 → 与用户真实写法比对，更接近才保留」。
  4. 默认开关与自主程度 → 用户选「默认关，用户手动开启；开启后自动分析，但改进后先给我看再启用」。
  5. （附加，已确认）计数按项目还是全局 → 按项目：每本书自己的文风各自进化。
  6. （v2 附加）候选被用户启用后怎么回滚 → 见 06 节「回滚的正确语义」：已被启用则拒绝删除，如实告知用户去文风库取消启用。原稿那句「回滚 = 删候选预设」在启用态下会把项目文风整个关掉，已废弃。
