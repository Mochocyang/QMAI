# QMAI 开放插件系统 —— 设计方案

> 目标：让第三方开发者能把**一个带代码的插件**装进青幕AI写作，插件在后台常驻运行、给 Agent 加工具、能调宿主能力，装挂了不影响主程序。
>
> 参考对象：DeepSeek Harness（DSH）的插件体系。本方案的骨架照它，传输层换成跨进程。
>
> 边界：**第一期只做「工具插件 + 后台常驻」**。界面插件（iframe 面板）协议预留但不实现；插件市场索引不在本方案范围。

---

## 一、为什么照 DSH 做，但必须换传输层

### 1.1 DSH 的插件长什么样（实测结论）

DSH 的插件**就是一个 npm 包**，契约写在 `package.json` 的 `dsh.bundle` 里：

```jsonc
{
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },   // 必须，没有它就不是插件
    "client": { "platform": "web" }                // 只有当插件带浏览器 UI 时才需要
  },
  "peerDependencies": { "@deepseek-ai/cordis": "^4.0.1" }
}
```

`cordis.patch.yml` 往宿主插件树里插一行：

```yaml
- insert:
    - id: my-plugin
      name: my-plugin            # npm 包名，不是路径
      config: { root: !!js dshHomePath('my-plugin') }
```

服务端入口是**任意 JS**，宿主把一个 `ctx` 容器交给它：

```js
export const inject = ['connection']                 // 声明依赖哪些宿主服务
export const Config = Schema.object({...})

export function apply(ctx, config) {
  ctx.effect(() => ctx.reflect.provide('myService', {...}))   // 对外提供服务
  ctx.connection.fetch.register({ path: '/api/my-plugin/x', ... })  // 注册 HTTP 端点
  ctx.inject(['desktopPnpm'], (ctx) => {...})                   // 延迟依赖注入
}
```

**关键观察**：我统计了 `dsh-desktop-workbenches` 的客户端入口，全文件只有 **7 处 `require`**，且只用于 `react` / `cordis` / `UI primitives` 这三个共享单例；**插件的能力全部从 `ctx` 对象上取得**（`ctx.connection` / `ctx.reflect` / `ctx.inject` / `ctx.effect` / `ctx.layout` / `ctx.sessions` / `ctx.locale` / `ctx.logger`）。

**所以 DSH 插件系统的本质是：一个 `ctx` 服务容器 + 插件树 + 生命周期管理。市场只是分发渠道。**

### 1.2 DSH 生态的真实构成（7211 个插件全量统计）

数据来源：`awesome-dsh-plugin.com/plugins.json`（2026-10-27 拉取）。

| 能力声明数 | 插件数 | 占比 |
|---|---|---|
| 0 个 | 1626 | 22.6% |
| 1–2 个 | 1405 | 19.5% |
| 3–5 个 | 3510 | 48.7% |
| 6 个以上 | 670 | 9.3% |
| 其中「读凭证 + 能联网」（红线组合） | 575 | 8.0% |

高频能力：`fs-read` 4750、`network` 3761、`env` 3761、`fs-write` 3734、`shell` 2465、`credentials` 708、`llm` 606。

**结论：DSH 插件的主流能力是「读文件 + 联网 + 写文件」，即插件确实在做真事，不是纯配置。** 这印证了「插件必须是能跑代码的」。

### 1.3 QMAI 不能照搬的地方

DSH 服务端插件能跑任意 JS，是因为 **Harness 本身就是 Node 运行时**，插件与宿主同进程。

QMAI 的宿主是 **Rust + Tauri WebView**，`src-tauri/Cargo.toml` 里没有任何 JS 引擎（无 boa / quickjs / deno_core）。硬塞一个 JS 引擎意味着：

- `rquickjs` 需要编译 C 代码，Win/macOS/Linux 三平台交叉编译都会变复杂
- `boa_engine` 纯 Rust 但体积大、性能一般
- 还要自己设计一整套 `ctx` 能力面并在 JS 沙箱里实现

**因此换传输层：插件跑在独立子进程里，宿主只做进程管理 + RPC。** 这个选择有三条实证支持：

1. `src-tauri/src/commands/` 下已有 **四套成熟的子进程实现**：`claude_cli.rs` / `codex_cli.rs` / `cursor_cli.rs` / `antigravity_cli.rs`，全部是「起进程 + 流式读回 + 取消」的模式
2. `mcp/server.rs` 已有「回环端口 + UUID token + 逐请求鉴权」的实现
3. `cli_resolver.rs` 已处理跨平台命令发现（macOS 登录 shell PATH、Windows 候选列表 + 缓存）

**不引入任何新技术栈，只补两块：插件注册表、宿主能力面分发。**

## 二、已定案的两个决策

### 决策 1：通信协议 = MCP（JSON-RPC 2.0），传输用 **stdio**

| 维度 | stdio（选定） | 回环 HTTP |
|---|---|---|
| 端口管理 | 不需要 | 每插件一个端口，要防冲突/泄漏 |
| 认证 | 不需要（父子进程天然边界） | 需要 token |
| 生命周期 | `kill` 即断，无需清理 | 僵尸端口、监听泄漏 |
| Windows 防火墙 | **完全不触发** | 监听 socket 可能弹用户提示 |
| 性能 | 无网络栈开销 | 有 |

**决定性理由：Windows 上监听端口会触发防火墙提示，对写手用户是信任伤害。stdio 没有这个问题。**

MCP 的 `tools/list` + `tools/call` 与现有 `ToolRegistry` 的形状一一对应，`mcp/protocol.rs` 的 `tools_list_result` / `handle_jsonrpc` 可直接复用。

### 决策 2：第一期**不做**界面插件

1. DSH 本身的顺序就是先 `dsh.bundle`（服务端），`dsh.client` 是可选补充
2. 界面插件需要先定义 slot 契约，而 QMAI 的 UI 刚经历 4.0 重构，公共 slot 还没定；此时冻结等于给未来设限
3. 工具 + 后台已覆盖 DSH 插件的主流价值（见 1.2 的能力统计）

**协议不返工的做法**：`plugin.json` 保留 `contributes.panels` 字段，第一期解析但不渲染，管理页提示「该插件含界面部分，当前版本暂不支持」。

## 三、总体架构

```
                    ┌──────────────────────────────────────────┐
                    │  QMAI 前端（React / WebView）             │
                    │  ├─ 插件管理页（列表/安装/启停/权限/日志） │
                    │  └─ [后续] iframe 沙箱                    │
                    └───────────────┬──────────────────────────┘
                                    │ Tauri invoke
                    ┌───────────────▼──────────────────────────┐
                    │  Rust 宿主                                │
                    │  ├─ plugins::manifest   清单解析与校验     │
                    │  ├─ plugins::registry   插件树 + 状态      │
                    │  ├─ plugins::supervisor 进程生命周期       │
                    │  ├─ plugins::host_api   宿主能力面(axum)   │
                    │  ├─ plugins::mcp_bridge MCP 客户端/注入     │
                    │  └─ plugins::installer  GitHub 下载与安装   │
                    └───────────────┬──────────────────────────┘
                                    │ stdio JSON-RPC（MCP）
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  插件 A (node)              插件 B (python)            插件 C (binary)
  常驻 · 后台任务             常驻 · 监听事件             常驻 · 本地服务
         │                           │                           │
         └───────────── 需要宿主能力时，反调 host_api ─────────────┘
                       （回环 HTTP + token，按 permissions 拦截）
```

### 3.1 与 DSH 概念的逐项对应

| DSH | QMAI | 说明 |
|---|---|---|
| 插件树（`insert` 行） | `PluginRegistry` 注册项，含 `id` + `inject` | 同构 |
| `export const inject` | `"inject"` 字段 | 同构 |
| `Schema.object()` 的 `Config` | `"config"`（JSON Schema） | 同构 |
| `apply(ctx)` 里注册的东西 | `"contributes"` 字段 | 声明式替代命令式 |
| `ctx.effect` 清理 | 进程退出 / Supervisor 的 disposer 栈 | 进程级更彻底 |
| `ctx.connection.fetch.register` | `HostApi` 的 `host.route()` | 同构 |
| `ctx.reflect.provide` | `HostApi` 的 `host.provide()`，其他插件可 `inject` | 同构 |
| `window.__ModuleLoader__` | iframe 沙箱 + postMessage RPC | 第二期 |
| `cordis.patch.yml` | `plugin.json` | 合并为一个文件 |

## 四、插件清单契约 `plugin.json`

### 4.1 完整字段

```jsonc
{
  "schema": 1,
  "id": "chapter-insights",
  "name": "章节洞察",
  "version": "1.2.0",
  "description": "后台分析章节，产出节奏与伏笔报告",
  "author": { "name": "某某", "url": "https://github.com/someone" },
  "license": "MIT",

  "requires": { "qmai": ">=4.4.0" },

  "runtime": {
    "type": "node",
    "entry": "index.js",
    "args": ["--stdio"],
    "keepAlive": true,
    "startTimeoutMs": 10000
  },

  "inject": ["host.qmai.tools", "host.logger"],

  "contributes": {
    "tools": [
      {
        "name": "analyze_chapter_rhythm",
        "description": "分析指定章节的叙事节奏",
        "parameters": {
          "chapterPath": { "type": "string", "description": "章节文件路径", "required": true }
        }
      }
    ],
    "stages": ["planning"],
    "panels": []
  },

  "permissions": ["fs:project-read", "net:https"],

  "autoStart": true
}
```

### 4.2 字段约束表

| 字段 | 必需 | 约束 | 校验失败的错误码 |
|---|---|---|---|
| `schema` | 是 | 必须为 `1` | `E_SCHEMA_UNSUPPORTED` |
| `id` | 是 | `^[a-z0-9][a-z0-9-]{1,63}$`，全局唯一 | `E_ID_INVALID` / `E_ID_DUPLICATE` |
| `name` | 是 | 1–64 字符 | `E_NAME_INVALID` |
| `version` | 是 | 完整 SemVer | `E_VERSION_INVALID` |
| `requires.qmai` | 否 | semver range，与 `CARGO_PKG_VERSION` 比对 | `E_HOST_INCOMPATIBLE` |
| `runtime.type` | 是 | `node` \| `python` \| `binary` | `E_RUNTIME_INVALID` |
| `runtime.entry` | 是 | 相对路径，**禁止 `..` 与绝对路径** | `E_ENTRY_INVALID` |
| `runtime.keepAlive` | 否 | 默认 `true` | — |
| `runtime.startTimeoutMs` | 否 | 1000–60000，默认 10000 | — |
| `inject` | 否 | 只允许白名单内的服务名 | `E_INJECT_UNKNOWN` |
| `contributes.tools[].name` | 是 | `^[a-z][a-z0-9_]{2,63}$`（**插件内部名**，不含前缀）；注入宿主时统一加 `<pluginId>__` 前缀，因此不可能与内置工具重名 | `E_TOOL_NAME_INVALID` |
| `permissions` | 否 | 只允许白名单内的权限串 | `E_PERMISSION_UNKNOWN` |

### 4.3 `entry` 路径安全

`schema` 校验通过后，还要做一次**路径归一化检查**：

```
canonical(pluginDir.join(entry)) 必须以 canonical(pluginDir) 为前缀
```

否则拒绝安装。这是防 zip-slip 的第二道闸（第一道在解压时）。

## 五、MCP 协议约定

### 5.1 传输

- 宿主以 `stdin` / `stdout` 承载 JSON-RPC 2.0，**每行一条消息**（NDJSON）
- `stderr` 全部收进插件日志，不受协议影响
- 文档消息顺序：宿主先发 `initialize`，插件回 `initialize` 响应，宿主再发 `notifications/initialized`

### 5.2 宿主 → 插件（请求）

```jsonc
// 1. 初始化
{ "jsonrpc": "2.0", "id": 1, "method": "initialize", "params": {
    "protocolVersion": "2024-11-05",
    "clientInfo": { "name": "qmai", "version": "4.4.0" },
    "capabilities": { "tools": {} },
    "_qmai": {
      "pluginId": "chapter-insights",
      "hostUrl": "http://127.0.0.1:52341",
      "hostToken": "…",
      "grantedPermissions": ["fs:project-read", "net:https"],
      "projectPath": "D:/novels/我的书"
    }
} }

// 2. 工具清单
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list", "params": {} }

// 3. 工具调用
{ "jsonrpc": "2.0", "id": 42, "method": "tools/call", "params": {
    "name": "analyze_chapter_rhythm",
    "arguments": { "chapterPath": "D:/novels/我的书/正文/第12章.md" }
} }

// 4. 关闭（宿主退出前）
{ "jsonrpc": "2.0", "id": 99, "method": "shutdown" }
```

### 5.3 插件 → 宿主（HTTP 反调）

宿主能力面通过环境变量注入：`QMAI_HOST_URL`、`QMAI_HOST_TOKEN`、`QMAI_PLUGIN_ID`。

每个请求必须带 `Authorization: Bearer <token>`，且 token 与 `pluginId` 绑定（一个插件一个 token，不共享）。

### 5.4 为什么用「stdio 主 + HTTP 反调」而不是纯 stdio 双向

MCP 是客户端发起请求、服务端应答的单向模型。插件需要**主动**调宿主能力（读文件、写日志、发事件），纯 stdio 没有这个通道。

两个选择：扩展 MCP 加自定义 method（污染协议），或给一条反向 HTTP 通道（标准做法）。选后者：插件用现成的 `fetch` / `requests` 就能调，无需额外 SDK 支持。

## 六、宿主能力面（HostApi）

### 6.1 端点表

基址：`http://127.0.0.1:<随机端口>`，单例服务（所有插件共用端口，按 token 区分身份）。

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/host/log` | 自动 | 写插件日志（级别 + 消息） |
| POST | `/host/emit` | 自动 | 向前端发事件（事件名 + payload） |
| POST | `/host/data/read` | `data:write` | 读自己的数据目录 |
| POST | `/host/data/write` | `data:write` | 写自己的数据目录 |
| POST | `/host/data/list` | `data:write` | 列自己的数据目录 |
| POST | `/host/project/read` | `fs:project-read` | 读当前项目文件（路径必须在项目根内） |
| POST | `/host/project/list` | `fs:project-read` | 列当前项目目录 |
| POST | `/host/project/write` | `fs:project-write` | 写当前项目文件 |
| POST | `/host/net/fetch` | `net:https` | 发起 https 请求（仅 https，禁 http） |
| POST | `/host/llm/complete` | `llm:use` | 用用户当前配置的模型做一次补全 |
| GET | `/host/status` | 自动 | 返回宿主版本、当前项目、已授予权限 |

### 6.2 权限矩阵

| 权限 | 危险度 | 默认 | 说明 |
|---|---|---|---|
| `data:write` | 低 | **自动授予，不必在 `permissions` 里声明** | 只能操作插件自己的数据目录；声明了也不额外要求用户确认 |
| `fs:project-read` | 中 | 需用户勾选 | 路径限制在项目根内，符号链接需解析后检查 |
| `fs:project-write` | 高 | 需用户勾选 | 同上；写入前生成备份 |
| `net:https` | 中 | 需用户勾选 | 仅 https；禁止回环地址与私有网段（防 SSRF） |
| `llm:use` | 中 | 需用户勾选 | 消耗用户的 API 额度 |
| `ui:panel` | 低 | 第二期 | 现阶段不可申请 |

### 6.3 拒绝时的行为

权限不足返回 `403` + `{ "error": "E_PERMISSION_DENIED", "permission": "fs:project-write" }`。

**不静默降级、不返回空数组**——插件必须能明确知道「我没有这个能力」，否则作者会写出行为诡异的插件（DSH 的 `market-registry.mjs` 注释里记录过同类教训：两处 registry 不一致导致静默失败）。

## 七、进程生命周期

### 7.1 状态机

```
                    ┌─────────────────────────────────────┐
                    │                                     │
   ┌─────────┐  启动  ┌──────────┐  握手成功  ┌─────────┐  │
   │ stopped │──────▶│ starting │──────────▶│ running │  │
   └─────────┘      └──────────┘           └─────────┘  │
        ▲                 │ 超时/失败             │        │
        │                 ▼                      │ 进程退出│
        │            ┌────────┐                  ▼        │
        │            │ failed │           ┌────────┐     │
        │            └────────┘           │crashed │─────┘
        │                 │               └────────┘  重启次数 < 3
        │                 │                    │
        └─────────────────┴────────────────────┴── 重启次数 ≥ 3 → disabled_by_crash
              用户手动操作
```

### 7.2 规则

| 规则 | 值 | 理由 |
|---|---|---|
| 启动超时 | `runtime.startTimeoutMs`，默认 10s | 插件必须在这段时间内完成 `initialize` 握手 |
| 崩溃自动重启 | 最多 3 次 | 防止崩溃循环烧 CPU |
| 重启退避 | 1s / 3s / 9s | 同上 |
| 连续运行满 60s 后清零重启计数 | — | 避免「长期稳定后偶发一次崩溃就直接停用」 |
| 主程序退出 | 先 `shutdown`，5s 后强制 kill | 给插件写完日志的时间 |
| stdout 缓冲上限 | 64 KB（保留尾部） | 防插件疯狂打印打爆内存 |
| stderr 缓冲上限 | 64 KB（保留尾部） | 同上 |

### 7.3 「常驻」与「按需」的统一

`keepAlive: true` → 安装后随 App 启动，常驻。
`keepAlive: false` → 首次工具调用时启动，空闲 5 分钟后自动退出。

两套行为共用同一个 Supervisor，只差「空闲回收」这一条策略。

## 八、安装器

### 8.1 目录布局

```
<数据目录>/plugins/
├── .registry.json              # 注册表（原子写）
├── <plugin-id>/                # 插件本体（安装后只读）
│   ├── plugin.json
│   └── ...
├── .staging/<uuid>/            # 安装中临时目录
└── <plugin-id>-data/           # 插件私有数据（卸载不删）
```

数据目录位置参考 DSH 的 `$DSH_HOME`：QMAI 用 `app_data_dir()`（`mcp/paths.rs` 已有实现），可通过环境变量 `QMAI_PLUGIN_HOME` 覆盖（便于开发调试）。

### 8.2 安装流程

```
1. 校验来源
   ├─ 只允许 https
   ├─ host 必须是 github.com
   └─ 解析 <owner>/<repo>，可选 @<ref>，默认 main

2. 下载 zip
   ├─ 通道顺序（复用 update-channels.json 的加速策略）：
   │   gh-proxy.com → ghproxy.net → codeload.github.com 直连
   ├─ URL 形态：<base>/<owner>/<repo>/archive/refs/heads/<ref>.zip
   └─ 记录：commit（从 zip 内路径前缀提取）与 zip 的 sha256

3. 解压到 .staging/<uuid>/
   ├─ 逐条目校验：拒绝绝对路径、拒绝 `..`、拒绝符号链接
   ├─ 单文件上限 8 MB，总解压上限 64 MB
   └─ 只保留 zip 内第一层目录的内容

4. 校验 plugin.json
   ├─ 存在性 + JSON 合法性
   ├─ 字段约束（见 4.2）
   ├─ entry 路径归一化在插件目录内（见 4.3）
   └─ runtime 可执行性预检（node/python 是否存在）

5. 发布
   ├─ 原子 rename .staging/<uuid> → plugins/<plugin-id>
   ├─ 更新 .registry.json（写来源、commit、sha256、安装时间）
   └─ 更新失败则回滚 rename

6. 启动（autoStart: true 时）
   └─ 启动失败不回滚安装，标记为 failed，让用户看到原因
```

### 8.3 插件自带的依赖怎么处理

**核心原则：插件必须自带全部依赖，宿主不替它安装任何东西。**

| runtime | 依赖方式 | 示例 |
|---|---|---|
| `node` | 作者把 `node_modules` 提交进仓库，或打包成单文件 | `index.js` + `node_modules/@modelcontextprotocol/sdk/` |
| `python` | 作者用 venv 打包进仓库，或只用标准库 | `venv/` |
| `binary` | 作者上传预编译产物，按平台分目录 | `bin/win-x64/plugin.exe` |

**为什么不替它装依赖：**

1. 安装时执行 `npm install` / `pip install` = **在用户机器上执行任意代码**，这是最危险的一类安装行为（DSH 对此的处理是「pnpm ≥10 默认禁止构建脚本，放行需逐包显式授权」，并把它记为安全红线：7211 个插件里有 24 个因 `postinstall` 被标红）
2. Node 模块解析 + 宿主 fallback 会产生一整类「缺包 / 多版本 / 路径解析失败」的 bug（DSH 的 `AGENTS.md` 用整整一节讲这件事）
3. 自带依赖的插件是**自包含的**，卸载即干净，不会污染全局环境

**代价**：插件仓库体积会比较大（`node_modules` 可能几十 MB）。因此安装器的上限按「压缩包 8 MB / 解压 64 MB」控制，超限的插件会被拒绝——这会自然引导作者只依赖一个 MCP SDK，而不是拖进一整个框架。

**为作者提供的便捷**：文档里给出一个 20 行的 `bundle.mjs` 示例，用 esbuild 把插件打成单文件（含 SQL 等价物），体积通常在 100 KB 以内。这是推荐做法。

### 8.4 更新


- 比较远端 `plugin.json` 的 `version` 与本地
- 更新 = 下载新版 → 装到 `plugins/<plugin-id>@<version>` → 切换注册表指针 → 删除旧目录
- **不原地覆盖**（DSH generation 的核心经验：Windows 上对已存在目录做 rename 会卡死）
- 插件数据目录 `plugins/<plugin-id>-data/` 跨版本保留

### 8.5 卸载

- 从注册表移除 → 停进程 → 删插件目录
- **保留** `plugins/<plugin-id>-data/`，除非用户勾选「同时删除数据」

### 8.6 来源记录

`.registry.json` 里每个插件记录：

```jsonc
{
  "id": "chapter-insights",
  "version": "1.2.0",
  "source": {
    "type": "github",
    "repo": "owner/repo",
    "ref": "main",
    "commit": "a1b2c3d...",
    "zipSha256": "…",
    "installedAt": "2026-10-27T09:00:00Z"
  },
  "enabled": true,
  "grantedPermissions": ["fs:project-read", "net:https"]
}
```

**这一条是责任归属的凭据**：能证明「这个插件是用户从该作者的仓库、在该 commit 上装的，宿主没有改过」。

## 九、工具注入链路

```
插件启动
  → supervisor 完成握手
  → mcp_bridge 调 tools/list
  → 把每个工具包装成 Tool：
       name        = "<pluginId>__<toolName>"   // 加前缀，避免与内置工具重名
       description = 插件给的
       category    = "action"
       permission  = "confirm"                  // 默认要用户确认
       parameters  = 插件给的 JSON Schema 转 ToolParameter
       execute     = → stdio tools/call → 超时 30s → 文本结果
  → registry.register(tool)
```

### 9.1 `Tool` 接口复用

现有 `src/lib/agent/types.ts` 的 `Tool` 接口**不需要改动**：

```ts
export interface Tool {
  name: string
  description: string
  category: "read" | "write" | "action" | "virtual"
  permission?: "auto" | "confirm"
  parameters: Record<string, ToolParameter>
  execute(params, signal?, context?): Promise<string>
}
```

插件工具天然落进 `category: "action"` + `permission: "confirm"`。

### 9.2 为什么要加 `pluginId__` 前缀

内置工具里已有 `read_chapter`、`search_chapters` 等。不加前缀，一个叫 `read_chapter` 的插件工具会**静默覆盖**内置工具（`ToolRegistry.register` 是 `Map.set`，后写覆盖先写）。这是必须防的事故。

**前缀也会改变模型看到的工具名**，所以 `pluginId` 必须满足 `^[a-z0-9][a-z0-9-]{1,63}$`（见 4.2），转换规则：

```
最终工具名 = <pluginId 里的 - 换成 _> + "__" + <toolName>
例：pluginId "chapter-insights" + toolName "analyze" → "chapter_insights__analyze"
```

结果满足模型对工具名的要求（`^[a-zA-Z0-9_-]{1,64}$`），且与内置工具命名空间天然隔离。

`tools/call` 时必须把名字还原成插件内的 `analyze` 再发给插件——插件只认自己的名字。

### 9.3 工具卸载

插件停用/卸载时，`registry` 中对应前缀的工具全部注销。现有 `ToolRegistry.clear()` 是全清，需要新增 `unregisterPrefix(prefix: string)`。

## 十三、安全边界（明确写清，供用户和作者阅读）

### 13.1 这个系统能防住的

| 威胁 | 防护 |
|---|---|
| 插件读项目之外的文件 | `fs:project-*` 权限 + 路径归一化后必须落在项目根内 |
| 插件访问内网 | `net:https` 只允许 https，拒绝回环与私有网段 |
| 插件偷凭证 | 插件拿不到用户的 API Key（`llm:use` 走宿主代理，不暴露 key） |
| 插件崩溃带走主程序 | 进程隔离 |
| 插件在安装时执行代码 | 安装器只下载解压，**不执行任何插件代码**（`npm install` 之类一律不跑） |
| zip 路径穿越 | 解压逐条目校验 |
| 恶意插件窃取其他插件数据 | 各插件数据目录互相隔离，路径按 pluginId 绑定 |
| 插件伪造身份 | 每个插件独立 token，绑定 pluginId |

### 13.2 这个系统**防不住**的（必须写在文档和界面上）

- 插件是一个**完整程序**，它可以用自己的方式访问磁盘和网络，绕过宿主 API
- 宿主权限是在**调用 HostApi 时**拦截的，不是沙箱
- 因此：**装插件 = 安装一个第三方软件，用户必须信任作者**

**这条与 DSH 的立场一致**（awesome-dsh-plugin README 原文：「Installing a plugin runs third-party code on your machine with your own permissions — it can read your files, use your credentials, and reach the network. Tool approvals don't sandbox plugin code.」）。

### 13.3 界面上的三个必须

1. **安装弹窗显示来源**：`owner/repo`、版本、权限清单
2. **首次启用要求逐项勾选权限**，不提供「全部同意」
3. **插件更新后若权限扩大，必须重新确认**

1. 用**官方 MCP SDK 的示例 server** 包一层，装进 QMAI，能在对话里被 Agent 调用
2. 停用插件后，工具从模型可用列表里消失

## 十五、为什么这个方案能长出自己的生态

**它不需要等生态先长出来。** 理由：

1. 插件 = MCP server。**MCP 生态已经存在**——用户装了 Claude Desktop / Cursor 就可能已有 MCP server，把它们包一层 `plugin.json` 就是 QMAI 插件。
2. 作者门槛是「会写 30 行 Node」，而不是「会写 React 组件 + 会配构建」。
3. 安装是粘贴一个 GitHub 地址，不需要注册开发者账号、不需要提交审核。
4. 工具注入后，插件立刻出现在 AI 的可用能力里——**用户装完马上感知到变化**，这是留存的关键。

DSH 的插件生态是靠「7000+ 条目 + 一个 YAML 就能上架」长起来的。本方案的门槛比它更低：**不需要上架，一个仓库就能装。**

## 附：与 DSH 关键设计取舍对照

| 议题 | DSH 的做法 | QMAI 的做法 | 理由 |
|---|---|---|---|
| 插件载体 | npm 包 | GitHub 仓库 + plugin.json | 不引入包管理器 |
| 执行 | 同进程 JS（Node） | 独立子进程（node/python/binary） | 宿主是 Rust，无 JS 引擎 |
| 能力面 | `ctx` 容器（进程内对象） | HostApi HTTP（跨进程） | 跨进程只能走网络 |
| 传输 | 内部调用 | stdio JSON-RPC | 无端口、无防火墙提示 |
| 安装 | pnpm + generation | 自研 zip + staging + 原子 rename | 不依赖 pnpm |
| 开关 | `.dsh-market/state.json#disabled` + `cordis.patch.yml` | `.registry.json` 单一权威 | 单一开关写入点，避免两处不一致 |
| 崩溃恢复 | Safe Mode（另起干净 profile） | 进程隔离天然免疫 | 插件挂了不影响宿主 |
| 依赖解析 | Node 模块解析 + 宿主 fallback | 插件自带全部依赖（`node_modules` 打包进去） | 避免"缺包"问题的整类 bug |
