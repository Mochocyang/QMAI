公告功能 · 设计

2026-10-27 · 分支 feature/announcement-system · 涉及仓库：QMAI（客户端）、QMAIWEB（官网）

官网放一份 announcements.json 作为唯一事实源；软件启动与打开公告弹窗时拉取，本地缓存、本地记已读；侧栏底部加一个铃铛，未读用数字角标提示；弹窗里逐条展开即自动已读，另有「全部已读」。不做发布后台、不做轮询、不做清空。

1. 目标与范围

要做的

  • 在官网（www.qmai.pro）发布公告，软件能同步看到新公告。
  • 侧栏底部「设置」「外观」去掉汉字、只留图标；「设置」右侧新增铃铛入口。
  • 点铃铛打开弹窗；公告逐条可读；支持「全部已读」。

不做的（本期明确排除）

  • 清空公告：已读只是去掉未读标记，公告始终保留在列表里。
  • 发布后台 / 管理页：官网侧只新增一个静态 JSON，不新增页面、不加导航入口。
  • 公告与账号关联：已读状态是本机状态，不跨设备同步。
  • 版本定向、生效时间窗、类型分级：本期字段精简；过期公告直接从 JSON 删掉。
  • 系统通知 / 启动自动弹窗：只做角标，不打断写作。

2. 已确认的决定

决定选择理由
公告从哪来 官网静态 JSON（随站点部署） 官网是纯静态 Pages 站，靠 wrangler 手动部署；加一个文件即可，无后端、无密钥、可整份回滚。已上线的 analytics Worker 仍只承担统计，不掺进公告。
字段 精简集：id、标题、正文(Markdown)、发布时间、置顶、可选链接 够表达「发什么、什么时候发、点了去哪」；缺的字段（类型、时间窗、版本区间）等真有需求再补。
阅读状态 逐条自动已读 + 全部已读 「点开就算读过」符合直觉，不用用户额外交互；「全部已读」一次清掉剩余未读。没有「一键阅读」这个第三动作。
未读提示 铃铛右上角数字角标（9+ 封顶），不自动弹窗 公告是低频信息，弹窗打断写作；角标已经能让人知道「有事」。
同步时机 启动拉一次 + 每次点铃铛再拉一次 轮询对低频内容没有收益，却要常驻定时器与后台请求。
客户端分层 前端模块 + zustand store + app-state.json 持久化 与 analytics.ts 同构（plugin-http + 静默失败），无 Rust 改动；app-state 有原子写和 .bak 恢复，且跨窗口共享。

3. 架构与数据流

4. 数据契约 announcements.json

{
  "version": 1,
  "updatedAt": "2026-10-27T09:00:00+08:00",
  "announcements": [
    {
      "id": "2026-10-27-sync-fix",
      "title": "云同步重复上传已修复",
      "body": "## 修复内容\n- 同一文件不再被反复上传\n- 失败会重试两次\n\n详情见官网。",
      "publishedAt": "2026-10-27T09:00:00+08:00",
      "pinned": false,
      "url": "https://www.qmai.pro/"
    }
  ]
}
字段必填约束用途
version否当前 1结构升级预留；客户端只认 1，其它值按 1 尽力解析
updatedAt否ISO 8601仅调试用，客户端不依赖
id是稳定唯一，永不复用，≤64 字符已读状态的唯一依据
title是≤60 字，纯文本列表行标题
body是Markdown，≤2000 字展开后的正文
publishedAt是ISO 8601 带时区时间显示与排序
pinned否布尔，缺省 false置顶（排序优先，列表带「置顶」标）
url否仅 http/https「查看详情」用系统浏览器打开

校验与容错规则

  • 缺 id / title / publishedAt，或 publishedAt 无法解析 → 整条丢弃，不猜、不补默认值。
  • 重复 id → 保留第一条，其余丢弃（防止手写 JSON 复制粘贴出错）。
  • body 超长截断到 2000 字；条目超过 50 条只取排序后的前 50 条。
  • 整个 JSON 解析失败 / 顶层不是对象 / announcements 不是数组 → 视为拉取失败，保留本地缓存，不清空。
  • 排序不依赖文件顺序：pinned 降序，再按 publishedAt 降序。
id 的语义要说清：改错别字、补一段说明都属于「同一条公告」，id 不动，已读状态保持；想再次提醒用户，就换一个新 id。这条规则写进站点仓库的发布说明，否则「改了内容用户却没看见红点」会被当成 bug 报上来。

5. 官网侧改动（QMAIWEB）

文件动作说明
announcements.json（仓库根）新建公告数据，见第 4 节
_headers新建给该文件放开跨域与 5 分钟缓存
scripts/build.mjs修改把这两个文件加进复制白名单（当前是逐名拷贝 5 个文件）
scripts/test.mjs修改加一条结构校验，手写 JSON 出错时在部署前红

_headers

/announcements.json
  Access-Control-Allow-Origin: *
  Cache-Control: public, max-age=300

Pages 已按扩展名返回 application/json，不必覆盖 Content-Type。

build.mjs 的拷贝白名单

for (const name of ['index.html', 'styles.css', 'script.js', 'announcements.json', '_headers'])
  await cp(path.join(root, name), path.join(dist, name));
最容易漏的一步。 build.mjs 只拷贝点名的那几个文件，`announcements.json` 不在名单里就永远不会出现在 dist 里，线上 404，而本地看文件又是好的。

站点测试（scripts/test.mjs 追加）

  • 文件存在且 JSON.parse 通过；
  • announcements 是数组且长度 ≤50；
  • 每条都有非空 id / title / body / 可解析的 publishedAt；
  • id 不重复；url 若存在必须是 http/https。

6. 客户端数据层

src/lib/announcements.ts（新建）

export interface Announcement {
  id: string
  title: string
  body: string          // Markdown，已截断
  publishedAt: number   // epoch ms
  pinned: boolean
  url?: string
}

export const ANNOUNCEMENTS_URLS = [
  "https://www.qmai.pro/announcements.json",
  "https://qmai.pro/announcements.json",   // 备用域名
]

/** 纯函数：坏数据一律丢弃，不抛异常。 */
export function normalizeAnnouncements(payload: unknown): Announcement[]

/** 8s 超时；主域名失败换备用域名再试一次；仍失败返回 null。 */
export async function fetchAnnouncements():
  Promise<{ items: Announcement[]; fetchedAt: number } | null>
  • 走 getHttpFetch()（Tauri plugin-http，绕开 CORS），与全项目 HTTP 约定一致。
  • 失败不抛异常、不弹错误框，只在 console.warn 留一行，与 analytics.ts 同构。
  • normalizeAnnouncements 是纯函数，所有字段规则（第 4 节）都在这里，测试直接喂坏数据。

src/stores/announcement-store.ts（新建）

interface AnnouncementState {
  items: Announcement[]
  readIds: Set<string>
  lastFetchedAt: number | null
  status: "idle" | "loading" | "ready" | "error"
  dialogOpen: boolean
  // 派生
  unreadCount: number
  // 动作
  hydrate(): Promise<void>          // 读 app-state 缓存与已读
  refresh(): Promise<void>          // 单飞，失败保留旧数据
  openDialog(): void                // 开弹窗 + 触发一次 refresh
  closeDialog(): void
  markRead(id: string): Promise<void>
  markAllRead(): Promise<void>     // 清掉当前列表里的全部未读
}

持久化键（app-state.json）

键内容大小控制
announcementsCache{ items, fetchedAt }≤50 条、正文 ≤2000 字，整体约 100KB 上限
announcementReadIdsstring[]只保留当前列表里仍存在的 id，上限 200
  • 复用 getStore()：写入已有 100ms 防抖 + Rust 侧原子写与 .bak 恢复，不需要另做一层。
  • 不用 localStorage：项目里已有教训（皮肤存 localStorage 导致独立窗口不同步），且 localStorage 不进备份、不进迁移。
  • hydrate 容错：读到脏数据（不是数组、字段类型不对）就当空处理，并顺手覆盖成合法值。

触发点

时机行为
App 启动（挨着 initAnalytics 的 effect）hydrate() → 静默 refresh()，不阻塞渲染
点铃铛立刻 openDialog()（先显示缓存），同时 refresh()
弹窗内点「刷新」refresh()，失败时显示错误行

不做定时轮询：低频内容不值一个常驻定时器。

7. 界面规范

(a) 底栏去文字化 + 铃铛

改 src/components/layout/sidebar-bottom-actions.tsx（五个侧栏面板共用这一个组件）。

  • 两个按钮删掉 <span> 文字，保留 title 与 aria-label —— 纯图标没有悬停解释就等于不可辨识。
  • 三个按钮统一为 size-8 图标按钮（28px 命中区，与项目其它图标按钮一致）；设置选中态继续用 qm-selected。
  • 布局：设置与公告靠左（gap-0.5），外观用 ml-auto 锚在右边，用户原有位置感不变。

(b) 铃铛与角标

  • 图标 Bell（lucide），aria-haspopup="dialog"、aria-expanded。
  • 未读 > 0 时右上角 14px 红底数字，> 9 显示 9+；角标 aria-hidden。
  • aria-label 带数量：「公告」/「公告，3 条未读」。
  • 没有未读时完全不出现角标，不做「已读也留灰点」。

(c) 公告弹窗

src/components/announcements/announcement-dialog.tsx，挂在 App.tsx 根部（与 PersonaSkillCompletionDialog 并列）——只挂一次；若放进 SidebarBottomActions，五个面板各渲染一个，会出现多层遮罩。

  • 宽 640px、max-h-[70vh]，列表区内部滚动，头部与底栏固定。
  • 正文用 react-markdown 渲染；链接点击走 openExternalUrl 用系统浏览器打开（不在 webview 内跳转）。
  • 展开即 markRead(id) 并保持展开；再点一次收起，已读不回退。
  • 底栏左：上次更新时间 + 「刷新」（同时是失败后的重试入口）；右：「全部已读」，无未读时置灰不可点。
  • 空状态：「暂无公告」；无缓存且拉取失败：「暂时无法获取公告，请检查网络后重试」+ 重试按钮。
  • 无障碍：base-ui Dialog 自带焦点陷阱与 Esc 关闭；列表项用 button + aria-expanded。

(d) i18n

src/i18n/zh.json 增加 sidebarActions.announcements（「公告」）与 announcements.*（弹窗标题、未读数、空状态、全部已读、上次更新、重试、查看详情），与现有 sidebarActions 的用法一致。

8. 边界与错误

情况表现
断网 / 超时 / 站点 404 / JSON 坏静默使用缓存；无缓存时弹窗内给错误 + 重试；角标保持原值
公告被从 JSON 删除列表消失，其已读 id 在下次写入时被修剪
同一份 JSON 里重复 id保留第一条，其余丢弃
首次安装（无缓存）角标 0；点开先 loading，再出列表或错误
独立阅读窗口（reader-*）不渲染侧栏，不涉及；app-state 本身跨窗口共享
用户手改 app-state.json 写坏hydrate 判为脏数据按空处理，不影响启动
发布时间在未来（时钟/时区写错）时间显示「刚刚」，排序仍按时间戳，不隐藏

10. 实施顺序

  1. 站点先行：announcements.json + _headers + build.mjs 白名单 + 站点测试；先发一版占位公告，让客户端有东西可拉。
  2. 数据层：lib/announcements.ts + 单测（纯函数先立住字段规则）。
  3. 状态层：store + app-state 持久化 + 单测。
  4. 界面：底栏去文字化 → 铃铛角标 → 弹窗 → i18n + 组件测试。
  5. 接线与验收：App.tsx 启动拉取；手动跑第 9 节验收清单。
  6. 端到端：官网发一条真公告 → 部署 → 软件里看到角标、读掉、重启后仍是已读。

落地时的三处小偏离（都写进代码注释了）

  • normalizeAnnouncements 除了 ISO 字符串，也接受 epoch ms —— 否则写进缓存的条目在下次启动时会被自己的校验全部丢掉。
  • 角标与置顶标签的字号用 text-[0.625rem] 而不是 text-[10px]：全仓有字体单位换算守卫（scripts/convert-font-units-to-rem.spec.mjs），text-[Npx] 会直接让测试变红。
  • 弹窗标题下多一个 allReadHint（「已全部读完」）：未读数归零后描述行不能空着。

12. 风险与取舍

  • 发布要部署一次站点（约 5 分钟缓存 + 一条 wrangler 命令）。若之后想要「即时发布、不重新部署」，可把 JSON 换成 analytics Worker 的一个只读接口 —— 客户端契约不变，只换 URL。
  • 代理：客户端 HTTP 走 plugin-http/reqwest，沿用项目现有的 HTTP_PROXY 环境变量方案；若实测代理不生效，再按 updater 的做法把代理显式传入（届时才考虑加 Rust 命令）。
  • app-state 体积：靠「50 条 + 2000 字截断」把缓存压到 100KB 以内；写入有防抖与原子落盘，不影响启动。
  • 没有「清空」：公告会一直堆在列表里。列表上限 50 条 + 官网只保留最近 20 条，实际不会难看；真觉得长，后续再加归档而不是删除。
