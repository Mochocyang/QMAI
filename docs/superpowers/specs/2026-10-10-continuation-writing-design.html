章节「续写」

已批准 · 2026-10-10 · 实施计划见 docs/superpowers/plans/2026-10-10-continuation-writing.html
原始需求（用户原话，逐字保留）

如图中所示，在章节当中手写内容时，用户点击右键和选中内容后，比如选中“随后”两个字，会显示润色和去AI味，这时再增加一个续写，右键第一个选项应该显示为“续写”。

关于“续写”功能，具体需求如下：
1. 续写字数：每次续写 300 到 400 字左右。
2. 输入交互：续写界面上有一个类似于搜索框的输入框。用户可以在里面填入内容去续写，也可以不填内容直接续写。
3. AI 读取范围：续写时，AI 需要能够读取到当前章节的内容，不需要读取全部内容。

注：上面为逐字保留。原话里「点击右键和选中内容后……会显示润色和去AI味」指的是选中浮出工具栏，而「右键第一个选项」指的是右键菜单——代码里这是两个不同组件（见 01 节）。经询问，用户选定「两处都加」。

01

起点：两个组件、两种语义

动手前必须先把这两件事分清楚，否则会把「续写」写进错误的管道。

UI 上是两个不同的东西

入口组件内容触发
右键菜单 EditorContextMenu
wiki-editor.tsx:601		 撤销 / 重做 / 复制 / 剪切 / 粘贴 / 全选 / 查找 / 替换 —— 没有任何 AI 项 任意位置右键
选中浮出工具栏 wiki-editor.tsx:512-539 AI润色 / 去AI味 选中文本后浮出（右键也会触发它，因为 mouseup 会刷新选区）

用户看到的「润色和去AI味」是第二行那个浮层；「右键第一个选项」指第一行那个菜单。两者都要加（用户已确认）。

数据上是两种语义

现有 AI 润色 / 去AI味走的是替换语义：replaceChapterBodySelection（chapter-selection.ts:66）用 bodySnapshot 校验选区是否过期，然后原地替换，配套浮层是「原文 vs 候选稿」对比。

而续写是插入——不替换任何已有文字，只在其后追加。硬塞进那条管道会让浮层同时承担「输入框」与「原文对比」两种形态，语义变浑。这是本节最重要的一条判断。

为什么不能直接流式写进正文

这个编辑器是 React 受控 textarea，它的「撤销」走 document.execCommand("undo")（wiki-editor.tsx:393）——受控组件上原生撤销栈通常已被程序化赋值清掉，很可能按了没反应。所以「写进去之后不满意怎么办」必须一开始就设计好，不能依赖 Ctrl+Z。用户据此选定「先在浮层里流式显示，满意再插入」。

02

方案选择

方案做法优点代价
A 接进现有「选区变换」管道：ChapterSelectionAction 加 "continue"，复用 runSelectionTransform + 候选稿浮层 + 写回 改动面最小，流式 / 浮层 / 写回 / 统计全现成 浮层形态不对（续写要输入框）；写回要改成插入；de-ai 分支绕进来，语义变浑
B ✓ 独立轻管道：新纯函数模块 + 新浮层组件 + preview-panel 新增编排，只复用 streamChat / 浮层定位 / 写盘入口 语义干净（插入≠替换）；浮层可做成「输入框 + 流式预览 + 插入」；纯函数可单测；不污染现有两条路径 新增 2 个文件与一段状态
C 复用深度章节写作工作流（run_chapter_workflow / deep-chapter-generation） 上下文最全，质量最高 与需求 3 直接冲突（它正是要读记忆/维基/前情/技能）；慢、贵、重

结论：采用 B。A 的浮层是为「对比替换」设计的，硬塞输入框会变成四不像；C 正是用户明确说不要的那条路。B 顺手复用 A 的两个好东西：bodySnapshot 那套「过期就拒绝写回」的防错思路，以及浮层定位函数 getFloatingPanelPosition。

04

数据流

用户右键（或选中后点浮层按钮）──「续写」
   │
   ├─ wiki-editor 上报 { at, bodySnapshot, position }
   │     at = 选区末尾；无选区时 = 光标位置
   │
   ├─ preview-panel 打开浮层（idle：输入框 + 「续写」按钮，可留空直接点）
   │
   ├─ 点「续写」→ buildContinuationMessages(整章正文, 指令)
   │     → streamChat(默认模型, messages, {onToken}, signal, { max_tokens })
   │     流式文本显示在浮层里，**不碰正文**
   │
   ├─ 点「插入正文」
   │     → insertContinuationBody(当前正文, 锚点, 候选)
   │        · bodySnapshot 不一致 → 拒绝，提示「正文已变化，请重新选中」
   │        · 片段先过 formatChapterWriting → 自动补 　 缩进 + pangu 间距
   │     → handleSave(markdown, { source: "ai", immediate: true })
   │     → 光标落到插入内容末尾并滚动到可见
   │
   └─ 另有「重新生成」「停止」（AbortSignal）「取消」
可直接复用的现成能力
  • handleSave(md, { source: "ai", immediate: true }) → recordChapter 按增量 diff 记账。只把新增那段算成 AI，手写部分不会被误算。
  • getTextareaSelectionToolbarPosition(el, at, at)：内部已用 || "\u200b" 兜住零宽度选区（wiki-editor.tsx:887），传 start === end 就能算出光标位置，定位不用新写。
  • streamChat 自带写作防休眠；signal 直接支撑「停止」；max_tokens / temperature 走 requestOverrides。
05

五个决定性的设计选择

① 插入而非替换

不动 ChapterSelectionAction 与 replaceChapterBodySelection 的替换语义；新增 insertContinuationBody(currentBody, { at, bodySnapshot }, continuation)，返回新正文与新的光标偏移。插入规则写成确定性的一条，不留「智能」余地：

before = body[:at]        after = body[at:]
lead   = before 为空或以换行结尾 ? "" : "\n"
tail   = after  为空或以换行开头 ? "" : "\n"
next   = before + lead + 片段 + tail + after
caret  = before.length + lead.length + 片段.length

插入点落在一段中间时，续写内容自成一段（前后各补一个换行），不做「把原段落挪走再拼回来」这类聪明行为——那种行为在用户眼里就是「我的字被动了」。

② 不重排整章

只对插入的片段跑 formatChapterWriting。现有代码里只有去AI味那条路径会整章归一化，润色路径不。续写跟随润色——否则你手写的正文会被 pangu 顺手改一遍（中英文间距、缩进全变）。

③ 光标落位不复用 highlightRequest

现有 highlightRequest 是按文本 indexOf 查找定位的（wiki-editor.tsx:277），正文里出现重复句子时会定位到错误的地方。改为新增一个按偏移量定位的 caretRequest。

④ 模型用「默认模型（通用）」

与 AI润色同一处 resolveDefaultModel，也符合设置页那句「写正文以外的功能都用它……AI 改写/润色」。若日后想给续写单独指定模型，照去AI味的 deAiModel 加一个 continuationModel 即可，是独立小改动，本设计不做。

⑤ 超长章节截断

≤ 8000 字整章送；超过则送「开头 2000 字 + 结尾 6000 字」，中间插省略标记。这样「读整章正文」与「不读全部内容」两个要求同时成立（后者指不读记忆/维基/其它章节）。

06

提示词契约

写进 continuation.ts 并单测。以下每一条都对应一个可验证的断言，不是装饰。

[system]
你是中文小说写作助手。任务：接着给定正文继续往下写。

- 输出 300–400 字。
- 只输出续写的正文。不要解释、不要复述已有内容、不要「好的」这类开场。
- 承接最后一段的动作与情绪，自然衔接。
- 保持人称、时态、叙事视角、文风、人物语气与给定正文一致。
- 段落之间用换行分隔。**不要自己加缩进**，应用会统一处理。
- 不要在结尾强行升华、总结或预告。

[user]
【本章已有正文】
<整章正文，或截断后的开头+结尾>

【续写要求】
<用户指令；为空时写「未指定方向，请自行判断合理的推进」>

字数由提示词负责（用户说「300 到 400 字左右」，是软目标）；同时传一个宽松的 max_tokens（约 2000）防跑飞——留足余量是因为带思考的模型会把思考 token 也算进上限，卡太紧会截断成空。

07

界面与交互

两个入口

  • 右键菜单：新增「续写」并排在第一位（在「撤销」之上）。用户明确要求。菜单已支持 actions 参数控制菜单项与顺序，所以能只加在章节编辑器里——大纲编辑器不出现（那是 Milkdown 富文本编辑器，共用同一个菜单组件）。
  • 选中浮出工具栏：新增「续写」并排在 AI润色 之前。

两处入口走同一个锚点计算：at = 选区末尾；无选区时 = 光标位置。所以「选中随后两个字再续写」与「光标停在随后后面直接续写」结果一致。

浮层三态

状态内容按钮
idle单行输入框（形如搜索框，占位文字「想写什么？可留空直接续写」）续写
streaming输入框禁用；实时文本区（最高约 120px，可滚动）停止
done候选文本 + 字数显示（如「312 字」，便于确认是否落在 300–400）插入正文 / 重新生成 / 取消
error错误说明重试 / 取消

浮层贴在光标上方（复用现有浮层定位并把位置夹进视口）。位置在打开那一刻算定；浮层是短生命周期交互，不做滚动跟随。

09

测试与反向验证

  1. 纯函数单测（continuation.ts）：指令空 / 非空、超长章节截断、插入点四种位置（行首 / 行尾 / 段中 / 空正文）、锚点过期、空续写。
  2. 组件测试：浮层三态、输入框可留空、停止、字数显示。
  3. 契约测试（本仓库既有习惯，用源码断言）：右键菜单首项是「续写」且只在章节编辑器出现；浮层工具栏含「续写」；写回确实传 source: "ai"。
  4. 反向验证（逐条把修复拿掉，确认变红后再还原）：去掉 source: "ai" → 统计用例红；去掉 bodySnapshot 校验 → 过期用例红；把「续写」加进公共 ITEMS 默认值 → 「大纲编辑器不得出现续写」用例红。
纪律

每一条新守卫都必须先证明「无修复必红」。只跑一遍绿的测试不算验证——上面第 4 条就是为了避免假绿。

10

明确不做（YAGNI）

  • 不读记忆 / 维基 / 前情 / 其它章节（用户需求 3 明确排除）
  • 不做「续写下一章」——那是深度章节工作流的入口，不是编辑器内的快写
  • 不做连续自动续写（一次一个浮层，插入后结束）
  • 不加新的模型设置项（用默认模型）
  • 不改动现有 AI润色 / 去AI味 的任何行为
11

待确认点的结论（已销账）

设计过程中问过三个问题，此处保留问题与结论的对应关系，便于日后回溯为什么是这样。

  1. 入口加在哪里 → 用户选「两处都加」：右键菜单首项 + 选中浮出工具栏首项。
  2. 模型读取多少当前章节 → 用户选「整章正文都送」，超长章节（> 8000 字）自动截断为开头 + 结尾。三种选项都不读其它章节与记忆库。
  3. 生成内容怎么进正文 → 用户选「先在浮层里流式显示，满意再插入」。这是受控 textarea 原生撤销不可靠的直接后果（见 01 节）。
