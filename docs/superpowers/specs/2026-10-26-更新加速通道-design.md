# 软件更新加速通道 —— 设计方案

> 目标：用户点「检查更新」时，**自动在多条通道里选最快的那条**下载安装包，全程无感。
> 边界：**只服务"公开的软件更新文件"**。云同步（用户的小说）不走任何第三方中转。

---

## 一、现状与问题（实测结论）

| 现象 | 根因 |
|---|---|
| 检查更新极慢 | `latest.json` 在 `github.com`，会 302 跳到 `objects.githubusercontent.com`；后者在国内多次实测 20s 超时 |
| 用户开了代理也没用 | `tauri-plugin-updater` **没有吃** 应用自己的 `proxy.rs`（只写环境变量，插件不读） |
| 一次失败要等很久 | 固定 30s 超时，不复用、不退避 |

实测数据（同一网络，3 分钟内）：

```
cdn.jsdelivr.net       990 ms   ✅
api.github.com         320 ms   ✅
github.com            19543 ms  ✅（慢）
github.com/releases   ��� ×3（20s 后连不上）
raw.githubusercontent  ❌ 15073 ms
```

## 二、总体架构

```
┌───────────────────────────────────────────────┐
│ 设置 → 检查更新（前端，已有流程不变）           │
└──────────────────┬────────────────────────────┘
                   │ 1. 拿一份「通道候选表」
                   ▼
      ┌────────────────────────────┐
      │ 通道表（channels.ts / .json）│  ← 内置默认 + 远程可覆盖
      └────────────┬───────────────┘
                   │ 2. 并发探活（每个通道 1 个 HEAD/GET 小文件）
                   ▼
      ┌────────────────────────────┐
      │ probe：测 RTT + 是否可用     │  → 排序，缓存 10 分钟
      └────────────┬───────────────┘
                   │ 3. 取第一名开始下载，失败自动换下一名
                   ▼
      ┌────────────────────────────┐
      │ download：断点无关的整包下载 │  → 校验 sha256/signature（插件负责）
      └────────────────────────────┘
```

**三层各自独立、可单测：**

| 模块 | 职责 | 依赖 |
|---|---|---|
| `channels` | 只管"有哪些通道、每个通道怎么拼 URL" | 无（纯数据 + 纯函数） |
| `probe` | 只管"测出哪个能通、多快" | HTTP |
| `download` | 只管"按顺序尝试，成功即返回" | HTTP + channels |

## 三、通道表设计

### 3.1 数据结构

```ts
export interface UpdateChannel {
  id: string                      // "direct" | "ghproxy" | "jsdelivr" | "custom"
  label: string                   // 展示用，例如「加速通道 A」
  /** 把 GitHub 原始地址映射成该通道的地址；identity 表示直连 */
  rewrite: "identity" | "prefix" | "jsdelivr"
  base?: string                   // prefix 型通道的加速前缀
  /** 只有 update 用途；数据（云同步）永远不用镜像 */
  scope: "update-only"
}
```

### 3.2 内置默认名单（可远程覆盖）

```json
{
  "version": 1,
  "channels": [
    { "id": "direct",   "label": "直连",       "rewrite": "identity" },
    { "id": "ghproxy",  "label": "加速通道 A", "rewrite": "prefix", "base": "https://ghproxy.net/" },
    { "id": "ghproxy2", "label": "加速通道 B", "rewrite": "prefix", "base": "https://gh-proxy.com/" },
    { "id": "jsdelivr", "label": "加速通道 C", "rewrite": "jsdelivr" }
  ]
}
```

**URL 映射规则：**

- `identity`：`https://github.com/O/R/releases/download/TAG/FILE` 原样用
- `prefix`：`<base>https://github.com/O/R/releases/download/TAG/FILE`
- `jsdelivr`：**只对 `latest.json` 有效**（它只能代理仓库文件，不能代理 release 资产）：
  `https://cdn.jsdelivr.net/gh/O/R@main/latest.json` —— 所以它只能用来加速"检查更新"这一步，
  不能用来下安装包。**这是硬约束，必须写进代码注释**，否则会对着 404 干等。

### 3.3 远程覆盖

- 应用启动时（异步、不阻塞）尝试拉
  `https://cdn.jsdelivr.net/gh/Mochocyang/QMAI@main/update-channels.json`
- 成功且 `version` 比本地新 → 写入本地缓存 `update-channels.cache.json`
- **失败就静默用内置默认**（绝不因为通道表拉不到而让更新不可用）
- 校验：`channels` 必须是数组、每项 `id` 唯一、`rewrite` 必须是三个已知值之一、`base` 必须 `https://`

**为什么用 jsDelivr 拉这张表**：它实测 990ms，是唯一稳定可达的；这张表本身是公开配置，无隐私。

## 四、探活与择优

### 4.1 探什么

每个通道探的是一个**固定的小文件**：`latest.json`（实测 785 字节）。

- **能拿到 200** → 可用
- 拿到 404/403 → 这个通道**不支持该文件类型**（jsDelivr 对 release 资产就是 404）→ 标记不可用
- 超时（**连接 3s / 总 5s**）→ 不可用

### 4.2 怎么排

- 并发发起（不串行，串行会慢 4 倍）
- 按"可用 + RTT 升序"排序
- 结果缓存 **10 分钟**（内存，不落盘）
- **直连永远保留在列表末尾**作为最终兜底 —— 即使它探活失败也留着

### 4.3 什么时候探

| 时机 | 行为 |
|---|---|
| 用户点「检查更新」 | 探一次（若无缓存） |
| 启动后 30 秒（空闲） | 后台预探一次，让用户点的时候直接有结果 |
| 下载失败 | 立刻换下一名，**不重新全量探活** |

## 五、下载流程

```
1. 拿通道表 → 探活排序
2. 从第一名开始：
     用该通道拼出 latest.json 地址 → 取到清单
     → 用该通道拼出安装包地址 → 下载
     成功 → 结束
     失败（超时/403/404/连接重置）→ 记一条日志，换下一名
3. 全部失败 → 报告"网络不可用"，并给出可操作建议：
   开启代理 / 稍后再试
```

**关键：清单和安装包必须走同一条通道。** 不能"用镜像取清单、用直连下包"——
那样跳转后的 `objects.githubusercontent.com` 仍然会卡住，用户看到的还是慢。

**校验不变**：Tauri 插件会用 `pubkey` 验签，**镜像不能篡改包**（验签失败会直接拒绝）。这是镜像方案能安全成立的前提。

## 六、与现有代码的接入

| 文件 | 改动 |
|---|---|
| `tauri.conf.json` | `updater.endpoints` 保持单一直连地址（真正的多通道由我们自己控制，不用插件的多端点机制，因为插件不支持"每个端点不同映射规则"） |
| `src-tauri/src/updater/channels.rs`（新） | 通道表的读取、校验、远程覆盖、URL 映射 |
| `src-tauri/src/updater/probe.rs`（新） | 并发探活 + 排序 + 缓存 |
| `src-tauri/src/updater/download.rs`（新） | 按序尝试下载（带进度事件） |
| `src-tauri/src/proxy.rs` | 增加 `current_proxy_url()`，供 updater 的 http client 使用 |
| `src/lib/app-updater.ts` | 改成调用我们自己的命令，而不是 `plugin-updater.check()` |
| 设置页 | 只显示一行只读状态：「更新通道：加速通道 A（210ms）」，不可改（全自动） |

### 为什么不用插件自带的 `endpoints: [a, b, c]`

插件的多端点是"同一个 URL 换域名"，而我们需要"**同一个文件，不同 URL 拼法**"
（jsDelivr 只认仓库路径，反代要前缀）。自己控制映射更清楚，且**失败能精确记录到哪个通道**。

**但验签仍然用插件**：下载完成后把文件交给插件验签 + 安装，安全边界不动。

## 七、安全红线（写死在代码里，不给开关）

1. **`scope: "update-only"`** —— 通道层只接受"更新"用途的调用；云同步模块**不允许 import 它**（用 ESLint 规则 + 目录边界强制）
2. **不内置任何翻墙节点/机场订阅**
3. **镜像只能用于公开文件**（`latest.json`、release 资产），因为它们是公开的
4. **验签不能省**：镜像返回的包必须通过 `pubkey` 校验，否则拒绝安装
5. 通道表拉取失败 → 静默退回直连，**绝不阻断更新**

## 八、失败兜底与用户可见信息

| 情况 | 用户看到 |
|---|---|
| 某通道失败，换了一个成功 | 无感（只记日志） |
| 全部失败 | 「网络连不上 GitHub，检查更新失败。已尝试全部加速通道；可以稍后重试，或在设置里配置自己的代理。」 |
| 验签失败 | 「下载的安装包校验不通过，已丢弃。」（绝不安装） |
| 通道表拉取失败 | 无感（用内置默认） |

## 九、测试计划

| 层 | 测什么 |
|---|---|
| `channels` | URL 映射三种规则；jsDelivr 对 release 资产返回 `None`；坏数据（重复 id、非 https、未知 rewrite）被丢弃 |
| `probe` | 全失败时返回空但保留 direct；缓存 10 分钟内不重复探；RTT 排序正确 |
| `download` | 第一个失败自动换第二个；全失败返回明确错误；清单与包必须同通道 |
| 集成 | 用一个本地 HTTP 替身（照 `webdav.rs` 的 `TcpListener` 写法）模拟"通道 A 超时、通道 B 正常" |

## 十、不做的事（YAGNI）

- ❌ 不做"下载限速/多线程分段下载"（单线程足够，复杂度不值）
- ❌ 不做"增量更新"（Tauri 插件不支持）
- ❌ 不做镜像的手动选择 UI（你要全自动）
- ❌ 不做云同步走镜像（安全红线）

---

## 十一、验收标准

1. 在**当前这台网络**上点「检查更新」：**5 秒内**出结果（成功或明确失败），不再出现 20 秒无响应。
2. 日志里能看到本次用了哪条通道、RTT 多少、失败时换了哪条。
3. 把网络断掉：给出"全部通道不可用"的明确提示，**不再卡住**。
4. 通道表里的 jsDelivr 被正确识别为"只能检查更新、不能下包"，不会拿它去下 200MB 安装包。
5. 云同步代码**编译期就不可能**引用到通道模块。
