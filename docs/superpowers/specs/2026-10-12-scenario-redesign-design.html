「舞台情景」重设计

已批准 · 2026-10-12 · 实施计划待生成
原始需求（用户原话，逐字保留）

分析当前“青木AI写作”软件中的“舞台情景”模块，具体反馈如下：

1. 角色数量：
现在有 3 个、4 个、5 个角色，后续要支持用户手动选择。提取的章节数量要与角色数量保持一致，这一点没有问题。

2. 角色选择与绑定：
(a) 从已写章节中选择角色时，不需要从下拉框中选择，也可以直接在这里选择。
(b) 选择后若提示“未绑定灵魂”，这里应该增加一个“绑定灵魂”的功能。
(c) 主持人相关功能没有问题。

3. 情景设定：
这 4 个输入框的输入体验不是特别好，框太窄了，应该再宽一些。

因此，目前关于“舞台情景”模块需要重新设计一下。

另外，关于生成内容：
生成内容时，形式应类似于对话框或群组，由每一个角色自动回复内容。

注：以上为逐字保留。三处需要澄清的地方已在「12 已销账的确认点」逐条记录了用户的选择与理由。

动手前先把「用户看到的现象」与「代码里的事实」对上，避免把问题修在错误的层。

1. 角色数量 —— 只有写死的 3/4/5，且不参与提取

2(a) 角色选择 —— 确实只有一个下拉框，候选看不到信息

现在是「下拉挑一个 → 加进已选列表」。没被选中的候选只能在下拉里看到「名字（灵魂：xx）」，看不到性格 / 说话风格；只有已选卡片才有完整信息。

2(b) 绑定灵魂 —— 现在只是一句不可点的死文案

bindCharacterAura 写盘前会查 hasCharacterProfile()（character-aura.ts:510、:733），要求该角色在 wiki/entities（type: entity + tags 含 character）或 wiki/outlines 里有「人物小传 / 人物设定」，否则直接抛 「请先在大纲中添加人物小传或人物设定，再绑定角色灵魂」。

而舞台情景的候选角色是 extractStoryContent() 从章节正文提的，提取过程只读不写（story-extractor.ts:534-537 只读 wiki/entities/{name}.md）。所以很可能一点「绑定灵魂」就撞上那句报错——这正是这个功能必须先解决的问题，而不是加一个按钮就完。

2(c) 主持人 —— 确认没问题，本次不动

主持人下拉（你 / 某个已选角色）+ 串场间隔 + 行为说明（scenario-setup-panel.tsx:422-475）；角色主持时负责开场、每 N 轮串场、结尾收束；你主持时「主持人要求」即开场白且不额外消耗调用。本轮只把这个下拉的等价操作搬到角色卡上（见 04 节），行为本身一行不改。

02

方案选择：角色区怎么重做

方案做法优点代价
A ✓ 一个统一网格：候选角色全部铺成卡片，点一下上台（带序号、高亮），再点一下下台；数量按钮只做校验与提示（「已选 2/4，还差 2 人」） 只有一处列表，不必在「候选下拉」与「已选列表」之间来回看；绑定灵魂 / 设为主持人都有位置放；候选信息（性格/风格/认知）第一次全部可见 候选很多时需要补一个搜索/过滤框
B 候选网格 + 已上台清单两块，上台清单带主持人 / 绑定 / 移除 结构最清楚，「台上是谁」一眼可见 同一个角色出现两次，卡片内容重复；「未绑定灵魂」这个提示要在两处同步
C 维持下拉，只是把下拉加宽 改动最小 没有解决需求 2(a)，不采用

结论：采用 A。「已上台」这件事由卡片自身的高亮 + 序号 + 顶部计数共同表达，不需要第二份清单。B 的重复呈现会带来「同一条绑定状态写两遍、两处都要刷新」的同步负担，而它换来的信息 A 已经有了。

04

角色区交互细节

数量：3/4/5 一键 + 自定义

  • SCENARIO_CHARACTER_PRESETS = [3, 4, 5]：三个按钮原样保留。
  • 右侧「自定义」数字输入，范围 [SCENARIO_CHARACTER_MIN, SCENARIO_CHARACTER_MAX] = 3 – 10；SCENARIO_CHARACTER_MAX 由 5 改为 10。
  • 该常量目前只被提示文案使用（scenario-setup-panel.tsx:272），不参与引擎计算 —— 改它不会影响任何生成行为。
  • 自定义值超界时夹取到边界并给出一行提示，与既有「轮数夹取」同一套做法（scenarioRoundsClamped）。

开始条件（语义不变，只是变得看得见）

canStart =
  !extracting
  && !insufficientCandidates        // 候选 < 3 人：素材不够，明确报错
  && selectedIds.length === characterCount   // 选满
  && directive.trim().length > 0   // 填了情景规则
  && (!needsCostAck || costAck)    // 成本护栏

这五条一个都不放宽。区别只在于：原来「没选满」只能靠一个灰着的按钮表达，现在顶部有 「已选 2 / 4，还差 2 人」 的明确计数。

发现一处文案与实现不一致（本规格给出处理方式，请复核）

现提示文案是「角色数不含主持人（3-5）」（scenarioCharacterCountHint），但实现要求的是 selectedIds.length === characterCount，而 selectedIds 包含被选为主持人的那个角色（scenario-setup-panel.tsx:148、:186）。也就是说：选 3 人、其中一人当主持人时，实际发言只有 2 人，和文案说的「3 个发言角色」不符。

本规格的处理：保留实现语义、修正文案。理由：① 用户原话说的是「现在有 3 个、4 个、5 个角色」，指的是台上人数，与实现一致；② 改实现会让「选 3 人 + 指定角色主持」变成 4 次点选，是行为回退；③ 只需把文案改成「上台角色总数（3-10 人，含由角色担任的主持人）」，并保留已有的「主持人由角色担任，实际发言角色 N 人」提示即可说清。

类型注释里的旧说法（scenario-types.ts:53-56「角色数不含主持人」）同步更正。

候选卡片：三种状态

状态外观点击行为
未上台普通边框；显示名字、灵魂（或「未绑定灵魂」）、性格词前 3 个点卡片 = 上台（未满时）；已满时点击给提示，不静默失败
已上台主色边框 + 主色底 + 左上角上台序号（①②③…，与发言轮转顺序一致）点卡片上的移除按钮 = 下台；下台若其正担任主持人，主持人自动回落为「你」（沿用现有 removeCharacter 行为）
已上台且是主持人额外一枚「主持人」徽标徽标可取消（回落为「你」）

卡片上的两个操作

  • 绑定灵魂 / 灵魂：xxx：未绑定时是可点的「绑定灵魂」按钮；已绑定时显示金色徽标「灵魂：xxx」，点它可重新绑定或解绑（复用 unbindCharacterAura）。
  • 设为主持人：单选语义（全局只有一个）。放在已上台的卡片上，等价于现在的主持人下拉，但不必翻到下一节去找名字。③ 节的下拉保留，两处状态同源，改哪边都同步。

候选很多时

候选超过 12 个时，网格上方显示搜索框（按名字/灵魂名过滤，纯前端过滤，沿用 soul-binding-target-dialog.tsx:118-127 的输入样式）。少于 12 个不显示，避免多一个空控件。

05

绑定灵魂与「就地补小传」

这是需求 2(b) 的核心。因为 bindCharacterAura 有「必须先有人物小传」的前置校验（见 01 节），所以「绑定」在缺小传时是一次两步写入，必须让用户在写盘前看清要写什么。

流程

全过程是一个弹窗组件、两个内部步骤（步骤 1 选灵魂 → 步骤 2 补小传），不是一个接一个的两个独立弹窗；步骤 2 可以退回步骤 1 重选灵魂，也可以直接取消。

点「绑定灵魂」
   │
   ├─【步骤 1】灵魂选择：listCharacterAuras(projectPath)（内置 + 自定义），带搜索
   │
   ├─ 用户选定某个灵魂，点「绑定」
   │     → bindCharacterAura(projectPath, { characterName, auraId })
   │          ├─ 成功 ─────────────────────────────► 关窗，刷新候选，徽标变「灵魂：xxx」【结束】
   │          └─ 抛「请先在大纲中添加人物小传…」─► 切到【步骤 2】
   │
   └─【步骤 2】补小传确认
         · 正文预填（不调模型、不消耗 token）：由已提取信息拼出
         · 用户可自由编辑
         · 点「创建小传并绑定」
              → 写 wiki/entities/{安全文件名}.md（已存在则不覆盖，直接绑定）
              → 再 bindCharacterAura
              → 关窗，刷新候选
         · 点「返回重选」→ 回【步骤 1】
         · 点「取消」→ 全程零写入
为什么用「先试后补」而不是「先查后补」

hasCharacterProfile 除了查 wiki/entities / wiki/outlines，还会兜底走一次 searchWiki（character-aura.ts:737-745）。若我们事先用 listBindableNovelCharacters 自己预判，会漏掉 searchWiki 这条命中路径，对本来能绑成功的角色弹出多余的补小传弹窗。所以顺序必须是「直接绑 → 失败且原因正是缺小传 → 才补」。

为了让调用方能识别失败原因，需要把 CHARACTER_AURA_BINDING_BLOCK_MESSAGE 导出（character-aura.ts:228，当前是模块内私有）。这是本次对该文件的唯一改动。

预填小传的内容（纯函数，可单测）

buildProfileDraftFromCandidate(candidate) 只使用 ScenarioCandidate 里已有的字段，不新增任何模型调用：

# {candidate.name}

## 基本信息
- 姓名：{candidate.name}
- 灵魂：{candidate.auraName}          （无则省略该行）

## 性格
{candidate.personality.join("、")}    （空则写「（待补充）」）

## 说话风格
{candidate.speakingStyle}            （空则写「（待补充）」）

## 认知范围
- 知道：{candidate.knowledgeScope}    （各占一行，最多 10 条）
- 不知道：{candidate.doesNotKnow}      （同上，无则省略整段）

绑定后候选如何立刻刷新

不必重新跑一次章节提取。候选构造器早就预留了这个入口但没被接线：

buildScenarioCandidates(extraction, { bindings, auras })   // scenario-participant-selector.ts:55-90

而现在视图调用时没传这两个参数（story-simulation-view.tsx:1399-1402）。接线后：

  • 视图加载 listCharacterAuras + getCharacterAuraBindings 存入状态；
  • 绑定/解绑成功后重载这两份数据 → useMemo 依赖变化 → 候选卡片的灵魂徽标与「性格/说话风格」立即更新；
  • 兜底匹配分支只在提取产物没带光环时生效（scenario-participant-selector.ts:65-73），恰好就是「刚在情景面板里绑上」的这一类角色。
06

房间视图：群聊在场感

只改呈现。发言顺序、轮转起点、主持人串场节奏、插话 / 续跑 / 导出 / 插入章节全部保持原样。

新增：顶部成员条

在现有信息条下方加一行成员徽章：每个参与者一枚「圆形头像（名字首字）+ 名字 + 灵魂小字」，主持人带徽标。作用有两个：开演前就知道这场有谁；发言时当前发言者的徽章高亮，形成「谁在说」的在场感。

新增：稳定的角色配色

新增纯函数模块 scenario-avatar.ts：

边界与错误处理

情况处理
候选 < 3 人保留现有明确报错（scenarioCandidatesInsufficient）：提示增加提取章节数并「重新分析角色」
候选 < 用户选的数量（如提取 4 人、想开 5 人）自定义输入与 3/4/5 按钮均夹取到候选数并提示；沿用现有的 useEffect 夹取逻辑（scenario-setup-panel.tsx:130-134），不静默失败
已选满还点未上台的卡片给一行提示「已选满 N 人，先取消一位」，不作静默忽略
绑定灵魂时灵魂列表为空空态提示：去「灵魂」页创建或导入灵魂后再来绑定（不阻断其它操作）
绑定失败且原因不是缺小传原样抛出、由面板既有的错误条呈现（不吞错）
补小传时目标实体页已存在跳过写入、直接绑定（绝不覆盖用户已有内容）
补小传写入成功但绑定失败如实告知「已创建人物页，但绑定失败：…」；人物页保留（用户已确认要创建它）
解绑后候选徽标回到「未绑定灵魂」，性格/风格回落到档案兜底（构造器内既有行为）
历史情景（旧数据没有 speakerId）可选字段缺省时按 speakerName 兜底取配色，不报错
参与者名字重复排序与配色按 speakerId 计算，不依赖名字唯一

11

明确不做（YAGNI）

  • 不改对话引擎：发言顺序、轮转起点、主持人串场节奏、收束全部原样
  • 不做「角色数量 ↔ 提取章节数」联动（用户在澄清中确认保持现状）
  • 不改提取逻辑（story-extractor.ts 只读不写的现状保留）
  • 不动主持人功能本身（用户明确说没问题）
  • 不动成本护栏（阈值 40、二次确认）
  • 不动历史情景列表、导出、插入章节、插话续跑、继续生成
  • 不做角色的增删改（新增/重命名/删除角色），那是「人物小传」页的职责
  • 不自动生成小传正文（补小传只做预填 + 用户编辑，不调模型、不消耗 token）
  • 不改左右布局（用户选的是「加群聊在场感」，不是左右分栏）
12

已销账的确认点

设计过程中问过的问题与用户的选择，逐条留档，便于日后回溯为什么是这样。

  1. 角色数量怎么改 → 用户选「保留 3/4/5 按钮，另加「自定义」输入」。自定义范围由本规格定为 3–10（下限沿用既有 MIN=3，上限由 5 放宽到 10）。
  2. 提取章节数与角色数量的关系 → 用户选「现状就好，这条不用改」：提取章节数仍是独立下拉，只作为「从最近多少章里提角色」的输入范围，两者不联动。
  3. 「绑定灵魂」绑到什么范围 → 用户选「写项目绑定 + 缺小传时就地引导补一份」：与灵魂页绑定行为完全一致、全项目生效；缺人物小传时在情景面板就地补一份最小小传再绑。本规格据此确认会新增写入 wiki/entities/{角色名}.md 的动作（仅在文件不存在时写入）。
  4. 「生成形式像群组」具体指什么 → 用户选「加「群聊在场感」」：保留气泡流，增加头像 / 专属配色 / 「×× 正在输入」/ 成员条；不做左右分栏，不做气泡内角色信息卡。引擎不动。
  5. 「提取的章节数量要与角色数量保持一致，这一点没有问题」的含义 → 经核实，现状是两者完全独立、无任何联动；用户确认按现状理解，本条不作为改动项。
  6. 角色数量含不含主持人 → 设计过程中新发现的文案/实现不一致（见 04 节）。本规格按「含主持人」保留实现语义并修正文案，若期望「3 个发言角色 + 额外 1 名主持人」，需改为选择 4 人，请在规格复核时指出。
