01

背景：为什么不能复刻已有的「角色 Skill」

仓库里存在三套都被称作「角色 Skill」的东西。选错复用对象会让整个功能建立在错误的基座上，所以先厘清；同时这也正是本功能最终定名为「人物 Skill」的原因（见第 2 节 D8）。

代号落盘位置绑定「本作人物」已注入写作上下文
A 拆书库角色 Skill book-analysis/<bookId>/skills/ ✗ 绑定的是别的作品里的角色 仅通过 C 间接进入
B 写作 Skill 的「角色」分类 <project>/writing-skills.json ✗ 全局通用技能，无人称维度 走 skill-route
C 角色灵魂 CharacterAura .qmai/character-aura.json + <slug>-perspective/SKILL.md ✓ 按 characterName 绑定本作人物 ✓ 直接注入

C 是唯一具备「按人物绑定 + SKILL.md 落盘 + LLM 生成 + 编辑 UI + 写作注入」的底座。但它仍不是本功能的直接复用对象，原因见第 2 节的 D1／D7 两项决策。

现有注入链路（已通，本功能不重建）

章节生成 → context-engine.ts → 动态 await import("./character-aura") → buildCharacterSoulContext() → 从「任务描述 + 章纲 + 人物状态 + 认知状态」匹配本章出场角色（含别名／拼音／简繁模糊匹配） → 写入上下文包 characterAuras 字段 → 进写作提示词「人物气质」小节。

02

决策记录

以下七项由逐题问答确认，构成本设计的全部自由度边界。

D1
按重要度分级，而非全量生成

主角／核心配角首次出场即生成并持续完善；次要角色出场 ≥2 次才生成；龙套／路人只进人物页，永不建 skill。 「第一章有 5 个角色就生成 5 个 skill」被明确否决——这正是规模失控的源头。

D2
档位来源：读已有角色定位 + 出场次数动态升降级

定位取自 wiki/characters/角色-<定位>-<名>.md 的文件名（列一次目录即得，不读正文）； 出场次数取自章节快照与自有计数。零额外 LLM 成本、结果可预测。 不采用「让 LLM 打重要度分」——每章多一次调用且分数会漂移。

D3
每次「提取记忆」触发，同章所有角色合并成 1 次 LLM 调用

忠于需求原文「第二次出现时完善」，但把同一章需要新建／完善的角色合并进单次调用—— 成本与出场人数脱钩。后台异步（void），不阻塞按钮。

D4
生命周期三态：活跃 → 休眠 → 归档，永不自动硬删除

连续 N 章未出场转休眠（不再注入，但保留可见），更久转归档（默认折叠）。 正文里写过的角色，用户可能几十章后突然要用，所以全程不丢数据、不删文件。

D5
按档位分级注入

绿标／major：结构化字段 + SKILL.md 摘要；minor：只给「怎么说话 + 怎么判断」两条；休眠／归档：不注入。

D6
绿色复选框 = 角色重要性标记，一票定档

用户手动点击。绿色 = 永不归档 · 最高档注入 · 每次出场都做重点分析更新 skill · 且只有绿色角色才生成／维护研究文件。 用途是解决自动分档的固有盲区：一个被设定为主要角色、却在前 30 章都没怎么出现的人物，只看出场次数会被误判为次要甚至龙套。

D7
独立轻量索引 + 每角色一份 SKILL.md，与「灵魂」彻底隔离

不复用 CharacterAura 的数据结构，也不共用它的 bindings。 这是本设计最重要的一个决定——它使 character-aura.ts 零改动， 也让自动学习绕开了 bindCharacterAura() 的校验链（见第 6 节）。

D8
定名「人物 Skill」，内部标识一并使用 persona-skill-*

「角色」是本仓库里被复用的过度词——拆书库角色 Skill、写作 Skill 的「角色」分类、角色灵魂、角色认知、模拟角色都叫角色。 而「人物」恰是仓库既有的、专指本作人物的词：character-state.ts ↔ UI「人物状态」、 character-profile-template.ts ↔「人物小传／人物设定」、listBindableNovelCharacters() ↔「可绑定人物名单」。 因此定名不是单纯回避重名，而是回到本作人物本来的词。

内外统一：用户可见处一律「人物 Skill」；代码标识一律 persona-skill-*／personaSkillLibrary， 落盘目录 .qmai/persona-skills/。刻意不在代码里继续用 character-skill-*： 那样英文前缀会与 character-aura.ts（角色灵魂）撞车，正是本次改名要消掉的混淆。

不变的部分：分支名仍为 feature/character-skill（本分支约定文件围绕它书写，未做分支改名）， 因此分支说明文档按仓库约定仍取名 docs/character-skill-分支说明.md。

03

架构与存储

三个平面严格分离：摄取平面只负责产出，写作平面只负责读取，落盘平面只被这两者接触。

数据流

【摄取平面】用户点「提取记忆」
ingestChapter()                      ← 现有链路一行不动
  ├─ …（读文件 → 校验 → extractSnapshotWithLLM → canonicalize）
  ├─ syncSnapshotToMemory()          ← 现有
  └─ void learnPersonaSkillsFromChapter({...})   ← 新增，后台异步，不阻塞

【写作平面】生成章节
context-engine.ts
  └─ const { buildCharacterSoulContext } = await import("./character-aura")   ← 现有
  └─ const { buildPersonaSkillContext } = await import("./persona-skill-context")  ← 新增
     → joinNonEmpty([灵魂文本, 人物 Skill 文本], "\n\n")
     → 写入同一个 characterAuras 字段（不新增上下文字段、不动 token 预算编号）

落盘结构

.qmai/persona-skills/
├── index.json              只有「已有 skill 的」人物（预期几十条）
│                           元数据 + 出场计数 + 档位 + 绿标 + 状态
├── sightings.json          只记「还没建 skill 的」候选人物，纯粹数阈值
└── <id>/
    ├── SKILL.md            人物 Skill 正文（一人一份，可独立编辑）
    └── references/research/  ← 仅绿标（pinned）人物才生成

index.json 元数据字段

字段含义与来源
id稳定标识，同时用作目录名
characterName规范名（取自快照 characters[]，已 canonicalize）
aliases[]别名／昵称，来自快照 characterAliases，用于注入匹配
roleType主角／配角／反派／导师…，取自 wiki/characters 文件名解析
tiermajor / minor
pinned绿色复选框，压过所有自动分档
statusactive / dormant / archived
firstChapter / lastChapter首次／最近出场章号
appearanceCount累计出场次数（用于阈值判定与排序）
createdAtChapter该 skill 建立时的章号
lastLearnedChapter最近一次学习／完善的章号（幂等守卫）
skillRevision正文版本号，每次完善 +1
editedByUser用户手动编辑过 → 之后 AI 不再整份覆盖
关键性质

character-aura.ts 一行都不用改。因为不共用 bindings，自动学习根本不会调用 bindCharacterAura()，也就不会撞上它内部的 hasCharacterProfile() 校验—— 那 3000 个实体文件的逐份正文扫描不在本功能的路径上。 「灵魂」页照旧，零回归风险。

两个文件的职责边界（重要）

文件装什么规模与维护
index.json 已有 skill 的角色，出场计数存在这里（appearanceCount / lastChapter） 预期几十条。元数据单条增删，不重写正文。
sightings.json 只记还没建 skill 的角色，纯粹为了数「够不够阈值」；一旦建了 skill 就移出，交给 index 接管 每个角色只被数一次，不存在两处计数对不上的问题。可安全修剪 count=1 且久未出场的路人条目，不会随篇幅无限膨胀。
写在设计里的修正记录

最初草案让 sightings.json 记录全部出场角色，那会把 3000 条记账压在每次摄取上。 收窄为「只装候选」后，两个文件各自只承担一个明确的规模：index = 有 skill 的人（几十），sightings = 待观察的候选。

04

学习机制

需求的两条主机制——「初始生成」与「持续完善」——在这里落地，并共用一次 LLM 调用。

挂钩位置

挂在 chapter-ingest.ts 的 syncSnapshotToMemory() 之后（当前实现约在第 442 行），照抄既有「社区摘要」的 void rebuild…() 后台异步范式：

if (!isReingest && snapshot) {
  void learnPersonaSkillsFromChapter({
    projectPath: pp,
    chapterNumber: snapshot.chapterNumber,
    chapterBody: body,
    snapshot,                     // 用 snapshot.characters 与 snapshot.characterAliases
    llmConfig, novelConfig, signal,
  })
}
两道幂等闸门

① isReingest 必须短路——重新提取一遍不应重复生成、重复烧 LLM；
② 再叠一层 index/sightings 的 lastLearnedChapter === chapterNumber 守卫，防并发或重复触发。

每次运行的步骤

零 LLM 的确定性部分：

  1. 读 index.json + sightings.json。
  2. listDirectory(wiki/characters) 解析 角色-<定位>-<名>.md，得到角色→定位映射（只列目录，不读正文）。
  3. sightings 对本章出场角色全部记账（count++、lastChapter）；已在 index 的角色直接更新 index 内的计数。
  4. 按第 5 节阈值算出本章的 create 目标 与 refine 目标。

一次 LLM 调用：

  1. 仅当 create 或 refine 目标非空时才发起——一章最多一次，与出场人数无关。 走 resolveNovelModel(llmConfig, novelConfig, "extract")（符合项目约定：新增 LLM 调用必须走模型解析器）。
  2. 提示词输入：本章正文（截断）+ 每个 refine 目标现有的 SKILL.md（截断）+ 该角色的定位与已出场信息。 要求返回严格 JSON：按角色名分组的 skill 正文（含起始风格／说话方式／性格）。

落盘：

  1. 为每个 create 目标写一份 SKILL.md，并在 index.json 建条目（同时从 sightings 移出）。
  2. 为每个 refine 目标更新 SKILL.md（editedByUser 为真时改为增量补充／保留用户段落，不整份覆盖），skillRevision++、lastLearnedChapter 更新。
  3. index.json 单次原子写。

生命周期扫描：

  1. 按 当前章 − lastChapter 更新 status（active / dormant / archived），pinned 角色豁免，不进入休眠与归档。

研究文件策略（对应需求追问）

已采纳的产品判断

研究文件只给绿标（pinned）角色生成，且只生成一次：在该角色创建的那一次批量调用里顺带产出—— LLM 在同一次响应里同时返回 SKILL.md 与 6 份研究内容。因此每章仍然只有 1 次 LLM 调用，与出场人数无关， 也不会因为绿标而变贵。不活跃、出场很少的配角完全不生成研究文件。 如果一个角色建档之后才被点亮绿勾，则它下次出场时生成研究文件。

已经有研究文件的角色，AI 不会自动重写：章节学习的提示词只看得到 SKILL.md，看不到那 6 份研究文件， 自动重写等于用只有本章的素材覆盖掉累积内容。要刷新请用界面上的「重新整理研究文件」按钮（v1 不做自动刷新）。

失败策略

全程 best-effort：每一步的异常都 console.warn 吞掉，绝不向外抛。 人物 Skill 学习是「锦上添花」，不能因为它的失败把整章摄取搞失败——这也是 buildEstablishedContextForExtraction() 已经在用的原则。

05

档位、阈值与生命周期

所有阈值集中在一处常量模块，便于日后调整，也便于表驱动测试。

档位定位来源建 skill / 完善条件
major 主角 · 男主 · 女主 · 反派 · 导师 出场 1 次即建 skill，之后每次出场都完善
minor 配角 · 男配 · 女配 · 盟友 出场 ≥2 次建 skill，≥3 次起完善
未标注定位 文件名解析不出定位 出场 ≥3 次才按 minor 处理（自动滤掉一笔带过的路人）
绿色 pinned 用户手动标记 一票压过以上全部：立即建、永不归档、最高档注入、并生成研究文件

生命周期阈值

  • 连续 10 章未出场 → dormant（不再注入写作，但保留在库中可见、可唤醒）
  • 连续 30 章未出场 → archived（技能库默认折叠）
  • pinned 角色豁免以上两档，始终 active
  • 任何时刻不物理删除 SKILL.md；删除只能由用户在界面上显式执行（带确认）
  • 出场后自动复活：任何一次出场把 status 拉回 active，lastChapter 更新
为什么用「休眠」而不是直接归档

只看出场次数的硬阈值，会在「角色沉寂几章、剧情马上要回到他身上」时误折叠。 中间态让沉寂有缓坡：休眠只是不注入（省 token），成本几乎为零，但角色仍在用户的视野里。

06

规模分析：3000 个角色会不会卡

这是需求中重点提出的疑问。结论：卡顿的成因不是 skill 数量，而是「每次写作都全量扫」与「按人名逐个读正文」。两者已分别被分级与独立存储解掉。

两个规模必须分开算

规模分级前分级后
有 skill 的人
几十个		 character-aura.json 含全部 aura 的全部文本字段，MB 级；每次写作整份 JSON.parse； 匹配循环对每一条 binding 做「正常化 + 拼音 + 简繁」三次转换；命中角色各读 7 个文件（SKILL.md + 6 份研究） ✓ 已解：index 只几十条元数据；研究文件不再是章节角色的默认产物；命中谁才读谁的 SKILL.md
有名字的人
3000 个		 listBindableNovelCharactersLocal() 逐个 readFile 读 wiki/entities 下每个 .md 的正文来判定「是不是角色」； 其指纹缓存含修改时间，而每章摄取都会写实体页 → mtime 变化 → 指纹失效 → 重新全读 ✓ 已解：本功能不走这条路径。定位从 wiki/characters 的文件名解析（一次目录列举），匹配只在几十条 index 上做
结论

选择独立存储（D7）后，「谁是角色」的判定不再需要读实体页正文，也不再有「每章一次 3000 文件全读」。 这两个问题由架构本身免费解决，因此不额外引入索引缓存层——不造多余机制。

内存与 I/O 的确定上界

  • index.json：条目数 = 有 skill 的角色数，随剧情推进缓慢增长，量级为几十到低百位。
  • 单次写作读取：index.json 一次 + 命中角色的 SKILL.md 各一次（≤ 12 份，见下节封顶）。
  • 单次摄取写入：index.json / sightings.json 各一次原子写 + create/refine 目标的 SKILL.md。
  • LLM 调用：每章最多 1 次，与本章出场人数无关。
07

分级注入

回答「章节生成时会不会自动引用」：会，且复用既有链路，不新增上下文字段。

档位注入内容
pinned / major 7 个结构化字段（分类 · 摘要 · 怎么说话 · 怎么想 · 怎么判断 · 什么不做 · 知道局限）+ SKILL.md 压缩摘要
minor 只给两条最关键的：怎么说话 + 怎么判断
dormant / archived 不注入（保留在库中，可随时唤醒）

注入位置

沿用 context-engine.ts 现有的同一个 matchingText（任务描述 + 章纲 + 人物状态 + 认知状态），与灵魂共用一次匹配时机。新模块 persona-skill-context.ts 导出 buildPersonaSkillContext()，在同一个 await import() 区块内调用，结果拼进已有的 characterAuras 字段：

characterAuras: joinNonEmpty([soulContext.text, characterSkillContext], "\n\n")

不新增上下文字段、不动 SECTION_PRIORITY 编号与 token 预算边界。

匹配规则（v1）

归一化（NFKC + 去空白与标点 + 小写）后依次尝试：

  1. 精确相等
  2. 别名命中（来自 aliases[]）
  3. 双向子串包含——角色名出现在 matchingText 中，或反之
刻意不做的事

不引入 pinyin-pro / opencc。那会把两个重量级 vendor 拖进本模块，而 bundle-boundaries.spec.ts 专门盯着这条体积边界（它断言 character-aura.ts 只能用 opencc-js/t2cn、 且 context-engine.ts / review-adapter.ts 只能用动态 import()）。
别名已由快照 characterAliases 覆盖昵称，双向子串覆盖「小晴 / 林小晴」这类情形，代价为零。

双重封顶

  • 排序：pinned → major → minor，同级按 appearanceCount 降序，取前 12 人
  • 聚合文本上限 4000 字（超出截断）
  • 群像章节（婚宴、宗门大会）不会把上下文吃穿

技能库界面

技能库从 3 个 tab 扩到 4 个；人物 Skill 的列表、绿标与编辑都在这里。

新增第 4 个 tab

去AI味技能  |  写作 Skill  |  人物 Skill  |  收藏

skillLibraryTabs 增加一项 → activeView = "personaSkillLibrary"。 需要同步扩的地方：src/stores/wiki-store.ts 的 activeView 联合类型、 src/components/layout/icon-sidebar.tsx 的高亮条件、src/components/layout/content-area.tsx 的 case 分支。

不需要做的事

复用 data-ui-page="skills" 外壳，因此不需要往 ui-test-tools.spec.tsx 的页面注册表（it.each 那张「每页一条」的表）里加条目。

列表

  • 卡片内容：角色名 · 定位 · 档位 · 出场 N 次 · 最后第 M 章
  • 绿色复选框——点击即落盘 pinned，是本功能唯一的手动干预入口
  • 筛选：按档位 / 按状态 / 关键字搜索
  • 归档角色默认折叠，可展开查看；提供「唤醒」操作

编辑器

  • 直接编辑 SKILL.md 正文并保存
  • 保存后置 editedByUser = true——之后 AI 自动完善改为增量补充／保留用户段落，不再整份覆盖。 否则用户的手工修改会在下一次「提取记忆」时静默丢失，这是必须守住的一条。
  • 操作：唤醒 / 归档 / 删除（带确认）；pinned 角色可「重新生成研究文件」

硬约束与风险

以下均为已核对源码的既有约定，实现时必须遵守；违反其中任何一条都会直接让测试变红或让产品行为回退。

约束 1 · 保存正式章节不自动摄取

preview-panel.tsx 明确写着「保存正式章节时已按用户要求不再自动提取记忆」。 自动学习不能挂在「保存章节」上，只能挂在 ingestChapter()（用户点「提取记忆」）。✓ 设计已符合

约束 2 · 不能改 ingestChapter 的签名

chapter-ingest.spec.ts 用源码字符串断言 export async function ingestChapter。 改动其签名会触发该测试失败。✓ 设计只在函数体内加一行 void

约束 3 · 体积边界

bundle-boundaries.spec.ts 强制 context-engine.ts / review-adapter.ts 对 character-aura 只能用动态 await import()，且 character-aura.ts 不能改成 from "opencc-js"。 ✓ 新模块同样走动态 import()，且不碰这两个文件

约束 4 · 新增 LLM 调用必须走模型解析器

项目约定：resolveNovelModel() / resolveReviewModel()。✓ 学习调用走 resolveNovelModel(…, "extract")

约束 5 · 草稿隔离

未确认内容不得触发摄取、不得污染记忆库。本功能只挂在 ingestChapter() 内， 而该函数本身已带 isFinalChapter(fm) 与 allowDraft 校验。✓ 天然继承

残余风险

  • 同名角色：两个不同人物共用同一名字时，会共用一条 skill。v1 接受该限制（既有角色匹配同样如此）， 用户可在技能库中手动改名或删除其一。
  • LLM 返回不规范 JSON：解析失败即本次学习整体跳过并 warn，lastLearnedChapter 不推进， 下次摄取可重试。
  • 自动分档误判：这是 D6 绿色复选框存在的理由。用户一旦标记 pinned，后续不再受自动规则影响。
  • 学习落后于正文：后台异步意味着紧接下一章生成时，skill 可能还没落盘。可接受—— 人物 Skill 是渐进累积的资产，不是硬约束。

需求对照表

逐条回应原始需求，确保没有遗漏或过量实现。

需求原文落地方式
技能库中增加「角色 skill」（现定名「人物 Skill」，见 D8）技能库第 4 个 tab（第 8 节）
初始生成：分析角色风格、说话方式、性格，自动加入技能库摄取时按阈值 create，一次 LLM 批量生成 SKILL.md（第 4 节）
持续完善：第二次出现时再次完善每次摄取对 refine 目标完善，与 create 合并进同一次调用（第 4 节）
人为编辑编辑器可直接改 SKILL.md，并置 editedByUser 保护（第 8 节）
第一章 5 个角色就生成 5 个 skill已被 D1 修正为按重要度分级——这是规模失控的源头
3000 个人物会不会生成 3000 个 skill、会不会卡第 6 节完整分析；分级把「有 skill 的人」压到几十，独立存储避开 3000 文件全读
这些 skill 是不是也要做分类三个维度：档位（major/minor）、定位（沿用 CHARACTER_ROLE_TYPES）、状态（active/dormant/archived）
出场配角的 skill 什么时候删除不删除；三态归档，pinned 豁免（第 5 节）
章节生成时是否会自动引用这些 skill会。复用既有 characterAuras 注入链路，按档位分级（第 7 节）
这个「角色 skill」会不断学习、不断提升（现为「人物 Skill」）每次摄取出场即刷新，skillRevision 累积（第 4 节）
