# work/scratch-20261010 分支说明：事件细纲（轻量章细纲）

> 目标：在大纲对话里新增一条**轻量章细纲**产线——一章一批，产出 4~8 个连续事件，
> 每个事件带可直接落笔的细节抓手，再一键扩成 3000 字正文。
> 起因：现有「章节细纲」是 17 节重型章纲（整故事 10–12 章分批、必须对齐卷纲骨架、
> 六项交叉校验），重量压在**开书期**是合理的，但**连载期每天写一章**时太重：
> 用户往往只想「这一章发生哪几件事」，写完就往下推。

## 1. 问题定位

| 现象 | 根因 |
|---|---|
| 写到第二章时不敢点「章节细纲」 | 它会要求先明确「当前要拆哪一个故事（10–12 章）」，并强制 `story` 骨架与卷纲逐字一致 |
| 生成一次要等十几分钟 | 强制**分 3 章一批**跑完整流程（`CHAPTER_BATCH_SIZE = 3`）+ 末批一次定向重写 |
| 产出颗粒度对不上日常写作 | 17 节里大量字段（§7 四段式、§8 情绪四节点、§17 十条自检）是「规划」口径，不是「提纲」口径 |
| 用户实际在用的方法没入口 | 用户手工做法是「列 4~6 个事件，每个事件 200–300 字 + 台词神情环境细节，扩成一章 3000 字」——软件里没有对应按钮 |
| 写起来更顺的那种大纲反而不被支持 | 用户反馈：写成事件流之后「剧情写着写着更顺」，但这种事只能发生在聊天框里，沉淀不成项目资产 |

关键结论：**不是要把重型章纲改轻，而是它服务的是另一个阶段**。开书期要的是
「结构正确、能对齐卷纲骨架」的规划书；连载期要的是「今天这一章写哪几件事」的现场提纲。
两者应该并存。

## 2. 方案要点

### 2.1 单章 · 4~8 个连续事件

一章一批，不做跨章分批，不做跨章节拍对齐。产出契约：

```ts
interface EventOutlineEvent {
  id: number            // 1..N，连续
  title: string         // 20 字左右一句话事件
  points: string[]      // 2~5 条细节抓手：关键台词 / 神情动作 / 环境物件 / 推进或钩子
}

interface EventOutlineData {
  version: 1
  chapterNumber: number
  title: string         // 第N章 · 一句话章名
  targetWords: number
  events: EventOutlineEvent[]   // 4~8 条
  endingHook: string            // 全章结尾钩子
}
```

`points` 就是用户说的「对话中的神情描绘、环境添加等小细节」——事件标题给骨架，
抓手给血肉，两者合起来才够直接扩写。校验口径：

- 事件数 4~8（边界含），`id` 从 1 连续递增；
- `title` ≤ 24 字（超出提示压缩，不算错）；
- 每条事件 `points` 2~5 条；
- `endingHook` 非空；
- 事件工作量合计落在 `targetWords ±25%`。

校验**返回问题清单而不是阻断保存**，与 `validateChapterOutlineData` 同风格：
卡片上标红 + 给修复建议，用户仍可选择「保存当前内容」。

### 2.2 与重型「章节细纲」并存，不替代

| | 章节细纲（既有） | 事件细纲（新增） |
|---|---|---|
| 范围 | 一个故事 10–12 章，3 章一批 | 一章 |
| 类型 | `chapter-outline` → 文件夹「章纲」 | `event-outline` → 文件夹「事件细纲」 |
| 结构 | 17 节 + `story` 骨架对齐 + 交叉校验 | 4~8 事件 + 首尾钩子 |
| 渲染 | `chapter-outline-template.ts` 卡片流 | 事件卡片（新组件） |
| 校验 | `validateChapterOutlineData`（13 组） | `validateEventOutlineData`（5 条） |
| 阶段 | 开书期规划 | 连载期每日提纲 |

两者**不共用** `chapterOutlineData` 解析、分批续跑、草稿续跑与模板渲染链路，
只在保存确认弹窗、`outlineSaveRequest` 协议、`kind` 索引这几处复用既有设施。

### 2.3 不碰上下文引擎

这是本分支最重要的约束。`resolveChapterOutline()`
（`src/lib/novel/outline-context-index.ts:620`）用 `index.documents.find(kind === "chapter")`
**取首个匹配**——如果事件细纲落进「章纲」文件夹，同一章会同时命中重型章纲与事件细纲，
谁生效取决于文档顺序。因此：

- 事件细纲落进**独立文件夹「事件细纲」**，且**不注册**为 `STANDARD_FOLDER_KINDS`
  里的 `chapter` kind，`resolveChapterOutline` 的候选池与行为保持不变；
- 事件流注入正文走**「用户指定」这一档**（`FIELD_PRIORITY` 最前，见
  `context-engine.ts:35-65`），即作为本轮任务的硬要求随消息发出，
  **不新增 context 数据源、不改 `SECTION` 顺序、不动 token 预算结构**。

代价：通用「继续生成下一章」按钮读不到事件细纲，只有卡片上的「按这份细纲写这一章」
能注入。这是**刻意的取舍**——用一条显式入口换掉上下文引擎的回归风险。

### 2.4 交互流程

1. **空会话中央并排两个按钮**：「生成小说大纲」（原样）｜「生成章节细纲」（新）。
   按用户选择，入口只做在空会话中央，不动「生成大纲模块」菜单里的「章节细纲」。
   按钮文案用「生成章节细纲」（用户原话），模块 / 文件 / 类型名用「事件细纲」以区分。
2. 点新按钮 → 轻量向导 `EventOutlineWizardDialog`：
   - 目标章节：默认自动探测「下一章」＝ 章节库里最大章号 + 1，空库为第 1 章。
     章节号来自 `useWikiStore.fileTree` + `flattenMdFiles()` /
     `extractChapterNumber()`（`src/lib/novel/chapter-utils.ts:4,12`）——现有代码只有
     这两个零件，本分支补一个纯函数 `resolveNextChapterNumber()`（含单测），
     不新增数据源；
   - 事件数量：4 / 5 / 6 / 7 / 8，默认 6；
   - 本章目标字数：默认取项目单章目标字数设置（`resolveChapterLengthSpec`）；
   - 本章想法 / 硬要求（可选）：例如「这一章要让楚白第一次动用令牌」；
   - @ 引用沿用当前会话已有引用。
3. 提交后**直接进生成腿，不走 `intent_clarity` 意图分析**。理由：范围（章号、事件数、
   字数）已在向导里定死，再跑一轮意图清晰度只是烧 token；也避开「写到第二章还要
   重新回答『要拆哪一个故事』」的摩擦。这一步与 `handleGenerateSection` 的
   fast 分支同构（`outline-chat-panel.tsx:4467`）。
4. 结果渲染成**事件卡片**（只读）：编号 + 20 字标题 + 抓手要点 + 章尾钩子 + 字数小计；
   末尾附 `outlineSaveRequest`。不满意直接在对话里说「第 3 个事件改成…」重出；
   满意走既有保存确认弹窗落盘。
5. 卡片上「**按这份细纲写这一章**」→ 切到写作现场并注入事件流（见 2.5）。

### 2.5 扩成正文

复用**既有的输入框草稿**，不新增 store 字段、不改写作面板：

1. 卡片按钮：`chatStore.setConversationInputDraft(会话ID, prompt)` +
   `wikiStore.setActiveView("wiki")` + 一条 toast 说明；
2. 写作现场的输入框由 `activeConversation?.inputDraft` 派生
   （`chat-panel.tsx:980`），切过去即可看到填好的提示词，用户确认后发送；
3. 正文照旧是草稿：草稿隔离 → 用户确认正式保存 → `ingestChapter()`。
   本功能**完全不碰**摄取链、快照、向量索引与图谱。

**刻意不自动发送**：点击按钮只填输入框，避免一次误点就花掉一次正文生成；
同时让用户有机会先改两句再发。`chat-store` 里既有的 `inputDraft` 字段足够，
不需要仿 `pendingReferenceTokens` 再加一个投递队列。

### 2.6 保存链路

事件细纲沿用既有「所有大纲必须人工确认、禁止静默落盘」的硬规则
（`outline-save-request.ts:696-705`，`autoSaveable: []`）。需要动的是：

- `OutlineSaveRequestFileType` 枚举 + `ALLOWED_FILE_TYPES` 白名单
  （`outline-save-request.ts:26-34,74-83`）+ 中文别名「事件细纲」；
- `outline-save-classifier.ts` 的 `FILE_TYPE_FOLDERS` 加 `event-outline → 事件细纲`；
- HTML 预览走既有兜底（`renderOutlineFallbackHtml` → `renderCardFlowForSpec`，
  `outline-save-request.ts:228-245`），因此**无需**新写 template.html 也有卡片流可看。

## 5. 已知取舍

- **通用「继续生成下一章」读不到事件细纲**（见 2.3）。若后续要打通，正确做法是给
  「事件细纲」注册独立 kind 并在 `resolveChapterOutline` 里显式定义优先级，
  而不是塞进「章纲」文件夹抢首个匹配。
- **卡片只读**：改事件靠对话，不做卡片内受控编辑。先把「生成 → 认可 → 扩写」这条
  主链路跑通。
- **扩写不自动发送**：「用这份细纲写这一章」只把提示词填进写作输入框（见 2.5），
  由用户确认后发送。
- **本次不加更新日志**：等本地打包验证满意后再补 `src/lib/changelog.ts` 条目。
