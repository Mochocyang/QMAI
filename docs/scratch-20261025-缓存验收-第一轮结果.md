## 2. 必须先说清的对比口径

改造前的 5.7% 是 `deepseek-v4.1-flash`（happycoding 网关），
这次的 79.7% 是 `deepseek-ai/DeepSeek-V4.1-Flash`（硅基流动）。

**这不是同一模型的严格前后对比**——换了网关。所以 79.7% 不能直接说成"从 5.7% 提升到 79.7%"。

它能证明的是：**同样的软件、同样的用法，在硅基流动上做到了 79.7%**。
而改造前在另一个网关上只有 5.7%，说明问题不在网关，在于我们每轮改前缀（这一点已由
`docs/scratch-20261025-缓存命中率-真机基线.md` 的三条根因证据独立支撑）。

要拿到严格对比，需要用**同一个网关**各跑一次。当前数据还做不到。

## 3. 新发现：小请求完全不吃缓存（门槛效应）

今天 31 条里有 8 条 ≤20k token 的请求，**命中全部为 0**：

| input token | 命中 |
|---|---|
| 266 | 0 |
| 275 | 0 |
| 1008 | 0 |
| 5201 | 0 |
| 5215 | 0 |
| 5219 | 0 |
| 5222 | 0 |
| 5219（另一次） | 0 |

而所有 >69k token 的请求都命中了。门槛落在 5.3k ~ 69k 之间，本次数据无法精确定位。

**但这件事不值得为它改结构**：这 8 条合计只有 22,673 token，
占今天总 input 的 **0.8%**。为省 0.8% 去合并碎调用，风险收益不成比例。

它的真实影响是**把"零命中占比"从 8.7%（2/23）拉高到 32%（10/31）**——
这是个统计口径问题，不是成本问题。看板如果报"零命中 32%"会吓人，
实际该看的是分层后的数字。

## 4. 剩余 20% 未命中来自哪里

23 条大请求里只有 2 条零命中，都是合理的冷启动：

- `11:23:17` 本轮第一条，全新前缀
- `11:24:07` 前缀估算从 126,282 突增到 151,568（上下文增长 25k），重新冷启动

其余 21 条命中 69.3%~99.5%。没到 100% 的原因是各轮新增内容
（本轮用户输入、回复追加）本身不在缓存内，这属于正常现象。

另一个值得注意的现象：`prefixEstimatedTokens` 在 **126,282 / 151,568 / 129,881 / 149,800 / 129,600 / 151,261 …** 之间交替，
说明前缀仍在两种规模间切换。这是下一轮可以继续挤的地方，但对账单影响已经很小。
