# 缓存命中率优化·P2：上下文输出顺序（跨章前缀 0.2% → 73.4%）

> 2026-10-25
> 前序：P0（主对话资料前移）、P1（审稿复用写作前缀）
> 本轮是**目前收益最大的一项**：跨章公共前缀 0.2% → 78.1%（本地字节） / 73.4%（真机）

---

## 一、发现

用第 19 章 / 第 20 章两份只差章节字段的上下文包做对比，实测**公共前缀只有 0.2%**，
断点在第 20 个字符：

```
# 小说上下文包
## 当前任务
写第19章          ← 第 20 个字符就断了
```

也就是说：**每写一章，整包上下文（大纲 + 设定 + 状态……）全部按全价重发**。
按 40k token 的上下文包算，每章白烧约 40k 输入 token。

### 根因：把"裁剪优先级"当成了"输出顺序"

`context-engine.ts` 里 `FIELD_PRIORITY` 的本意是"预算不够时先留谁"，
但代码直接用这个优先级 `sort` 后输出。于是最该先写的稳定字段（作品灵魂/世界规则/
核心设定/写作风格）排到了**任务、本节速记、章纲、人物状态之后**。

顺带发现一个质量问题：在 12000 token 预算下，**硬性世界规则（优先级 17）和写作风格（19）
会被整段裁掉**，而"本节速记"（优先级 0）永远保留。这属于既有优先级设计，本轮不动。

---

## 二、改动

**只改一个文件**：`src/lib/novel/context-engine.ts`

1. 新增 `FIELD_EMIT_ORDER`（输出顺序）与 `emitRank()`，把"输出顺序"从"裁剪优先级"里拆出来。
   顺序：作品级稳定（灵魂/框架/正典/世界规则/文风） → 大纲 → 任务 → 章纲 → 状态/伏笔/检索。
2. `## 当前任务`不再硬编码在头部：`pack.task` 作为普通字段参与排序（优先级仍是 1，仍优先保留），
   但**输出位置移到稳定字段之后**。
3. 两个输出分支（"装得下"与"裁剪后"）都改为按 `emitRank` 排序输出。

**关键点：裁剪结果的集合完全没变**——选择仍由 `FIELD_PRIORITY` 决定，只改了书写顺序，
所以"预算不够时留谁"的行为与旧版一致。

## 四、本轮同时纠正的两个判断（都是我之前的错）

| 之前的说法 | 实测结论 | 处理 |
|---|---|---|
| 「章节三阶段改单会话追加，每章未命中 6772 → 3900（−42%）」 | 那个 42% 是小样本造成的误判。真实项目里稳定前缀 P 占请求的 93%，兄弟请求本来就能吃到 90%+，单会话化只省各阶段增量（几千 token），**不是大杠杆** | 降级，不再优先做 |
| 「stableCore 固定配额可让稳定块从 43.9% → ~100%」 | **对前缀缓存零收益**。断点发生在被改动的那一段内部，后面各段即使字节相同也够不着（前缀必须从 0 连续） | 已写好后按实测撤回（`composer.ts` 恢复原样，git diff 为空） |

这两条合起来说明一件事：**缓存只认"从第 0 个字节起的连续相同"，所以唯一有效的动作是调整顺序，不是调整截断算法。**

## 六、剩余空间与下一步

1. **跨章还能再涨**：现在跨章命中 73.4%，剩下没命中的部分是"大纲"（`mergedOutline` = 作品大纲 + 卷 + 章纲，随章变）。
   如果把 `projectOutline`（作品级）单独前置、章纲下沉，跨章理论上能到 90%+。
   改动点：`buildStableContextPrefix` 增加"作品级"参数，`deep-chapter-generation` 分两次渲染上下文包。
2. **硬性世界规则/写作风格被裁**：优先级 17/19 → 预算紧时整段消失。这是设定漂移风险，建议单独评估是否提权（会改变"留谁"的行为，需产品确认）。
3. **stableCore（主对话稳定块）的片段顺序**：`stableFragments` 里"核心设定"排在"大纲"前面、"写作风格"倒数第二，同样应该按"稳定→易变"重排。
4. **资料章内冻结**（P0 遗留）。
5. **2k token 以下的碎调用**合并。
