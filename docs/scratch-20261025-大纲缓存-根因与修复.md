## 1. 我前两轮都判断错了，这次找到了确切的机制

**第一轮**：说"前缀每轮都在变" → 太笼统。
**第二轮**：说"7 条是 7 个不同任务，结构性问题，建议不动" → 结论对了一半，但**放弃了本该修的东西**。

真正的机制在截断算法里。旧代码：

```ts
const pending = new Set(blocks.map((_, index) => index))
let remaining = charCap - Math.max(0, blocks.length - 1) * 2
while (pending.size > 0 && remaining > 0) {
  const share = Math.floor(remaining / pending.size)   // ← 问题在这里
  for (const index of Array.from(pending)) {
    if (blocks[index].length <= share) { kept[index] = blocks[index]; ... }
  }
  if (!consumedSmallBlock) {
    for (const index of pending) kept[index] = excerptHeadTail(blocks[index], share)
  }
}
```

`share = 剩余预算 / 待分配块数`。**只要块的数量变一个，所有大块的分片位置就整体平移。**

而大纲链路恰恰在**不停生成新的设定文档**——每生成一篇，`settings` 就多一块。

### 数据证据（严丝合缝）

| 时间 | 你做了什么 | cached | input | 命中 |
|---|---|---:|---:|---:|
| 12:12 | 生成所有核心角色人物小传 | 0 | 195,797 | 0.0% |
| 12:13 | 杨小晚 人物小传 | 0 | 196,128 | 0.0% |

12:12 生成完之后，wiki 里多了几份人物文档 → 12:13 的 `blocks.length` 变大 →
`share` 变小 → **所有大文档的截取片段一起缩短** → 整段大纲字节全变 → 命中归零。

再看四条有命中的请求，`cached` 分别是 **86784 / 87808 / 87168 / 87168**——几乎恒定为 8.7 万。
而 `input` 在 15~24 万之间。**差额那 6~15 万，就是被平移的大纲段。**
稳定的 8.7 万 = 灵魂 + 框架 + 正典 + 规则 + 文风，它们排在大纲之前，所以还能命中。

## 2. 修复：让每篇文档的截取量只由它自己决定

```ts
// 按顺序整篇装入，装不下就停
const kept: string[] = []
let used = 0
for (const block of blocks) {
  const cost = block.length + (kept.length > 0 ? 2 : 0)
  if (used + cost > charCap) break
  kept.push(block)
  used += cost
}
// 剩余预算只给「第一个装不下的块」
const remaining = charCap - used
const next = blocks[kept.length]
if (next && remaining > 200) kept.push(excerptHeadTail(next, remaining - 2))
```

三个性质：

1. **已保留的块内容完全由它自己决定**，不受兄弟数量影响；
2. **新增文档只会追加在末尾**，不会回头改写前面块的字节；
3. 剩余预算只喂给"下一个块"，所以预算微调也不会波及已装好的部分。

---

## 3. 代价（必须知道）

旧的"均分"能让**每一篇都不完整地进来**；新的"整篇装"会让**末尾的文档整篇进不来**。

也就是说：预算紧张时，模型看到的是「前面几篇完整 + 一篇部分 + 后面没有」，
而不是「所有篇都残缺」。

这是 **稳定性优先于信息量** 的取舍。判断依据：被丢的是按路径排序靠后的文档，
通常是次要设定；而省下的是整段大纲的重复输入费用（约 90%）。

**如果试读后发现"某份重要设定模型看不到了"，把它的路径往前挪即可**（排序决定保留顺序）。
