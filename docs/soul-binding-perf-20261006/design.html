编号问题你的描述
P1 自定义灵魂显示异常 + 极慢 角色从「拆书库」加入「自定义灵魂」后，页面先显示「还没有自定义灵魂」；等约 3 分钟这些信息才出现。
P2a 绑定对话框每次都「正在读取小说人物」 第一次打开要读，第二次打开还要读；第一次已经读过大量角色，应该已经存下来了。

2. 根因定位

P1 与 P2a 是同一个根因，不是两个 bug。定位过程只读代码与磁盘文件，未做任何猜测性改动。

2.1 灵魂列表被「扫人物」拖住

src/components/novel/character-aura-view.tsx:196 的 refresh()：

const [loaded, loadedCharacters, loadedBindings] = await Promise.all([
  listCharacterAuras(project.path),          // 快：只读一个 json
  listBindableNovelCharacters(project.path), // 慢：逐文件扫描（可能调 LLM）
  getCharacterAuraBindings(project.path),    // 快：同一个 json
])
setAuras(loaded)   // ← 被最慢的那个 Promise 卡住

灵魂列表的渲染被「读取小说人物」阻塞了。setAuras 必须等 Promise.all 全部结束才执行，所以只要人物扫描没完，右侧就一直是 character-aura-view.tsx:498 的空状态文案——正是你看到的那句「还没有自定义灵魂。点击左侧上方“新建角色灵魂”后，就可以生成并保存到当前小说项目。」

这也解释了截图里的矛盾现象：灵魂库画廊页是快的（它只调 listCharacterAuras），点进详情的 CharacterAuraView 是慢的（它多调了人物扫描）。

2.2 「扫人物」为什么能花掉几分钟

src/lib/novel/character-aura.ts:759 的 listBindableNovelCharacters：

  1. 没有任何缓存。每次调用都从头扫盘 → 这就是 P2a「第二次打开还是正在读取」。
  2. wiki/entities 下串行逐个 await readFile（实测某项目 260 个实体页）。
  3. wiki/outlines 下每个通过 isCharacterOutlineFile 的文件，都会走 extractCharacterNamesFromOutlineEnhanced → extractCharacterNamesWithLLM（character-aura.ts:2150）。这是串行的，且每次带 AbortSignal.timeout(30000)。

3 分钟就是对上了：6 个大纲文件各等一次 30 秒超时 ≈ 180 秒。LLM 不可用或超时后才会回退到本地的标题解析。也就是说，为了拿到一份人物名单，程序可能连续发起多次注定要等满 30 秒的请求，而且每次都重来。

对照数据：readFile 只是 src/commands/fs.ts:34 的一次 invoke（毫秒级），所以 260 次实体读盘本身只有一两秒——几分钟全部来自 LLM 超时，不是读盘。

2.3 结论

症状根因
P1 先显示空、约 3 分钟后才出现灵魂列表 setAuras 被人物扫描阻塞；扫描因逐文件 LLM 超时而耗时数分钟
P2a 每次打开都要重新读取listBindableNovelCharacters 无缓存，且每次重跑 LLM 路径
P2b / P2c纯 UI 缺失，与上面无关

3. 修复设计

3.1 解耦：灵魂列表永不等人物扫描 修 P1

把一次性的 Promise.all 拆成三条互不阻塞的加载线：

数据用途加载策略
listCharacterAuras灵魂列表本体立即 setAuras，不受其他任何请求影响
getCharacterAuraBindings「已绑定 N 人」角标立即 setBindings
listBindableNovelCharacters仅绑定下拉框 / 绑定对话框独立加载，只在该 UI 内部显示局部 loading

验收要点：灵魂列表的渲染路径里不得出现任何人物扫描的 await。这条会写成测试钉死——把人物扫描换成永不 resolve 的 Promise，灵魂列表仍必须正常渲染。

3.2 缓存 + 秒显：人物名单不再反复扫 修 P2a

分两层

  1. 本地解析先行（毫秒级）：实体页标题 + 大纲标题解析是纯本地的，先立刻出一版名单并渲染，用户不再看到空白等待。
  2. LLM 识别按策略处理：见第 4 节的选项。

持久化缓存

  • 落盘到 <项目>/.qmai/bindable-characters.json，与灵魂库同目录（该目录已存在且已有 character-aura.json）。
  • 带指纹：wiki/entities 与 wiki/outlines 下的文件清单 + 大小 + mtime 的哈希。指纹未变时直接复用，既不扫盘也不调 LLM。
  • 内存层缓存：同一会话内切换页面不重复读盘。
  • 失效时机：指纹变化、项目数据版本 bump（refreshProjectState）、用户点「重新扫描」。
  • 缓存文件只存名字数组与指纹，损坏或格式不符时静默重建，不阻塞 UI。

你期望的「第一次读过就该存下来」由此满足：第二次打开是一次 json 读盘。

3.3 绑定对话框加搜索框 修 P2b

  • 对话框顶部加输入框，自动聚焦，按子串过滤（不区分大小写、忽略首尾空格）。
  • 命中数量实时显示：「已选 N 个 · 匹配 M / 共 K」。
  • 已勾选的项目在过滤后仍然保留——搜索不能悄悄丢掉已经选好的人。
  • 无命中时给出「没有匹配「xxx」」而不是空白。
  • Esc 清空搜索 vs 关闭对话框：Esc 先清空搜索（有内容时），空时再关闭。

3.4 人物列表横向排列 修 P2c

  • 改为 CSS Grid：每行 5 个（repeat(5, minmax(0, 1fr))）。
  • 窄窗口逐级降级（5 → 3 → 2 列），名字过长时省略号 + title 悬浮显示全名。
  • 点击整格都能勾选（不只点复选框）。

4. 需要你决策的点

4.1 LLM 识别人物，怎么处理？

方案效果代价
A 只做本地解析，彻底不调 LLM 名单永远瞬时（毫秒级），行为完全可预期 复杂大纲里「人名写在正文而不是标题」的条目会漏，需要用户自己在大纲里补人物小传
B
推荐		 本地解析秒显 + LLM 在后台精修，结果并入缓存 任何时刻打开都是瞬时的；LLM 回来后名单自动补全，且只算一次 实现最复杂；需要一个「正在精修…」的弱提示
C 默认只用本地解析；LLM 仅在用户点「AI 精确识别」时调用 最省算力，用户完全掌控何时花时间 想用 AI 时要手动点一次

被缓存覆盖的前提下，三者的日常体验都是瞬时的。差别只在「第一次遇到新项目」和「复杂大纲的召回率」。

4.2 明显不是人名的条目要不要过滤？

你发来的截图里有「编号派通用手段」「编号体执行群」「成长或崩坏路径」「冲突点」「当前状态」「城中百姓」这类条目——它们来自实体页/大纲小标题，不是人名。

方案说明
A
推荐		本轮不过滤，靠搜索框解决人名启发式很容易误杀真名（如「城中百姓」确实是某些作品里的角色称呼）。搜索框已经能解决「找不到」。风险最低。
B加一份可编辑的忽略词表 + 明显的非人名后缀规则更干净，但需要长期维护，且一定会有误杀。可以后续单独做。

5. 验收标准

  1. 从拆书库「加入自定义灵魂库」后切到角色灵魂页，灵魂立即出现，不再出现先空后有的停顿。
  2. 把人物扫描替换成永不 resolve 的 Promise 时，灵魂列表依旧正常渲染（阻断回归）。
  3. 第二次打开绑定对话框（同一会话）不再显示「正在读取小说人物」，直接出名单。
  4. 应用重启后再次打开（项目未变）同样秒开——缓存已落盘并命中指纹。
  5. 项目 wiki 变化后缓存自动失效并重新扫描。
  6. 搜索框能按子串实时过滤；已勾选项在过滤后不丢失。
  7. 人物列表每行 5 个；窄窗口降级不溢出、不重叠。
  8. 原有绑定行为不变：绑定仍会自动把灵魂加入自定义灵魂库，幂等不重复建。

6. 测试计划

  • TDD：每条验收标准先写失败测试再实现，逐条留下「红→绿」证据。
  • 变异测试：对缓存命中判定、解耦、搜索过滤、已选保留各做一次变异，确认测试真的抓得住。
  • 缓存指纹：覆盖「未变命中」「新增文件失效」「改动文件失效」三种情况。
  • 真实浏览器几何验证：用 Playwright 量绑定对话框，确认每行 5 个、窄屏降级无溢出、搜索过滤后行数正确。
  • 全量回归对比：与基线跑同一份测试，要求失败数不增加（已知基线存在与本次无关的既有失败）。

7. 不做的事

  • 不动内置灵魂（BUILT_IN_CHARACTER_AURAS）与灵魂生成工作流。
  • 不改绑定语义（仍用 bindCharacterAura、仍按人物名绑定、仍自动入库）。
  • 不重构灵魂库画廊页（它本来就快）。
  • 不顺手做 4.2 的忽略词表（若你选 A）。
