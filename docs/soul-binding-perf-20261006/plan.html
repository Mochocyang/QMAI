Task 1 · 人物名单缓存与指纹 纯 lib

新增 src/lib/novel/bindable-characters-cache.ts

  • computeBindableFingerprint(projectPath)：对 wiki/entities 与 wiki/outlines 下的文件（路径 + 字节数 + mtime）排序后做哈希。
  • readBindableCharactersCache(projectPath)：读 <项目>/.qmai/bindable-characters.json；文件缺失、JSON 损坏、字段类型不符一律返回 null（不抛异常）。
  • writeBindableCharactersCache(projectPath, entry)：writeFileAtomic 落盘。
  • loadBindableCharactersWithCache(projectPath, compute)：指纹命中 → 直接返回缓存；未命中 → 调 compute 并写入。

Task 2 · 本地解析与 LLM 后台精修分层 修 P2a 核心

改 src/lib/novel/character-aura.ts

  • 新增 listBindableNovelCharactersLocal(projectPath)：只做实体页 + 大纲标题的本地解析，同步毫秒级、绝无网络。
  • 保留 listBindableNovelCharacters(projectPath) 签名不变，内部改为：先返回本地结果；LLM 精修作为独立导出 refineBindableCharactersWithLlm(projectPath)，由调用方在后台触发。
  • LLM 精修完成后把合并结果写回缓存（Task 1），并标记 llmRefinedFingerprint，同一指纹下不再重复精修。
  • LLM 超时下调（30s → 可配置且更短），且并发而非串行；超时或失败静默保留本地结果。

绝不能出现的形态：任何「等 LLM 回来才返回」的路径。首次调用必须在毫秒级返回本地名单。

测试（先红）：本地路径在 mock 掉 streamChat 为「永不 resolve」时仍立即返回；第二次调用命中缓存不重复精修；精修结果并入本地结果并去重；LLM 抛错不影响本地名单。

根因确认（实测，不是推测）

关键的一条回归测试把 listBindableNovelCharacters 打成永不 resolve 的 Promise，修复前的失败信息正是用户看到的那句空状态文案：

AssertionError: expected '还没有自定义灵魂。点击左侧上方"新建角色灵魂"后，就可以生成并保存到当前小…'
                to contain '拆书库导入的自定义灵魂'

根因是 CharacterAuraView.refresh() 把快的 listCharacterAuras 与慢的 listBindableNovelCharacters 放进了同一个 Promise.all，于是 setAuras 必须等最慢的那个； 而那个慢的每次都要对每个大纲文件串行发一次 30 秒超时的 LLM 请求（6 个文件 ≈ 180 秒，正好是用户说的 3 分钟）。 readFile 只是一次 invoke（毫秒级）—— 那 3 分钟全是等模型超时，不是读盘。

为什么「先红后绿」在这里特别关键

本次有两处修复是在写完修复之后才补测试的（残缺缓存、超时判定）。 那两条都补做了变异验证：把守卫删掉，对应用例必须失败，并各附一条正向对照 （防止「一律不缓存 / 一律不标记」这种蒙过去的假修复）。没有变异验证的自测等于没测。

几何检查脚本自身踩的两个坑（已堵上，记下来免得再犯）

坑 1：只注入单个 CSS 包会把布局量错。第一版只注入含 grid-cols-5 的那个包，结果 .flex 没被注入，label 退化成 display:block，于是一个并不存在的「超长名字撑破单元格」被报了出来。改成注入 dist/assets 下全部 CSS 包后，实测 truncate 正常工作（scrollWidth 322 > clientWidth）。教训：几何检查必须注入完整样式，否则量到的是假象。

坑 2：class 不能全文取第一个匹配。第一版用 /<label className="([^"]+)">/ 取 label class，抓到了别处的 wb-pending-filter，量出来的结构完全不是绑定列表。改成把范围锚定在 bindable-name-grid 区块内。

坑 3（非空洞证明自身的假证明）：最初把 md:grid-cols-5 改成 md:grid-cols-1 来证明列数断言有效，但 Tailwind 按需生成，产物里根本没有 md:grid-cols-1，于是退回到 sm:grid-cols-3 的 3 列，量到「首行 3 个」——变异没真正生效，属于假证明。改成删掉 md:grid-cols-5 这一条规则，断言列数确实不再是 5。

对抗性终审发现的 CRITICAL 及其修复

F1（CRITICAL，已修 a3c1185）：精修失败被永久误标成「已精修」。 requestCharacterNamesWithLLM 原本写的是 onError: () => {}、onDone: () => {}， 两个回调都不看，直接返回累积到的 result。但 streamChat 的真实失败形态是回调 onError （llm-client.ts 里 onError 有二十多处调用，只有少数分支才 throw）；超时更隐蔽 —— signal 一 aborted，isUserAbortError 就返回 true（user-abort.ts:10）， 于是走 onDone() 分支，看起来跟成功一模一样。

后果：任何真实失败都会「正常返回」→ 写下 llmRefinedFingerprint → 缓存短路永久生效。 LLM 才能发现的人物永远不出现，且没有任何报错、重试或日志。 这正好把「慢但终会正确」换成了「快而永远错」。

换句话说：拦截重复精修的哨兵必须可信，否则「第二次打开要快」这件事本身就是假的。 修复：改成显式记录 onDone / onError / 自建计时器超时三个信号，返回 { ok, names }； 只有每一批都 ok 才写标记。超时改为自己起 AbortController + setTimeout， 「是不是被超时掐掉的」由自己说了算，不再依赖 signal.aborted 去猜。

为什么 207 条测试全绿却没抓到：唯一那条失败用例用的是 mockRejectedValue， 而 reject 根本不是线上失败的主要路径。新增 5 条按真实形态（onError / onDone 伪装 / 混合）写的用例， 先红后绿；其中「onError 失败后修好模型，同一指纹仍然会重新精修」直接钉住了这个 CRITICAL 的用户可见后果。

几何检查脚本的保真缺陷（已修）

审查者指出 check.mjs 直接字符串拼接 DialogContent 的基础 class 与覆盖 class， 绕过了生产代码的 cn()（clsx + tailwind-merge）。于是 grid 与 sm:max-w-sm 都没被顶掉， 悬空对话框只有 384px（真实是 640px），单元格 60.8px，所有真实人名都被压成 8px 宽的省略号 —— 量到的是假象。已补上「同类后者胜」的合并，并加了一条保真自检： 宽度 ≥768px 时断言对话框实测就是 760px，否则整个脚本的数字都不算数。

修正后实测：对话框 760px，超长名字 clientWidth 87px（此前是 8px 的假象），三个宽度全部通过。 这个缺陷方向上是「比真实更严」，不会造成假通过，但会让数字误导后来人。
