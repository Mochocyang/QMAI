# 4.1.2 发布后验证记录

## 目的

证明修复在**真实发布链路**上端到端生效 —— 这是桩服务与临时降版本都无法替代的
一项检查：只有在 4.1.2 真正发布之后，已发布的 4.1.1 才会成为"有更新"的一方。

## 被测对象

| 项 | 值 |
|---|---|
| 程序 | `QMaiWrite_4.1.1_fixed.exe`（本机构建，版本号 4.1.1，含修复代码） |
| SHA256 | `627D19F333F5A8376B692CD9AA90E899C63487FAD5F59739BB2B7B2C94EE6CEB` |
| 端点 | 真实 GitHub（`releases/latest/download/latest.json`） |
| 期望 | 弹出「发现新版本」，正文为 4.1.2 |

## 结果：通过

- 窗口枚举命中：`20280|#32770|发现新版本`
- 截图：`shot-post-release-412-prompt.png`
- 正文：「检测到新版本 4.1.2。是否立即下载并安装？」+ 两条更新说明
  （含「设置 → 更新日志 → 检查更新」的手动更新指引）

## 首次失败与排查（记录以免误判）

第一次运行时 **90 秒内没有弹出提示**，应用界面完整运行（不是崩溃）。

当时的两种可能，仅凭"没有弹窗"无法区分：

1. 修复没生效 —— 没有发起请求
2. 请求发出了但失败（本机到 GitHub 的 TLS 不稳定）

排查：

| 检查 | 结果 | 结论 |
|---|---|---|
| `probe-connectivity.mjs`（node fetch 连测 4 次） | 4/4 成功，latest = 4.1.2 | 发布已生效，latest 正确 |
| `curl` / `git`（schannel） | 连续失败 `schannel: failed to receive handshake` | 本机部分 TLS 栈不稳 |
| `gh`（Go 自带 TLS） | 正常 | 同上，属环境问题而非项目问题 |

重试时改用 `watch-app-network.ps1`，同时观测窗口与该进程的远端 TCP 连接，
使下一次失败能立刻区分"没请求"与"请求失败"。

重试结果：**弹窗出现**，通过。

## 结论

- 修复在真实发布链路上生效：4.1.1 能感知到 4.1.2
- 首次失败是环境性网络抖动，**不是**修复缺陷
- 教训：单次失败不足以判定修复无效。若当时直接下结论，就会去改本来正确的
  代码；因此补上了连接层观测脚本，让"没请求"与"请求失败"可区分。
