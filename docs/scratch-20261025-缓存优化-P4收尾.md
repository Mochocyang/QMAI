## 一、确认 P3 是否全量生效（结论：正常路径全量生效）

追了一遍数据源：

```
context-data-sources.ts  outlineDataSource
  → readOutlineContextLayers(pp, chapter)
    → buildOutlineContextLayers(index, chapter)
        project = master（总纲） + settings（设定）      ← 作品级，整本稳定
        task    = volumes（卷纲） + chapterPlans（章纲）   ← 随章变化
        full    = master + volumes + chapterPlans + settings
```

- `buildContextPack` 正常路径一定走这个数据源，返回的是**对象**（含 `full/project/task` 三个 string），
  满足 `context-engine.ts` 的类型守卫 → `projectOutline` 必然存在。
- 读盘失败时 `readOutlineContextLayers` 会 catch 并返回三个空串对象（仍是对象），
  → `projectOutline = ""` → 我的代码回退到 `mergedOutline`，行为等于改动前，不会更差。
- 只有显式按 categories 排除 `outline` 数据源时才会没有该字段，同样走回退。

**所以 P3 对正常写章链路 100% 生效，不需要额外开关。**

## 二、章纲去重（P3 引出的新开销）

`chapterOutlineContext` 原来的拼法是：

```ts
joinNonEmpty([outlineLayers.task, rawData.volumeContext, rawData.chapterOutline], "\n\n")
```

`outlineLayers.task` 本身已经等于「卷纲 + 章纲」，再拼上单独读取的 `volumeContext`
和 `chapterOutline`，**同一段章纲会出现 2~3 次**。这个字段以前不在 `FIELD_CONFIGS` 里、
从不输出，所以没人发现；P3 让它进入 prompt 之后，重复就成了真实开销，还会让模型读到重复段落。

### 改法：只追加"确实没被 task 覆盖"的部分

```ts
const taskText = outlineLayers.task.trim()
const extras = [rawData.volumeContext, rawData.chapterOutline].map(v => v?.trim() ?? "").filter(Boolean)
if (!taskText) return joinNonEmpty(extras, "\n\n")
// 用前 200 字做"是否已包含"的判定：索引落后/漏收时仍然不会丢内容
const uncovered = extras.filter(v => !taskText.includes(v.slice(0, Math.min(200, v.length))))
return joinNonEmpty([taskText, ...uncovered], "\n\n")
```

没有简单粗暴地 `task || 其它`——那样会在大纲索引落后、漏收某章时**直接丢掉章纲**。

## 三、稳定块排序（主对话链路同类问题）

`composer.ts` 的 `stableFragments` 原来顺序：

```
作品灵魂 → 故事框架绑定 → 原作正典 → 硬性世界规则 → 核心设定 → 写作风格 → 大纲骨架
                                          ↑ 随章变，却排在中间
```

「核心设定」= `relatedSettings`，是按**本章**相关度挑出来的，换章就变。
它排在中间，一变就让后面的「写作风格 / 大纲骨架」全部够不着缓存。

改成：

```
作品灵魂 → 故事框架绑定 → 原作正典 → 硬性世界规则 → 写作风格 → 大纲骨架 → 核心设定
```

规律统一为：**作品级不变 → 作品级稳定（文风/大纲）→ 随章变化（核心设定）**。

### 新增护栏

`composer.spec.ts`：

```
核心设定随章变化，必须排在稳定块最后，且不影响前面的字节
  - 核心设定 index > 写作风格 index
  - 核心设定 index > 大纲骨架 index
  - 两次不同核心设定的 stableCore，在「### 核心设定」之前的字节完全相同
```

## 六、剩余项（都需要你拍板或有前置条件）

| 项 | 现状 | 为什么没做 |
|---|---|---|
| 「禁止违背」「写作风格」在紧预算下被整段裁掉 | 优先级 17 / 19；12000 token 实测两者都消失 | 提权会改变"预算不够时留谁"的行为，是产品决策，不是纯优化 |
| 资料章内冻结 | P0 后资料前移，但每轮仍重算 | 冻结会带来"改了设定看不到"的副作用，需要定失效策略 |
| 合并 2k token 以下的碎调用 | 低于 ~2048 门槛直接不缓存 | 要动调用编排（多次调用合并成一次），影响面大 |
| 跨章最后 30% | 断点在「本章章纲」 | 已到该结构的物理上限；再往上要么改章纲的组织方式，要么接受 |

**结论：在不改变产品语义的前提下，这条链路的缓存优化已经做到头了。** 再往上都要动"留谁/看什么"的取舍，得先定策略。
