拆书库卡片精简 + 章节目录记忆绿点

两部分互不相干，合在一份文档里：① 侧边栏章节目录按「是否已提取记忆」显示绿点；② 拆书库 Skill 卡片的证据索引下沉、冗余文案与状态徽标删除、文风「启用」按钮按需入库

1. 需求（用户原话归纳）

编号要求
1a「证据索引与实际覆盖」挪到卡片里「N 条规则 · M 条依据」之后，字体大小与它们一致
1b该位置只显示「证据索引」，不要显示太多字数
1c删除「旧版资料导入」「无结构化规则」等冗余信息
2a删除文风 / 角色故事 Skill 上的「待确认」「已入库」字样
2b文风 Skill 增加「启用」按钮（现在没有这个按钮）
3章节目录里，已提取过记忆的章节前面显示绿色小圆点；没提取过的不显示

2. 现状与根因

2.1 绿点：判定「已提取」没有现成的标记可读

章节记忆的落盘产物只有 .novel/snapshots/NNN.snapshot.json （chapterSnapshotJsonPath）。核对 chapter-ingest.ts 后确认： 提取不往章节 frontmatter 写任何标记，也不写「已提取」日志字段。所以判定只能是 「该章号的快照文件是否存在」——即按章号比对，而不是按路径。

读取方式上，树里已有先例：大纲行的「已提取」是 outlineSnapshotExists 逐行探测。 但大纲按文件名哈希取快照（getOutlineIngestIdentity），章节不行，章节只有章号。 因此章节侧改为调用一次 listSnapshots(projectPath) 拿到号码集合： 一次目录读取，而不是每章一次文件探测（大纲那种逐行 fileExists 在几百章时会退化成几百次 IO）。

2.2 章号有三个来源，且真实数据里互相矛盾

根因：parsePageInfo（树）推章号用 frontmatter 的 chapter_number ?? 标题里的数字； 而 chapter-bulk-ingest.ts（提取）用 frontmatter ?? 文件名里的数字。两者都会漏同一类文件： 章号只写在文件名里、标题里没有数字——快照存在，绿点却不亮。

在真实作品《他，只想活着》里，三个来源确实互相打架（这正是绿点必须选对推导规则的原因）：

文件frontmatter chapter_number文件名里的数字标题里的数字
chapter-012.md1012第 12 章
chapter-015.md1315第 8 章
chapter-018.md1818第 2 章
第17章.md1517第 17 章

同目录下该作品只有 002.snapshot.json 一个章节快照，对应 第2章.md（chapter_number=2）。 三个来源在它身上一致，所以这个作品看不出问题；但推导规则必须对不一致的文件也正确。

取号规则：树已知的章号 ?? 文件名里的数字。 理由是它同时覆盖两条真实路径——批量提取时 ingestChapter 收到的章号来自 page?.chapterNumber（即树的推法），树推不出时 ingestChapter 自己回退到文件名。 不新造第三套规则，避免以后再漂。

2.3 为什么「启用此文风」按钮不显示 —— 两个原因，且与「待确认」互为因果

原因一（截图里的情况）：styleState 的加载有一道 if (revision.skill !== "style" || !revision.confirmedAt) return 提前返回。 版本停在「待确认」时 styleState 恒为 null， 整个 .wb-results-tools 工具栏不渲染——不是按钮被禁用，是压根没渲染。

原因二：即使已入库，若该版本的预设已被更新的一版顶掉， 渲染的是「此历史版本已被替换」而不是按钮。

关键因果：启用需要「文风预设」存在，而预设是入库时才建的 （confirmWorkbenchRevision → upsertWritingStylePreset → publishedIds）。 所以「待确认」不是纯装饰——它标记的正是「没有预设可启用」的状态。 这解释了为什么单纯删掉「待确认」并不能让按钮出现：2a 与 2b 必须一起解决。

自动入库（book-analysis-workbench.tsx 的 effect）本应对 !confirmedAt && origin !== "legacy" && canPublishRevision(revision) 的版本发布； 截图里那版有 5 条规则，按理应被自动发布。它停在「待确认」说明该次入库失败或未重载回来。 本次不去猜这条自动路径为什么不生效，而是让按钮本身不再依赖它——按用户选择，未入库时点「启用」先入库再启用。

2.4 证据索引现在挂在版本级

现在每个版本在合并列表之后渲染一个 <details><summary>证据索引与实际覆盖</summary>， 内容是整版聚合：已读取 N 章、M 个正文分段、规则引用 K 条原文，加上 metrics（样本字数 / 平均句长 / 平均段长）与整版 coverage 列表。 位置离卡片很远，「字数太多」，而且点开一张卡看不到它引用的原文到底在哪。

2.5 冗余文案

卡片上有一枚 .wb-card-status 徽标（已入库 / 待确认）， 角色卡还有一枚 .wb-origin-tag（旧版导入 / 旧版资料导入 · 无结构化规则）。用户认为都是噪声。

3. 设计

3.1 绿点：三态与判定

状态外观悬停说明条件
已提取实心绿点已提取记忆该章号的快照存在
提取中灰点脉冲正在提取记忆该章路径在本项目的运行中章节提取任务里
未提取不渲染任何元素—其余情况

提取中优先于已提取：重新提取一章时，旧快照仍在盘上；此时显示灰点才符合 「提取中→完成变绿」的语义。

位置：行按钮内部、标题 <span> 之前（即标题左侧）。 只在 filterType === "chapter" 时渲染；大纲页签已有自己的绿色对勾按钮，不再叠加。

3.2 判定逻辑抽成纯函数

// src/lib/novel/chapter-memory-dot.ts
export type ChapterMemoryDotState = "done" | "running" | "none"

export function resolveChapterMemoryDotState(input: {
  snapshotChapterNumbers: ReadonlySet<number>
  chapterNumber?: number        // 树已知的章号（frontmatter ?? 标题）
  fileChapterNumber?: number    // 文件名里的数字
  running: boolean
}): ChapterMemoryDotState {
  if (input.running) return "running"
  const number = input.chapterNumber ?? input.fileChapterNumber
  if (typeof number !== "number" || !Number.isFinite(number) || number <= 0) return "none"
  return input.snapshotChapterNumbers.has(number) ? "done" : "none"
}

抽出来的理由是它可以真正被单测（而不是只断言源码里出现过某个字符串）， 并且把「两种章号来源、越界值、非有限数」这些分支集中在一处。

3.3 「提取中」按路径匹配，不按标题

ImportProgressTask 现在只有 currentTitle（标题）。 按标题匹配是错的：同一本书里两章重名并不罕见（「第3章 无名」这类）， 届时点一次提取会让两行同时亮起灰点。

因此给任务增加可选字段 activeChapterPaths?: string[]（规范化后的路径）， 在三个发起章节提取的调用点各写一次：

  • knowledge-tree.tsx 的「一键提取所有章节」循环内 updateTask
  • preview-panel.tsx 单章「提取记忆」/「重新提取记忆」
  • sidebar-panel.tsx 导入后的批量提取 onProgress（那里本来就有 progress.currentPath）

任务结束时清空该字段，避免残留让绿点一直显示「提取中」。

树侧只认「本项目 + kind === "chapter" + status === "running"」的任务， 与已有的大纲任务筛选口径一致。

3.4 证据索引下沉到卡片

卡片内、「N 条规则 · M 条依据」之后渲染 <details class="wb-card-evidence"><summary>证据索引</summary>， 字号沿用 small（11px），与上面那行完全一致。

展开后只列该对象自己引用的原文：

  • 条目来源：new Set(item.rules.flatMap(rule => rule.evidenceIds))， 与上面「M 条依据」的计数用同一个集合，两处不可能互相矛盾
  • 每条渲染「第 N 章 · 位置起～止」加摘录文字，复用规则详情里 .wb-evidence 的既有样式
  • 找不到对应 evidence 的 id 直接跳过（与规则详情的 .filter(Boolean) 一致）

版本级的「证据索引与实际覆盖」整块删除，其中包括整版 metrics （样本字数 / 平均句长 / 平均段长）与「已读取 N 章、M 个正文分段」聚合—— 这是用户明确选择的「一并删掉」。数据仍在 revision.metrics / revision.coverage 里、落盘未动，需要时可恢复显示。

3.5 删除状态徽标与旧版标签

  • .wb-card-status（已入库 / 待确认）整段删除 —— 两个文案都删
  • .wb-origin-tag 整段删除 —— 两种文案都删（含单纯的「旧版导入」）
  • 连带删除只服务它们的 CSS：.wb-card-status 三条规则、.wb-origin-tag 一条
已知代价（用户已确认接受）：删掉旧版标签后， origin === "legacy" 的卡片与普通卡片在界面上不再可区分 （徽标也已删除，且旧版卡片本来就不渲染徽标）。这是「删除冗余信息」的直接后果，不是遗漏。

随之失效的注释也要一并更新：SkillCard 里那段解释「旧版为什么不显示状态徽标」 的长注释在徽标删除后已无对应代码，留着会误导后来者。

3.6 文风「启用」按钮：始终显示，按需入库

styleState 从 { current, enabled } | null 改为三态，并且不再因 !confirmedAt 提前返回：

状态判定界面
未入库在 revision.publishedIds 里找不到预设按钮「启用此文风」→ 先入库再启用
当前版本预设存在且 profile.generatedAt === revision.createdAt「启用此文风」/「取消启用文风」切换
已被替换预设存在但 generatedAt 不匹配「此历史版本已被替换」（沿用现状）

「未入库」与「已被替换」必须分开：前者是从没发布过（可以补发布）， 后者是本版内容已被更新的一版顶掉（补发布等于用旧内容覆盖新预设，是破坏性的）， 两种情况给同一个文案会把用户引向危险操作。

入库动作由父组件提供（它才持有 book 与 reloadRevisions）： onEnsurePublished: () => Promise<WorkbenchRevision>， 内部走既有的 inspectWorkbenchPublication → confirmWorkbenchRevision。 confirmWorkbenchRevision 返回带新 publishedIds 的版本对象， 所以入库完能立刻用它找到预设并启用，不必等父组件重载再回头点第二次。

4. 不做的事

  • 不动 renderOutlineHtmlForPath（上一轮已确定的历史文件范围）
  • 不改任何提示词
  • 不修上文 2.3 里「自动入库为何没生效」——本次让按钮不依赖它；若自动入库确有缺陷，是独立问题
  • 不为历史快照补绿点（绿点读的是盘上现状，没有历史概念）
  • 不做「已提取」的进度百分比或章节级详情浮层

5. 验证方案

  1. 单测：resolveChapterMemoryDotState 的全分支（已提取 / 提取中覆盖已提取 / 两种章号来源 / 章号缺失 / 章号 0 与负数 / 非有限数）
  2. 单测：快照号码集合的读取（含只取正数、忽略大纲的负数与 .cache 目录）
  3. 组件断言：卡片里不再存在 .wb-card-status 与 .wb-origin-tag； 卡片里出现「证据索引」而版本级不再有；三态各自的文案
  4. 组件断言：未入库的文风版本渲染「启用此文风」；点击后确实先调入库再启用； 「已被替换」的版本不渲染启用按钮仍显示替换文案
  5. 变异验证：逐条把新逻辑改坏（提取中不优先、取号丢掉文件名回退、 未入库态退化成「已被替换」），确认对应用例变红，再按 SHA-256 还原
  6. 真实浏览器：用真实作品打开侧边栏，确认已提取的章有绿点、未提取的没有； 拆书库三态卡片截图比对
  7. npx tsc -p tsconfig.app.json --noEmit 退出 0；全量 A/B 不得新增失败文件
