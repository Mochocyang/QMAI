QMAI · 剧情推演

独立功能优化方案

只谈剧情推演本身 · 基于 QMAI-main v4.3.1 源码直读 · 不含与其他功能的整合建议

结论先行

我把这个功能从配置面板一路读到落盘，结论比我预想的尖锐：剧情推演的引擎不缺能力，缺的是"接线"和"收尾"。

具体地说：三处用户按了但没反应的断线，一处主动砍掉自己最值钱功能的设计，一个贵的没护栏、便宜的才有护栏的成本倒挂。

它真正的价值定位应该是：一次昂贵的"平行世界探索"，价值不在跑的那一次，而在跑完之后能被反复追问、能被写进计划。现在恰恰是这两件事被切断了——这才是使用率低的直接原因。

01三处断线：用户按了，但没反应

断线一：导演 Agent 是一个装饰性开关

配置面板里有一个「导演 Agent」复选框，用户可以勾。但那个值永远到不了引擎：

// 1) 面板：复选框 → store // simulation-config-panel.tsx:54, 229 const directorEnabled = useStorySimulationStore((s) => s.directorEnabled) <input type="checkbox" checked={directorEnabled} ... /> // 2) store：字段和 setter 都有 // story-simulation-store.ts:111, 326 directorEnabled: boolean setDirectorEnabled: (directorEnabled) => set({ directorEnabled }), // 3) 但引擎输入里没有这个字段 —— 传不进去 // types.ts:369-383 SimulationInput export interface SimulationInput { agents framework mode wordBudget llmConfig userIdea? injectionEvent? maxRoundsPerNode? dynamicEventPool? resume? // directorEnabled —— 不存在 } // 4) 引擎只读 modeConfig.directorEnabled // simulation-engine.ts:1214 directorEnabled: modeConfig.directorEnabled ?? false, // 5) 而四个模式的这个值，全是 false // types.ts:423, 432, 441, 450 "event-driven": { ..., directorEnabled: false } "free-emergence": { ..., directorEnabled: false } "decision-tree": { ..., directorEnabled: false } hybrid: { ..., directorEnabled: false }

引擎里唯一的消费点，守卫恒为 false：

// simulation-engine.ts:1511 if (state.directorEnabled && ni < totalNodes - 1) { const directorEval = await directorEvaluate({ ... }) // director-agent.ts:179 if (shouldInjectEvent(directorEval) && directorEval.injectEvent) { state.nextNodeInjectionMap.set(nextNodeIndex, directorEval.injectEvent) } }

连带瘫痪的东西比想象中多

directorEvaluate 全库只有这一个调用点（其余引用全在 director-agent.spec.ts 单测里），所以整条链全部不可达：

  • 7 维评分（张力/节奏/角色利用率/角色弧光/信息密度/情感共鸣/逻辑一致性）——从不产生
  • 导演注入事件机制（shouldInjectEvent → nextNodeInjectionMap）——:1271 那个消费点永远读到空
  • SimulationBranch.directorEvaluations —— 初值空数组（story-simulation-store.ts:373），全库无写入方
  • 因此分支对比里的「评分对比」页恒为 0 / 空（branch-compare-view.tsx:191 ScoreCompareTab；getAvgDirectorScore 里有 length === 0 的兜底，说明作者想过这个情况）

这不只是"少了个功能"。它让四个模式失去了评判依据。六个字段里有两个从来没被读过：

也就是说，模式面板向用户承诺的「是否强制按节点目标推进」和「是否启用导演」，两句话都是假的。真正生效的只有三个数：轮数乘数、随机事件概率、活跃比例。

断线二：历史结果里，两个最有价值的按钮被主动摘掉

这是最关键、也最能解释"使用频率低"的一处。

// simulation-report-view.tsx:599-600（对比模式）与 :622-623（单栏） <ReportContent report={activeReport} timelineEvents={activeTimeline} onInterviewAgent={!currentResult ? onInterviewAgent : undefined} onGenerateDraft={!currentResult ? onGenerateDraft : undefined} /> // :451, :454-457 —— currentResult 非空 ⟺ 用户正在看历史结果 const [viewingResultId, setViewingResultId] = useState<string | null>(null) const currentResult = useMemo(() => { if (!viewingResultId) return null return savedResults.find(r => r.id === viewingResultId) || null }, [viewingResultId, savedResults])

直译：只要你在看一条历史推演结果，采访角色和生成草稿这两个按钮就不存在。

而装备其实是齐的——这才是最让人难受的地方

这不是"技术上做不到"，而是"做了但没接上"：

  • Agent 快照已经落盘。保存结果时会写 agentSnapshot（framework-store.ts:417, 435, 519, 590）。
  • 反序列化恢复的代码已经写好，而且就是给"继续推演"用的：story-simulation-view.tsx:714-716
    agents = deserializeSimulationSnapshot(resumeSnapshot.agentSnapshot).agents
  • 采访的恢复回退甚至已经实现了。story-simulation-view.tsx:1111-1129 明确写着"内存里没有状态时，去历史结果里恢复"：
    // story-simulation-view.tsx:1111-1121 if (!lastSimulationStateRef.current || lastAgentsRef.current.length === 0) { // 尝试从当前选中的历史结果中恢复 if (selectedResultId) { const result = savedResults.find((r) => r.id === selectedResultId) if (result?.agentSnapshot) { const { agents, state } = deserializeSimulationSnapshot(result.agentSnapshot) lastAgentsRef.current = agents lastSimulationStateRef.current = state

恢复路径写好了，但触发它的那个按钮被 :599/:622 从界面上删掉了。用户根本点不到那个会去调它的地方。

顺带暴露一个状态不一致：报告页判断"我在看哪条历史"用的是局部 state viewingResultId（:451），而恢复逻辑用的是 store 里的 selectedResultId（story-simulation-view.tsx:149, 1113）。两个各自维护的"当前历史结果"，可以指向不同条目——这也是为什么恢复回退即使被触发，也可能拿错快照。

为什么这一处直接导致使用率低

把成本算清楚：一次中等规模推演约 175~415 次 LLM 调用、几十分钟等待。这是全软件最昂贵的一次操作。

而这么贵的一次探索，成果在离开页面的那一刻就无法再深挖；刷新一下更彻底，连内存态都没了（见 §02 发现二）。

用户的理性反应就是不跑第二次。不是功能不好用，是它的产出是一次性的。

断线三：strictNodeProgression 是纯粹的死配置

四个模式各自声明了这个字段，grep 全库只有两处命中：定义处（types.ts）和测试文件的构造字面量（multi-agent-orchestrator.spec.ts:84）。没有任何一行运行时代码读它。

所以模式卡片上「强制按节点目标推进 / 剧情自由涌现」这条对比不产生任何行为差异。真正决定节点会不会提前结束的是 isNodeGoalReachedWithEmbedding（simulation-engine.ts:1496）和轮数上限，与该字段无关。

02成本与效率：三个发现，其中一个是我上次说错了

发现一：贵的没护栏，便宜的反而有 —— 成本倒挂

舞台情景（便宜）

有成本护栏。scenario-setup-panel.tsx:138 预估条数，超过 SCENARIO_COST_WARN_THRESHOLD = 40（scenario-types.ts:74）就要求勾选 costAck 才能开始（:144），:590-601 是那块 UI。

还有专门的测试钉住它：scenario-ui-wiring.spec.ts:42-48

剧情推演（贵得多）

没有任何预估或确认。simulation-config-panel.tsx 的 7 个配置区里没有一处计算调用量，也没有任何 costAck 类闸门。

填完字数/轮数/角色，点开始，然后等。

量级差多少？按代码里的公式算：

节点数 N = calcNodeCount(字数) ≤1万→4 ≤3万→6 否则→8 types.ts:388-392 基础轮数 = maxRoundsPerNode ?? max(2, ⌊字数/1万⌋) types.ts:394-396 实际轮数 R = round(基础轮数 × 模式乘数) simulation-engine.ts:1179 活跃角色 A = ceil(候选角色 × agentSubsetRatio) multi-agent-orchestrator.ts:229 每角色每轮 1~3 次调用（ReAct 工具循环） simulation-engine.ts:1082 ────────────────────────────────────────────────────────────────── Agent 调用 ≈ N × R × A × [1~3] embedding = 2 × N × R （节点目标判定，每轮 2 次） simulation-engine.ts:810-811 固定开销 = 1（报告）+ N（逐节点草稿） story-draft-generator.ts:133 【小项目】1 万字 / hybrid / 5 角色 N=4 R=round(2×1.2)=2 A≈5 → 4×2×5×[1~3] = 40~120 + embedding 16 + 报告 1 + 草稿 4 ≈ 61~141 次 【中等项目】3 万字 / hybrid / 5 角色 N=6 R=round(3×1.2)=4 A≈5 → 6×4×5×[1~3] = 120~360 + embedding 48 + 报告 1 + 草稿 6 ≈ 175~415 次

而舞台情景的护栏阈值是 40。也就是说：那个 40 次就要求确认的功能，和这个 175 次起步、连一句提示都没有的功能，是同一个家族。

发现二：刷新即丢 —— store 没有持久化

// story-simulation-store.ts:238 —— 裸 create，无 persist 中间件 export const useStorySimulationStore = create<StorySimulationState>((set) => ({ phase: "idle", timelineEvents: [], debugTraces: [], activeChatAgent: null, agentChatMessages: [], branches: [], ... }))

phase / timelineEvents / debugTraces / branches / 采访消息全在内存。推演跑到第 6 个节点时刷新页面 → 进度、时间线、分支、正在进行的采访，全部消失。

（要公平地说明：磁盘存档是另一条路——savedResults 从 .qmai/simulations/ 读，那条路是持久的。丢的是"正在进行中的会话语境"，以及所有依赖 lastSimulationStateRef 的内存态。但正因为磁盘上有，历史结果里却点不到采访按钮，断线二才更没道理。）

发现三：更正我上次的说法 —— 同轮串行是故意的，不能直接并发

撤回：我上一份报告把这件事说错了

我之前写「同轮 agent 决策互相独立，可用 Promise.all 并发化，是最高 ROI 的工程改动」。这个判断是错的，我在这次逐行读代码时发现了反驳证据。

// simulation-engine.ts:1314-1322 —— 串行循环，但注释说明了原因 for (const agent of roundAgentList) { // 获取最新状态的 agent 引用（可能被之前的事件更新了记忆） const currentAgent = state.activeAgents.get(agent.characterId) ... result = await agentDecideAndActWithReact(currentAgent, node, state, ...) // :1388 立即写入黑板 —— 同轮后续 agent 会读到 recordBlackboardEvent(blackboard, tlEvent) maybeDeriveRumor(tlEvent, blackboard, Array.from(state.activeAgents.keys())) // :1403 追加到 recentEventDescs —— 正是传给下一个 agent 的那份 recentEventDescs.push(...) }

同轮里 agent B 会看到 agent A 刚刚做的事：黑板在 :1388 立即写入，recentEventDescs 在 :1403 追加，而两者都会被循环中下一个 agent 读到。

这对叙事模拟是正确设计——一场戏里角色本来就该对彼此刚刚的动作做出反应。改成 Promise.all 会让所有同轮角色基于同一份"过期"黑板做决定，语义直接变了，产出的剧情会不一样。

那真正该做的是什么

既然同轮串行是语义要求，优化方向就不是"并发同轮"，而是这三条：

  • 并发"分支之间"，而不是"角色之间"。一次跑 3 条分支对比，本来就是这功能的卖点，现在只能一条条等。分支彼此完全独立（各自一份黑板和事件线），并发是语义安全的，墙钟时间直接除以分支数。
  • 减少每轮的调用次数。每角色每轮 1~3 次（ReAct 工具循环）是主要成本项。绝大多数角色回合并不需要调工具，可以让普通路径做默认、只在确实需要检索时才升级到 ReAct。
  • 缓存恒定输入。见下。

发现四：embedding 每轮重复算同一个字符串（免费的等价优化）

// simulation-engine.ts:805-814 const eventsText = nodeTimelineEvents.map(...).join("\n") const expectedEmbedding = await embed(expectedOutcome, llmConfig) // ← 每轮都重算 const eventsEmbedding = await embed(eventsText, llmConfig) const similarity = cosineSimilarity(expectedEmbedding, eventsEmbedding)

expectedOutcome 来自 node.expectedOutcome（:796）——同一个节点内恒定不变，而这个函数每轮被调用一次（:1496）。所以同一个字符串被重复 embedding 了 R 次。

按上面的公式，2 × N × R 次 embedding 里有一半是纯浪费。3 万字场景是 48 次里的 24 次。用一个 Map<nodeIndex, number[]> 按节点缓存即可，输出完全等价，无任何语义变化。

03与 MiroFish 的对照：该学的是收尾，不是引擎

既然要把它做成一个独立功能，值得明确一件事：引擎层面我们已经领先，差距在报告和收尾。

能力QMAI 剧情推演MiroFish
信息隔离（谁知道什么）有。observableBy: all / target_only / self（simulation-engine.ts:383, 555, 573）无
谣言传播与失真有。maybeDeriveRumor（:821-880），含可信度与扭曲无
叙事结构（起承转合）有。StoryNode 节点目标 + expectedOutcome无
分支 / 回滚 / 快照有。SimulationBranch + agentSnapshot + resume无（simulation_runner.py:45 的 PAUSED 是个没接线的枚举值）
导演评分 / 质量裁判写了但没接通（§01 断线一）无
报告如何产出单次 LLM 出 JSON，无工具、无追问（simulation-report-agent.ts:165-204）ReAct + 4 工具（insight_forge / panorama_search / quick_search / interview_agents），每章至少 3 次工具调用，且必须逐字引用 agent 原话（report_agent.py:925-961, 643-653）
世界可被盘问有采访 UI 和 sim-agent-tools.ts，但报告阶段不用；且历史结果里入口被摘（§01 断线二）是其第 5 步核心：可深度采访任意 agent

这也反过来印证了结论

MiroFish 是个社会舆情模拟器，不是叙事模拟——它的 ontology_generator.py:48-73 强制 10 类实体（含 Person / Organization）并排除立场类概念，agent 只通过 Twitter / Reddit 动作交互，报告 prompt 至今是"未来预测报告"，全库没有一行小说/故事代码路径。

所以它没有什么叙事机制可以抄。它唯一真正值得我们搬的东西，恰好是"这个世界可以被反复盘问，而且报告必须引用原话"——这正好补上我们最弱的一环：报告的产出方式。

04优化清单

P0：先把它修成"按了有反应"（改动都很小，收益立刻可见）

#动作性质具体改法与理由
1 接通导演 Agent
（或删掉开关）		 接线 SimulationInput 增加 directorEnabled?: boolean；引擎 :1214 改为 input.directorEnabled ?? modeConfig.directorEnabled ?? false；视图 :789 调用处传入 store 值。
接通后一次性复活：7 维评分、注入事件、directorEvaluations、分支评分对比页。
如果不打算接通，就必须删掉面板上的复选框——留一个假开关比没有更伤信任。
2 历史结果恢复采访 + 生成草稿 接线 去掉 simulation-report-view.tsx:599/:622 的 !currentResult ? 三元，让 onInterviewAgent 直接透传；触发已有的 story-simulation-view.tsx:1111-1129 恢复路径（它本来就是为此写的）。
同时统一状态：让 viewingResultId 与 selectedResultId 指向同一个值，否则恢复可能取错快照。
这是投入产出比最高的一处——几行改动，直接解决"产出是一次性的"。
3 给主推演加成本护栏 补齐 复用现成模式（scenario-setup-panel.tsx:138-144 的预估 + 勾选确认），在 simulation-config-panel.tsx 里按 N × R × A × 1.5 + 2NR + 1 + N 预估并显示"预计约 XXX 次模型调用"。
这是用户唯一能在点击前感知代价的地方，也是"贵的没护栏"的正面解决。
4 处理 strictNodeProgression 二选一 要么在节点推进逻辑里真正读它（strictNodeProgression: false 时不被 isNodeGoalReached 提前截断），要么从 ModeConfig 和模式说明里删掉。不能让模式卡片继续承诺一个不存在的行为差异。
5 embedding 按节点缓存 等价优化 isNodeGoalReachedWithEmbedding 的 expectedEmbedding 按 node.index 缓存（Map<number, number[]>）。输出完全等价，直接省掉大约一半 embedding 调用。
6 store 加 persist 补齐 给 useStorySimulationStore 挂 persist 中间件，至少保留 phase / timelineEvents / branches / debugTraces，让刷新不丢进行中的推演。注意 extractionResult 体积大，需放进 partialize 白名单外。

P1：让它值得跑第二次

#动作性质具体改法与理由
7 报告 Agent 升级为
ReAct + 工具		 学 MiroFish 现在报告是单次 LLM 出 JSON（simulation-report-agent.ts:165-204），等于让模型"回忆"几十万字推演。改为让报告 Agent 用已有工具（sim-agent-tools.ts：查时间线、查角色认知、采访 agent）主动取证，并要求逐字引用 agent 原话作为证据。
这是把"模型总结"变成"从模拟里挖出的证据"的关键一步。
8 分支并发运行 提速 分支之间语义独立（各自一份黑板与事件线），可并发。跑 3 条分支对比从 3× 时间降到 1×。
注意不要动同轮角色循环——那是语义要求（§02 发现三）。
9 降低 ReAct 默认档位 省钱 每角色每轮 1~3 次调用是主要成本。让普通路径（agentDecideAndAct）做默认，仅在需要检索时升级到 ReAct（agentDecideAndActWithReact）。现在的降级逻辑已经存在（ModelDoesNotSupportToolsError 时回退，:1340-1355），只是方向反了。
10 报告结果回流到"计划" 收尾 目前只有"生成草稿"（→ wiki/chapters/ 正文）。但 branch.summary / keyEvents 与章纲 §5「核心事件链」（chapter-outline-template.ts，≥6 条因果）结构同构。
加一个"把这条分支写成本章事件计划"的出口，推演成果就从"草稿正文"升级为下一章的计划——这才是写作流程真正需要的形态。

P2：体验收尾

  • 推演过程中的可见性。现在有进度回调与 onDebugTrace（黑板快照、谣言、活跃角色），数据都在，但这是几十分钟的等待——值得把"当前节点/轮次/已发生事件数/已花费调用数"做成常驻状态条。
  • 保留"自由沙盘"。推演室里确实没有"位置"约束的那条脑暴路径（不绑定任何章节）应该保留，它是这个功能作为独立存在时的探索模式。
  • 把历史结果列表做成一等公民。既然核心价值在"事后盘问"，历史列表就该显示：分支数、总调用数、导演均分（接通后）、是否已生成草稿——让用户一眼看出哪条值得再挖。

05优先级判据

为什么 P0 排这六项

因为它们有一个共同特征：功能已经写完了，只是没接上或没兜住。P0 里没有一项需要新设计——导演 Agent 的 7 维评分、采访恢复、快照反序列化、成本护栏的模式，全都在代码里躺着。这六项的工程量加起来，大概小于 P1 里任何单独一项。

而它们解决的是同一个问题：让用户"按了有反应"。在这一点修好之前，讨论"推演准不准""模式好不好"都没有意义。

一句话总结
