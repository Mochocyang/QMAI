# work/scratch-20261009 分支说明：同人创作支持

> 目标：修复「无法生成同人类型小说」的问题。
> 起因：分析 [Narcooo/inkos](https://github.com/Narcooo/inkos) 的同人方案后，发现 QMAI 整个管线
> 缺少「外部原作既成事实」这一层概念——同人只能被当成一个题材标签，模型拿到的是
> 「从零设计卖点和人物」的原创技能，于是写出来的东西是原创而不是同人。

## 1. 问题定位

| 现象 | 根因 |
|---|---|
| 向导里没有同人选项 | `outline-wizard.ts` 只有「受众 + 题材」两维，没有「创作类型」这一维 |
| 选了同人也只是换了个 label | `tongren` 只存在于 `outline-genres.ts` 的展示表，`getMainGenreLabel()` 之外没有任何导出，`GENRE_SKILL_NAMES` 里没有对应项，命中不了就静默回退到 `idea-market-positioning` + `character-design` |
| 没有地方放「原作」 | `OutlineWizardRequest` 没有 `fanficMode` / 原作名称 / 原作素材字段 |
| 原作事实进不了正文 | 唯一的相近字段 `canonRules` 靠 `searchWiki` 模糊检索 `wiki/canon.md` 再 `slice(0, 2000)`，命不中就是空；且它语义上是**本作**已确认的正史 |
| 提示词里没有同人约束 | `buildOutlineWizardPrompt()` 的九项充分性闸门与固定工作流都是原创口径 |

关键结论：这不是「少一个题材」，而是**少一个维度**。同人是创作类型（原创 / 同人），
与受众、题材是正交的，必须叠加而不是替代。

## 2. 方案要点

### 2.1 新增「创作类型」维度

`OutlineWizardRequest` 增加一组可选字段，**全部可选**，因此既有调用点与手工构造的
上下文包不受影响：

```ts
creation?: "original" | "fanfic"      // 省略视为 original
fanficMode?: string                    // canon | au | ooc | cp | 自定义文本
fanficCustomMode?: string
fanficSourceName?: string
fanficSourceMaterial?: string
fanficAllowedDeviations?: string[]
```

同人**叠加**在受众/题材之上：`同人 + 玄幻` 同时加载 `fanfic-derivative` 与
`male-xuanhuan-xianxia`。

### 2.2 原作正典落盘为独立资产

`.novel/fanfic-canon.md`，与 `.novel/cognition-state.json` 等既有资产同构，自带
frontmatter（模式 / 原作 / 容许偏离 / 编译信息），因此：

- 用户可以直接在编辑器里改，改完仍能被解析；
- 不需要额外的项目元数据字段就能自描述；
- frontmatter 在注入上下文时被剥掉，不占预算。

**与原 `canonRules` 最本质的区别：按固定路径直读，不做模糊检索。**
检索漏一次，模型就会凭空编造原作事实——这正是「同人写得像原创」的直接原因。

### 2.3 超长原作靠分片编译，不靠截断

`splitFanficSourceMaterial()` 优先在段落边界切分；多片段时逐片整理成证据包再合并。
这样几百万字的原作也能进正典，而不是被 `slice()` 丢掉后半本。

编译提示词反复强调：**只保留有明确证据的内容，没有证据的字段直接省略，不要推测。**

### 2.4 注入走上下文包，不改提示词函数签名

新增 `ContextPack.sourceCanon` 字段，经 `FIELD_PRIORITY.sourceCanon = 4.5` 排在
`mustAvoid(4)` 之后、`soulDoc(5)` 之前——高于 `characterStates(9)`，所以预算紧张时
先保住硬约束。用 4.5 而非整数是为了**不改动任何既有字段的序号与 token 预算边界**
（沿用 `storyFrameworkBinding: 5.5` 的既有先例）。

因为走的是上下文包，正文的 brief / draft / expansion / polish 五个阶段以及
ContextHub 的第二条管线（AI 对话 / AI 大纲系统提示词）都自动继承，无需逐个改。

同时把正典接入硬约束保护：正典被预算裁掉时**直接报错并停机**，而不是静默丢弃
（沿用 `writingStyle` 与 `portablePersonalities` 的既有守卫）。

> ⚠️ 这一条最初只在 `contextPackToPrompt()` 上成立，是一个**名不副实的承诺**。
> 对抗式审查发现提示词有两条构建路径，另一条（`trim-context-plugin` 走
> `trimContextPack`）没有任何守卫，生产装配恰好走的就是它；ContextHub 的
> composer 还会把正典按比例截到约 5% 而不报警。三处缺口已补齐，见 §8。

## 3. 与「参考拆文 / 人格迁移」的分工（重要）

QMAI 原有的参考拆解子系统规定（`dismantling.ts:512`、`portable-personality.ts:29`）：

> 不得复用原作人物、不得复用原作设定、不得复用原作剧情、不得复用原作具体表达。

同人正典的要求正好相反。两者若不区分会直接打架，因此显式写死作用域，
并随正典一起注入（`FANFIC_REFERENCE_SCOPE_NOTE`）：

| | 作用对象 | 规则 |
|---|---|---|
| 参考拆文 / 人格迁移 | 拿来当范本的**其它**作品 | 只学节奏与结构，不得复用人物、设定、剧情、表达 |
| 同人正典 | **本作原作** | 既成事实必须沿用 |

两者都**禁止抄录原句**：同人沿用的是事实，不是文字。

## 5. 验收

`buildOutlineWizardPrompt()` 在同人模式下产出：

1. `- 创作类型：同人创作（基于已有原作）`
2. `## 同人创作约束（优先级高于原创度要求）`，含原作、模式、容许偏离
3. 六条同人硬规则
4. 「先输出原作正典卡，再写大纲」的输出顺序要求
5. 「原作未交代」的留白约定
6. 与参考拆文的分工说明
7. 充分性闸门改为要求「原作名称、同人模式、原作正典信息」
8. Skill 名单含 `fanfic-derivative`

正文侧：`.novel/fanfic-canon.md` 存在时，上下文包出现 `## 原作正典（不可违背）`，
`必须避免` 段出现正典硬约束条目，且正典被裁掉时**报错并停机而非静默丢弃**
（三条提示词构建路径都有守卫，见 §8）。
原创项目无正典文件时以上全部为空，行为与改动前一致。

## 7. 本轮明确不做

- **不抓取原作**：原作素材由用户粘贴/导入，没有爬虫。
- **不加七维审稿**：只把正典与模式喂进既有六个维度的上下文，不新增维度。
- **不做逐子题材同人 Skill**：只有一个 `fanfic-derivative`；
  `tongren_*` 那 14 个子题材标签仍只是展示用。
- **不加项目元数据字段**：正典文件自带 frontmatter 即可自描述，
  不往 `project-meta.ts` 加字段，避免扩散改动面。
- **不改 `buildStableContextPrefix()`**：它是五阶段逐字节一致的缓存前缀，不能动。
- **不自动删除残留正典**：把项目从同人改回原创时，`.novel/fanfic-canon.md`
  不会被自动删掉（它是用户可能手改过的资产，静默删除太意外）。
  改为在提交原创大纲时探测并提示用户手动删除。
  需要真正清理时可调用已导出的 `clearFanficCanon()`。
- **不修 `buildContextPack` 传 `categories` 时的既有崩溃**：
  `context-engine.ts:247` 直接读 `rawData.snapshots.previousChapterEnding`，
  只加载部分分类时 `snapshots` 源不存在会抛错。这是**改动前就存在**的问题，
  与同人无关；当前两个生产调用点（`chat-panel.tsx`、`outline-chat-panel.tsx`）
  都不传 `categories`，所以线上走不到。已记录，留待单独修。

## 8. 对抗式审查记录（第二轮）

交付后做了一次独立的对抗式审查（另一 agent + 自查探针，只找缺陷不确认），
重点是**证伪**而非复述。查出 6 个真实缺陷，全部已修并带回归测试：

| # | 缺陷 | 影响 |
|---|---|---|
| C-1 | `trim-context-plugin` 走 `trimContextPack`，该函数**没有守卫**；生产装配两个 fn 依赖都不传，恰好落在这条路径 | AI 对话与写作前置链上正典可被静默压缩或整体丢弃。实测 `trimContextPack(pack,200)` 静默丢、`contextPackToPrompt(pack,200)` 抛错 |
| C-2 | `composer` 的 `stableBudget` 占 40% 再按片段均分，正典被按比例截断且 `warnings` 为空 | 6000 字正典在 `maxContextSize=2000/4000/8000` 下 6310→317 tokens（约 5%） |
| C-3 | `chat-panel.tsx` 里 `contextPackToPrompt` 的抛出被 `console.warn` 吞掉，随后在**完全没有小说上下文**的情况下继续生成 | 用户只看到控制台警告，看不到「已停止生成」 |
| A-1 | `readYamlListValue` 只剥外层引号、从不反解 `yamlScalar` 的转义 | `改写"原作结局"` → `改写\"原作结局\"`；`C:\a` → `C:\\a` |
| D-1 | `buildChapterPlanSelfCheckContext` 漏 `sourceCanon`，而自检提示词已有该行 | 该交付项在生产路径**恒为空**（死代码） |
| D-2 | `buildLocalWritingCorpus` 漏 `sourceCanon` | 原作出处实体被当成待查实体联网补搜，可能搜回与正典冲突的资料 |
| — | 每次提交都重新编译正典，不复用已落盘文件 | 400000 字素材 = 每次大纲请求 34+1 次 LLM 调用，且用户每次都要重贴 |

修法分别是：新增 `assertSourceCanonPreserved()` 并让插件在溢出时返回
`shouldStop + stopReason="source_canon_overflow"`；composer 对未完整注入的正典抛
`SourceCanonOverflowError`；两处 catch 改为停机 + 提示；补 `splitInlineYamlList`
（引号内逗号不切分）并复用 `unquoteYamlScalar` 对称还原；两个构造点补字段；
新增 `fanficReuseCanon` 开关复用落盘正典。

审查**查证为干净**的部分（避免误报）：分片切分在 0/1/11999/12000/12001/400000/400001
逐长度实测不丢内容（含无段落硬切路径），400001 是**带提示的拒收**而非静默丢弃；
`FIELD_PRIORITY` 的 4.5 排序正确且已在 `FIELD_CONFIGS` 注册；
`fanfic-derivative` 运行时可解析（`missingNames: []`，这正是原始 bug，确实修好了）；
`request` 重赋值对同回调内后续读取可见，无陈旧闭包。
