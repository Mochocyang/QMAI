     `streamChat` 在用户取消时调的是 **`onDone()` 而不是 `onError`**

   #### ⚠️ 落盘时必须补的两件事（**已实读 `preview-panel.tsx` 与 `chat-panel.tsx` 确认**）

   **(1) 必须自己记写作统计，否则「今日 AI 生成」会静默少算。**
   `preview-panel.tsx` 的 `handleSave` 在 `:979-983` 会
   `useWritingStatsStore.getState().recordChapter(pathAtSave, persistedMarkdown, opts?.source ?? "human")`
   ——但**它写不了新章节**（见下），所以走直写就必须自己补这一步。
   照抄 `chat-panel.tsx:1322-1325` 的形状：
   ```ts
   const previousMarkdown = await readFile(chapterPath).catch(() => undefined)
   await writeFile(chapterPath, chapterMarkdown)
   useWritingStatsStore.getState().recordChapter(chapterPath, chapterMarkdown, "ai", previousMarkdown)
   ```
   `recordChapter` 是**差分口径**（`preview-panel.tsx:725` 的注释：
   「重复记账是安全的：正文没变就是空增量」），所以多记一次无害、漏记则是永久偏差。

## 3. 子批丙-3：卡片「重新修改」

用户原话：「用户可以手动去编辑，也可以让 AI 重新生成」。所以是**两个**动作。

### 3a. AI 重新生成（低风险，先做）

- 复用消息级「重新生成」（`outline-chat-panel.tsx:1808-1822` → `handleRegenerate` `:5476`），
  或复用「一次性修复」模式（`buildVolumeOutlineRepairPrompt` `:1153-1164` +
  `outlineRepairAttemptsRef` 限一次，`:4379-4398`）。
- 原始请求可从 `modelContent` 恢复（`novel-generation-request-package.ts:94`）。
- **不改数据结构**。
- ⚠️ **在章节区方案下（设计 §2.2b）**：卡片数据来自 §2.2 新建的章节区存放点，
  所以「重新生成」= 用存放点里留存的 `EventOutlineRequest` 重跑 §2.2 那条生成通路，
  把 `status` 置回 `generating`。**上面那两条大纲面板的先例只是参考实现**
  （它们闭包了未挂载面板的 ref），不要直接照搬调用。

#### ✅ 已实测：不需要新增任何 store action，直接复用提交函数即可
`EventOutlineTask` 上**已经**存了原始请求
（`event-outline-task-store.ts:20` `request: EventOutlineRequest`），
而 `startTask`（`:96-121`）本身就会
**替换**「同项目 + 同章号」的旧任务，并返回**新的** taskId
（新任务 `status: "generating"`、`receivedChars: 0`、`outline: null`）。
所以：

> **「重新生成」= 直接再调一次 `handleSubmitEventOutline(task.request)`。**

一行搞定，且语义**恰好正确**：
- 旧卡片被**替换**而不是并排（`:114-117` 的过滤条件），符合
  `:44` 注释「同一章同时挂两份细纲卡片没有可用语义」；
- 进度条从 0 重新开始；
- 旧 controller 在生成结束时已经 `settle()` 掉，不会残留。

⚠️ **不要**为它新增 `restartTask` 之类的 action —— 那会引入第二条「重置任务」的路径，
与 `startTask` 的替换语义重复，将来必然分叉。
⚠️ **不要**用 `finishTask`/`failTask` 去「改回 generating」：它们的语义是终态，
签名也不接受 status（`:131`/`:141`）。

### 3b. 手动编辑（需要动数据链路）

- ⚠️ **章节区方案简化了这一步**：卡片数据来自 §2.2 新建的章节区存放点
  （**不是** `OutlineChatMessage`），所以手改的落点就是这个存放点——
  **不需要**再往 `OutlineChatMessage` 上加 `eventOutlineOverride` 字段
  （那是「卡片仍在消息流里」时的方案，现已不适用）。
  仍要遵守的原则：**「取这份细纲」只有一个取值函数**，
  卡片渲染与「用这份细纲写这一章」都走它，避免「界面里改过、模型不知道」的双份真相
  （正是 `event-outline-card.tsx:15-20` 注释担心的）。

#### ⚠️ 已实测：这一步**需要**新增一个 store action（与 3a 不同）
现有 action 只有 `startTask` / `appendProgress` / `finishTask` / `failTask` / `removeTask`
（`event-outline-task-store.ts:45-49`），**没有任何一个能改 `outline`**。
所以手改无处可落。**二选一并说明理由**：

- **(i) 推荐：给 store 加 `updateTaskOutline(taskId, outline: EventOutlineData)`**，
  照 `finishTask`（`:131-139`）的形状写（`map` + `id` 匹配 + 更新 `updatedAt`）。
  这样 `task.outline` 仍是**唯一真相**，
  `EventOutlineCard` 与「用这份细纲写这一章」都读它，
  天然满足上面那条「只有一个取值函数」的原则。
- **(ii) 组件本地 state 按 taskId 存覆盖值**：不推荐——真相变成两处
  （store 里的 `outline` 与组件里的覆盖值），任何一处忘了走覆盖函数就会出现
  「界面改过但生成正文时用的是旧细纲」。若选这条，
  **必须**把「取这份细纲」收敛成**一个**函数并在卡片渲染与扩写两处都调用它，
  且在报告里说明怎么保证。

无论哪种，都要注意：`updateTaskOutline` 只改这一条任务，
**不要**顺手把 `status` 也改掉（手改之后仍然处于「待确认」）。

- 以下原方案**仅在**「卡片仍在消息流里」时适用，保留供对照：
  在 `OutlineChatMessage`（`src/stores/outline-chat-store.ts:116+`）上加一个可选字段
  `eventOutlineOverride?: EventOutlineData`；渲染时
  `override ?? extractEventOutlineData(msg.content)`。
- **收敛双份真相**：把「取这份细纲」抽成**一个**取值函数，
  让卡片渲染、「用这份细纲写这一章」、以及任何将来的消费都走它
  ——这正是 `event-outline-card.tsx:15-20` 注释担心的「界面里改过、模型不知道」。
- 编辑 UI：卡片上加「修改」入口，「手动编辑」打开表单（复用
  `event-outline-wizard-dialog.tsx` 的字段风格），保存写回 override。
- ⚠️ 若加字段会影响 `outline-chat-store` 的持久化或既有 spec，**改用按消息 id 的 override map**。
  实施前先读 `outline-chat-store.ts` 的 `scheduleSave`/`doSave` 与相关 spec。
