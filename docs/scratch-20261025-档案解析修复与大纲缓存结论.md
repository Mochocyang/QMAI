## 一、两个档案问题（已修复，可保存了）

### 1. 真正的根因不是 `**` 格式，是模型没输出 `sections`

你截图里看到的内容，落盘原文是这样的（我从 `outline-chats.json` 里取出来的）：

```json
"powerProfileData": {
  "name": "基因锁七重体系·第四重 灭欲／无念境",
  "tag": "编号派核心成果层 · 未来向度去人格化",
  "meta":      [ { "k": "档案对象", "v": "..." }, ... ],
  "overview":  [ { "k": "官面名", "v": "无念境" }, ... ],
  "stages":    { "columns": [...], "rows": [...] },
  "costs":     { "columns": [...], "rows": [...] },
  ...
}
```

**原文里没有 `**`**，`meta`/`overview` 也都是正常 JSON。你看到的 `**name**:` 是界面渲染层加的高亮标记。

真正的问题是：**它有 16 个顶层键，却没有 `sections` 字段**。

而 `normalizeProfileDocument` 只读 `payload.sections`：

```ts
const sections = (Array.isArray(payload.sections) ? payload.sections : [])
  .map(normalizeProfileSection).filter(Boolean)
```

于是 `sections` 为空 → 渲染时报 `未包含档案数据（sections 为空）` → 你攒的内容全丢。

对比同一批另外两条正常输出，它们老老实实写的是
`sections: [{kind:"kv", heading, items:[{label,text}]}]`，所以能存。

### 2. 为什么模型会跑偏

模型的意图是好的——它把档案拆成了更细的板块（阶段/晋升/代价/禁忌/克制/漏洞…），
但不知道必须塞进 `sections` 数组。而且它用 `columns` 表示表头（Excel 习惯），
契约里叫 `head`，我们的解析也只认 `head`。

### 3. 修了三处

| 位置 | 改动 |
|---|---|
| `profile-document.ts` `normalizeProfileSection` | 表头识别加 `columns` 兜底（原来只认 `head`） |
| `profile-document.ts` `normalizeProfileDocument` | **没有 `sections` 时按结构还原**：`{columns,rows}`→表格分区、`[{k,v}]`→kv 分区、`string[]`→列表分区；键名映射成中文标题（meta→档案信息、costs→代价、taboos→禁忌…） |
| `setting-profile-contracts.ts` | 契约加「顶层字段白名单」：只允许 name/tag/tagline/sections，明确禁止自创 meta/overview/stages/… 这类顶层键 |

**解析兜底 + 契约约束 = 双保险**：模型听话时走契约，不听话时也能救回来。

### 4. 用你那条真实数据验证

```
[verify] name=基因锁七重体系·第四重 灭欲／无念境 | sections=14
[verify] 分区：档案信息(kv) / 概览(kv) / 阶段(table) / 晋升路径(table) / 能力(table) /
         资源(table) / 代价(table) / 克制方式(table) / 禁忌(table) / 阵营与归属(table) /
         漏洞与破绽(kv) / 成长节奏(table) / 剧情用法(list) / 写作规则(list)
```

**14 个分区全部救回，表格也正确识别成 table。**

另外加了 4 条回归测试（`profile-document.spec.ts`），其中一条断言"摊平后渲染不出空档案"。
回归：novel + sources 共 **4100 项通过**，tsc 干净。

## 二、大纲缓存：不是"每轮都变"，是"每轮都是不同任务"

我上一条说"7 条请求 7 个不同指纹 → 前缀每轮都在变"，**这个结论下得太快**。

把这 7 条对应的用户输入拉出来看：

| 时间 | 用户输入 | 命中 |
|---|---|---:|
| 12:12 | 生成所有核心角色独立人物小传 | 0% |
| 12:13 | 杨小晚 人物小传 | 0% |
| 12:16 | 人物小传分歧拍板 | 0% |
| 12:17 | `/力量体系` | 42.4% |
| 12:18 | 力量体系（基因锁七重体系，补全四重~七重） | 40.6% |
| 12:22 | 战时编号契强化档案 | 67.7% |
| 12:26 | 基因锁七重体系·第四重灭欲境专项细化 | 70.7% |

**这是 7 个不同的生成任务**，不是同一会话的连续追问。人物小传、力量体系、物品档案
三种完全不同的对象，上下文本来就不同。

### 结构性矛盾

`est`（断点前的估算）在 15 万~24 万 token 之间。这个项目的 `wiki/outlines` 有 1.5 MB，
`entities` 783 KB——**stableCore 的主体就是"当前项目的全部大纲与设定"**。

而大纲链路的任务，恰恰是在**不断生成这些内容**。每生成一份档案，wiki 就变、上下文就变、
前缀就断。

**这是在"边写边把写的东西当上下文"，属于结构性问题，不是排列顺序问题。**

### 所以

| 对比 | 是否可比 |
|---|---|
| 主对话 79.7% | 同一会话连续追问，历史只追加 → 高命中是应该的 |
| 大纲 29.4% | 每轮换一个对象，且对象库本身在增长 → **不可直接对比** |

后 3 条能到 40~70%，说明"作品灵魂 / 世界规则 / 文风"这些跨任务共享的部分确实命中了，
**稳定核心在起作用**。这已经是这个场景的合理水平。

### 要再往上，只能动产品设计（需要你拍板）

| 方案 | 效果 | 代价 |
|---|---|---|
| 大纲生成时只注入**相关章节**的大纲，不再塞全量 | 前缀从 22 万降到几万，命中率可能到 70%+ | 模型看不到全貌，跨卷一致性有风险 |
| 保持现状 | 29.4% | 无 |

**我的建议是保持现状**。理由是：大纲生成是低频操作（一本书几十次），
而主对话是高频的（已经 79.7%）。为低频操作改上下文注入策略，风险大于收益。
