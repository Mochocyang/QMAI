> 复核中发现的、比清单描述更严重的一点：`SimulationReportView` 原本完全自包含——`viewingResultId` / `compareMode` / `selectedCompareId` 都是组件内 `useState`，它**从不写** store 的 `selectedResultId`（只有历史弹窗那条路径 `applySimulationResult` 会写）。所以两个「当前历史结果」不是"可能不一致"，而是**根本不连通**。
>
> 由此带出两个必须一并处理的正确性问题：
> - **生成草稿会拿错报告**：`handleGenerateDraft` 用的是 store 的 `currentReport`，而分支对象来自界面上展示的那份报告。只改「选中 id」会出现「界面显示 B，草稿按 A 的角色分析生成」（`story-draft-generator.ts:139` 确实读 `report.characterAnalyses`）。因此下拉切换统一走 `applySimulationResult`，让整份结果成为当前上下文。
> - **新一次推演后仍显示旧结果**：既然 `viewingResultId` 就是 `selectedResultId`，就必须在 `handleConfirmFramework` / `handleResimulate` 开跑前清掉它。
>
> 另修一处同类的「取错快照」隐患：选中一条**没有 `agentSnapshot`** 的历史结果时，原先只是什么都不做，`lastSimulationStateRef` 会留着上一次推演的世界，采访会指着界面上根本没显示的角色回答。现改为清空内存态，采访走恢复分支并给出「没有可用的角色状态」这个诚实提示。

> **与清单原公式的偏差（有意）**：清单写的是 `N×R×A×1.5 + 2NR + 1 + N`，其中 `2NR` 是 P0-4/P0-5 之前的口径。现在按实际实现改为：
> - strict 模式：`N`（`expectedOutcome` 每节点只 embedding 一次，P0-5 的缓存）+ `N×R`（事件文本每轮一次）
> - 非 strict 模式：`0`（P0-4 之后根本不做目标判定）
> - `directorEnabled` 时补 `N-1`（引擎只评估 `ni < totalNodes-1`）
> - `+1+N` 保留：报告 1 次 + 逐节点草稿 N 次
>
> 另说明：角色数在配置阶段不可知（提取发生在点「开始」之后）。实现上优先用已有 `extractionResult.characters`，其次用 `currentFramework` 单节点最多参与角色数，都拿不到才用保守默认值 5。
>
> **`costAck` 会在预估值变化时作废**：避免「改小再改大」用旧勾选蒙过去。

### P0-6 store 持久化

- [x] `story-simulation-store.ts` 是裸 `create`，无 `persist` —— **不挂 `persist`**，见下方范围变更
- [x] 改为文件持久化：`src/lib/novel/story-simulation/simulation-session.ts`（`.qmai/simulations/session.json`）+ `src/components/novel/story-simulation/use-simulation-session.ts` 在 view 里挂载

- [x] 补测试：`simulation-session.spec.ts`（12 条）+ `use-simulation-session.spec.tsx`（9 条）+ view 源码扫描（1 条）
- [!] **范围变更（与原清单不符，需知悉）**：原计划挂 `persist` 并保留 `phase` / `timelineEvents` / `branches` / `debugTraces`，实现时**两项都放弃**，理由：
  1. **本仓库没有 `zustand/middleware` 的 `persist`**，持久化一律走 `.qmai/` 文件读写。新引入这个中间件会打破既有约定（用户明确要求不用它）
  2. **不重复存结果数据**：`timelineEvents` / `branches` / `debugTraces` 已经按条落在 `.qmai/simulations/results/` 下，再抄一份就制造第二个来源 —— P0-2 刚修过一组「两份状态不一致、于是采访拿错快照」的缺陷，不该再引入同类结构
  3. **瞬时 phase 恢复不了**：`extracting` / `framework-generating` / `simulating` / `report-generating` / `draft-generating` 背后是一个已经消失的异步任务，恢复到这些阶段只会得到一块空面板
  4. **`report-viewing` / `draft-viewing` 依赖 `currentReport`**，而它不在会话文件里；只恢复 phase 会让报告页 `activeReport` 为 null、直接渲染成空白
- [x] 因此「进行中的会话语境」这一目标**部分达成**：配置输入能跨重启保留（最常见的那件麻烦事），推演进度/结果靠磁盘存档 + 历史结果入口恢复。若后续确要恢复 phase，必须先连 `currentReport` 的引用一起设计

> 实现里两个刻意处理的时序细节（都有测试钉住）：
> - **水合完成前绝不写盘**，否则挂载瞬间就会用默认值覆盖磁盘上的会话
> - **水合本身不触发回写**（比对内容而非无脑写），且首次使用不会平白创建文件；窗口期内用户改过的配置仍会被存下
