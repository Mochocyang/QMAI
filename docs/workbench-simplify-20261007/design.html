拆书库结果面板简化

设计文档 · 2026-10-07 · 状态：用户已确认 · 关联分支 main

1. 你的诉求（原话）

「拆出库当中像"结构版本搜索框"、"用户已确认本次需求"以及"仅待确认已加入使用库"这些内容，都是什么作用啊？觉得没什么用，导出结果也没有必要，所以这些都可以删除了。」

「为什么非要显示"加入使用库"呢？所有生成的内容（包括生成的角色）直接显示在最下面不就好了吗？所以将那些都给删除了。」

这些控件实际在做什么（如实说明，再决定删不删）

控件实际作用结论
结果版本（下拉）回顾历次分析版本；每次「补充修订」产生一个新版本，旧版本保留删除，改为全版本平铺
搜索角色 / 规则按名字过滤下方卡片（纯前端筛选）删除
仅待确认本来就是坏的：判断的是「整个版本有没有确认」而不是每个条目，勾上要么全显示、要么全空删除
用户已确认 · 9章 · 1个对象状态说明 + 章数/对象数；其中「N 项未采纳」是唯一有信息量的部分删除，把章数/对象数/未采纳挪到版本标题行
确认并加入 / 已加入使用库不是装饰按钮：它是「拆书库」→「角色灵魂库/文风库/故事框架库」唯一的落盘动作删除按钮，改为分析完自动入库
导出结果导出成 Markdown 文件删除

关键澄清：删除「确认并加入」不等于删除入库这个动作。拆书库分析结果原本只是暂存，需要点按钮才真正写进使用库。 按你的决定，改成分析完成后自动入库，所以「内容直接显示在最下面」能成立的前提是：入库已自动完成。

2. 用户决策记录

决策点你的选择
结果怎么进库分析完自动入库，不再需要确认；但要在「查看规则/补充修订」旁新增删除按钮
多版本怎么摆全部平铺，旧版本在前、新版本在后（不再通过下拉框选择）
是否显示生成时间每个生成内容都要显示日期，例如「许七安」名字后面带生成日期
删除按钮的行为点击时新增弹窗让用户确认
删除的范围连角色灵魂库一起删（真删），不可撤销

3. 数据模型现状（决定了实现边界）

export interface WorkbenchRevision extends WorkbenchOutput {
  id: string; taskId: string; bookId: string; bookTitle: string; skill: AnalysisSkill
  requirements: string; selectedChapterIds: string[]; parentRevisionId?: string
  createdAt: number          // ← 生成时间（整个版本一个）
  confirmedAt?: number       // ← 已入库标记
  publishedIds?: string[]    // ← 入库后拿到的 id
  origin?: "legacy"
}
export interface WorkbenchItem {
  subject: string; summary: string; limitations: string
  rules: WorkbenchRule[]; styleFingerprint?: StyleFingerprint
}                            // ← 注意：对象本身没有时间戳

三条硬约束（实测得出，直接影响可做与不可做）：

  1. 对象没有独立时间戳。所以「生成日期」只能取所属版本的 createdAt。一个对象在不同版本里会显示不同的日期，这是正确且有意义的。
  2. 只有角色是「一个对象一个条目」。文风是整版只生成 1 个预设（${书名} · 文风），故事也是整版 1 个框架（${书名} · 故事机制）。
  3. 角色灵魂 id 是确定性推导的：wb-${sha256(subject).slice(0,16)}。发布与删除可以用同一个函数算出同一个 id，不依赖 publishedIds 的持久化。

4. 技术方案（含取舍）

4.1 自动入库放在哪

方案取舍
A. 结果组件里挂 effect 自动确认组件一渲染就发请求，容易重复触发，且会被 React 严格模式的二次渲染干扰
B. 在 reloadRevisions 之后统一发布所有 !confirmedAt 的版本 采用幂等、天然去重、任务完成刷新时自然触发；与现有 signature 刷新机制天然契合
C. 挪进分析流水线 store与 UI 解耦更彻底，但要改动流水线并重写其测试，改动面远大于收益

4.2 怎么记住「用户删除了某条」

方案取舍
A. WorkbenchRevision 新增 removedSubjects?: string[]，随版本落盘 采用已有 confirmedAt/publishedIds 先例；可选字段向后兼容，旧数据可直接读
B. 单独开 .qmai/removed-items.json多一份状态要同步，删版本时还要清理孤儿记录
C. 只删库，靠「库里查不到就隐藏」脆弱：分不清「用户主动删的」和「发布失败/尚未发布的」，会把没发布的内容也藏起来

5. 界面变更清单

5.1 删除的元素

  • 结果版本下拉框 → 连 selectedRevision state 一起删除。活动跳转改为「切换页签 + 滚动定位到该版本」（原本靠 setSelectedRevision 实现，全版本平铺后不再需要「选中」这个概念）
  • 搜索框 → 连 query state 一起删
  • 仅待确认 → 连 pendingOnly state 一起删
  • 状态行（wb-summary 整行）→ 信息挪到版本标题行
  • 确认并加入 / 已加入使用库按钮 + 导出结果按钮 → 连 confirm()、exportResult() 与相关 import 一起清理

5.2 保留的元素

四个技能页签、视图切换（卡片/列表）、本次需求、原作结构观察导图、查看规则、补充修订、证据索引与实际覆盖、与上一版本的变化、角色卡片上的「加入自定义灵魂库 / 绑定…」。

5.3 新增的布局

顺序要动的是「渲染顺序」，不是存储顺序。实测 loadWorkbenchRevisions 结尾是 sort((a,b) => b.createdAt - a.createdAt)，即数组里最新的在前；组件里还有一条注释明确警告 「追加在末尾，不要放开头：下面的 selectedRevisions[0] 会让前置的旧版条目盖住用户最新生成的结果」。 本设计不改数组顺序，只在渲染时按 createdAt 升序排列（旧版本在前、新版本在后）。 这样既满足你的要求，又不会破坏那条既有不变量。

┌─ 2026/10/6 22:17:53 · 9章 · 1个对象 · 1项未采纳 ──────────┐   ← 旧版本在前（createdAt 小）
│  [许七安 · 10/6 22:17]  规则卡…                          │
│  [魏渊 · 10/6 22:17]    规则卡…                          │
└──────────────────────────────────────────────────────────┘
┌─ 2026/10/7 09:03:11 · 9章 · 2个对象 ─────────────────────┐   ← 新版本在后（createdAt 大）
│  [许七安 · 10/7 09:03]  规则卡…                          │
└──────────────────────────────────────────────────────────┘

每个对象名称后追加生成日期（来自所属版本 createdAt），格式 M/D HH:mm。

6. 删除功能设计

6.1 确认弹窗

使用仓库现成的 base-ui Dialog（与绑定对话框同一套），不自己搭遮罩。文案按技能页区分：

角色页：从角色灵魂库删除「许七安」？
        将删除该角色的灵魂及其规则，并解除它已绑定的小说人物。此操作不可撤销。

文风页：删除文风预设「《书名》· 文风」？
        将删除该文风预设。此操作不可撤销。

故事页：删除故事框架「《书名》· 故事机制」？
        将删除该故事框架。此操作不可撤销。

按钮：取消 / 删除（危险色）。

6.2 各技能页删除语义

技能页库中条目使用的接口
characters一个角色一个灵魂deleteCustomCharacterAura(projectPath, wb-${sha256(subject)}) 已存在，且会自动解除绑定
style整版一个预设removeWritingStylePreset 需新增（文风库目前没有任何删除接口）
story整版一个框架removePlotFramework(projectPath, frameworkId) 已存在

风格 / 故事页的删除粒度必须说清楚：因为整版只有一个库条目，点任一对象上的删除， 实际删掉的是该版本的整个预设/框架，并把该版本全部对象都记进 removedSubjects （否则会出现「预设已删、同版另一个对象还显示着」的不一致状态）。弹窗文案已按此写（写明是《书名》· 文风 / 故事机制）。

6.3 删除后的状态

删除成功后把 subject（风格/故事页为该版本全部 subject）追加进该版本的 removedSubjects 并落盘，重新打开页面该卡片不再出现。

7. 需要新增/修改的接口

文件变更
workbench-core.tsWorkbenchRevision 新增 removedSubjects?: string[]。校验策略：清洗而非抛错 —— 非法值一律丢弃成空数组，绝不因为这一个字段让整个版本读不出来（现有的 items/evidence 缺失是抛错的，但那是数据主体，性质不同）

workbench-publish.ts 或新文件新增 removeWorkbenchRevisionItem(projectPath, bookPath, revision, subject)：按技能页分派删除 + 记录 removedSubjects

8. 风险与已知代价

风险 1：自动入库会静默覆盖已有条目。重跑同一本书的分析会生成新版本，发布时同 id 覆盖库中旧条目。 以前弹窗会警告「确认替换 N 个已有条目？」，现在没有这个拦截点了。备份仍会写入 analysis/publication-history/（含被替换目标的快照），可人工回滚，但不会有任何提示。

已向用户说明，用户选择接受。若日后希望「仅在覆盖已有条目时弹一次窗」，可单独加，不影响本设计。

风险 2：删除不可撤销。用户要求的是「点击时弹窗确认」，未要求撤销。误删后只能靠 publication-history 备份手工恢复，界面无入口。

风险 3：旧版在前意味着最新结果在最下面，每次打开需要滚到底才能看到最新内容。这是「全部平铺、旧版本在前」的直接结果，已向用户说明。
