先认错：我上一版方案犯了同一个病

我提的是「场景级 / 章节级 / 卷级 / 离线脑暴」四个档位、四个入口。你已经说了"不知道该用哪一个"，我却把选择题从 N 项变成了 N+4 项——而且还是让用户去选一个本来不该他选的维度（颗粒度）。

我把整个软件数了一遍（88 个入口 / 23 个概念），结论比我预想的更清楚：颗粒度不是你选的东西，是你站在哪里的必然结果。而且我发现了一个比"入口乱"更该先修的问题（§02 形态六），以及三个不要动的正交边界（§4.1）。

02乱的四种形态（含五处铁证）

形态零：同一件事有两个门，而且门牌号不一样 —— 这是"不知道该用哪个"的头号来源

在谈正交维度之前，先说最直白的一个：卷纲和章纲，各有两套入口，指向同一套实现。

门 A：大纲向导

OutlineWizardDialog，18 个字段（篇幅/频道/题材/灵感/卖点/目标/规模/叙事/资料源/原创 vs 同人/同人模式/原作名/原作素材/容许偏离/复用正典）

outline-wizard.ts:50-82，入口 outline-chat-panel.tsx:7034

门 B：模块菜单 / 对话

OUTLINE_SECTION_GENERATION_CONFIGS 的 10 项菜单 + /模块名 斜杠命令 + 自由对话

outline-section-configs.ts:24-105，入口 outline-chat-panel.tsx:2009-2043,1025-1036

而这两扇门后面是同一套东西：共用 buildGenerationPrompt:1038、extractVolumeOutlineData:1233、extractChapterOutlineData:1130、同一个保存请求、同一个落盘路径（wiki/outlines/卷纲/、wiki/outlines/章纲/）。

这对用户意味着什么

用户看着两处入口，会合理地以为它们是两种不同的能力——一个"向导"（正式、完整）和一个"菜单"（快速、局部）。于是他会想：我该用哪个？用错了会不会不一样？

答案是不会不一样，它们产出完全相同的文件。但他没有任何办法从界面上知道这一点。这不是功能多，这是同一功能被计了两次。

形态一：正交的两个维度被塞进同一个选择器 —— 有铁证

章节 AI 会话的模式是四选一：快速 / 标准 / 严格 / 共创。前三个是执行力度，第四个是要不要先对齐再写。这两件事互相正交。

把类型定义并排看，问题就暴露了：

// src/lib/agent/workflow-mode.ts:1-6 export type AiWorkflowMode = "fast" | "standard" | "strict" | "discuss" export type OutlineWorkflowMode = "fast" | "standard" | "plan" | "discuss" // ↑ 有 strict 没 plan ↑ 有 plan 没 strict // 两边都有 discuss，但语义不同

同一个「execution mode」概念，两套面板两个类型、成员还不一样。而作者为了让它能工作，被迫在 store 里加了一个影子字段：

// src/stores/wiki-store.ts:1154-1163 setAiWorkflowMode: (aiWorkflowMode) => set((state) => ({ aiWorkflowMode, // ↓ 仅仅为了记住「切进共创之前是什么力度」 aiWorkflowModeBeforeDiscuss: aiWorkflowMode === "discuss" ? (state.aiWorkflowMode !== "discuss" ? state.aiWorkflowMode : state.aiWorkflowModeBeforeDiscuss) : aiWorkflowMode, })),

作者的注释写得更直白：

"只在切入「共创」时持久化"上一个模式"：此时才需要它来记住选定方向后用什么强度生成。"
chat-panel.tsx:1011-1012

然后在用户选定方向时，把这个值取回来：

// src/components/chat/chat-panel.tsx:3019-3020 const storedMode = useWikiStore.getState().aiWorkflowModeBeforeDiscuss const generationMode: AiWorkflowMode = storedMode === "discuss" ? "standard" : storedMode

为什么这是铁证

代码必须"存起来—再取回来"的那个维度，就是被枚举挤掉的那个维度。

aiWorkflowModeBeforeDiscuss 这个字段的存在本身，就是系统在承认：「共创」不是一种力度，它是一个阶段。当它被塞进力度枚举时，真正的力度信息就丢了，只能靠一个影子字段救回来。

而代价由用户承担。代码自己招了——tooltip 里写着："快速与共创模式下不支持计划；请切换到标准或严格模式。"（chat-panel.tsx:3310-3312；判定逻辑 :1005）

翻译成人话：你不能既说"我想先跟你讨论清楚"，又说"这次给我做完整质检"。想两者都要，只能手动来回切。

同一个词在两套面板里形状也不一样：

概念章节 AI 面板大纲 AI 面板
快速 / 标准模式模式
「严格」模式（第三档）不存在
「计划」可组合的开关（chat-panel.tsx:3293-3312）不可组合的模式（outline-chat-panel.tsx:641-646）
「共创」一批 3~4 条方向候选，单向选择多轮分歧拍板，每问 ≥2 选项 + AI 倾向

同名不同义，同义不同形。「计划」在一个面板是开关、另一个是模式；「共创」在一边是单选一批、在另一边是多轮问答。这两个词已经不能作为用户的导航依据了。

形态二：同一个问题，两套实现，而且它们不承认彼此是同一个问题

形态三：入口按「这个能力属于哪个模块」摆，不按「用户此刻在哪」摆

推演室是最典型的受害者：它是一个整窗目的地（full-window-views.ts:43-49）。要用它，用户必须离开正在写的这一章、离开编辑器、进入另一个视图、配 5 项、点 4 次、等 15 分钟。

而软件里被验证过高频的功能，入口全都在现场：

功能入口位置用户要付的代价
AI润色 / 去AI味选区浮动条（wiki-editor.tsx:621-639）选中 → 点 → 看对比 → 接受。不切视图
生成章节细纲章节工具栏（preview-panel.tsx:2949）点 → 就地生成卡片 → 确认 → 就地写正文。不切视图

作者其实知道「续写」重复了。右键菜单的注释写着（editor-context-menu.tsx:5-12）：

"刻意不做成「数组项里带 label」的一张表……而「续写」不能出现在默认项里 —— 大纲的 Milkdown 编辑器与章节正文共用这个组件……菜单里长出「续写」是错的。拆成两张表后，「续写」只有调用方显式列进 actions 才会出现。"

他解决的是「Milkdown 编辑器里不该有续写」，但没解决「章节正文里续写出现了两次」——选区浮动条一次（wiki-editor.tsx:611-620），右键菜单一次（editor-context-menu.tsx:13-14）。

这就是"乱"的微观形态

每一次都在解决局部问题，没有一个角色负责全局。

同样的痕迹还有两处，都是作者自己注释出来的：

  • preview-panel.tsx:3139-3416 有一整套第二份工具栏实现（含 AI会话、去AI味、一键排版、更多功能菜单）。但 :2882 对 markdown 章节/大纲恒真，所以这一整套对写作现场不可达——是同一批能力的死副本。改按钮名要同时改两处。
  • ui-test-editor.tsx:274 与 chat-panel.tsx:3218 各有一坨 {false && …} 死 UI，注释里已自认"别再去改它"。

形态四：文档类型被当成了用户意图 —— 名字还撞车

「生成大纲模块」菜单里平铺着 10 项（outline-section-configs.ts:24-105）。按性质分开看，是两种完全不同的东西：

这 2 项是「意图」

卷纲、章节细纲

用户真的会想"这一卷接下来怎么走"。这是他脑子里的问题。

这 8 项是「文档类型」

人物小传 / 组织势力 / 力量体系 / 金手指 / 背景设定 / 地理设定 / 伏笔计划 / 地点设定

用户不会想"我要生成一份地点设定"。他会想"这个地名我上次怎么写的？"

而软件里本来就有这些档案的位置——记忆中心（memory-center.ts:281）、小说图谱（13 类节点，graph-adapter.ts:126-130）。它们该在那里被自动维护 + 按需补齐，不该占着主菜单。顺带一提：这两个视图里目前 0 个 AI 动作按钮。

附赠一个更硬的名字撞车

「章节细纲」这个词，在同一个软件里指两件不同的东西：

  • 大纲菜单里的「章节细纲」= 17 节重型章纲（outline-section-configs.ts:35-38：基础信息 / 上章承接 / 本章定位 / 浓缩剧情 / 核心事件链 ≥6 条 / 四段式 / 情绪曲线 / 爽点 / …）
  • 章节工具栏里的按钮 aria-label="生成章节细纲" = 事件细纲，一章 4~8 个事件（preview-panel.tsx:2949 → EventOutlineWizardDialog）

用户在菜单里点「章节细纲」和在工具栏点「生成章节细纲」，得到的是两种完全不同粒度、不同结构、不同落点的东西。同一个标签，两个产品。

（公平地说，事件细纲的入口已经去重过了——outline-chat-panel.spec.tsx:3641 明确断言"向导已搬去章节区，面板里不得再留引用"。所以问题不在入口重复，在命名。而且这个命名冲突有精确的两行证据：outline-section-configs.ts:35 与 event-outline-wizard-dialog.tsx:86，两个都写着「章节细纲」。）

形态五：产物有落盘与不落盘之分，但界面上看不出来

整理过程中冒出一个我原本没料到的、性质完全不同的问题：这几个"接下来发生什么"的功能，产物的持久化地位差别极大，而 UI 对这件事一言不发。

两个都叫「章节细纲」的东西，一个有持久化权威、一个是内存草稿。用户看到的是同名的两个按钮，拿到的是两种命运。

形态六：两条"走向权威"同时注入正文，可能互相打架

这是最隐蔽、后果最实的一处。深度章节生成的上下文里，会同时进入两条关于"剧情该怎么走"的指令：

  • 章纲 + 卷纲：chapterOutline（优先级 2）、sectionBriefing（优先级 0）、volumeContext——按章号精确解析，有交叉校验 crossCheckChapterAgainstVolume:1455
  • 推演框架绑定：storyFrameworkBinding——就是把 StoryFramework 的节点按章节区间摊开的那段话

它们各自都声称自己是"这一章该怎么走"的依据，但系统里没有任何代码检查它们是否一致。章纲说「第 5 章主角要输」，推演框架说「第 3-5 章是【承】的转折节点」，模型收到两条冲突指令时只能自己圆。

为什么这比"入口乱"更该先修

入口乱只是让人困惑；这个会让人写出跑偏的稿子，而且不知道为什么跑偏。

修法不复杂：要么把绑定降级为"仅供推演参考、不进正文上下文"，要么把它纳入章纲生成与偏离校验（chapter-plan-compliance.ts）成为一条轨道而不是一个并列权威。二选一，但不能两者都要。

命名不一致还不止这一处：侧栏叫「拆文库」而创作工具菜单叫「拆书库」；「剧情搜索」有 3 个入口（侧栏 / 顶栏 / 创作工具）；「剧情推演室」有 2 个。

03正确的坐标系：位置是入口，颗粒度是位置的属性

回答你的两个疑问

「颗粒度假设」错在哪：我把颗粒度当成了用户要选的维度。它不该是。玩家不选镜头焦距，站到哪里就是什么焦距。

「位置假设」对在哪，我上次没做透：我说"按位置入口"，但还是把四档并列成四个入口。位置假设必须彻底到"颗粒度由位置推导出来"，否则等于没做。

3.1 位置 → 颗粒度，是推导关系，不是并列关系

你在哪 颗粒度自动是 ───────────────────────────────────────────────────── 卷纲视图 → 卷级（10 故事 × 10 环节） 章纲视图 → 章级（本章的事件链） 正文 + 选中一段文字 → 场景级（这几个人的这一场） 正文 + 光标停在末尾 → 段级（下面这几百字） ───────────────────────────────────────────────────── 推演室自由沙盘（没有"位置"） → ★ 唯一需要显式选颗粒度的地方

注意最后一行。颗粒度只在"没有位置"的地方才需要用户选——而那种地方恰恰不该是主路径。它应该是少数人的探索模式，不是所有人的入口。

3.2 「用哪个引擎」同样不该是用户的选项

用户在章纲位置点「推演这一章」，系统该自己判断：这个问题给 3 条方向就够（走共创，1~2 次调用），还是值得跑一次多 Agent 模拟（100+ 次）。

默认走便宜的。给一个「更深入」开关让用户主动升级。一个开关，不是一个菜单。

理由：用户没有能力在点击之前预估"这个问题需要多深"。让他选，他只会在两种情况下选错——要么花了大钱办小事，要么省了小钱办不成事。而系统手上有章号、有出场人数、有历史调用量，它比用户更知道该用哪档。

4.1 反向清单：这三样是真正正交的，不要动它们

整理功能最容易犯的第二个错，是"看着像就合并"。有三样东西看起来属于同一类，实际上是全场最干净的边界，动它们只会把清晰的地方弄脏。

06一条治理规则，以及落地顺序

治理规则（建议写进开发约定）

新能力不许新增入口，只能增强已有入口。

如果一个新能力无法归入「位置 × 意图」的某个格子，那么它多半不是用户需要的功能，而是引擎的内部能力——那就该藏在已有按钮的背后，而不是自己长一个按钮。

这条规则能直接防止今天这个问题再发生一次。现有 88 个入口、28 个需要专有概念的按钮，绝大多数都是这条规则缺席的产物。

落地顺序：前四步是减法与位移，用户马上能感觉到

步动作性质为什么排这个顺序
1 修掉两条"走向权威"的冲突：把推演框架绑定纳入章纲生成与偏离校验，或明确降级为"不进正文上下文" 正确性 唯一一个会让人写出跑偏稿子的问题（§02 形态六）。它不是体验问题而是正确性问题，所以排在所有整理动作之前。改动也小：一个数据源的取舍 + 一处校验挂钩
2 模式选择器拆分：「先对齐」从 4 选 1 里拿出来做成可组合开关；合并「计划」与「共创」；两套面板统一形状；删掉 aiWorkflowModeBeforeDiscuss 减法 改动小（两个面板各一处 + 一个 store 字段），消除一个"用户必须理解才能操作"的冲突。而且它是唯一一处代码已经承认自己错了的地方，收益最确定
3 合并大纲的两扇门：向导的 18 字段收进菜单首项的「完整设定」展开，只留一扇门 减法 直击"不知道该用哪个"的头号来源（§02 形态零）。合并后用户面对的从 2 个入口 + 10 项菜单变成 1 个入口 + 10 项菜单
4 统一「候选走向卡片」：章节共创与推演分支共用一个数据结构与一个卡片渲染 减法 两套实现合一，不是新增。之后"推演"对用户来说只剩一种产出形态
5 舞台情景搬到正文选区浮动条 位移 这一步才是真正"让推演进写作现场"。引擎和 UI 都是现成的（scenario-engine.ts / scenario-importer.ts），已有成本护栏、已能插入章节，只是换挂载点。做完推演就从"要去的地方"变成"伸手就够得着"
6 命名与去重：续写去一处；「章节细纲 / 事件细纲」改名分清；「拆文库 / 拆书库」统一；「剧情搜索」3 个入口收成 1 个；8 项设定档案移出生成菜单 减法 纯清理。菜单从 10 项变 2 项，是用户最容易感知到的"变清爽了"。同时顺手处理掉 preview-panel.tsx:3139-3416 那份死工具栏副本
7 推演室改造为世界状态视图；保留"自由沙盘"入口 重定位 放这里，因为它依赖前面已经把"动作"迁走了。此时推演室剩下的自然就是"看"
8 （承接上一份报告）成本护栏、同轮并发化、报告 Agent 加工具、结果回流章纲 §5 增强 等入口理顺之后再加强度，否则是在一个没人找得到的入口上做优化

一句话总结

现在的乱，是「同一个用户问题有多个入口」，以及「正交的维度被挤进同一个枚举」。

要治的不是把功能切得更细（那是我上次的错），而是把入口收敛到"位置"，让颗粒度和引擎都从位置推导出来。

收敛的判据很简单：用户在任何一个写作现场，需要面对的选择不超过 3 个，而且每一个都能用一句不含专有名词的话说清用途。
