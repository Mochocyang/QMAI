> 2026-10-25
> 本稿取代 v1（`scratch-20261025-缓存命中率-分析.md`）与 v2 合并稿中的**估算部分**。
> 所有数字来自可运行诊断：`src/lib/__tests__/cache-prefix-diagnostic.spec.ts`（8 项，全绿）。
> 运行：`node_modules/vitest/vitest.mjs run src/lib/__tests__/cache-prefix-diagnostic.spec.ts`

---

## 0. 先说结论

**当前命中率低，主因不是"system 提示词每轮变"，而是"本轮资料放错了位置"。**

实测（真实函数 + 真实量级）表明：每轮注入 user 消息的「本轮参考资料 + 会话摘要」约 6k~25k 字，
这部分**永远不会被下一轮命中**，因为它下一轮回放的是未注入的原文。
它占一次请求的 40%~50%，直接把命中率的天花板压到 45% 左右。

修好它（把这批资料前移成"章节级前缀"）不需要多花一个 token，命中率就能从 ~45% 提到 ~85%。

---

## 1. 实测结果（8 项）

度量口径：按 provider 实际看到的顺序把消息序列化成一条串（纯文本块数组会被
OpenAI/DeepSeek 线折叠，`llm-providers.ts:518`），
**命中率 = 公共前缀长度 / 本轮请求总长**（分母是本轮，不是上一轮）。

| 场景 | 复现的代码路径 | 本轮总长 | 命中 | 命中率 | 未命中 |
|---|---|---|---|---|---|
| S1 理想：发送态=存储态、历史只追加 | 目标形态 | 15037 | 11616 | **77.2%** | 3421 |
| S2 **发送态≠存储态**（尾部注入资料） | `chat-panel.tsx:2364,2386` + `prompt-content.ts:50` | 19390 | 12276 | **63.3%** | 7114 |
| S3 超预算裁剪，连续两轮 | `chat-request-budget.ts:311` + `runner.ts:315` | 14513 | 10173 | **70.1% → 70.1%** | 4340 |
| S4 任务契约写本轮输入 | `runner.ts:88,110` | 12205 | 10190 | **83.5%** | 2015 |
| S5 stableCore 比例截断（前段 +1 行） | `composer.ts:181-197,246` | 2300 | 1009 | **43.9%** 稳定块幸存 | — |
| S7 工具集删减 | `chat-panel.tsx` sessionTools + `tools-schema.ts:27` | 11455 | 152 | **1.3%** | 11303 |
| S6 正文折叠 | `chapter-body-injection.ts:131` | 指针 40 字 | — | 逐轮变字节 | — |
| S8 尾部块顺序 | `prompt-content.ts:39-46` | — | — | 摘要排在最前，污染其后全部 | — |

### S1 的 77% 说明什么

即使是**最理想**的形态，短会话也只有 77%。因为命中率 = 历史 /（历史 + 本轮新增），
本轮新增 3.4k、总量 15k。会话越长这个数越高——这就是 DSH 能到 99% 的原因：
**它把"本轮新增"摊薄到很长的历史上**。所以优化目标不是"让某一轮 100%"，
而是**让"本轮新增"尽可能只有用户那句话**。

## 2. 我前两版哪里错了（必须纠正）

做实测的最大价值是打掉想当然。以下三条是我前两版给错的判断，以本节为准：

| 前版判断 | 实测 | 纠正 |
|---|---|---|
| 「主对话命中率 0~7%」 | S2 = 63.3%，S4 = 83.5% | **严重低估**。system 块（含 stableCore）占总量近一半，它没变，所以并不是"全冷"。真实差距是"掉 20~35 个点"，不是"归零"。 |
| 「裁剪破坏是累进的，永不恢复」 | S3 第1→2轮 70.1%，第2→3轮 70.1% | **不累进**。裁剪每次都收敛到同一预算窗口、保留最新几组，损失稳定在"最旧一组"。所以它是一条**固定税**，不是雪崩。 |
| 「契约进头部 → 整条历史 0 命中 → 0~7%」 | S4 = 83.5% | **断点在 system 块末尾**，它之前的 system+tools 仍命中。损失 = 契约之后的历史长度，不是全量。 |
| 「stableCore 比例截断会一处变处处移」 | 第一版 fixture 用重复字符 → 测出"完全无差异"；换成编号行后 43.9% 幸存 | 结论**成立且很严重**，但第一版差点因为 fixture 不合格而误判为"没问题"。**测量方法决定结论**。 |

## 3. 根因重新排序（按"每次请求白烧多少 token"）

| 排名 | 根因 | 每次白烧 | 依据 |
|---|---|---|---|
| **1** | **本轮资料注入 user 消息，下一轮回放的是未注入原文** | 6k~25k 字 | S2：未命中 7114（样本）；真实尾部更大 |
| **2** | **stableCore 按剩余预算平均分配 → 前段一变、后段截断位全移** | 稳定块的 56% | S5：43.9% 幸存 |
| **3** | **工具集随模式变化（工具块在消息之前）** | 整条请求 | S7：1.3% |
| **4** | 任务契约写"本轮"输入且放 system 块末尾 | 历史长度 | S4：2015 |
| **5** | 超预算裁剪从最旧一组丢 | 一组/轮 | S3：4340 |
| **6** | 章节产线多阶段是兄弟请求 + 无 system + 审稿另起前缀 | 每章 2 份全价 P | 见 §5.3 |
| 7 | 正文折叠按磁盘状态重渲染、会话摘要位序 | 单条消息 + 尾部 | S6/S8 |
| 8 | 观测缺失：DeepSeek 不发 `include_usage` | 无法度量 | `llm-providers.ts:953` |

> 排名第 1 和第 2 项合计解释了大部分损失，而且**都不需要模型配合、不需要产品改动**。

## 4. 修复规格（按顺序执行，每步独立可验）

### F1 尾部资料前移成"章节级前缀"（解决根因 1）

**改哪里**：`src/components/chat/chat-panel.tsx:2340-2390`、`src/lib/context-hub/prompt-content.ts:28-48`

**现状**：
```
[system: 软件规则 + stableCore] [history] [user: 摘要 + 本轮资料 + 要求 + 用户输入]
                                              ↑ 每轮重发、永不命中
```

**改成**：
```
[system: 软件规则 + stableCore] [章节级前缀: 摘要 + 本轮资料] [history] [user: 要求 + 用户输入]
                                ↑ 一章之内冻结，可命中        ↑ 只追加
```

**实现要点**
1. `buildContextHubPromptParts` 拆成三段返回：`systemContent`（已有）、`chapterPrefixContent`（新增，装 sessionSummary + dynamicContext）、`taskContent`（只留"本轮执行要求"）。
2. `chat-panel` 把它作为一条 **`role: "user"` 的独立消息**插在 system 之后、history 之前（不要塞进 system，否则会挤开 stableCore 的断点语义）。
3. **章内冻结**：以 `会话ID + 章节号` 为 key 缓存这段文本；同一章内复用同一份字节。写章完成 / 切章 / 用户手动"刷新上下文"时清 key。
4. 保底：若这段超过可用预算的 45%，降级为原来的尾部注入（避免把历史挤没）。

**预期**：S2 的 63.3% → 82%+（那 7114 字未命中变成命中）。
**风险**：章内资料若被后台任务改写，前缀会失效一次。用"章内冻结"规避；失效时在 trace 里记 `reason: "chapter-prefix-invalidated"`，便于观察。

---

### F2 stableCore 改为"固定配额 + 片段级截断"（解决根因 2）

**改哪里**：`src/lib/context-hub/composer.ts:181-197`（`fitFragmentsProportionally`）、`:246`

**现状**：`share = remaining / (count - index)` —— 前面片段一变，后面所有片段的 share 都变，
于是它们的截断位整体平移（实测只剩 43.9% 公共前缀）。

**改成**：给 7 类稳定片段一组**固定权重**，share 只与总预算和自身权重有关，与兄弟片段大小无关。

```ts
const STABLE_WEIGHTS = {
  作品灵魂: 0.10, 故事框架绑定: 0.08, 原作正典: 0.15, 硬性世界规则: 0.15,
  核心设定: 0.17, 写作风格: 0.10, 大纲骨架: 0.25,
} as const
// share_i = floor(stableBudget * weight_i)，逐片段独立 fitFragment；
// 空间不足的片段按权重比例回收未用配额（一轮即可收敛，且只在总预算变化时才变）。
```

**预期**：前段变化只影响自己，其余片段字节不动 → 稳定块命中率 43.9% → 接近 100%。
**风险**：上下文构成比例会变（原本"平均分配"偏向长片段）。权重按现有 7 类的实际重要性给，需用户确认一次。

---

### F3 工具集冻结（解决根因 3）

**改哪里**：`src/lib/agent/tools-schema.ts:27`、`src/components/chat/chat-panel.tsx`（`sessionTools` / `advertisedTools`）

1. `toOpenAITools` 输出前按 `function.name` 排序（消除注册顺序抖动）。
2. 会话内工具**集合不变**：计划阶段 / 共创阶段不再从数组里删工具，改为在"本轮执行要求"里声明禁用，并在**执行层**拦截（现有 `planExecuteActive` 已有拦截逻辑，扩展它即可，不必改 tools 数组）。
3. 若必须删（模型不适配），把它作为一次"显式重建请求头"，并在 trace 里记原因。

**预期**：消除 1.3% 这种断崖。
**风险**：删减工具原本是为了硬约束模型，改到执行层拦截要确认拦截覆盖面（计划阶段、共创阶段各一条）。

---

### F4 任务契约改用会话首条目标（解决根因 4）

**改哪里**：`src/lib/agent/runner.ts:88-91`

```ts
- const taskGoal = config.taskGoal || 最后一条 user
+ const firstUser = messages.find((m) => m.role === "user")
+ const taskGoal = config.taskGoal || text(firstUser?.content) || "未命名任务"
```
同时 `chat-panel` 不再传 `taskGoal: plainText`（那是"本轮"输入，语义上就不是"初始任务目标"）。

**预期**：契约在同一会话内恒定 → 断点消失（S4 的 2015 字回来）。
**风险**：几乎为零；但"当前用户新要求优先"这句仍在契约里，语义不变。

---

### F5 裁剪改为"固定下界 + 只丢尾部"（解决根因 5）

**改哪里**：`src/lib/chat-request-budget.ts:283-320`、`src/lib/agent/runner.ts:315-326`

1. 超预算时**只从最旧的一组往前丢**（已是如此），但丢弃结果要**写入会话状态** `historyFloorSeq`，之后每轮用同一个 floor，不再浮点漂移。
2. 删除"原地截断旧消息"这条分支（`:340-379`）——它会让历史消息字节变化，收益（省几百 token）远小于代价。
3. `runner.ts:326` 的 `splice` 只影响本轮多步，可以保留；但不要把它当成跨轮的裁剪结果。

**预期**：把"每轮一组"的固定税，变成"每 N 轮一次"的阶跃。
**风险**：丢一组会丢上下文质量 → 需要配合章节边界（尽量在换章时丢）。

---

### F6 章节产线：单会话化 + 审稿复用前缀 + 补 system（解决根因 6）

三件事一起做，因为它们都会改请求头，分开做会各冷一次。

1. **补 system**（`deep-chapter-prompts.ts`）：把 `DE_AI_GENERATION_RULES` + 输出硬性要求 + 语言提醒抽到 system，排在 L0。
2. **审稿复用写作前缀**（`review-adapter.ts:143`）：`buildReviewPrompt` 首段改成 `buildStableContextPrefix(outlinePrompt, contextPrompt)`；取消/延后"用初稿重匹配 `characterAuras`"，改为把新角色光环追加在前缀之后。
3. **单会话化**（`deep-chapter-generation.ts` 的 5 处 `collectModelText` 调用点）：任务书 → 初稿 → 返修 → 局部修改，改成同一条 messages 数组逐轮追加，上一阶段输出**原样**作为 assistant 消息回传。

```
req1: [L0][L1][L2][指令A]                              → 任务书
req2: [L0][L1][L2][指令A][A(任务书)][指令B]               → 初稿
req3: [L0][L1][L2][指令A][A(任务书)][指令B][A(初稿)][指令C] → 返修
```

**预期**：每章"全价 P"从 2 份降到 1 份；审稿从 0% → 80%+。
**风险**：历史里带着任务书 + 初稿，token 总量上升。必须同时看"命中量×0.1 + 未命中量×1.0"的总账，不能只看命中率。

2. `context-hub-stats-summary.tsx:68`：去掉 `?? localCacheRate` 的冒充——供应商没报就显示"未提供"。

4. `LlmRequestCacheTrace` 增加 `prefixChangeReason`：`chapter-prefix-invalidated` / `tools-changed` / `trim` / `fold` / `user-edited`。有了原因，才知道下一次回归是谁干的。

## 5. 修复顺序与预期

| 顺序 | 动作 | 改动面 | 预期命中率 | 风险 |
|---|---|---|---|---|
| 0 | F7 观测 | 1 文件 + 1 组件 | —（基线） | 无 |
| 1 | F1 尾部资料前移 | 2 文件 | 63% → **82%** | 中（位置改变影响模型注意力，需试读几章） |
| 2 | F2 固定配额 | 1 文件 | 稳定块 44% → **~100%** | 中（上下文构成比例变化） |
| 3 | F4 契约 + F3 工具冻结 | 3 文件 | 去掉 2 处固定税 | 低 |
| 4 | F5 裁剪下界 | 2 文件 | 裁剪税从每轮降到每 N 轮 | 低 |
| 5 | F6 章节产线三合一 | 4 文件 | 每章输入成本 **−35%~45%** | 高（需灰度） |

**不要一次全上。** F1/F2 是"改结构不改语义"，先做；F6 是"改产线"，最后做且带开关。

## 6. 怎么验证（别靠感觉）

1. `cache-prefix-diagnostic.spec.ts` 已就位。每改一项，重跑并看 S2/S5/S7 的数字变化。
2. 每项修好后，把对应断言从"结构事实"翻转成"目标阈值"（例如 S2 改成 `expect(hitRate).toBeGreaterThan(0.8)`）——**断言翻转的那一刻，就是这项修复完成的定义**。
3. 真实环境验证：同一会话连发 5 轮，看 `cacheReadTokens/inputTokens` 是否单调上升且不归零。
4. 每章看总账（不是命中率）：`命中量×0.1 + 未命中量×1.0`，对比改造前后同题材 3 章。

## 7. 仍未验证、必须实测的三件事

1. **DeepSeek 的 prompt 模板里，tools 在 messages 之前还是之后**（决定 F3 的价值是 100% 还是 0）。
   → 两次请求只改工具集、不改消息，看 `prompt_cache_hit_tokens` 是否归零。
2. **兄弟请求到底能不能吃到公共前缀**（决定 F6 是"必做"还是"锦上添花"）。
   → 连发 3 次 `P+A`、`P+B`、`P+C`，看第 2 次是否命中。
3. **F1 前移后模型是否还用得上那批资料**（位置从"末尾"变"中段"，注意力权重会变）。
   → 试读 2~3 章，对比"人物状态/伏笔"的实际采纳率。

---

## 8. 一句话

**不要再往"提示词写得更省"上使劲了。**实测证明损失不在字数，在**位置**：
每轮新注入的那 6k~25k 资料放错了地方，而稳定块又被按比例截断打碎。
把资料前移、把截断解耦，命中率就从 45% 级跳到 85% 级，且不增加任何 token。
