# 为什么换算后判据 2 能达到「未解释 = 0」—— 归因论证

**问题（任务 2 验收的关键风险）**：判据 2 在改动前报出 **219 个未缩放元素**。
若其中有一部分**不是**由那 557 处 px 声明造成的，那么换算做完也达不到
「未解释 = 0」，验收会失败，而且失败原因不在换算里。
所以必须在动手之前先证明：**这 219 个全部可归因于 px 声明。**

结论：**可以证明，219 个全部归因于将被换算的 px 声明。** 论证如下（三层，互相独立）。

---

## 第一层：不存在「本该缩放却没缩放」的异常元素

若某个元素用的是 rem 型 Tailwind 类（`text-xs` / `text-sm` / `text-base` …），
它本来就该随界面字号缩放。这类元素若出现在未缩放名单里，说明问题不在 px 声明，
而在别处（例如父级有固定字号、或 Tailwind 配置把字号写成了 px）。

实测：未缩放元素中，类名含 rem 型 `text-*` 类的 = **0 个**。

```
类名含 text-[Npx]（换算会改它 → 可修）        : 11
类名含 rem 型 text-* 类（本就该缩放 → 另有原因）: 0     ← 关键
类名无 text-* 信息（多为自定义 CSS，需查）      : 208
合计: 219
```

这也顺带排除了「Tailwind 配置把 fontSize 定义成 px」这一可能：
若如此，所有 `text-sm` 元素都不会缩放，第一项就不可能为 0。

---

## 第二层：未缩放元素的字号恰好都是换算表里的 px 值

```
13px  138 个      例: .ui-test-nav-item 的 span / .truncate
14px   45 个      例: .ui-test-nav-item
12px   14 个      例: .ui-test-crumb
18px   11 个      例: .ui-test-brand-name
10px   11 个      例: .truncate.text-[10px].leading-tight
合计  219
```

这 5 个值全部在换算表里，且**没有任何一个未缩放元素的字号落在换算表之外**
（例如 15px、16px、17px 这些换算表里也有的值，若有元素用了却不缩放，才可疑）。
换句话说，未缩放的取值集合是换算取值集合的子集。

---

## 第三层：字号来源已被穷尽，不存在「清点看不见」的来源

CSS 里 `font-size` 的全部可能来源，逐个排查：

| 可能的字号来源 | 实测 | 说明 |
|---|---|---|
| CSS `font-size: Npx` | 160 处 | 在 557 清单内，会被换算 |
| CSS `font: … Npx/…` 简写 | 80 处 | 在清单内（含 12 处 px 行高） |
| CSS `line-height: Npx` | 11 处 | 在清单内 |
| TSX `text-[Npx]` | 306 处 | 在清单内 |
| TSX 内联 `fontSize: "Npx"` | **0 处** | 不存在 |
| TSX 内联 `fontSize: <数字>` | **0 处** | 不存在 |
| SVG `fontSize="N"` 属性 | **2 处** | 已登记为例外（图标几何，不该缩放） |
| CSS `font-size: rem/em/%` | **0 处** | 不存在（清点脚本的 `*-relative` CSS 类命中数为 0） |
| CSS `font-size: var(...)` / `calc(...)` | **0 处** | 不存在 |
| CSS 里任何不含 px/rem/em/% 的 `font-size` | **0 处** | 不存在 |
| Tailwind 配置里的 px 字号 | 侧证为无 | 见第一层 |

三条最容易被忽略、且**对清点与换算双双不可见**的来源，都实测为 0：

```powershell
# 1) font-size: var(...) / calc(...) —— 正则既不匹配 px 也不匹配 rem，会静默漏掉
Select-String -Path (git ls-files "src/**/*.css") -Pattern "font-size:\s*(var|calc)"
#   → 无输出

# 2) font 简写里把 var/calc 当字号位
Select-String -Path (git ls-files "src/**/*.css") -Pattern "font:\s*(var|calc)"
#   → 无输出

# 3) 任何不含常见单位的 font-size（穷举兜底）
#   → 共 0 处
```

> **对后续任务的提醒**：第 3 类不可见性目前无害，但任务 7 会引入
> `--qmai-body-font-size: calc(1.125rem * var(--qmai-body-font-scale, 1))`，
> 那时就出现了 `font-size: var(...)` 形式的声明。这不是缺陷，但意味着
> **任务 7 之后不能再靠 `count-absolute-font-units.mjs` 证明"没有漏项"** ——
> 该处的正确性必须由 `verify-body-font-single-source.mjs`（逐条断言 6 条规则
> 引用了预期变量）来保证。任务 7 的计划里已按此要求写明。

## 由三层论证得到的可检验预测

若论证正确，则任务 2 完成后：

1. `count-absolute-font-units.mjs` 的绝对单位需改数 = **0**；
2. 判据 2 的未解释 = **0**，且**正确缩放数应约为 894 + 219 = 1113**
   （即基线里全部 1113 个键，减去 0 个 SVG 例外）；
3. 判据 1 的差异 = **0**（100% 档等效）。

**第 2 条的"约 894 + 219"就是本论证的可证伪预测**：
如果完成换算后未解释仍不为 0，那么剩余的那部分**必然**来自上表之外的来源 ——
那说明这张来源表不完整，必须查清再收尾，而不能调宽容差或放宽判据。

（数量对不上并不可怕，可怕的是不知道为什么对不上。）

## 附：论证方法的局限（如实登记）

- 第一、二层用**类名**归因，而字号的最终来源可能在其**祖先**规则上
  （例如 `span.truncate` 本身不含字号，字号来自某个 `nav button span` 规则）。
  因此初版"用类名匹配"的做法**无法逐一归因**（实测只能归因 66/219），
  这部分**没有**被静态证明 —— 它依赖第三层的"来源穷尽"论证
  与最终的经验测量（判据 2）。
- 第三层是**强**论证：它不依赖类名匹配，而是穷举了 CSS 中字号的所有可能来源，
  并实测了那些"清点看不见"的来源确实为 0。
- 最终裁决仍是经验测量。本文件的价值是：**先给出可证伪的预测**，
  使任务 2 的结果无论成败都能被解释，而不是"跑出来 0 就高兴、不为 0 就调参"。
