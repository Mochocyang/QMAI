# DeepSeek 缓存命中率：DSH 做法拆解 + 青木改造方案

> 分析日期：2026-10-25
> 对照对象：`C:\Users\Administrator\Downloads\dsh-desktop-master`（DSH Desktop，DeepSeek 官方桌面客户端外壳 + `@deepseek-ai/dsh-*` 运行时）
> 被分析对象：青木 AI 写作（`src/lib/**`）
> 结论先行：DSH 的高命中率不是某个"参数"，而是**四条铁律**：头部冻结、历史只增不改、易变内容一律放尾部、压缩只在必要时替换中段一次。青木目前**四条都在违反**，所以命中率上不去。

---

## 一、先对齐规则：DeepSeek 缓存到底怎么命中

这决定了所有设计取舍，必须先说清楚（官方 `上下文硬盘缓存` + 2026 版 Sliding Window Attention 规则）：

| 规则 | 含义 | 对我们的含义 |
|---|---|---|
| 前缀匹配，从第 0 个 token 开始 | 中途相同不算命中 | 越靠前的内容越值钱，头部改一个字＝后面全废 |
| 每条缓存前缀是**独立完整单元**，必须**完整匹配**才命中 | 不是"最长公共前缀"式的模糊匹配 | `A+B` 的下一轮如果是 `A+C`，**这一轮不命中**，只能等系统把 `A` 识别成公共前缀并落盘，第三轮才命中 |
| 落盘时机：用户输入结束处、模型输出结束处、公共前缀检测、长输入按固定间隔 | 追加式对话天然踩在落盘点上 | "上一轮输出直接成为下一轮前缀"是最优形态 |
| 缓存构建秒级、几小时到几天自动清理 | 短时间内的连续请求才有复利 | 同一章的多阶段调用要**连着发**，别隔很久 |
| `prompt_cache_key` 不支持、`cache_control` 在 DeepSeek 端被忽略 | — | 我们给 Anthropic 做的显式断点对 DeepSeek **零作用**，只有字节稳定才有用 |
| 命中价约为未命中的 1/10 | — | 命中率 90% ≈ 成本打 1.8 折 |

**一句话**：对 DeepSeek 来说，唯一有效的优化是**让请求 N+1 的字节前缀严格包含请求 N**。所有"语义等价但字节不同"的重排、重截断、重折叠，都是 0 命中。

## 二、DSH 是怎么做到的（9 条，均带代码证据）

DSH 的运行时是 npm 包（`vendor/dsh-runtime/0.2.1-rc.3/*.tgz`），核心在 `dsh-session` / `dsh-agent-loop` / `dsh-compaction-basic` / `dsh-time-context` / `dsh-llm-deepseek`。

### 1. 会话是"事件日志 + surface 投影"，历史只增不改

`dsh-session` 把每个消息都记成一条事件，事件上带 `surfaceOp: "append"` 或 `{op:"replace", startSeq, endSeq}`。历史不是每轮重新拼字符串，而是从日志投影出来的**深度冻结对象数组**，并带增量缓存：

```js
// dsh-session/lib/index.js:1672 deriveMessages()
// CACHED: pure tail growth costs O(new nodes); a replacement rebuilds.
for (const seq of nodes.slice(this.derivedNodes)) { ... }
```

关键点：**旧消息对象是同一份冻结引用**，物理上不可能被"重渲染"成不同字节。这是青木最大的差距（见后文 §3.2）。

### 2. System prompt 是"持久事件"，不是每轮拼出来的字符串

`system/message` 写在 surface 的 node 0，只有当 system 内容**真的变了**才重新 append：

```js
// dsh-agent-loop/lib/index.js:1059
startsSeries: startsRequestSeries
  || this.requestSurfaceGeneration !== this.session.surface.contentGeneration
  || preparedCall?.toolUpdate === void 0 && this.toolsChanged(assembly.tools)
```

不改就复用同一条 → 请求头部字节天然稳定。

### 3. 时间/环境这类高频变化信息，塞在**尾部**，还做了节流

`dsh-time-context` 把时间做成**追加的 user 消息**，默认 10 分钟才刷新一次（`refreshIntervalMs ?? 6e5`），且同一 turn 内不重复注入：

```js
if (lastInjection != null && now - lastInjection < refreshIntervalMs) return decision;
return { ...decision, messages: [...decision.messages, createUserMessage({...})] };
```

> 顺带说明：绝大多数"缓存命中率莫名很低"的产品，都是把 `当前时间` 写进了 system prompt。DSH 明确不这么干。

### 4. 请求头规范化 + 相等判定，只在真变化时记账

```js
// dsh-session canonicalHeader / headerEquals
// Tool schemas compare in order.
```
`request/header` 事件只在 config/tools 变化时追加（`reason: "initial" | "resume" | "change" | "series"`）。工具 schema 按**固定顺序**逐项比较，顺序抖动会被判定为"变了"。

### 5. 工具集变化用"尾部小消息"表达，而不是重排工具列表

工具增删时追加一条 developer 消息，里面只放 `tool_addition` / `tool_removal` 引用：

```js
session.append("developer/message", { message: createDeveloperMessage({
  content: [...additions, ...removals] }) }, { surfaceOp: "append" });
```
并且支持 `defer_loading: true`（工具延迟加载），让工具 schema 块尽量小且稳定。

### 6. 工具结果在**落盘那一刻**就确定性裁剪，永不回改历史

`compaction-tool-result-pruner`：>8192 字符就保留头 4096 + 中间标记 + 尾 1024（`PRUNE_MARKER`）。**写入即定型**，之后这份字节永远不变。青木的对应实现是"每次渲染时按当前磁盘状态重算"，方向正好相反。

### 7. 压缩只在 80% 压力时做一次"中段替换"

`compaction-basic` 默认 `thresholdRatio=0.8`、`retainRatio=0.16`、`headroomTokens=65536`：
- 只在上下文用到 80% 才触发（绝大多数轮次根本不压缩）；
- 保留最近 16% 的尾巴**原样不动**；
- 从"第一个非 system 节点"到"保留尾巴之前"整段替换成一条 checkpoint 消息（`surfaceOp: replace`）；
- 替换点只能在工具调用/结果**成对**的边界上（`toolPairingBalancedBefore/After`）。

代价是"压缩那一次全废"，收益是**其余 99% 的轮次全命中**。这就是"9x%~99%"的来源。

### 8. 连压缩请求自己都是"对话的真前缀"

这是最漂亮的一手：

```js
/**
* Reconstruct the last routed request's cacheable prefix for the shadowed
* region: the system prompt held by the `system/message` at surface node 0,
* the header's tool schemas, then the region's own derived messages in surface
* order. The summarizer appends only the compaction instruction after this, so
* the call is a genuine prefix of the conversation and reuses the provider's
* KV cache.
*/
function buildSummarizationInput(session, shadowedSeqs) { ... }
```

连"做摘要"这一步都不制造额外 miss。

### 9. 观测口径分开：cacheRead / cacheWrite / uncached 三分

`token-meter` 每个 turn 记 `{uncachedInputTokens, cacheReadTokens, cacheWriteTokens, outputTokens}`，`llm-deepseek` 把 `cache_read_input_tokens` 映射成 `cacheReadTokens`。有独立口径，才谈得上优化。

### DSH 的请求长什么样（示意）

```
┌───────────────────────────── 逐轮只增不改 ─────────────────────────────┐
│ [system 快照(冻结)] [工具 schema(冻结/有序)] [历史... 只追加] [本轮 user] │
└───────────────────────────────────────────────────────────────────────┘
                      ↑ 命中                                        ↑ 唯一 miss
压缩时：只在中段做一次 replace，尾巴原样保留
```

## 三、青木现状：底子在，但四处"主动截断前缀"

### 3.1 已经做对的部分（不要推翻）

| 已有能力 | 位置 | 评价 |
|---|---|---|
| 稳定上下文前缀 `buildStableContextPrefix` | `src/lib/novel/deep-chapter-prompts.ts:56` | ✅ 设计正确，且已有回归护栏 `deep-chapter-prompts.cache.spec.ts` |
| 系统提示拆"稳定/动态"两段 | `src/lib/context-hub/prompt-content.ts:28` | ✅ 思路与 DSH 一致：动态资料放尾部 |
| 显式缓存断点（Anthropic 用） | `cache-aware-messages.ts`、`markHistoryCacheBoundary` | ✅ 对 Claude 有用，对 DeepSeek 无效（正常） |
| 前缀指纹 + 逐请求 trace | `src/lib/llm-request-trace.ts` | ✅ 基础设施很好，但没被用来做"稳定性告警" |
| 命中率展示 | `context-hub-stats-summary.tsx:65` | ⚠️ 见 §3.3 第 1 条，DeepSeek 上很可能压根没数据 |

### 3.2 六个"断点杀手"（按影响从大到小）

#### 杀手 1（P0）：超预算时"砍头 + 改旧消息"，而且写回内存历史

`src/lib/chat-request-budget.ts:311`：
```ts
while (estimateChatMessagesTokens(next) > maxTokens) {
  const removableIndex = retainedGroups.findIndex((entry) => !entry.protected)
  retainedGroups.splice(removableIndex, 1)   // ← 从最旧的一条开始丢
  ...
}
// 还不够就逐条原地截断旧消息（第 340-379 行）
```
然后 `src/lib/agent/runner.ts:326` 把裁剪结果**写回**工作历史：
```ts
workingMessages.splice(0, workingMessages.length, ...compacted)
```

后果：一旦触发裁剪，**第 0 个 token 就变了**，整轮 0 命中；而且破坏是**累进**的——下一轮的历史起点又不一样，永远回不到稳定前缀。
这正是 DSH 用"80% 阈值 + 中段压缩"极力避免的事。

#### 杀手 2（P0）：历史正文折叠是"按磁盘状态实时渲染"的

`src/lib/context-hub/chapter-body-injection.ts:131`：
```ts
// assistant 消息里 >1500 字的正文，如果章节已入库，就替换成一行指针
return buildFoldedChapterPointer({ chapterNumber, relativePath, originalChars, summary });
```
指针文本里含 `原文约 N 字` 和 `提要：${summary}`。于是同一条历史消息的**渲染结果会随时间变化**：
- 写第 5 章那一轮：历史里还没有它；
- 章节入库后的下一轮：变成指针；
- 之后摘要生成完成：指针里又多一行"提要：…"。

同一条消息在三次请求里是三种字节 → 从这条消息往后全 miss。
另外 `readChapterToolAvailable`（工具是否可用）也会切换折叠与否，等于一个隐藏的全局开关。

#### 杀手 3（P0）：任务契约把"本轮用户消息"塞进了 system 块

`src/lib/agent/runner.ts:88-91`：
```ts
const taskGoal = config.taskGoal || (最后一条 user 消息)   // chat-panel 传的是 plainText（本轮输入）
const taskContract = `## 任务契约\n初始任务目标：${taskGoal.slice(0, 1800)}...`
```
并由 `runner.ts:110` 插到**第一个非 system 位置**（即 system 块末尾）。

后果：每轮用户的输入不同 → system 块尾部不同 → 而 system 块在历史**之前** → 整段历史 0 命中。
（`cache-aware-messages.ts` 会在"可缓存路径"把契约挪到尾部，但这条路径要求消息里带 `cacheControl`；`contextHubResult` 为 null 时走的是"插在头部"的分支。）

#### 杀手 4（P1）：有会话摘要时，历史被砍成"最后 2 条"

`src/lib/context-hub/session-summary.ts:20-28`：
```ts
if (!summary?.trim()) return [...messages]
...
return messages.slice(-2)
```
配合 `chat-panel.tsx:2376` 的历史预算 `Math.min(4000, window*0.05)`：

```ts
const historyForModel = selectContextHistoryMessages(
  activeConvMessages,
  contextHubResult?.sessionSummary,
  Math.min(4000, Math.floor(getEffectiveMaxContextSize(agentConfig.llmConfig) * 0.05)),
)
```

后果：历史窗口**每轮滑动**，`[倒数2条]` 每轮都不一样 → 从历史开始处全部 miss；能稳定命中的只剩"system 块"这一段。命中率上限被 system 块占比锁死。

#### 杀手 5（P1）：stableCore 每轮重算 + 按比例截断（一处变，处处变）

`src/lib/context-hub/context-hub.ts:262` 每轮都 `composeContext(...)`；`composer.ts:246-254`：
```ts
const stableBudget = Math.floor(tokenBudget * 0.4)     // 0.65*0.4 ≈ 窗口的 26%
const { fitted } = fitFragmentsProportionally(stableCandidates, stableBudget)
```
`fitFragmentsProportionally`（composer.ts:181）按 `remaining / (count - index)` **平均分配**余量。于是：
- 只要"核心设定 / 大纲骨架 / 写作风格"里**任何一段**长度变了（换章、补设定、改文风），
- 后面所有段落的截断位置**全部跟着平移**，
- → stableCore 整体字节变化 → 头部失效。

而且 `context-hub.ts:276-291` 虽然算了 `stablePrefixStatus = "unchanged"`，但**只是记账**，并没有复用旧字节。

#### 杀手 6（P1）：工具集每轮可能不同

`chat-panel.tsx` 里 `sessionTools` 会随 `planExecuteActive` / `chapterDiscussActive` / `isQuickGeneralChat` / `preEnabledToolNames` / `contextHubResult` 是否存在而变化；`toOpenAITools` 按注册顺序输出（`tools-schema.ts:27`）。
工具 schema 在 prompt 里位于消息**之前**，集合一变，**整条 prompt 0 命中**。

#### 附带问题：chapter 多阶段是"兄弟请求"而非"父子请求"

`deep-chapter-prompts.ts` 各阶段前缀一致（这点做对了），但：
- 任务书请求 = `P + X2`
- 初稿请求 = `P + X3`
- 返修请求 = `P + X4`

三者互为**兄弟**，不是**父子**。按 DeepSeek 新规则（"必须完整匹配缓存前缀单元"），第二轮**不会**立刻命中 `P+X2` 单元；要等"公共前缀检测"把 `P` 落盘，第三轮起才命中 `P`。也就是说：**当前设计只吃到"P 那一截"，吃不到"任务书 / 初稿"这两截**。

### 3.3 两个"看不见"的问题

1. **DeepSeek 上很可能根本没有 usage 数据**
   `llm-providers.ts:953-958`：
   ```ts
   if (config.provider === "openai" || config.provider === "azure"
       || (config.provider === "custom" && isAzureOpenAiEndpoint(config.customEndpoint))) {
     body.stream_options = { include_usage: true }
   }
   ```
   DeepSeek 走 `custom` + `chat_completions` 时**不会**带 `stream_options.include_usage`，而 DeepSeek 的流式 usage 只在**最后一个 chunk**（且需显式开启）才返回 → `prompt_cache_hit_tokens` 拿不到 → `cacheRate` 回落到"本地文件缓存命中率"（`context-hub-stats-summary.tsx:68` 的 `?? localCacheRate`），这个数字和 prompt 缓存**不是一回事**。优化前先修这个，否则改完也不知道有没有效。

2. **没有"前缀稳定性"回归护栏**
   现有 `deep-chapter-prompts.cache.spec.ts` 只测"同一章各阶段前缀一致"，没测"同一会话第 N+1 轮是否以第 N 轮为前缀"。而后者才是命中率的直接决定因素。

## 四、目标架构：三条铁律 + 一个布局

### 铁律

1. **头部冻结**：一个会话的 system 块一旦发出，就不再改。项目资料变了 → **在尾部追加"上下文更新"**，不回头改头。
2. **历史只增不改**：已进入历史的每条消息字节永久固化（含正文折叠结果）。要瘦身 → 走"中段压缩一次"。
3. **易变内容全部在尾部**：时间、本轮资料、任务契约、当前请求、工具变更说明。

### 目标请求布局

```
[ system 快照 : 软件规则 + 稳定核心        ] ← 会话内冻结，逐字节不变
[ tools     : 固定全集 + 固定顺序          ] ← 会话内冻结
[ 历史 ...  : 只追加，字节固化             ] ← 命中
[ 上下文更新: 第 N 章后的增量（可选）      ] ← 部分命中
[ 本轮 user : 摘要 + 动态资料 + 契约 + 请求 ] ← 唯一 miss
```

理想稳态：第 N 轮命中率 ≈ `(system + 历史) / 全部输入`。会话越长越高，30k 输入里 2k 新增 → **≈ 93%**；把多阶段改造成追加式后，章节链路也能到 90%+。

## 五、改造清单

### P0（先做这 4 个，不改架构，收益最大）

#### P0-1 打开 DeepSeek 的 usage 上报（先能测）

`src/lib/llm-providers.ts:953`
```ts
if (
  config.provider === "openai"
  || config.provider === "azure"
  || (config.provider === "custom"
      && (isAzureOpenAiEndpoint(config.customEndpoint) || isDeepSeekEndpoint(config)))
) {
  body.stream_options = { include_usage: true }
}
```
顺带：`context-hub-stats-summary.tsx:68` 的 `?? localCacheRate` 建议改掉——供应商没报就是"未提供"，别拿本地文件缓存率冒充。

#### P0-2 任务契约改用"会话首条目标"，且永不进头部

`src/lib/agent/runner.ts:88`
```ts
const firstUserGoal = messages.find((m) => m.role === "user")  // 会话第一条，不是本轮
const taskContract = firstUserGoal ? `## 任务契约\n初始任务目标：${text(firstUserGoal).slice(0, 1800)}` : ""
```
并且统一走"尾部注入"（`cache-aware-messages.ts` 的 `dynamic` 路径），不要有"插进 system 块"的分支。
效果：同一会话内 system 块彻底稳定。

#### P0-3 历史正文折叠"定型化"：算一次，写回消息，之后不再重算

`chapter-body-injection.ts`
- 折叠结果写进消息记录（如 `message.modelContent` / `foldedAt`），后续渲染直接读；
- 已经折叠过的消息**不再因为磁盘上出现摘要而改写**；
- `readChapterToolAvailable` 造成的折叠/不折叠差异，锁定为"会话创建时的能力"，中途不变。

#### P0-4 裁剪器改成"只动尾部，绝不砍头、绝不改旧消息"

`chat-request-budget.ts:283`
- 若超预算：**保留全部 leading system + 最近 N 组**，超出的部分**整组丢弃**是允许的，但必须**从最新往前保留连续区间**，且**丢弃点一旦确定就写入会话状态**（`historyFloorSeq`），此后每轮都用同一个 floor，不再浮动；
- 禁止 `trimMessageToTokenBudget` 去截断**旧**消息（那会让旧消息字节变化）；
- 更优选：**先压缩中段**（P1-2），把裁剪当兜底。

> 只要做到"floor 固定 + 旧消息不改"，就已消除最大的一类 0 命中。

### P1（结构性，收益最大但要小心）

#### P1-1 会话级 system 快照，资料变化走"尾部增量"

- `composeContext` 结果按 `sessionId + 首次快照指纹` 缓存，**同一会话复用同一份 stableCore 字节**；
- 资料变化时，不再重建头部，而是生成一条 `## 上下文更新（第 N 章后）`，只含**发生变化的片段**，追加到尾部；
- 触发重建头部的时机只有两个：**用户手动"刷新上下文"** 或 **压缩点**（与 DSH 一致）。
- `stableFragments` 建议拆两组：
  - 真不变：`soulDoc`、`canonRules`、`sourceCanon`、`writingStyle`、`projectOutline`（完整大纲）
  - 随章变：`relatedSettings`、`storyFrameworkBinding`（如果有联动）→ **下沉到尾部**
- `fitFragmentsProportionally` 改成**逐片段独立预算**（固定 token 配额），避免"一处变、处处移"。

#### P1-2 会话压缩（把"砍头"换成"中段替换一次"）

照抄 DSH 的语义即可：
- 阈值：上下文用到窗口 75%~80% 才触发（我们已有 `0.75` 的内部预算，可以直接复用）；
- 保留：最近 ~16% 尾部原样；
- 动作：把"第一个非 system 节点 … 保留尾巴之前"整段替换成一条摘要消息；
- 摘要请求本身**复用同一前缀**（`buildSummarizationInput` 那套），别另起一条 prompt；
- 落盘：摘要 + `shadowedRange` 记录，供回溯。

#### P1-3 章节多阶段改成"一条追加式对话"

这是**性价比最高**的结构改动。把现在的三次独立单轮请求：

```
req1: [P, 指令_任务书]                      → 任务书
req2: [P, 指令_初稿, 任务书]                 → 初稿      ← 与 req1 是兄弟，不命中
req3: [P, 指令_返修, 任务书, 初稿, 意见]      → 返修      ← 与 req2 是兄弟，不命中
```

改成一条会话逐轮追加：

```
req1: [P, 指令_任务书]                                  → 任务书
req2: [P, 指令_任务书, A(任务书), 指令_初稿]              → 初稿     ← 命中 req1 全段
req3: [P, 指令_任务书, A(任务书), 指令_初稿, A(初稿), 指令_返修] → 返修 ← 命中 req1+req2 全段
```

保守估计：每章输入从"3 份 P 全价"降到"1 份 P 全价 + 2 份命中价"，**输入成本降 60% 左右**（P 是 prompt 主体）。
实现上 `collectModelText` 已经支持传 messages 数组，把"上一阶段输出"作为 assistant 消息追加即可，改动面很小。

#### P1-4 工具集冻结

- 同一会话内工具**集合与顺序固定**；计划阶段/共创阶段需要的"禁用"改为**在 system 尾部或用户尾部声明**（"本轮不要调用 run_chapter_workflow"），而不是真的从 `tools` 数组里删；
- `toOpenAITools` 输出前按 `name` 排序，消除注册顺序抖动；
- 描述文案里的动态部分（如果模板里塞了变量）要挪出去。

#### P1-5 历史窗口从"最后 2 条"改成"摘要 + 连续尾部"

`session-summary.ts`
- 不要 `slice(-2)`；改成"从 floor 开始的连续区间"，floor 只在压缩点前移；
- 预算不够时**先降摘要粒度**，再考虑前移 floor。

### P2（观测与护栏）

#### P2-1 前缀稳定性护栏（一条测试顶十条经验）

新增 `src/lib/__tests__/prefix-stability.spec.ts`：
```
同一会话连续构造第 N、N+1 轮请求体（JSON.stringify 后的字符串）

```
这条测试一旦红，就是命中率在掉。比事后看账单可靠得多。

#### P2-2 命中率看板

复用现成的 `LlmRequestCacheTrace`（已有 `prefixFingerprint`）：
- 每轮记录 `cacheReadTokens / inputTokens`；
- 同时记录 `prefixFingerprint` 是否与前一轮相同；
- 面板上显示"本会话命中率曲线 + 前缀变更次数"。前缀变更次数应该接近 0，一旦 >0 就能立刻定位是哪个改动导致的。

## 六、预期收益（按改动累加估算）

假设典型写作会话：窗口 128k，单轮输入 ~30k tokens（system 稳定核心 ~8k、历史 ~12k、动态资料 ~8k、请求 ~2k）。

| 阶段 | 单轮可命中 | 命中率 | 说明 |
|---|---|---|---|
| 现状 | 0 ~ 2k | **0~7%** | 头部每轮变 + 历史滑动/折叠，基本全 miss |
| P0 完成 | ~20k | **~65%** | 头部与历史稳定，动态尾部照旧 miss |
| P0 + P1-1/1-5 | ~22k | **~73%** | 资料变化不再打头 |
| P0 + P1 全部 | ~28k | **~93%** | 仅本轮动态资料 + 请求未命中 |
| 章节链路（P1-3 后） | — | **90%+** | 3 阶段从"3 份全价"变"1 份全价 + 2 份命中" |

成本口径：命中价 ≈ 1/10，命中率 65% → 账单约打 4 折；93% → 约 1.6 折。

## 七、验收方法（别靠感觉）

1. **单会话连续压测**：同一项目、同一会话，连发 6 轮"读上一章并总结"，记录每轮 `prompt_cache_hit_tokens / prompt_tokens`。
   - 期望曲线：第 1 轮 0% → 第 2 轮起单调上升 → 第 4 轮后 ≥ 90%。
   - 现在的曲线：**锯齿状、反复归零**，那就是头部在变。
2. **对照实验**：用开关（`settings` 里加隐藏 flag）分别关/开 P0-4，比同一序列的命中 token 总量。
3. **前缀指纹序列**：把每轮 `prefixFingerprint` 打出来，正常情况下**同一会话应长期是同一个值**（除非压缩）。变了就是有东西在改头部。
4. **回归**：先跑现有 `deep-chapter-prompts.cache.spec.ts` + 新增 `prefix-stability.spec.ts`，全绿再谈上线。

## 八、一句话总结

DSH 的高命中率来自**"不敢改历史"**：头部冻结、历史只增、易变下沉、压缩一次性。
青木现在做的恰恰是**"每轮都在改历史"**：任务契约进头部、历史滑动取末 2 条、正文按磁盘状态重折叠、超预算砍头并写回内存、stableCore 每轮按比例重截断。
所以不需要换模型、不需要调参数——**把"每轮重算"改成"一次定型 + 尾部增量"，命中率自然上去**。
