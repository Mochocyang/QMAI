docs(更新): 补充逐版核实脚本与 exe 内嵌压缩的诊断结论

接 471a0dc（恢复启动时的应用更新检查）。本提交只加验证工具与文档，
不动业务代码。

新增三个核实脚本：

- check-manual-update-path.mjs：逐版核实 v4.0.0–v4.1.1 的手动检查更新入口
  是否可用。结论：**每一版都有**，路径为「设置 → 更新日志 → 检查更新」，
  用户升级一次即可恢复自动更新，不必手动下载安装包。
  该脚本第一版把判据写成"必须出现 checkForChangelogUpdate"，把
  v4.0.0/v4.0.1 误判为"没有入口" —— 实际那两版用的是文件内的
  handleCheckUpdate()，内部同样 await check()，入口完全可用（v4.0.2 才抽成
  会话函数并改名）。判据已改为锚定**能力**而非具体标识符。
  这与拆书库 chunk 的锚点问题是同一类错误：锚点过窄会给出反向结论。

- check-affected-versions.mjs：核实各版本是否含本次修复。**重要发现：
  已发布的 v4.1.1 本身也含此 bug**（v4.0.0–v4.1.1 全部接线失效）。
  含义：这些版本的用户永远收不到自动更新提示，无论再发多少新版本 ——
  必须先手动更新一次，此后自动更新才恢复。

- diagnose-exe-embedding.mjs：我用 app-updater 的文案搜 exe 全部未命中，
  一度以为"修复代码没打进去"。对照实验否证了这一点：从 dist 里取 5 条
  确定存在的普通业务文案（如「软件上次关闭时任务尚未完成」），在 exe 里
  同样一条都搜不到 —— **exe 内嵌资源是压缩的，明文搜索对 exe 无效**。
  这是方法问题，不是缺陷。据此删除了会给出假 FAIL 的
  check-updater-in-exe.mjs，并把正确结论留在诊断脚本里。
  验证 exe 是否含修复代码，必须靠运行时行为。

运行时的最强证据在 471a0dc 之后的验证中取得，已写入 design.md：
- 已发布的 v4.1.0 便携版 + 真实 GitHub 端点 → 60 秒内无任何提示（复现）
- 修复版（临时置版本号为 4.1.0）+ 同一真实端点 → 弹出「发现新版本」，
  正文为 4.1.1 与 14 条真实更新说明
两者端点与判定逻辑相同，唯一差别是修复代码。验证后临时改动的三个版本
文件已全部还原，git 层面零改动。
