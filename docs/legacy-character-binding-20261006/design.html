拆书库：旧版角色整合与绑定

设计文档 · 2026-10-06 · 状态：待用户确认 · 关联分支 main

1. 背景与问题

拆书库目前存在两代结果，它们是两套互不相通的数据：

  • 新版工作台 BookAnalysisWorkbench：三个页签（角色 Skill／故事 Skill／文风 Skill），结果以 WorkbenchRevision 落盘在 <书目录>/analysis/revisions/<id>.json。
  • 旧版面板 BookAnalysisCharacterPanel：读 book.characters + book.skills，由 LegacySkillResults 嵌进新版页签里展示。

问题 1：同一个页签里有两份角色列表

旧版角色与新版条目彼此独立，既不合并也不互认，用户看到两份「角色」。

问题 2：绑定能力事实上不可达（本次的核心诉求）

经全项目调用点排查，绑定链路的三条实现路径全部不可达：

路径位置为什么点不到
完整绑定 UI（「添加所选角色到自定义灵魂」＋「绑定 N 并加入灵魂」） book-analysis-result-viewer.tsx:187-216 该组件只在 LegacyBookAnalysisView 内渲染（book-analysis-view.tsx:1078 / :1266），而 LegacyBookAnalysisView 未挂载。
handleLibraryBindCharacter use-library-operations.ts:151 全项目零调用点，死代码。
「加入自定义灵魂库」按钮 book-analysis-character-panel.tsx:84-94 按钮由回调门控（{onAddSelectedSkillsToSoul && …}）。LegacySkillResults 只传了 onSelectCharacter，回调缺失 → 按钮整体不渲染。

今天唯一可达的绑定入口是「灵魂」页（character-aura-view.tsx:303、soul-sidebar-panel.tsx:59），但它只能绑已经在自定义灵魂库里的 aura。而旧版角色连「进灵魂库」这一步的入口都没有。

补充事实：新版角色在「确认并加入」时会自动创建 aura 进自定义灵魂库（workbench-publish.ts:51-70），但该路径明确不自动绑定人物（book-analysis-workbench.tsx:420 的文案即「不会自动绑定人物或启用文风」）。

问题 3：重要度显示 100/10（顺带修复）

use-character-extraction.ts:338 把 0–100 的 importanceScore 直接写进只该装 1–10 的 importance 字段。项目内正确的换算已存在于 character-candidate-selection.ts:60 与 character-extraction-engine.ts:395。这正是截图里「重要度 100/10」「重要度 55/10」的成因。

2. 目标与非目标

目标

  1. 把旧版角色数据级升级为新版条目（WorkbenchRevision），沉入「角色 Skill」页签，不再有第二份列表。
  2. 新版与旧版生成的角色，都具备两个按钮：「加入自定义灵魂库」与「绑定…」。
  3. 「绑定」在完成绑定的同时自动把角色灵魂放入「自定义灵魂库」。
  4. 修复 importance 换算。

非目标

  • 不做「从拆书库新建大纲人物」。绑定的候选目标只限项目里已有的人物。
  • 不保留旧版那套四栏富详情（性格／说话风格／动机／行为模式／代表台词）。它来自 PersonalityProfile，与新版人格规则不是同一个类型；迁移后由新版卡片呈现人格规则。
  • 不清理未挂载的 LegacyBookAnalysisView 与 BookAnalysisResultViewer（含其中的旧绑定 UI）。属于既有历史包袱，本次仅不再依赖它。BookAnalysisCharacterPanel 因该路径仍在引用而保留文件，只是工作台不再使用。

3. 关键事实（勘察结论）

3.1 两代数据在同一个中间类型汇合

这是方案可行的根本原因——不需要新造发布逻辑：

旧版可发布数据：book.skills[].skillContent ──readPersonalitySkill()──┐
新版可发布数据：revision.items ──workbenchPersonality()──────────────┴─→ PortablePersonality
                                                                          │ renderPersonalitySkill
                                                                          ▼
                        buildGeneratedAuraInputFromBookCharacter() ─→ 自定义灵魂库 aura
                                                                          │
                                                          bindCharacterAura() ─→ 绑定小说人物

3.2 迁移必须落盘，且 evidence 必须为空

confirmWorkbenchRevision（workbench-publish.ts:31）按 id 从磁盘重读 revision（:35），并逐条校验 evidence 的正文偏移（:41-45：chapter.sourceHash !== e.sourceHash || chapter.content.slice(e.start, e.end) !== e.text → 抛「原文证据已变化」）。因此：

  • 纯内存的虚拟条目走不通「确认并加入」，必须落盘。
  • 旧版人格来自 LLM 摘要，没有正文偏移，故迁移条目的 evidence 必须留空数组——空数组既合法（:41 循环不执行），又被 loadWorkbenchRevisions 的 Array.isArray(value.evidence) 校验接受。

3.3 维度标签无需新增映射

WORKBENCH_DIMENSIONS（workbench-core.ts:9-12）已经把 PortablePersonality 的五个字段映射为中文：expressionDna→表达方式、mentalModel→思考方式、decisionHeuristics→决策倾向、valueAntiPatterns→价值底线、honestyBoundaries→信息与诚实边界。因此迁移条目把 rule.dimension 设为人格字段名即可正确显示。

3.4 绑定目标的范围与限制

listBindableNovelCharacters(projectPath)（character-aura.ts:759）扫描 wiki/entities 与 wiki/outlines，返回已有小说人物的名字集合；bindCharacterAura({ characterName, auraId })（:499）按名字绑定。所以绑定前提是大纲里已有人物，否则只能提示用户先去补小传。

3.5 相关类型

WorkbenchRule   { id; dimension; observation; condition; action; boundary; evidenceIds[] }
WorkbenchItem   { subject; summary; limitations; rules[]; styleFingerprint? }
WorkbenchRevision { workbenchVersion:2; items[]; evidence[]; coverage[]; metrics?; storyMap?;
                    id; taskId; bookId; bookTitle; skill; requirements; selectedChapterIds[];
                    parentRevisionId?; createdAt; confirmedAt?; publishedIds? }
PersonalityRule { id; field; condition; tendency; boundary; evidenceIds[] }
PortablePersonality { version:1; editedByUser?; summary; scope; rules[]; evidence[] }
PersonalityProfile { personality; motivation; speechStyle; behaviorPatterns; quotes[] }
注意类型区分：ExtractedCharacter.personalityProfile（types.ts:145）是 PersonalityProfile（散文式富详情，含 personality／speechStyle／motivation／behaviorPatterns／quotes），不是 PortablePersonality（结构化规则）。两者不可互换，各自的用途见 3.6。

3.6 两套 Skill 生成器：人格块并非必然存在 重要修正

旧版角色 Skill 有两条生成路径，产出格式不同：

生成器触发产出含 portablePersonality？
generateSkillsForCharacters（skill-generator.ts:254） 简单提取路径；use-character-extraction.ts:376 调用 :322 renderPersonalitySkill(...) 是
generateCharacterSkill（skill-generator.ts:95） isSixDimensionSkill(character) 为真，即角色带 sixDimensionResearch + sixDimensionMeta（:30-31；由 character-extraction-engine.ts:467／:634 的 analyzeSixDimensions 产生） :162-185 累积 LLM 原始 token，只在缺少 frontmatter 时补 name/description/sourceBook/category 否

因此 readPersonalitySkill(skill.skillContent) 对六维路径的角色返回 undefined。不能假定「有 Skill 就有人格块」。

但绑定并不因此受阻——buildGeneratedAuraInputFromBookCharacter（aura-adapter.ts:34）本身就有兜底：人格块取不到时（:60 起）改用 character.personalityProfile 的完整数据，取不到再退回 character 上的散文字段（:69-95）。结论：只要角色本身有资料，就能生成 aura、就能绑定，与是否存在人格块无关。这条结论直接决定了 5.2 与 5.4 的设计。

4. 方案选择：迁移什么时候落盘

方案做法取舍
A. 加载即落盘 打开拆书库时就把旧版角色写成 revision 文件 较差：静默写用户数据；用户删除后下次打开又回来
B. 懒落盘（采用） 列表里先显示「旧版导入」条目；用户点「确认并加入／加入灵魂库／绑定」时才 saveWorkbenchRevision 落盘，再走原有发布 采用：无静默写入；用户动作即授权；代价是多一步「落盘后再发布」
C. 只补按钮不迁移 在旧版面板上补两个按钮 否决：不满足「放入新版角色 Skill 当中」，同一页签仍有两份列表

5. 详细设计

5.1 迁移模块 legacy-character-revision.ts新增

导出两个函数：

buildLegacyCharacterRevision(book: BookAnalysisLibraryBook): WorkbenchRevision | null
materializeLegacyCharacterRevision(bookPath, book): Promise<WorkbenchRevision>

buildLegacyCharacterRevision 为纯函数（可单测）；materializeLegacyCharacterRevision 负责 saveWorkbenchRevision 落盘。字段映射：

目标来源
items[].subjectcharacter.name（发布时也用它反查源角色）
items[].summaryportablePersonality.summary；无人格块时退回 character.personalityProfile?.personality ?? character.personality ?? ""（情况 Y/Z，不编造）
items[].limitationsportablePersonality.scope；无人格块时为空字符串
items[].rules[].id / dimension / condition / action / boundary人格规则 id / field / condition / tendency / boundary
items[].rules[].observation空字符串（旧版人格摘要没有对应的逐条观察文本，不编造）
items[].rules[].evidenceIds[]
evidence / coverage / selectedChapterIds全部空数组（理由见 3.2）
skill / workbenchVersion"characters" / 2
bookId / bookTitlebook.id / book.metadata.title
idlegacy-chars-<sha256(book.path + 排序后的角色名)[0:16]>，确定性，用于去重
createdAtbook.metadata.updatedAt（稳定值，避免每次构建产生不同文件内容）
requirements"旧版角色导入"
origin"legacy"（见下）

规则来源与三种资料情况

按 skill.characterId === character.id || skill.characterName === character.name 找到该角色的 CharacterSkill，用 readPersonalitySkill(skill.skillContent) 取 PortablePersonality 作为规则来源。但「有没有规则」与「能不能绑定」是两件事：

情况可用数据rules两个按钮
X 简单提取路径 Skill 含人格块 完整规则（字段直映射） 可用
Y 六维路径（generateCharacterSkill） Skill 无人格块，但角色有 personalityProfile []，卡片显示「旧版资料导入 · 无结构化规则」 可用（发布走 5.2 的 aura-adapter 路径）
Z 只有散文字段 无 Skill（或 Skill 无内容），也无 personalityProfile，只有 character.personality 等散文字段 [] 可用（3.6 兜底链最后一档也是从这里取）
W 完全无资料 上述都没有 [] 置灰，徽标「无可用资料」（确实没有可发布内容）

关键点：按钮是否可用取决于「有没有可发布的数据」，而不是 rules.length。否则 X 之外的全部旧版角色会失去绑定能力，直接违背需求 2。

若一个条目都没有，buildLegacyCharacterRevision 返回 null（没有旧版角色就什么都不显示，与既有的「空则不渲染」约定一致）。

类型新增字段（只有一个）

// workbench-core.ts · WorkbenchRevision
origin?: "legacy"   // 可选，向后兼容；loadWorkbenchRevisions 不校验该字段

用途：条目摘要行显示「旧版导入」而不是「自动核验通过 · 待用户确认」，避免对迁移数据做出未经核验的声明；落盘后仍能识别来源；同时也决定了发布时走哪条路径（5.2）。

不需要额外的回链字段。条目与源角色的对应关系由 item.subject === character.name 给出，这与 importBookAnalysisSkillsAsAuras 自身按名字匹配的做法一致（aura-adapter.ts:205 的 characterByName）。

5.2 两条发布路径重构

新版条目：把 workbench-publish.ts:51-70 的角色发布分支抽成

publishWorkbenchCharacter(projectPath, revision, item): Promise<{ auraId, auraName }>

批量「确认并加入」与该条目的两个按钮共用它——按钮需要发布单条而不确认整个版本，这正是抽取的动机。合成 ExtractedCharacter 的做法对新版条目是正确的（新版条目的全部信息本来就在 item 里），保持原样。

旧版条目：不复用上面这条，而是复用已存在且在用的函数

importBookAnalysisSkillsAsAuras(projectPath, metadata, characters, skills, [skillId])

理由（这是相对初版设计的关键简化）：

  • 它已经用真实角色构建 aura（aura-adapter.ts:230 传的是 characterById/characterByName 查出的真角色），因此 3.6 的完整兜底链天然生效，情况 X/Y/Z 全部覆盖，不需要为 legacy 分支写新代码。
  • 它自带去重（:209-227 的 existingAuraKeys），「已加入」可幂等。
  • 它已被 3 个测试文件覆盖：aura-adapter.e2e.spec.ts、aura-adapter-dedupe.spec.ts、以及 use-library-operations.spec.tsx 的 mock。复用它比新写一条发布分支风险低得多。

它需要一个 skillId，因此对情况 Y/Z（没有可用 Skill）就地合成一个 CharacterSkill：

// 仅作为 aura 输入载体，不写入 skills 目录、不进入作品库
{ id: `legacy-skill-${character.id}`, characterId: character.id, characterName: character.name,
  skillContent: character.personalityProfile
    ? generateSimpleSkillMarkdown({ characterName: character.name, profile: character.personalityProfile, sourceBook: book.metadata.title })
    : "",                       // 情况 Z：留空，由 aura-adapter 的散文字段兜底
  sourceBook: book.metadata.title, chapterRange: [...], createdAt: ... }

用 generateSimpleSkillMarkdown（skill-generator.ts:369）而非留空，是因为 character-aura.ts:454 会把 input.skillContent 写成 SKILL.md，且 story-extractor.ts:528 会读回它——空内容会削弱下游使用。generateSimpleSkillMarkdown 需要完整 PersonalityProfile，故情况 Z 无法使用它，只能留空（此时 aura 的字段仍由 3.6 兜底从散文字段取到，只是 SKILL.md 为空）。

批量确认对迁移版本的例外

confirmWorkbenchRevision:37 有一道门槛：if (!revision.items.some((item) => item.rules.length)) throw new Error("没有有依据的规则可加入")。情况 Y/Z 的迁移版本 rules 全空，但这个版本确实有可发布内容（靠 3.6 兜底）。因此该门槛改为：存在任一条目有规则，或该版本是 legacy（其源角色有可发布数据）时放行。非 legacy 版本行为不变。

5.3 动作层 workbench-soul-actions.ts新增

addCharacterToSoulLibrary(projectPath, book, subject)                  → 只入库，不绑定
bindCharacterToNovelCharacters(projectPath, book, revision, subject, names[])  → 先入库（幂等），再逐个绑定
loadCharacterSoulStatus(projectPath, bookTitle, subject)               → "none" | "added" | { bound: string[] }
  • 两个动作都先按 revision.origin === "legacy" 选路（5.2），得到一个 auraId：legacy 走 importBookAnalysisSkillsAsAuras，新版走 publishWorkbenchCharacter。
  • 因为 importBookAnalysisSkillsAsAuras 对已存在的 aura 会 continue（返回空数组），动作层需要在返回空时用 loadCharacterSoulStatus 查出已有 auraId 继续绑定——否则「已入库但未绑定」的角色将无法绑定。
  • bindCharacterToNovelCharacters 在拿到 auraId 后对每个目标名调 bindCharacterAura({ characterName, auraId })。这一步就是需求 2(c)「绑定时自动进入自定义灵魂库」的落点。
  • loadCharacterSoulStatus 读 loadCharacterAuraStore，用 isSameBookAnalysisCharacterAura(aura, bookTitle, subject) 找 aura，再用 store.bindings 反查该 auraId 绑定了哪些人物名——徽标的数据源。

5.4 界面：条目尾部的两个按钮修改

改 book-analysis-workbench.tsx。角色卡片的 .wb-card-footer（现为 :472-475）增加一条操作行，对每个角色条目都渲染（因此新版、旧版生成的角色自动都具备）：

  • 状态徽标与按钮状态一一对应，共三态：
    状态徽标「加入自定义灵魂库」「绑定…」
    尚未入库未加入灵魂库可点可点
    已在库、未绑定已在灵魂库置灰（重复加入无意义，与既有 book-analysis-character-panel.tsx:89 的 disabled={addingToSoul || !selectedSkill || selectedAuraAdded} 一致）可点
    已绑定已绑定「某某、某某」置灰仍可点（继续绑到更多人物）
  • 「加入自定义灵魂库」：只入库，不绑任何人。用于「生成了但暂时不想绑定」的角色。
  • 「绑定…」：打开绑定目标对话框（见下）。绑定成功后自动入库。
  • 按钮可用性由「有无可发布数据」决定，而不是 rules.length（见 5.1 表格）：无人格块但有 personalityProfile 的旧版角色（六维路径）照常可用；只有确实没有任何资料时才置灰，并在 title 里说明原因。

绑定目标对话框

  • 打开时调 listBindableNovelCharacters(projectPath)。
  • 列表为空 → 显示提示「请先在大纲中添加人物小传或人物设定，再绑定角色灵魂」（沿用 character-aura.ts:222 / use-library-operations.ts:157 的既有文案），确认按钮禁用。
  • 否则显示可勾选的人物清单（多选）＋ 该角色灵魂名，确认后逐一绑定，汇总 toast「已将「X」绑定到 N 个小说人物」；部分失败时如实报「成功 N，失败 M」。
  • 无障碍：role="dialog" + aria-label，焦点进入对话框。

合并与懒落盘

  • 加载时若非空，把 buildLegacyCharacterRevision(book) 的结果并入内存中的 revisions；已存在同 id（此前落过盘）则不重复添加。
  • 该条目的「确认并加入」：先 materializeLegacyCharacterRevision 落盘，再调原有 confirmWorkbenchRevision。落盘后重新加载列表，条目即成为普通条目。
  • 「加入自定义灵魂库」与「绑定」不需要落盘（动作层只依赖 projectPath 与条目本身），因此可以先行使用。

5.5 旧版分区收口修改

legacy-skill-results.tsx 去掉 characters 分支：skill === "characters" 时组件直接返回 null，只保留 style 与 story 两条分支。理由：旧版角色已作为新版条目出现在同一页签，保留旧版角色分区就是第三份列表。对应地，删除该文件对 BookAnalysisCharacterPanel 的引用与 characters 相关判定，其测试用例随之移除；style／story 的既有用例保持通过。

6. 数据流

【加入自定义灵魂库】
点按钮 → publishWorkbenchCharacter(projectPath, revision, item)
        → buildGeneratedAuraInputFromBookCharacter(character, skill, metadata)
        → createCustomCharacterAuraFromGeneratedSkill / updateCustomCharacterAura
        → refreshProjectState → 刷新徽标 → toast

【绑定】
点「绑定…」→ listBindableNovelCharacters(projectPath) → 勾选 → 确认
        → publishWorkbenchCharacter（自动入库，已存在则更新）  ← 需求 2(c)
        → 对每个目标名 bindCharacterAura({ characterName, auraId })
        → refreshProjectState → 刷新徽标 → toast

【旧版条目落盘】
点「确认并加入」→ materializeLegacyCharacterRevision → saveWorkbenchRevision
        → confirmWorkbenchRevision（原有路径，evidence 为空故校验通过）
        → 重新加载列表

7. 错误处理与边界

情形预期行为
角色无人格块，但有 personalityProfile（情况 Y，六维路径）条目保留，rules: []，卡片显示「旧版资料导入 · 无结构化规则」；按钮照常可用（走 5.2 的 aura-adapter 路径）
角色既无人格块也无任何资料条目保留，rules: []，徽标「无可用资料」，两个按钮置灰并在 title 说明

8. 测试策略

9. 风险与取舍

  • 迁移条目没有原文证据：旧版人格是 LLM 摘要，本就没有可回溯的正文偏移。因此迁移条目卡片上的「依据」为 0 条、覆盖为 0 章。这是如实呈现，不伪造证据。
  • 六维路径生成的 Skill 不含人格块（3.6）：迁移后这些条目的规则区是空的，卡片上不会有「N 条规则」。但绑定不受影响（走真实角色兜底）。代价是：同一页签里，简单提取的旧版角色有规则、六维的没有，看起来不一致——这是如实反映两种旧数据的差别，而不是遗漏。
  • 旧版富详情不再可见：四栏详情（性格/说话风格/动机/行为模式/台词）与代表台词不再显示。已确认接受。
  • 落盘后删除会重现：见 7 节，有意行为。
  • 旧版条目与新版条目在同一列表：靠 origin 标记区分，摘要行文案不同，不会混淆「已核验」与「旧版导入」。
  • 条目与源角色的关联靠名字：item.subject === character.name。这与 importBookAnalysisSkillsAsAuras 自身的做法一致（aura-adapter.ts:205），但如果作品库里出现同名角色，可能取到另一个。沿用既有代码的同一假设，不额外引入 ID 回链。

10. 验收标准

  1. 「角色 Skill」页签里，旧版角色以「旧版导入」条目出现，与新版条目同列表；不再有独立的旧版角色分区。
  2. 新版与旧版生成的每个角色条目都同时有「加入自定义灵魂库」与「绑定…」两个按钮。
  3. 六维路径生成的旧版角色（无人格块）也能正常加入灵魂库并绑定——即绑定能力不依赖于 portablePersonality 是否存在。
  4. 「加入自定义灵魂库」只入库、不绑定；「绑定…」完成后该角色灵魂已在自定义灵魂库中且已绑到所选人物。
  5. 无大纲人物时给出明确提示且不写数据。
  6. 角色「重要度」显示在 1–10 范围内（不再出现 100/10）。
  7. npx vitest run --dir src/components/novel 全绿；tsc -p tsconfig.app.json --noEmit 退出码 0；全量回归失败集合与基线逐文件一致。
  8. 真实浏览器几何检查 0 失败。
