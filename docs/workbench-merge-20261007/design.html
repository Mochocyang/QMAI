拆书库结果面板：版本合并与卡片按钮调整

设计文档 · 2026-10-07 · 承接「结果面板简化」那一轮

1. 这次要改的三件事

用户看到实际界面后提出三点，全部是视觉与信息密度问题，不涉及数据层：

  1. 版本合并：新旧版本的成果要排在一起，形成一份连续列表；新版本不再单独落在最下面。
  2. 按钮间距：每张卡上「修订」与「删除」两个图标按钮离得太远，应当紧挨着。
  3. 内容删除：版本标题行（2026/6/27 18:14 · 0章 · 2个对象 · 旧版导入）与「本次需求」折叠块都删掉。
已与用户确认的边界：第 1 条只合并对象卡。版本级内容 （原作结构观察导图、证据索引与实际覆盖、与上一版本的变化、补充修订） 仍然保留，但挪到合并列表之后，按版本顺序排列。 用户明确选择「保留版本级内容」而不是「只留对象卡」——证据索引这类可追溯信息不丢。

2. 为什么不能简单地「把卡片挪进一个网格」

当前结构是一个版本一个块，块内既有对象卡，也有版本级内容：

<section class="wb-revision-block" data-revision-id={revision.id}>
  <div class="wb-revision-heading">…版本标题行…</div>   ← 要删
  <WorkbenchResult>
    <details>本次需求</details>                          ← 要删
    <details>原作结构观察导图</details>                    ← 版本级
    <div class="wb-skill-grid">…对象卡…</div>            ← 要合并
    <section class="wb-rule-detail">…展开的规则…</section>
    <details>证据索引与实际覆盖</details>                  ← 版本级
    <details>与上一版本的变化</details>                    ← 版本级
    <div class="wb-revision-section">补充修订</div>        ← 版本级
  </WorkbenchResult>
</section>

直接合并会踩三个坑，设计必须逐一处理：

坑 1：卡片状态会串（同一个角色出现在多个版本里）

expandedSubject（哪张卡展开了规则）、expandedOverviews（哪张卡展开了概述）、 removingSubject（哪张卡要删除）现在是每个版本各存一份，且键只有对象名。 合并成一份列表后，两个版本里都有「许七安」——只用名字当键，点 A 版的「查看规则」会同时点亮 B 版。

修法：状态提到结果区，键改为 版本 id + 对象名 的复合键 （用 \u0000 连接，避免对象名里出现分隔符时误撞）。删除弹窗相应改为绑定「哪个版本的哪个对象」。

坑 2：活动跳转的锚点会丢

侧边栏点「查看结果」靠 [data-revision-id] 找到目标版本并 scrollIntoView。合并后如果锚点没了，跳转就会失效。

修法：每个版本仍然保留一个真实的、有高度的包裹元素并带 data-revision-id， 它就是该版本卡片组的容器。不用 0 高度占位元素，也不用 position:absolute （绝对定位的网格子项不参与网格布局，会落到容器原点，滚动位置就错了）。

坑 3：嵌套网格会破坏列宽与响应式对齐

若外层做成一个大网格、每个版本包成一个跨列子项，里层再套网格，那么两层网格的列宽与 断点必须完全一致，否则卡片对不齐。

修法（本设计采用）：不做嵌套网格。每个版本各自持有一个 .wb-skill-grid， 外层只用普通流式容器把它们竖向排列，并把版本之间的间距设成与卡片间距相同的 14px。 由于每个网格的列定义（repeat(3,…)/repeat(2,…)/1fr）与列间距完全相同， 且容器查询的容器都是 .book-workbench，相邻网格的列边界必然对齐 —— 视觉上就是一份连续列表。

3. 改动后的结构

<section class="wb-section wb-results-section">
  <div class="wb-results-bar">页签 + 视图切换（只有一份）</div>

  <div class="wb-card-list">                        ← 合并列表
    {orderedRevisions.map(revision =>               ← 旧版本在前（既有升序不变）
      <section class="wb-revision-block" data-revision-id={revision.id}>   ← 跳转锚点，保留
        <div class="wb-skill-grid" data-view={view}>{该版本的对象卡}</div>
      </section>)}
  </div>

  {orderedRevisions.map(revision =>                 ← 版本级内容，按版本顺序排在后面
    <RevisionExtras revision={revision} />)}        ← 导图 / 规则详情 / 证据索引 / 与上一版本的变化 / 补充修订
</section>

3.1 组件拆分

组件职责依赖
SkillCard一张对象卡：头像、名称+日期、状态徽标、概述、规则维度、页脚三按钮、灵魂库操作区。纯展示 + 回调。revision / item / 展开与删除回调
RevisionExtras一个版本的版本级内容：导图、展开的规则详情、证据索引、与上一版本的变化、补充修订（含日期标签）。自己持有 styleState（每版本一份的异步读取）。revision / previous / book / 修订回调
BookWorkspace持有 view、展开态、待删除态、正在补充修订的版本；渲染合并列表与版本级内容。store、revisions

拆分的意义：WorkbenchResult 原本同时管「卡片渲染 + 版本级内容 + 三种展开状态」， 合并后它必须裂开，否则状态无处安放。SkillCard 不再持有任何 state，因此 「同一个角色在两个版本里」这类问题在结构上就不会再出现。

4. 第 2 条：按钮挨在一起

现状 .wb-card-footer 是 justify-content:space-between，三个按钮被摊开： 「查看规则」最左、修订居中、删除最右。

改法：左侧「查看规则」不动，右侧两个图标按钮包进一个 <span class="wb-card-actions">，页脚改为 justify-content:space-between 保留，但右侧容器内部用 display:flex;gap:6px， 两个按钮自然紧挨。这样不依赖 margin-left:auto 之类的隐式行为，列表视图下也稳定。

间距取 6px：既明确区分两个按钮，又不会让人误以为是两个不同用途的分组。 真实浏览器里会实测这两个按钮的间距并断言（见 §6）。

5. 第 3 条：删掉标题行与「本次需求」

删掉版本标题行意味着 revisionMeta() 与 revisionOmittedCount() 成为死代码， 一并删除（noUnusedLocals 会直接编译不过）。

标题行承载的信息，逐项确认去处（不能悄悄丢）：
原信息去处
时间卡片名后已有短格式日期（10/7 09:03）；版本级内容那一组新增一个带年份的日期标签（本轮用户确认要）
N章「证据索引与实际覆盖」里本来就有「已读取N章、M个正文分段」
M个对象合并列表里直接数得出来
K项未采纳按条目仍可见（workbench-style-details.tsx:14 的「未采纳的候选（K项）」，需先展开该卡规则）；每版本合计不再显示
旧版导入卡片上已有 .wb-origin-tag（「旧版导入」/「旧版资料导入 · 无结构化规则」）
尚未入库卡片状态徽标已区分「已入库 / 待确认」；旧版版本不再显示徽标（见 §7.2）
因此删掉标题行不会丢失独有的**动作性**信息，只是把同一件事从「一行汇总」改回「各处就地显示」。
诚实修正：初稿把「K项未采纳」也写成「已由文风详情承接」，这不准确 —— 文风详情给的是**逐条目**的数量，而标题行给的是**整版合计**，后者现在确实没有任何地方显示。 判断：合计值只是概览，逐条目数量信息量更大，且用户明确要求删掉标题行，故不再补回； 但这条属于「确实不再可见」，不该被含糊带过。
实施后由独立对抗审查发现并已修复的缺陷（第二轮）
  1. 旧版版本永久显示「待确认」（用户可见的错误状态）。自动入库显式跳过 origin === "legacy"，工作台里也没有整版「确认并加入」入口，所以 legacy 版本的 confirmedAt 永远是 undefined —— 徽标就成了一个用户怎么操作都消不掉的假待办， 还与同一张卡片上的「旧版导入」自相矛盾（旧 revisionMeta 恰恰把 legacy 排除在 「尚未入库」之外）。已改为 legacy 不渲染状态徽标（来源由 .wb-origin-tag 说明）。
  2. 两条最关键的状态隔离用例是空洞的。审查用变异证明：
    • 「删除按钮作用于被点那一版」用例点的是 rev-old，而它恰好就是 orderedRevisions[0]，于是「永远删第一版」这种实现照样 69/69 全绿；
    • 卡片自身的展开态（aria-expanded）根本没被断言，把键退化成「只看对象名」 也照样全绿（界面上 B 版会错误显示「收起规则」）。
    已分别改为「点第二版删除」与「对两张卡都断言 aria-expanded」，并逐条重跑变异确认变红。
  3. 点另一版的「补充修订」会静默清空已输入内容（旧实现每版本各持一份草稿，合并后我用了单一字段）。 已改成按版本 id 存草稿 Record<revisionId, string>，并补用例。 同一条用例还暴露出：卡片上的笔只改状态、不聚焦（编辑器位于所有卡片之后，点它没有任何可见反馈）， 已改为由「编辑器是否打开」这一个信号统一驱动聚焦。
  4. 两个版本的版本级内容零间距，直接贴在一起，日期标签因此失去「分组标题」的意义。已加 18px 间距。
  5. harness 会把陈旧的 dist 一起注入，从而掩盖源文件的 CSS 回归（审查实测了漏报与误报两个方向）。 已在注入前钉死新鲜度：源 CSS 比 dist 新就直接失败，并明确「不自动构建」。

日期标签

版本级内容之后会出现 N 组长得一样的「证据索引 / 与上一版本的变化 / 补充修订」， 不标注就分不清归属。用户已确认要保留一个轻量标签：在「补充修订」那一行的左侧显示该版本的 2026/10/6 22:17（带年份，与卡片上的短格式区分开）。这是本轮唯一新增的可见元素。

实施中发现并修正的一处真实回归（设计→代码的偏差）：本节最初把「日期标签 + 补充修订按钮」 那一整段 .wb-revision-section 写成 display:flex。但该段下面还有 .wb-request（display:block，靠块级铺满整行）包着的补充修订输入框—— 一旦父级变成 flex 容器，它就从「铺满整行」变成「按内容收缩的 flex 项」，实测输入框宽度 从 1224px 掉到 180px，用户在补充修订时会看到一个被挤成一条缝的输入框。
修正：只把「日期标签 + 按钮」这一行包进新的 .wb-revision-head（flex）， .wb-revision-section 保持块级。
这一条已加入真实浏览器几何断言（见 §6.2），并做过变异验证：把段改回 flex 会让 6 个断点全部报红 （label 180px vs 段宽 1224px）。

6. 验证方案

6.1 单元测试（jsdom，house harness，先 RED 后 GREEN）

  • 合并列表：多版本渲染后，卡片在 DOM 顺序上必须是「版本从旧到新、版本内原顺序」，且所有卡片同处一个 .wb-card-list 内（防止只是看起来挨着、其实还是分块）。
  • 锚点保留：每个版本恰好一个 [data-revision-id]，跳转用例继续通过。
  • 状态不串：两个版本都含「许七安」时，点 A 版卡片的「查看规则」，只有 A 版出现规则详情，B 版没有；删除同理（弹窗删除的是被点那一版）。
  • 标题行与本次需求消失：.wb-revision-heading/.wb-revision-meta 不存在，正文不含「本次需求」。
  • 日期标签：每个版本的「补充修订」行上有带年份的日期。

6.2 真实浏览器几何（check-panel.mjs，Playwright）

  • 夹具改成合并布局（多个 .wb-revision-block，每个带自己的网格）。
  • 连续对齐：相邻版本第一张卡的左边缘必须与上一版本第一张卡对齐（同一列）， 且版本间纵向间距 == 卡片间纵向间距（证明「看起来是一份列表」不是巧合）。
  • 按钮相邻：修订与删除按钮的实测间距 ≤ 10px，且远小于「查看规则」到修订的间距 （证明是「挨着」而不是「都没了」）。
  • 既有的日期单行、不裁切、页脚三按钮不溢出、无横向溢出等断言全部保留。
  • 补充修订输入框必须铺满整行：夹具里让其中一个版本的补充修订处于展开态， 断言 .wb-request 宽度 == 该「版本级内容」段宽度（防止父级被误改成 flex 挤窄它）。
  • 空版本的空状态仍占满整行：合并列表里加一个没有任何卡片的版本，断言 .wb-no-results 的宽度 == 网格宽度（grid-column:1/-1 未被破坏）。

6.3 回归与反空洞

  • tsc -p tsconfig.app.json --noEmit 必须 exit 0（死代码删除的硬性检查）。
  • 全量套件 A/B（对照本轮改动前的 json）：新增失败文件必须为 0。
  • 对新守卫做变异验证（例如把复合键改回纯对象名、把间距改回 space-between）， 确认对应用例真的会红；改后按 SHA-256 还原。
  • 独立对抗审查（子代理）：专查「合并后是否有状态串、锚点失效、信息丢失、几何回归」。

7. 明确不做的事

  • 不动数据层：removedSubjects、publishedIds、删除与发布逻辑一行不改。
  • 不改渲染顺序不变式：loadWorkbenchRevisions 仍返回 createdAt 降序， 组件内仍单独升序排（既有注释警告过这条）。
  • 不合并同名角色（用户选择的是「只合并对象卡」，同一角色跨版本仍各显示一张，日期各不相同）。
  • 不新增除「日期标签」以外的可见元素。

7.1 一处连带的位置变化（已知并接受）

文风页的「启用此文风 / 此历史版本已被替换」工具条原先在版本块顶部，现已随版本级内容一起 挪到合并列表之后（它仍在该版本「版本级内容」的最上面，即紧接最后一张卡片）。 这是「版本级内容统一排到列表后面」的直接结果：工具条是版本范围的动作，不属于任何一张对象卡。 文风页通常只有一张卡，所以它看起来就像「卡片下面紧跟一个启用按钮」，未做额外处理。

7.2 两处刻意的行为变更

  • 规则详情改成手风琴：expandedCard 是单一槽位，所以在 A 版展开规则后去展开 B 版， A 版会收起（旧实现每版本块各有一个槽位，可同时展开）。合并成一份列表后同时展开两版会并排出现 两块长得一样的「XX · 完整规则」，反而更难分辨归属，故保留手风琴语义。
  • 旧版版本不显示状态徽标：理由见上方第二轮审查记录第 1 条。
