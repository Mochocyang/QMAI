### 1.3 `FILE_TYPE_ALIASES` 归错档隐患（丙必须一并处理）

### 1.9 遗留项结清（原乙批提出，归丙）：reasoning-only 终态文案的 RE 匹配**是承重的**

乙批收尾时留了一个未结清的疑点：`outline-chat-panel.tsx` 的
`OUTLINE_REASONING_ONLY_ERROR_MESSAGE`（`:396-397`）
> 「模型只输出了思考内容，没有输出正文。已关闭 reasoning 重试一次，仍未返回可用的大纲内容。」

**会**匹配 `reasoning-retry.ts:4` 的 `REASONING_ONLY_RESPONSE_RE`
（`/模型只输出了[\s\S]*思考内容[\s\S]*没有输出正文/`）。
而仓库对**同类**终态文案有**相反**的明文约定：
`analysis-model-call.ts:14-23` 的 `REASONING_ONLY_ANALYSIS_MESSAGE` 刻意写成
「没有**返回**正文」而**不是**「没有**输出**正文」，注释写明理由：

> 它**绝不能**匹配 `REASONING_ONLY_RESPONSE_RE`。因为上层（`agent/runner.ts:378`、
> `sources/outline-chat-panel.tsx:428`）都用同一个判定函数决定要不要再重试一次，
> 一旦匹配上，「已经关思考重试过的终态」会被当成可重试错误再重发一次整个 prompt，
> token 白白翻倍。

`analysis-model-call.spec.ts:198` 有专门用例钉住「不得匹配」。

**本次实读结清（结论：不是缺陷，但缺文档、且脆）**

1. **不会**产生多余重发。`.tsx:421-455` 的 `runOutlineAttemptWithReasoningRetry`
   本身就是「上层补一次重试」的唯一实现，且它**只在两处**被调用
   （`:3486` 发送路径、`:5803` 重新生成路径）。
   它在 `:434-436` / `:440-442` / `:447-453` 抛出的终态文案，
   **抛出后没有任何调用方会再调一次该 helper**：顶层的 catch（`:4363` 起）
   只把错误落到消息与 `failing` 状态（`:4373-4399`），不做重发。
   而 `runner.ts:374-391` 的那次重试有 `!isReasoningDisabled(...)` 守卫，
   也不可能被这个终态文案再次触发——该文案**从不**在 runner 轮内抛出。
2. **这个匹配是承重的**，不能随手改掉。`outline-chat-panel.tsx:4371-4372`
   在顶层 catch 里用 `isReasoningOnlyResponseError(err)` 判定
   `reasoningOnlyFailure`，据以强制 `showThinkingProcess: true`（`:4385`）。
   `:4383-4384` 的注释写明这正是「让用户明白**看着生成完了却没有结果**的原因」的机制。
   若把文案改成不匹配（照 `analysis-model-call` 的做法），
   `reasoningOnlyFailure` 会变 false → 用户看到「生成失败」却**看不到思考过程**，
   属于可见的体验回退。
3. 其余消费点检查过，均**不会**因此重发：
   `:3556` 与 `:5856` 判的是 `agentErrorBox.current`（runner 的错误），不是这条终态文案；
   `runner.ts:377/410` 判的是 `streamError`（轮内流式错误）；
   `deep-chapter-generation.ts:2137`、`analysis-model-call.ts:121/133` 与大纲面板无关。

**因此本项的正确处置不是改文案，而是补文档 + 钉测试**（照
`analysis-model-call.ts:17-22` 与 `analysis-model-call.spec.ts:198` 的先例）：

- 在 `OUTLINE_REASONING_ONLY_ERROR_MESSAGE` 上加注释，写明
  「**必须**匹配 `REASONING_ONLY_RESPONSE_RE`」及其承重点（`:4372` → `:4385`），
  并明确与 `analysis-model-call` 那条**相反的**约定——两者相反是因为
  `analysis-model-call` 的调用方会重试，而大纲面板这条的调用方把它当终态。
- 加一条 spec 钉住该性质（断言 `isReasoningOnlyResponseError(new Error(OUTLINE_...))` 为 `true`），
  使后来者改文案时会红，而不是悄悄丢掉思考过程展示。
- ⚠️ **时机**：`outline-chat-panel.tsx` 正被丙-2 修改中，
  该注释与 spec **放在丙-2 落地之后**做，避免与实现者并发改同一文件。

## 2. 方案

### 2.1 丙-1 数据层：不再把事件细纲存进大纲列表

**做法（三步，缺一不可）**：

1. **去掉生成侧的保存诱导**：`buildEventOutlinePrompt` 不再要求输出 `outlineSaveRequest` 围栏，
   只保留 `eventOutlineData` 一份围栏；删掉 `saveExample` 与 `:331-333` 里
   「保存归档靠它识别类型」的说明。
   → 生成结果只作为**对话消息 + 卡片**存在（已经在 `.qmai/outline-chats.json` 里持久化）。
2. **堵住两条保存通道**（兜底，防止手工/计划模式绕过）：
   - 自动：`handleAutoSaveOutlineRequests` 过滤掉 `fileType === "event-outline"` 的请求。
   - 手动：当消息内容能解析出事件细纲（`extractEventOutlineData(msg.content)` 非空）时，
     **不显示**「保存为大纲」按钮。卡片本来就已经算过这个值，复用即可，零额外成本。
3. **修 `FILE_TYPE_ALIASES`**：删掉 `"细纲": "event-outline"`，只保留 `"事件细纲": "event-outline"`。
   保留 `FILE_TYPE_FOLDERS["event-outline"]` 与 `hasEventOutlineStructure()`
   （读磁盘上**已存在**的旧文件仍需要它们）。

   #### ⚠️ 订正（2026-10-10，独立审查发现我先前两处说法是错的）

   **错话一**：本文件先前写「「细纲」恢复历史含义（17 节章纲）」。
   **实际代码不映射到任何类型**：`FILE_TYPE_ALIASES` 里没有 `"细纲"` 这个键，
   于是 `normalizeRequest`（`outline-save-request.ts:473`）拿到的仍是「细纲」，
   而它不在 `ALLOWED_FILE_TYPES` 里 → 整条请求**被拒**（报「不支持的大纲文件类型」），
   既不是 event-outline，**也不是 chapter-outline**。

   **错话二（更重要，它决定「能不能改成 chapter-outline」）**：不要试图把
   `"细纲"` 映射成 `chapter-outline` 来「恢复历史含义」。理由是硬性的：
   - `classifyOutlineSaveTarget` 的第一步是 `input.explicitFileType ?? …`（`outline-save-classifier.ts:139`）——
     **显式 fileType 会短路掉后面全部内容推断，包括优先级最高的 `EVENT_TYPE_MARK`**。
     所以一旦 `"细纲" → chapter-outline`，模型只要写 `fileType: "细纲"`，
     就绕过了事件细纲识别。
   - 而事件细纲**确实会带章纲关键词**：提示词里就有「本章目标字数：约 N 字」
     （`event-outline.ts:329`）与「必须要留下一个…**章尾钩子**」（`:338`），
     二者都在 `hasChapterOutlineStructure` 的关键词集
     （`本章目标|核心事件|场景顺序|章尾钩子|章首钩子`，`outline-save-request.ts:587`）里。
   - → 结果会是「事件细纲被落进 `章纲/`」，正是本分支要防的那一类串档
     （见 `outline-save-classifier.ts:46-50` 对后果的描述：
     `resolveChapterOutline` 会把它当 17 节章纲读走，隔离失效）。
   **所以「整条拒绝」是正确行为**，只需要把注释与文档说清楚，不要改代码去映射。
   `outline-save-request.spec.ts:1237-1257`（`§N` 分节）另有一个附带事实：
   `hasEventOutlineStructure` 的编号分节分支是 `^#{2,4}\s*\d+[.、]`，
   只认 `## 1.` 这种写法，不认模板的 `## §1`——两处描述对**不同标题风格**成立，
   注释里不要说成无条件成立。

4. **去掉计划模式里「可保存」的诱导**：`outline-plan-protocol.ts` 的
   fileType 白名单（`:394`）去掉 `event-outline`，**同时**把 `folderNames`（`:385`）
   里的「事件细纲」也去掉——用 `DEFAULT_OUTLINE_FOLDERS.filter((f) => f.id !== "event-outline")`。

   #### ⚠️ 订正（2026-10-10）：`folderNames` **不是**「可读/可引用的目录」

   本文件先前写「文件夹清单描述的是「可读/可引用的目录」，改它无必要」。**这是错的**：
   `folderNames` 在整个仓库里**只有一处使用**，就是 `:394` 那句
   「`plan.files` 的 `targetFolder` 只能用这些文件夹名」——它是一个**写盘白名单**。
   所以保留它等于**继续把 `事件细纲` 作为合法写入目标告诉模型**，
   而用户原话（主设计 §6 连带项）明确要求 `:385` 与 `:394` **两处一并撤掉**。
   → 本批改为**过滤掉**（不是改常量）。
   **`DEFAULT_OUTLINE_FOLDERS` 本身仍然不动**（`outline-workbench.spec.ts:13-24` +
   `:343` 守门项要求它保留「事件细纲」）：过滤发生在拼规则字符串的地方，
   常量与磁盘兼容性都不受影响。

   ⚠️ 这仍然**故意**打破 `outline-plan-protocol.spec.ts:352-358`，且因为过滤，
   该用例不能再断言 `toContain("事件细纲")`（那样会失败）——要改成
   **断言规则里不再出现 `event-outline`，也不再出现把「事件细纲」当写入目标的清单**，
   并保留「其余 8 个 fileType 一个都没被误删」的反向控制。

### 2.2b 丙-2b 确认后章节区就地生成正文

用户原话：「用户确认之后，**直接在章节区当中生成最新的章节内容**」。

**实测到的关键约束（这条决定了实现形态）**：正文生成的顶层入口
`runDeepChapterGeneration`（`deep-chapter-generation.ts:521`）
在**组件层没有任何直接调用方**——它只被注册成 agent 工具
（`use-agent-config.ts:155` → `tools/index.ts:118` → `run-chapter-workflow.ts:139`）。
也就是说，**今天生成正文必须经过一次 agent 回合**（模型决定调用 `run_chapter_workflow`）。

因此存在两条路（**已择定 (甲)**，见本节末的定案）：

- **(甲) 直接调用 `runDeepChapterGeneration`**：
  能从章节区直接生成，但需要自己拼出 `DeepChapterGenerationInput`
  与 `callbacks`/`deps`（`run-chapter-workflow.ts:139` 附近就是现成的拼法），
  并且要自己处理结果的落盘与草稿隔离（见 §3 第 1 条的草稿隔离约束）。
  这是**绕过 agent** 的路，能力最强、风险也最高。
- **(乙) 由章节区驱动已挂载的 `ChatPanel`（写作助手）**：
  ⚠️ **注意这与大纲那条路的关键差别**：章节区（`activeView === "wiki"`）挂载的
  正是 `ChatPanel`（`ui-test-workspace.tsx:116` 的 `mode === "chapter"` 分支），
  所以**面板是存在的**，不需要切视图——只是可能被折叠（`:76` 的 `assistantOpen`）。
  做法：章节区确认后，往 `ChatPanel` 注入一条「用这份细纲写第N章」的请求
  （照 `pendingReferenceTokens` 那种一次性队列先例，`outline-chat-store.ts:184/458-466`），
  必要时 `setChatExpanded(true)` 让它可见。
  这是**顺应现有架构**的路，改动小、与 agent 工具链天然一致。

**✅ 已定案（实读代码后）：走 (甲) 直接调用，且 (乙) 不满足用户诉求。**
详见《`docs/scratch-20261010-事件细纲流程-实施计划.md`》§2 步骤 5。

决定性事实：`runDeepChapterGeneration(input, callbacks, deps, signal)`
（`deep-chapter-generation.ts:521-531`）**本身与对话无关**——

### 4.2 ⚠️ 已知残留限制（**已评估，本批有意不修**，如实记录）

独立代码质量审查发现、经我方实读确认的一条**半修复**：

**症状**：在一个「事件细纲」会话里，若用户随后让 AI 产出**与该会话无关的交付物**
（例如「# 全书总纲」「# 世界观设定」），该交付物的**归类仍会被这个会话的对话措辞带偏**
——它不会被判成 `event-outline` 了（那是最严重的一条，已消除），
但会被判成 `chapter-outline`，于是确认框里的默认目标是 `章纲/`，
文件名退化成 `全书总纲.md`。

**成因（已实读）**：`collectOutlineSaveSourceHint`（`outline-chat-panel.tsx:2650-2664`）
会把「最后一条非内部用户消息」整条收进 hint，而事件细纲向导发的那条可见消息内容就是
「生成第N章事件细纲（M 个事件）」。摘掉「事件细纲」标记后，hint 里还剩「第12章」，
`resolveChapterOrVolumeType` 认 `第\d+章` → `chapter-outline`
（`outline-save-classifier.ts:141` 的 `inferFileTypeFromHint(sourceHint)` 在
`:144` 标题判定之前命中，把本该走 `:144`「全书总纲」→ `outline` 的路径短路了）。

**为什么不彻底修**：hint 层对「章纲/卷纲」这一族是**承重的**、
不能整体降级。`outline-save-classifier.spec.ts:110-119`
（「用户原话是章纲时，正文引用卷纲不能改判成卷纲」）就是靠它成立的：
该 fixture 的标题「第一次冷处理」与正文都推不出 chapter-outline，
去掉 hint 层会退化成 `outline`，直接打破这条既有契约。
要同时满足「当前轮的用户原话算数」与「上一轮生成的措辞不算数」，
需要把 hint **按轮次作用域化**（只取产出当前这条 assistant 消息的那一轮的 hint）——
那是一次独立的数据链路改造，**不属于丙-1 的修复范围**。

**为什么可以接受**：修复后该故障模式是
「默认归到 `章纲/`，但会弹出确认框、用户看得见也能改目标文件夹」，
不再是「被闸门**静默丢弃**」（修复前）或「归进 `事件细纲/`」（丙-1 之前）。
即从「静默且危险」降级为「可见且可纠正」。
且触发器是「在事件细纲会话里索要无关交付物」这一非典型用法。
