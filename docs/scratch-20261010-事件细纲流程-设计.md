### 1.3 `FILE_TYPE_ALIASES` 归错档隐患（丙必须一并处理）

`outline-save-request.ts:94-110`：
```ts
"事件细纲": "event-outline",
"细纲": "event-outline",   // ← 隐患
```
`:98-99` 的注释说明这是**本分支新加**的口径（「细纲」历史上指 17 节章纲）。

- **真实风险**：模型写 `fileType: "细纲"` 时，一本 17 节章纲会被归一化成 `event-outline`。
  内容闸门 `hasEventOutlineStructure()`（`:595-601`）**挡不住**它——
  该闸门只要求「有事件分节标记或编号分节」且「≥2 行列表」，而 17 节章纲的
  `## 1. 本章定位` 恰好是编号分节、且含大量列表项，**两者都满足**。
- ⚠️ **修正侦察报告的一处夸大**：`EVENT_TYPE_MARK` 的「劫持」说法**不成立**——
  它只在 `resolveChapterOrVolumeType()` 里作用于 `extractDocumentSubject()`
  （`outline-save-classifier.ts:58-66`），而后者**只取标题 + 首个 H1**，不读正文小节。
  所以「一份合法章纲只要正文出现『本章事件序列』就会被改判」是错的
  （`outline-save-classifier.spec.ts:218` 的反向守卫用例因此是**绿的**）。
  **丙不要按「已被劫持」这个前提去改。**

## 2. 方案

### 2.1 丙-1 数据层：不再把事件细纲存进大纲列表

**做法（三步，缺一不可）**：

1. **去掉生成侧的保存诱导**：`buildEventOutlinePrompt` 不再要求输出 `outlineSaveRequest` 围栏，
   只保留 `eventOutlineData` 一份围栏；删掉 `saveExample` 与 `:331-333` 里
   「保存归档靠它识别类型」的说明。
   → 生成结果只作为**对话消息 + 卡片**存在（已经在 `.qmai/outline-chats.json` 里持久化）。
2. **堵住两条保存通道**（兜底，防止手工/计划模式绕过）：
   - 自动：`handleAutoSaveOutlineRequests` 过滤掉 `fileType === "event-outline"` 的请求。
   - 手动：当消息内容能解析出事件细纲（`extractEventOutlineData(msg.content)` 非空）时，
     **不显示**「保存为大纲」按钮。卡片本来就已经算过这个值，复用即可，零额外成本。
3. **修 `FILE_TYPE_ALIASES`**：删掉 `"细纲": "event-outline"`，只保留 `"事件细纲": "event-outline"`。
   → 「细纲」恢复历史含义（17 节章纲），**归错档隐患随之消失**。
   保留 `FILE_TYPE_FOLDERS["event-outline"]` 与 `hasEventOutlineStructure()`
   （读磁盘上**已存在**的旧文件仍需要它们）。
4. **去掉计划模式里「可保存」的那半句诱导**：只把 `outline-plan-protocol.ts:394` 的
   fileType 白名单去掉 `event-outline`。
   **`folderNames`（`:385`）保持不动**——文件夹清单描述的是「可读/可引用的目录」，
   而磁盘上可能已有 `事件细纲/` 目录；改它既无必要，又会无谓地多破一条断言。
   ⚠️ 这会**故意**打破 `outline-plan-protocol.spec.ts:352-358`。该用例的前提
   （`:353-354`「AI 面向清单必须与已注册的 `FILE_TYPE_FOLDERS` 对齐」）本身因本批而**不再成立**，
   所以要**改写它的语义**（而不是删掉）：改为断言计划模式**不再**把 `event-outline`
   当作可保存类型，同时保留「事件细纲」文件夹名仍可被引用。

**为什么不删 `DEFAULT_OUTLINE_FOLDERS` 里的「事件细纲」**：`outline-workbench.spec.ts:13-24`
逐项钉死了那个数组（含「事件细纲」），且老项目磁盘上可能已有该目录；
保留它只影响「文件夹清单」，不影响「不再写入」这一行为。**改动更小、兼容更好。**

### 2.3 丙-3 卡片「重新修改」

用户原话：「用户可以手动去编辑，也可以让 AI 重新生成」。所以是**两个**动作：

- **AI 重新生成**：复用 `modelContent` 里的原始提示词重发（先例 `handleRegenerate` `:5476`），
  或复用「一次性修复」模式（`outlineRepairAttemptsRef` 限一次）。
  这条**不改数据结构**，风险低。
- **手动编辑**：这是**唯一**需要动数据链路的部分。因为卡片是「每帧从 `msg.content` 现算」，
  手改必须有一个可写落点。建议**最小方案**：
  在 `OutlineChatMessage` 上加一个可选字段
  （如 `eventOutlineOverride?: EventOutlineData`），
  渲染时 `override ?? extractEventOutlineData(msg.content)`；
  「用这份细纲写这一章」与将来的任何消费都读**同一个**取值函数，
  避免「界面里改过、模型不知道」的双份真相（正是 `:15-20` 注释担心的）。
  → 这样「双份真相」被**收敛到一个取值函数**，而不是散落在各处。
