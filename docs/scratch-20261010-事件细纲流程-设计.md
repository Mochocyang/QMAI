### 1.3 `FILE_TYPE_ALIASES` 归错档隐患（丙必须一并处理）

`outline-save-request.ts:94-110`：
```ts
"事件细纲": "event-outline",
"细纲": "event-outline",   // ← 隐患
```
`:98-99` 的注释说明这是**本分支新加**的口径（「细纲」历史上指 17 节章纲）。

  `## 1. 本章定位` 恰好是编号分节、且含大量列表项，**两者都满足**。
- ⚠️ **修正侦察报告的一处夸大**：`EVENT_TYPE_MARK` 的「劫持」说法**不成立**——

  **丙不要按「已被劫持」这个前提去改。**

## 2. 方案

### 2.1 丙-1 数据层：不再把事件细纲存进大纲列表

**做法（三步，缺一不可）**：

1. **去掉生成侧的保存诱导**：`buildEventOutlinePrompt` 不再要求输出 `outlineSaveRequest` 围栏，
   只保留 `eventOutlineData` 一份围栏；删掉 `saveExample` 与 `:331-333` 里
   「保存归档靠它识别类型」的说明。
   → 生成结果只作为**对话消息 + 卡片**存在（已经在 `.qmai/outline-chats.json` 里持久化）。
2. **堵住两条保存通道**（兜底，防止手工/计划模式绕过）：
   - 自动：`handleAutoSaveOutlineRequests` 过滤掉 `fileType === "event-outline"` 的请求。
   - 手动：当消息内容能解析出事件细纲（`extractEventOutlineData(msg.content)` 非空）时，
     **不显示**「保存为大纲」按钮。卡片本来就已经算过这个值，复用即可，零额外成本。
3. **修 `FILE_TYPE_ALIASES`**：删掉 `"细纲": "event-outline"`，只保留 `"事件细纲": "event-outline"`。
   → 「细纲」恢复历史含义（17 节章纲），**归错档隐患随之消失**。
   保留 `FILE_TYPE_FOLDERS["event-outline"]` 与 `hasEventOutlineStructure()`
   （读磁盘上**已存在**的旧文件仍需要它们）。
4. **去掉计划模式里「可保存」的那半句诱导**：只把 `outline-plan-protocol.ts:394` 的
   fileType 白名单去掉 `event-outline`。
   **`folderNames`（`:385`）保持不动**——文件夹清单描述的是「可读/可引用的目录」，
   而磁盘上可能已有 `事件细纲/` 目录；改它既无必要，又会无谓地多破一条断言。
   ⚠️ 这会**故意**打破 `outline-plan-protocol.spec.ts:352-358`。该用例的前提
   （`:353-354`「AI 面向清单必须与已注册的 `FILE_TYPE_FOLDERS` 对齐」）本身因本批而**不再成立**，
   所以要**改写它的语义**（而不是删掉）：改为断言计划模式**不再**把 `event-outline`
   当作可保存类型，同时保留「事件细纲」文件夹名仍可被引用。

**为什么不删 `DEFAULT_OUTLINE_FOLDERS` 里的「事件细纲」**：`outline-workbench.spec.ts:13-24`
逐项钉死了那个数组（含「事件细纲」），且老项目磁盘上可能已有该目录；
保留它只影响「文件夹清单」，不影响「不再写入」这一行为。**改动更小、兼容更好。**

### 2.2 丙-2 章节区就地生成事件细纲（**全流程在章节区**）

> ⚠️ 本节已按用户 2026-10-10 的决定**重写**。原方案（「按钮在章节区、生成仍发生在大纲会话」）
> 已被实测否定，理由见 §3 第 1 条。

- **增**：在 `preview-panel.tsx` 的 `actions` 数组里（`:1841-1861`）新增**一个**
  `ui-test-editor-action` 按钮，`aria-label` 用「生成章节细纲」，图标选一个与
  `WandSparkles`/`Type` 都不同的（**不要**复用 `Type`——`:118-141` 的 spec 要求
  一键排版块内图标恰好 1 个且为 `WandSparkles`；新按钮在自己的块里，但不要跨块串味）。
- 按钮打开 `EventOutlineWizardDialog`，默认章号取当前选中章节的下一章
  （复用 `resolveNextChapterNumber()` 与 `pickChapterLibraryFiles()`，与旧入口一致）。
- 提交后**在章节区**生成细纲：
  - 复用 `buildEventOutlinePrompt(request)` 这个**纯函数**产出提示词；
  - ⚠️ 模型调用必须走仓库既有封装（`.agents/AGENTS.md` 改动清单：
    「新增 LLM 调用是否走 `resolveNovelModel()`」）——**不要**自建调用、不要新开一条
    LLM 通路。实施前先在 `outline-chat-panel.tsx` 里找到它今天是怎么调的并复用同一条。
  - 结果需要一个**章节区的存放点**（新 store 槽位或现有 store 加字段），
    保存 `{ chapterNumber, request, content, status }`。

### 2.2b 丙-2b 确认后章节区就地生成正文

用户原话：「用户确认之后，**直接在章节区当中生成最新的章节内容**」。

**实测到的关键约束（这条决定了实现形态）**：正文生成的顶层入口
`runDeepChapterGeneration`（`deep-chapter-generation.ts:521`）
在**组件层没有任何直接调用方**——它只被注册成 agent 工具
（`use-agent-config.ts:155` → `tools/index.ts:118` → `run-chapter-workflow.ts:139`）。
也就是说，**今天生成正文必须经过一次 agent 回合**（模型决定调用 `run_chapter_workflow`）。

因此只有两条路，**实施前必须择一并说明理由**：

- **(甲) 直接调用 `runDeepChapterGeneration`**：
  能从章节区直接生成，但需要自己拼出 `DeepChapterGenerationInput`
  与 `callbacks`/`deps`（`run-chapter-workflow.ts:139` 附近就是现成的拼法），
  并且要自己处理结果的落盘与草稿隔离（见 §3 第 1 条的草稿隔离约束）。
  这是**绕过 agent** 的路，能力最强、风险也最高。
- **(乙) 由章节区驱动已挂载的 `ChatPanel`（写作助手）**：
  ⚠️ **注意这与大纲那条路的关键差别**：章节区（`activeView === "wiki"`）挂载的
  正是 `ChatPanel`（`ui-test-workspace.tsx:116` 的 `mode === "chapter"` 分支），
  所以**面板是存在的**，不需要切视图——只是可能被折叠（`:76` 的 `assistantOpen`）。
  做法：章节区确认后，往 `ChatPanel` 注入一条「用这份细纲写第N章」的请求
  （照 `pendingReferenceTokens` 那种一次性队列先例，`outline-chat-store.ts:184/458-466`），
  必要时 `setChatExpanded(true)` 让它可见。
  这是**顺应现有架构**的路，改动小、与 agent 工具链天然一致。

**倾向 (乙)**，因为它复用了已被验证的正文生成链路（含审稿返修、字数控制、草稿隔离），
而 (甲) 等于把 `run_chapter_workflow` 的职责重新实现一遍。
但 (乙) 有一个必须实测确认的点：**生成的正文是否会自动落到当前章节**，
还是只作为聊天消息出现、需要用户再手动采纳。若只是聊天消息，
那就不满足用户「直接在章节区生成最新的章节内容」——这时要么补一个「写入本章」动作，
要么改走 (甲)。**实施前必须先确认这一点，不要猜。**

### 2.3 丙-3 卡片「重新修改」

用户原话：「用户可以手动去编辑，也可以让 AI 重新生成」。所以是**两个**动作：

- **AI 重新生成**：复用原始请求重发（先例 `handleRegenerate` `outline-chat-panel.tsx:5476`）
  ——在章节区则是重新调用 §2.2 那条生成通路，把 `status` 置回 `generating`。
  这条**不改数据结构**，风险低。
- **手动编辑**：这是**唯一**需要动数据链路的部分。

- 编辑 UI：复用 `event-outline-wizard-dialog.tsx` 的字段风格；表单字段与
