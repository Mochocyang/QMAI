## 1. 乙-1 · 修文风生成失败

### 1.1 根因

用户实测报错（原文）：

```
分析失败：模型只输出了 17,331 字符的思考内容，但没有输出正文。这通常表示接口触发了
思考 token 上限、模型没有从思考阶段切换到正式回答，或当前兼容接口的流式输出不完整。
请关闭模型思考、切换到非推理模型，或缩短输入后重试。
```

该文案来自 `llm-client.ts:870-885`：**流正常结束**、一个正文字符都没吐、
思考字符 ≥ 200 时抛出的诊断错误。

仓库里**已经**有应对它的机制——`reasoning-retry.ts` 的
`isReasoningOnlyResponseError()` / `withReasoningDisabled()`，做法是
「丢掉已收内容 → 关掉思考 → 整轮重发」：

| 调用方 | 是否接了重试 |
|---|---|
| `agent/runner.ts:374-391` | ✅ 接了 |
| `sources/outline-chat-panel.tsx:417-438` | ✅ 接了 |
| `lib/novel/deep-chapter-generation.ts:2137-2144` | ✅ 接了 |
| **`lib/novel/book-analysis/**` 全部 8 个文件** | ❌ **一处都没接** |

以文风为例，`style-analysis-adapter.ts:110-127`：

```ts
async function callStyleModel(
  messages: ChatMessage[],
  llmConfig: Parameters<typeof streamChat>[0],
  signal: AbortSignal,
  onRequestTrace?: (trace: LlmRequestCacheTrace) => void,
): Promise<string> {
  let output = ""
  let streamError: Error | null = null
  await streamChat(llmConfig, messages, {
    onToken: (token) => { output += token },
    onDone: () => {},
    onError: (error) => { streamError = error },
    onRequestTrace,
  }, signal, { reasoning: llmConfig.reasoning })
  if (signal.aborted) throw new Error("用户取消文风分析")
  if (streamError) throw streamError
  return output.trim()
}
```

它把 `{ reasoning: llmConfig.reasoning }` 原样传下去，**抛错就一路往上冒**。
于是用户那种「模型思考 17K 字符不切换成正文」的情况必然失败。

### 1.2 为什么不能修在 `streamChat` 里（重要）

`llm-client.ts` 内部确实有两处 `withReasoningDisabled`，但它们**都救不了这个错**：

| 位置 | 处理的是什么 | 为什么覆盖不到本问题 |
|---|---|---|
| `:304-314` | 请求**发出前**：上一轮 tool-assistant 思考无法回放时先关思考，避免 400 | 属请求侧预防 |
| `:669-692` | 请求**被接口拒绝**（reasoning content required）时关思考重发 | 属 HTTP 错误重发 |

而本问题是「**请求成功、流干净结束、只是内容全在思考里**」——只有流结束后才判定得出
（`:870-885`），**无法在 `streamChat` 内部重试**，因为重试等于重跑整个函数。
这正是 `runner.ts` 把重试放在调用方、并且要**先重置已累积文本**的原因。

结论：**不要**把重试塞进 `streamChat`。否则会与 `runner.ts` 自己的重试叠成
双重重试（重发整个 prompt，token 翻倍），并把诊断错误对所有调用方隐藏。

### 1.3 方案：抽一个共享的一次性文本调用

新增 `src/lib/novel/book-analysis/analysis-model-call.ts`：

```ts
import { streamChat, type ChatMessage } from "@/lib/llm-client"
import { isReasoningDisabled, isReasoningOnlyResponseError, withReasoningDisabled } from "@/lib/reasoning-retry"
import type { LlmRequestCacheTrace } from "@/lib/llm-request-trace"

/** 与既有 adapter 一致：直接取 streamChat 首参类型，不另引 LlmConfig。 */
type AnalysisLlmConfig = Parameters<typeof streamChat>[0]

/** 思考被关掉、重试一次仍拿不到正文时的终态文案。 */
export const REASONING_ONLY_ANALYSIS_MESSAGE =
  "模型只输出了思考内容，没有返回正文；已关闭思考重试一次仍未成功。" +
  "请换用非推理模型，或缩小分析章节范围后重试。"

/**
 * 拆书库统一的一次性文本调用。
 *
 * 存在理由：模型可能把预算全烧在思考上、一个正文字符都不吐（llm-client 会抛
 * 「模型只输出了 N 字符的思考内容」）。这条流在 HTTP 层没有错，所以 llm-client
 * 内部那两处 withReasoningDisabled（请求前置降级 / 请求被拒重发）都覆盖不到它，
 * 必须在调用方「丢掉已收内容、关掉思考、整轮重发」。
 * agent runner 与大纲链路各自实现了同一件事，这里是拆书库的第三份，故抽出共享。
 */
export async function callAnalysisModelText(
  llmConfig: AnalysisLlmConfig,
  messages: ChatMessage[],
  signal: AbortSignal,
  onRequestTrace?: (trace: LlmRequestCacheTrace) => void,
): Promise<string> {
  const attempt = async (reasoningOff: boolean): Promise<string> => {
    let output = ""
    let streamError: Error | null = null
    await streamChat(llmConfig, messages, {
      onToken: (token) => { output += token },
      onDone: () => {},
      onError: (error) => { streamError = error },
      onRequestTrace,
    }, signal, reasoningOff
      ? withReasoningDisabled({ reasoning: llmConfig.reasoning })
      : { reasoning: llmConfig.reasoning })
    if (signal.aborted) throw new Error("用户取消分析")
    if (streamError) throw streamError
    return output.trim()
  }

  try {
    return await attempt(false)
  } catch (error) {
    const first = error instanceof Error ? error : new Error(String(error))
    // 只在「确实是思考-only」且「原本没关思考」时才值得重发整个 prompt。
    if (signal.aborted || !isReasoningOnlyResponseError(first) || isReasoningDisabled(llmConfig)) {
      throw first
    }
    try {
      return await attempt(true)
    } catch (retryError) {
      const second = retryError instanceof Error ? retryError : new Error(String(retryError))
      if (isReasoningOnlyResponseError(second)) throw new Error(REASONING_ONLY_ANALYSIS_MESSAGE)
      throw second
    }
  }
}
```

三个要点：

1. **只在原本没关思考时重试**（`isReasoningDisabled` 守卫），否则重发一份一模一样的请求。
2. **每次 attempt 重置 `output`**，不复用上一轮已收的半截思考。
3. **缓存键天然隔离**：`analysis-result-cache.ts:99-101` 把 reasoning 模式纳入缓存键，
   所以「关思考」这次是独立条目，不会把失败结果缓存住。

  它们与本次改动是同一块空态，属于「在工作中的代码里做有针对性清理」。

## 4. 已知取舍

- **重试会让失败请求发两次**。这是刻意的：思考-only 的根因在模型侧，重发一次远比
  让用户对着文献级输入反复手点「重试」便宜。守卫（原本已关思考则不重试）挡住了
  无意义的第二次。
- **不做流式续跑**。更省的做法是「保留思考、追加一句『请直接输出正文』继续同一轮」，
  但兼容接口的续轮语义不可靠（`reasoning-retry.ts:10-13` 已经记录过
  DeepSeek `reasoning_content` 空串无法续轮），所以选整轮重发。
- **本批不碰文风在上下文里的优先级**。文风画像在 `FIELD_PRIORITY` 里排 19、
  超预算第一个被裁（`context-engine.ts:62`）——这是「甲」的范围。本批只保证**能生成出来**。
- **不把 `WritingStylePreset` 转成 `UserSkill`**（「丁」）。本批不动技能库。
- **第一批为事件细纲加的保存类型本批不删**。虽然用户的意图是「不再存大纲库」，
  但真正会主动出错的只有两处（`FILE_TYPE_ALIASES["细纲"]`、
  `outline-save-classifier.ts:66/:83` 的 `EVENT_TYPE_MARK` 优先判定），
  而它们要连同入口搬家一起处理才不会留下半截状态——放「丙」一并做，见 §6。

## 5. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 8 处委托漏改，用户换个功能又踩 | 加源码级守卫断言（§1.5 第 9 条） |
| 重试引入双倍 token 消耗 | 只在思考-only 且原本未关思考时触发；有单测钉住「只调 1 次」的几个分支 |
| `defaultSkills` 引用不稳导致勾选被重置 | 用模块级常量 + 专门测试（§2.4 第 5 条） |
