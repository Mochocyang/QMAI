QMAI · 功能诊断报告

剧情推演功能：为什么用不起来，以及它应该长在哪里

基于对 QMAI-main（v4.3.1，剧情推演室 22,730 行）与参考实现 MiroFish-main 的源码直读对比

结论速览

  1. 引擎没问题，是强的。信息不对称（observableBy）、谣言传播（失真度/代数/可信度）、导演 Agent 七维评分、分支管理——这四样 MiroFish 一样都没有。问题不在模拟内核。
  2. 真正的病因是「工作单元不匹配」。推演的最小单位是「一个 4~8 节点框架 → 1~5 万字 → 4~8 章」，一次跑 100~180 次串行 LLM 调用、5~15 分钟、无成本确认。而写手坐在第 47 章时的问题是「A 该不该现在告诉 B」，那是一个场景问题。用整个卷级仿真去回答单场景问题，成本与收益差着两个数量级。
  3. 产物没有座位。SimulationReport / StoryDraft 与大纲 store 零耦合：报告只能导出 .md，草稿只能整章导入 wiki/chapters/，branch.summary 与 keyEvents 没有任何通往章纲「§5 核心事件链」或事件细纲 events 的通路。写手拿到一份文档，却没法把它变成稿子。
  4. 最讽刺的一点：整个房间里最实用、最贴写作现场、唯一带成本护栏的功能（舞台情景，阈值 40 条），被关在了这个房间最深处。它本该在章节编辑器的选区浮动条上，和「续写 / 润色 / 去AI味 / 生成章节细纲」并排。
  5. MiroFish 最值得抄的不是模拟，是「世界可被追问」。它 5 步流程的终点是深度互动：可以随时采访任意 Agent，ReportAgent 带 4 个工具去调查图谱（每章至少 3 次工具调用、必须引用 Agent 原话）。QMAI 的报告是一次 LLM 出的 JSON，是终点不是入口；更糟的是，打开历史结果时角色采访与生成草稿被显式禁用（simulation-report-view.tsx:599-600,622-623）。

调用量的算法是：3 + N×R×A×[1~3] + 反应链 + 2×轮(embedding) + N(导演) + 1(报告) + N(草稿)。其中 N=calcNodeCount(targetWords)（types.ts:388-392）、R=round(baseRounds×roundsMultiplier)（simulation-engine.ts:1177-1179）、A=ceil(候选角色×agentSubsetRatio)（multi-agent-orchestrator.ts:237），每个角色回合最多 3 次 LLM 往返（simulation-engine.ts:1082）。

成本护栏的缺口是真实的、且不对称的

02MiroFish 与剧情推演：逐项差异

先纠正一个前提：两者根本不是同一类东西

MiroFish 是社会舆论模拟，不是叙事推演。它的本体生成 prompt 明确写着「社交媒体舆论模拟」，硬性要求正好 10 个实体类型、必须含 Person/Organization 兜底，并显式排除抽象概念与「支持方/反对方」式立场（ontology_generator.py:48-73,113-126）。人物被降维成「可以在 Twitter / Reddit 发声的账号」，推演动作是 CREATE_POST / REPOST / FOLLOW / CREATE_COMMENT / SEARCH_POSTS（run_parallel_simulation.py:178-202），报告 prompt 仍是「未来预测报告」（report_agent.py:552-556）。

全仓库代码里没有任何 novel/story 分支、prompt 或路由；小说只是通用管线的一种种子文档，而《红楼梦》demo 之所以成立，是因为它被当成了「一个包含大量人物的社会系统」来模拟。所以：你当年参考它的「想法」是对的，但它的实现里真正能迁移到小说创作的部分，比你以为的少得多。

2.2 差异的本质：两种产品哲学

MiroFish = 探索式沙盘

世界的价值在于被观察和被追问。

  • 跑得贵（~5$/次），但跑在后台，你可以走开
  • 报告是带工具的调查结果，引用原话、有出处
  • 终点是「和任意角色对话」，报告只是入场券
  • 没有分支——因为它不需要，它是一个社会趋势预测器，不是叙事生成器

QMAI 剧情推演 = 批处理产线

世界的价值在于产出一份可以用的稿子。

  • 跑得更贵（100~180 次串行调用），却在前台阻塞
  • 报告是一次性的格式化 JSON，不可追问
  • 终点是「导入到章节库」——但它只是把草稿写进文件，没有回写大纲
  • 有分支——因为它的目标确实是叙事，但分支没有下游

关键错位

你把 MiroFish 的沙盘世界观搬了过来，却给它配了一套产线的交付方式。结果是要么没人用（因为产线的入口太深、太贵、太慢），要么用了也接不住（因为产物落不进大纲，只落成一份 md）。

03病因：五个不匹配

不匹配一：工作单元 vs 写作循环的尺度

推演的最小单元是「4~8 个节点、1~5 万字、4~8 章」——那是一卷。而软件里被验证过的高频功能，工作单元全都是一章、一节、一段甚至一个选区：事件细纲是「一章一批 4~8 事件」（event-outline.ts:15-16），章纲是 17 节，选区工具条是「选中一段 → 润色」。

写手一天的循环是「写这一章 → 提取记忆 → 看审查 → 写下一章」。剧情推演不在这个循环上的任何一点。它要求用户从连载节奏里抽身，去回答一个卷级问题，然后在 15 分钟后回来面对一份可能已经过时的报告。

不匹配二：产物 vs 数据模型的位置

实测：src/stores/ 下没有任何 outline / chapter store 引用 story-simulation。报告页只有「导出报告 / 重新推演 / 生成草稿 / 角色采访」四个出口（simulation-report-view.tsx:567-586），没有「落到大纲」。

而软件里所有被验证过的 AI 产出，走的都是同一条路：outlineSaveRequest 三件套（content + htmlContent + structuredData，outline-save-request.ts:39-51）→ 分类型落盘 → 树里可见 → 可 @ 引用 → 可被下游交叉校验。剧情推演的产出完全不走这条路。

不匹配三：成本姿态 vs 用户耐受

100~180 次串行调用意味着 5~15 分钟墙上时间，且没有任何预告。对比软件里另外两个「长任务」的待遇：拆书库有后台任务卡（app-layout.tsx:147-215），让你离开现场、完成弹卡；舞台情景有请求数预估和确认勾选。推演是唯一一个「又贵、又慢、又在前台、又不说要多久」的功能。

不匹配四：结构冗余

软件里已经有三套结构在描述「剧情该怎么走」：

  • 卷纲：10 故事 × 10 环节矩阵（volume-outline-template.ts）
  • 章纲：17 节，含 §5 核心事件链、§7 四段式、§8 情绪曲线（chapter-outline-template.ts:15-81）
  • 事件细纲：一章一批 4~8 事件（event-outline.ts:30-56）
  • 加上拆书来的 PlotFramework：钩子→铺垫→爽点→结尾钩子，带版本历史（plot-framework.ts:44-99）

剧情推演的 StoryNode（起承转合 4~8 节点）是第五套。它既不消费上游（不读卷纲/章纲），也不服务下游（产出不回写），只靠 frontmatter 里的 framework_id 做单向软关联。用户没有任何理由去学第四套剧情结构语言。

不匹配五：绑定只是陪跑，不是约束

当前的绑定注入只渲染一句话式的内容：

# 故事框架绑定 - 框架标题：… - 目标章节数：… ## 章节分配 - 第3-5章 → 【承】节点标题 ## 要求 - 请严格遵循上述故事框架推进剧情… （framework-binding.ts:105-132）

它作为 priority 19 的数据源塞进系统提示（context-data-sources.ts:516-527），随后被 context-engine.ts:36-68 的 FIELD_PRIORITY 参与裁剪——可能被裁掉，且不参与任何校验。章纲生成不知道它的存在，chapter-plan-compliance.ts 的偏离检测也不检查它。它是一条建议，不是一条轨道。

04优化方向

一条总原则

不要新造工作单元，把同一个引擎按四种粒度重新包装，每一档都插进已有的写作现场，每一档的产物都落回已有的数据结构。引擎（simulation-engine.ts、multi-agent-orchestrator.ts、谣言、导演）不动——它已经是这个软件里最有技术含量的部分。

这一改造的核心动作其实只有一句话：把「舞台情景」从推演室里搬出来，放到它本来该在的地方。它已经是场景级推演、已经带成本护栏、已经能插入章节（scenario-importer.ts）、已经能选角色和主持人。它唯一的毛病是长错了位置。

方向 B P0 报告从「终点」改成「可追问的调查」

照抄 MiroFish 最值钱的那部分：

  • 报告 Agent 带工具：给 simulation-report-agent.ts 挂上查询能力（查某角色完整轨迹 / 查某条谣言的全部传播代际 / 查某轮全部事件），像 MiroFish 那样每章至少若干次工具调用、必须引用角色原话。现在的「一次 LLM 出 JSON」换不来任何有出处感的结论。
  • 历史结果必须可追问：删掉 simulation-report-view.tsx:599-600,622-623 那两行对 onInterviewAgent / onGenerateDraft 的置空。这是纯粹的自我阉割——一份三天前的报告，恰恰是最需要被追问「当时 XX 为什么这么做」的。
  • 时间线可点、可问：SimulationHistoryEntry 与播放控制（isPlaying / playbackSpeed / historyIndex）已经存在，把它从调试面板提升为正式视图，点任意事件就能问当事角色。

方向 C P0 成本与时间真实化 + 后台化

  • 预估与确认：把 SCENARIO_COST_WARN_THRESHOLD 的做法推广到主推演，在配置页实时显示「本次约 N 次模型调用，预计 M 分钟，建议使用 X 模型」。用户有权在为 180 次调用付钱之前知道这件事。
  • 并发化：三层循环里，同一轮内的角色决策之间没有依赖——它们读的是黑板快照、写的是事件。这一层可以 Promise.all，墙钟时间直接除以角色数。这是投入产出比最高的一处改动。
  • 后台化 + 任务卡：复用 app-layout.tsx:147-215，让推演离开现场跑，完成弹卡。story-simulation-store 加 persist，别让刷新毁掉世界。

方向 D P1 绑定从「建议」升级为「轨道」

  • 章纲生成时读取绑定，把节点目标/核心冲突写进 §3 本章定位与 §5 核心事件链。
  • chapter-plan-compliance.ts 的偏离检测纳入绑定校验：定稿章纲偏离节点目标时报警。
  • 反向回写：章纲定稿后，把实际发生的事回写进框架节点，让下次推演知道「这里已经定稿了，别再推翻」。
  • 把 storyFrameworkBindingDataSource 的 priority: 19 调整或标记为不可裁剪——一条会被 context 预算裁掉的约束，不构成约束。

方向 E P1 治理与度量

  • 补 feature 埋点：现在只有全局 /open、/heartbeat、/close（analytics.ts:15,76-105）。四档粒度上线后，哪一档有人用、跑到哪一步放弃，必须能量出来。不度量就无法判断这次改造是否有效。
  • 去掉 BETA：功能已经跑了十多个版本（changelog 从 3.0.0 到 4.3.1），一直挂着 BETA 角标（icon-sidebar.tsx:113-117）等于告诉用户「别指望它」。要么去掉，要么明确说清「哪一档是稳定的、哪一档还是试验」。
  • 术语瘦身：174 个 i18n key、4 种模式、14 种行为类型、3 种可见性、7 个导演维度、6 个工具。这些多数应该是引擎的内部实现，不该出现在用户要做的选择里。默认值 + 一句人话就够。

05实际应用：在大纲和章节里具体怎么用

下面六个场景，每一个都标注了：从哪进、给什么、出什么、花多少。共同点是不切视图、产物落进已有结构、用户随时可以拒绝。

5.1 在大纲里

场景 1 · 卷纲阶段：把「10 故事 × 10 环节」当作推演输入

从哪进
卷纲编辑器的「推演这一卷」按钮（新入口；不再是「读最近 N 章正文」）
输入什么
当前卷纲的矩阵（10 故事 × 10 环节）+ 本卷出场人物表 + 用户一句话想法。不再需要重新提取角色——卷纲里已经有了。
产出什么
每个「环节」下的 2~3 条走法；每条带角色行为与动机。一键写进对应故事的环节格，而不是落成一份独立报告。
替代了什么
现在的 StoryFramework 起承转合四节点——卷纲的 10×10 结构比它细得多，也已经是用户在用的语言。

场景 2 · 章纲阶段：「如果 A 在这里选了 X 而不是 Y」

从哪进
章纲编辑器（17 节卡片流）的工具栏按钮；也可从 AI 大纲会话一句话唤起
输入什么
本章章纲（尤其 §5 核心事件链与 §14 出场人物变化）+ 一个岔路口问题。用 @ 引用把相关记忆库、伏笔、上一章正文一起带进来（推演配置面板现在无法 @，这是接入既有范式的直接收益）
产出什么
3 条候选事件链，各带因果链与埋/收伏笔位置 → 用户挑一条 → 直接写回 §5 → 章纲的偏离检测后续会拿它做基准
规模
本章出场角色（通常 3~5）× 2 轮 ≈ 20~40 次调用，后台跑 1~3 分钟

场景 3 · 人物弧光体检：把导演 Agent 的七维变成待办

从哪进
卷纲完成后的「卷体检」，或审查中心的新检查项
输入什么
整卷章纲序列 + 人物出场表
产出什么
导演 Agent 已经在算 characterUtilization（角色利用率）与 characterArc（角色弧光）。把这两个维度从推演过程中的副产品，提升为卷级报告的两条结论：「角色 X 在故事 4-7 出现 12 次但零弧光推进」→ 落成审查中心的待办项
为什么值
这是只有多 Agent 模拟能给、而人写不出来的结论。它真正对应连载作者的实际焦虑：某个角色是不是被写废了。

5.2 在章节里

场景 4 · 写之前：事件细纲的「先演一遍」

从哪进
事件细纲卡片（event-outline-card.tsx）上、「用这份细纲写这一章」旁边加一枚「先推演一遍」
输入什么
当前细纲的 4~8 个事件 + 本章出场角色
产出什么
角色在这几个事件里的实际反应，暴露「这个事件站不住」或「这两个角色不会这样说话」→ 直接改细纲卡片上的事件，或重新生成
为什么值
它插在「生成细纲 → 确认 → 写正文」这条已经被验证的高频链路上，而不是另起一条链路。用户不需要学任何新概念。

场景 5 · 写之中：选区推演，救一段僵住的对话 最高频

从哪进
编辑器选区浮动条——就是现在「续写 / AI润色 / 去AI味」那一排（wiki-editor.tsx:601-642）
输入什么
选中一段对话 + 一句话意图（「我要 B 在这里察觉到不对劲，但不能说破」）
产出什么
3 条候选走法（不同角色的不同反应）→ 对比窗挑一条 → 插入或替换
规模
2~3 角色 × 1~2 轮 ≈ 6~15 次调用，30 秒内出结果
本质
这就是舞台情景，搬到它该在的地方。已有：角色选择、主持人、情景规则、成本护栏（阈值 40）、插入章节。缺的只是一个入口位置。

场景 6 · 写之后：把成稿丢回去，问「接下来最可能发生什么」

从哪进
章节编辑器的「推到下一章」，或章节记忆提取完成后的建议卡
输入什么
本章定稿正文 + 当前角色状态（记忆提取刚刚更新过）
产出什么
各角色「接下来最可能做什么」→ 作为下一章事件细纲的候选钩子，写进章纲 §14 交接或新细纲的第一个事件
为什么值
它把推演从「开写前的一次性投资」变成了每章收尾时的一次例行动作——这才是让使用率上去的机制。
