大纲 HTML 全覆盖

修复「保存框的 HTML 选项被置灰」与「从大纲继续生成的内容没有 HTML」；确立「任何大纲类型都必须能出 HTML」的保证

1. 现象

  • 保存确认框里「HTML 形式（.html）」是灰的，下面写着「本轮未生成 HTML 版本，无法保存 HTML。」—— 该提示由 outline-save-confirm-dialog.tsx 在 requests.some(r => r.htmlContent?.trim()) 为假时显示。
  • 从大纲继续生成的内容没有 HTML：先生成大纲，界面推荐「接着生成章纲」，从这条路径生成出来的章纲保存时同样没有 HTML。

2. 根因

根因（已用最小复现证实）：attachOutlineHtml（src/lib/novel/outline-save-request.ts） 对 chapter-outline / volume-outline 存在**两条短路分支，方向恰好是反的**。 
if (request.fileType === "chapter-outline") {
  const rendered = attachChapterOutlineHtml(request, text)
  if (rendered.htmlContent) return rendered
  // 正文「确实像章纲」→ 直接返回，不带 HTML  ← 真正的章纲落到这里
  if (isLikelyChapterOutline(request.content, request.fileName ?? "")) return rendered
  // 只有正文「不像章纲」时才兜底渲染        ← 分类错误反而有 HTML
  return borrowSettingFamilyHtml(request, text) ?? rendered
}

attachChapterOutlineHtml / attachVolumeOutlineHtml 都**依赖可解析的结构化 JSON** （chapterOutlineData / volumeOutlineData）。AI 只给 MD、或 JSON 缺字段解析失败时， 它们原样返回请求 —— 不带 htmlContent。

于是「像章纲但没有结构化数据」这一最常见的失败组合，得到的正是**空 HTML**；而 borrowSettingFamilyHtml 这个兜底只在「正文不像章纲」时才跑。

2.1 为什么「从大纲继续生成」这条路径必然撞上它

卷纲/章纲的结构化数据由专门的校验环节把关：解析不出数据、或数据不完整时， 面板会**自动补全一次**（validateChapterOutlineData → 重发提示词）， 仍失败才放行保存。放行保存的那一刻，结构化数据就是缺的 —— 因此这一路径**必然**产出无 HTML 的请求。 这也解释了真实项目里的分布（黑雨之下）：只有结构化数据齐备的卷纲/章纲才留下了伴生 .html。

3. 修法

3.1 单一出口保证（核心）

把「必须有 HTML」做成 attachOutlineHtml 的**唯一出口保证**，而不是散落在各分支里的条件判断。 分派逻辑保持原样，但只要分派后 htmlContent 仍为空，就用该请求的**自己的 MD** 兜底渲染一份卡片流： 

const attached = dispatchOutlineHtml(request, text)
if (attached.htmlContent?.trim()) return attached
// 最终保证：任何大纲类型都不允许「有正文却没有 HTML」。
const fallback = renderOutlineFallbackHtml({ content: attached.content, fileType: attached.fileType, ... })
return fallback ? { ...attached, htmlContent: fallback } : attached
为什么把保证放在出口而不是逐个补分支：ALLOWED_FILE_TYPES 有 8 个成员， 逐个补分支意味着「以后新增类型时又要记得补一处」，漏一处就重新出现永久置灰的保存框。 出口保证让「新增类型忘记补渲染器」这个错误**不可能静默发生**，并由一条遍历全部 8 类的用例守住。

3.2 兜底用什么渲染

新增 renderOutlineFallbackHtml（放在 setting-outline-template.ts，复用已验证的卡片流渲染器）：

  1. 先按标题/文件名/文件夹嗅探专属分项。若命中具体分项（力量体系 / 组织势力 / 背景设定 …）就用它 —— 这正是原 borrowSettingFamilyHtml 的意图：被判错类型的文档（例如「全版本力量体系总纲」因正文提到「第N章」被误判为章纲） 应当显示它**真正的样子**，而不是章纲的样子。此行为保持不变。
  2. 嗅不到具体分项时，用该大纲类型自己的中性规格，而不是一律退化成「设定 · 卡片流」： 章纲 · 卡片流 / 卷纲 · 卡片流 / 质量检查 · 卡片流。
这一步是必要的，不能省：若兜底一律用「设定 · 卡片流」，一份章纲会被冠上「设定」的标题 —— 等于用错误标签换取「有 HTML」，比没有更糟。

3.3 被一并覆盖的类型

fileType改动前改动后
chapter-outline缺结构化数据 → 无 HTML章纲卡片流
volume-outline缺结构化数据 → 无 HTML卷纲卡片流
quality-report永远无 HTML（没有渲染器，也不在设定家族里）质量检查卡片流
character / organization / foreshadowing / setting / outline已有渲染器不变（出口保证只在其失败时接管）

3.4 顺带修掉的死分支

出口保证接管后，borrowSettingFamilyHtml 与 VOLUME_OUTLINE_MARK 失去调用方，随之删除； isLikelyChapterOutline 仍被 hasChapterOutlineStructure 使用，保留。

4. 非目标

  • 不动历史文件。renderOutlineHtmlForPath（预览面板为「盘上已有 .md 但没有伴生 .html」即时渲染） 的放行范围保持不变，仍只覆盖能明确归入专属卡片类型者 —— 已确认这条路径在调用 attachOutlineHtml 之前 就会对中性兜底返回 null，因此出口保证不会波及它。
  • 不改任何提示词。卷纲/章纲的修复提示词里「不要写 HTML」是正确的（HTML 由软件渲染）；本次修的是软件侧漏渲染。
  • 不动结构化渲染。chapterOutlineData / volumeOutlineData 齐备时仍走专用折叠树/卡片流， 兜底版只是拿不到结构化数据时的降级，两者不会互相覆盖（已有 HTML 的请求一律原样保留）。

5. 验证方案

  1. 单元（新增）：遍历 ALLOWED_FILE_TYPES 全部 8 个成员，在「只有 MD、没有任何结构化 JSON」下断言 htmlContent 非空 —— 这条用例就是「一个不留」的守卫，新增类型忘记补渲染器时会红。
  2. 意图保持：把 outline-save-request.spec.ts:849 那条 expect(realChapter.htmlContent).toBeUndefined() 改为 「非空、且是 章纲 · 卡片流、且**不含** 设定 · 卡片流」。 该用例的原始意图是「真正的章纲不该被套上设定卡」—— 意图正确，但旧实现是用「干脆不出 HTML」来满足的； 改后同一个意图由更准确的断言守住。
  3. 端到端：parseOutlineSaveRequests 喂一份「AI 只给 MD + outlineSaveRequest」的回复（含章纲/卷纲）， 断言解析出的请求带非空 HTML —— 直接对应「保存框不再置灰」。
  4. 变异验证：移除出口保证 → 上述用例必须变红；把兜底规格换成通用设定 → 「不含『设定 · 卡片流』」必须变红。
  5. 全量回归：全量 A/B（新增失败文件必须为 0）+ tsc --noEmit。
