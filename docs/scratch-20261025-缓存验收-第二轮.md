
两个现象：

1. **每条都是新指纹**——断点之前的整段内容（`softwareRules + stableCore`）每轮都在变。
2. **`est` 在 15 万和 22 万之间大幅跳动**（差 7 万 token），说明稳定块本身规模在剧烈变化。

后 4 条能到 40~70%，说明**部分前缀确实是稳定的**（这是 P4「核心设定下沉到末尾」的功劳），
但前面那一段变了，所以拿不到满分。

### 根因：这条链路没吃到 P0 的改造

P0 改的是 `buildContextHubPromptParts`（三段拆分），调用方只有 `chat/chat-panel.tsx`。

大纲链路走的是**另一个函数**：

```ts
// outline-chat-panel.tsx:3728 / 5460 / 6196
buildContextHubSystemContent(baseSystemPrompt, contextHubResult, [...])
```

它的结构是：

```
[0] softwareRules          ← 含意图阶段规则、讨论模块，每轮可能变
[1] stableCore   cacheControl:true   ← 断点在这里
[2] dynamicText（摘要+动态上下文+策略+extraRules）  ← 断点之后，本来就不该命中
```

断点位置是对的（资料在断点之后），但**断点之前的 `softwareRules` 和 `stableCore` 每轮都变**，
所以指纹每次都全新。

**这是我上一轮的判断漏洞**：我说"P0 已修完主对话"，实际只覆盖了 chat-panel 这一条路径，
大纲链路用的是同一套底层能力、但另一条组装路径，从未被改造过。

历史数据也印证：改造前大纲链路（90 条）只有 31.4%，改造后 29.4%——**基本没动**，
因为改的本来就不是它。

## 3. 章节生成为什么 0 条数据

不是没触发，是**入口根本不存在**。

`outline-chat-panel.tsx:2257` 的注释写得很明确：

```
调用从不提供 runDeepChapterGeneration / getWritingStyleIdOverride
```

而 `run_chapter_workflow` 的注册条件（`agent/tools/index.ts:115-121`）要求：

```
shouldRegister("run_chapter_workflow") &&
options.projectPath &&
(options.chapterWritingLlmConfig || options.llmConfig) &&
options.aiWorkflowMode &&
options.runDeepChapterGeneration
```

`runDeepChapterGeneration` 只由 `src/hooks/use-agent-config.ts:168` 提供，
而这个 hook 只被 `chat/chat-panel.tsx` 使用。

**结论：在大纲界面发「写第21章」永远不会触发章节生成。**
必须在左侧的 **AI 会话** 里发。

判断有没有真的触发：正常触发时界面上会出现「写作任务书 → 正文初稿 → 审稿 → 返修」的阶段进度提示，
一次调用会产生 6 条以上的 API 请求。如果模型只回了一段文字、没有阶段提示，就是没调工具。

## 5. 下一步（按收益排序）

### A. 大纲链路改造（收益最大）

它现在占今日 token 的 43%（1,187,923 / 2,735,173+），命中只有 29.4%。
如果能做到主对话的水平，这条链路的输入成本能降一半以上。

要动的地方：
- `buildContextHubSystemContent` 增加"稳定前缀"与"本轮规则"的分离（或让大纲链路改用
  `buildContextHubPromptParts` 的三段结构）；
