# 缓存命中率真机实测报告（v4）

> 2026-10-25
> 测试对象：**硅基流动** `https://api.siliconflow.cn/v1` / `deepseek-ai/DeepSeek-V4.1-Flash`
> 凭据来源：本机 `com.qingmuai.writer/app-state.json` 里已配置的「硅基流动」供应商
> 素材来源：真实项目 `C:\QM-BOOK\黑雨之下`（purpose.md / schema.md / wiki/outlines / writing-skills.json / chapter-019.md）
> 提示词构造：用软件真实函数（`buildStableContextPrefix`、`buildDeepChapter*Prompt`、`buildContextHubPromptParts`、`withContextHubTaskContent`）
> 读数方式：`response.usage.prompt_tokens_details.cached_tokens`（该网关同时返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`）
> 本次共发出约 48 次真实请求、12.6 万 prompt tokens，费用可忽略（不到 0.1 元）

---

## 0. 六个实测结论（全部可复现）

| # | 结论 | 实测证据 |
|---|---|---|
| 1 | **完全相同请求：第 1 次 0%，第 2 次起 ~100%** | R1 0% → R2/R3/R4 均 100.0%（cached 2304/2305） |
| 2 | **追加式：命中上一轮的几乎全部** | AP2 = 98.8%（2304/2332），只有新增的 28 token 未命中 |
| 3 | **兄弟式（同 P 换尾部）：命中公共前缀，但每次都是"部分"** | 章节三阶段：0% → 71.9% → 48.8%（每轮都只命中 P=2688） |
| 4 | **头部改一行 = 当次全量归零，再发一次就恢复** | HD1 100% → HD2 **0%** → HD3 99.3% → HD4 100% |
| 5 | **prompt < ~2048 token 的请求完全不缓存** | 216/576/936/1476 token → 全部 0%；**2196 token → 64.1% → 99.1%** |
| 6 | **缓存块粒度 = 128 token** | 所有 cached 值都是 128 的整数倍（1408=11×128、2688=21×128、6912=54×128…） |

第 5 条是这次实践最重要的意外发现：**短请求白跑**。软件里所有"轻量调用"（技能库单独校验、短大纲问答、人格核对）都在 2k token 以下，等于自带 0% 命中，与布局无关。

## 1. 章节链路（用户问的第 1 项）

真实素材：`outlinePrompt`（大纲 3 篇）+ `contextPrompt`（index/overview/memory），稳定前缀 P ≈ 2688 token。

### 现状：三个阶段各发一条独立 user 消息（兄弟请求）

| 阶段 | prompt | cached | 命中率 | 未命中 |
|---|---|---|---|---|
| 任务书（冷启动） | 2902 | 0 | **0%** | 2902 |
| 初稿 | 3740 | 2688 | **71.9%** | 1052 |
| 返修 | 5506 | 2688 | **48.8%** | 2818 |
| 合计 | 12148 | 5376 | 44.3% | **6772** |

> P 确实被命中了（2688 三轮都一样），但**每阶段新增的任务书、初稿、审稿意见全部按全价重发**。

### 修后：同一条会话逐轮追加

| 阶段 | prompt | cached | 命中率 | 未命中 |
|---|---|---|---|---|
| 第1轮 任务书 | 2902 | 2816* | 97.0% | 86 |
| 第2轮 初稿 | 2945 | 2816 | 95.6% | 129 |
| 第3轮 返修 | 3734 | 2944 | 78.8% | 790 |
| 合计 | 9581 | 8576 | 89.5% | **1005** |

\* 第1轮的 97% 是因为内容与上一分支的"任务书"完全一致（同一批实测里已缓存）；真实首次仍是 0%。扣除这次预热，合计未命中约 3900，**仍比现状省 42%**。

**结论：章节链路改成单会话追加，未命中 token 从 6772 降到 ~3900（−42%）。**

## 2. 大纲链路（用户问的第 2 项）

| 形态 | prompt | cached | 命中率 |
|---|---|---|---|
| 第1轮（冷） | 2659 | 0 | **0%** |
| 第2轮（追加） | 2697 | 2560 | **94.9%** |
| 换成另一个问题（兄弟） | 2659 | 2560 | **96.3%** |

**结论：大纲链路只要 P（已有大纲 + 上下文）超过 2k token，第一轮之后基本都能命中（95% 左右）。大纲不是短板。**

## 3 & 4. 灵魂 + 技能库 + 剧情推演（用户问的第 3、4 项）

### 受控 A/B（每支都带唯一 nonce，保证真冷启动）

稳定块 = 作品灵魂（purpose.md）+ 核心设定（schema.md）+ 大纲骨架 + **写作技能库（writing-skills.json）**，
推演资料 = overview + 本章材料。两分支内容完全相同，**只有布局不同**。

| 分支 | 第1轮 | 第2轮（回放） | 第2轮未命中 |
|---|---|---|---|
| **现状**：资料注入到 user 消息尾部 | 0%（6992） | **85.8%** | **996 token** |
| **修后**：资料前移成独立消息，排在 system 之后 | 0%（6986） | **98.7%** | **94 token** |

**结论：同样的内容、同样的模型，只把"本轮资料"从 user 尾部挪到 system 之后，第二轮未命中从 996 降到 94，命中率 85.8% → 98.7%。这是本次最有价值的一条。**

### 技能库位置对照

| 形态 | prompt | cached | 命中率 |
|---|---|---|---|
| 技能库在 **system**（修后） | 3923 | 3840 | **97.9%** |
| 技能库第2轮 | 3942 | 3840 | **97.4%** |
| 技能库塞在 **user 正文**里 | 2121 | 0 | **0%** |
| 同上，第2轮回放原文（技能被丢掉） | **665** | 0 | **0%** |

**结论：技能库只要放进 system，就能被稳定命中（97%+）；放进 user 正文，不但 0%，第2轮还会因为回放丢内容让整条 prompt 掉到 665 token——低于 2048 的缓存门槛，永远不可能命中。**

## 4. 修正前几版的三处判断

| 前版说法 | 真机实测 | 修正 |
|---|---|---|
| 「资料注入尾部导致整轮 0 命中」 | 85.8% | **不是 0**，因为 system 那 6k 仍然命中。真实差距是 85.8% vs 98.7%，差 13 个百分点、每次多烧 ~900 token |
| 「兄弟请求可能完全不吃公共前缀」 | 71.9% / 48.8% | **吃**，但只吃 P 那一截（2688），阶段增量全价 |
| 「prompt 太小只是命中率低」 | 1476 token → **0%** | **低于 ~2048 token 直接不缓存**，是硬门槛不是比例问题 |

## 5. 按实测差重排的修复优先级

| 优先级 | 动作 | 实测依据 | 预期 |
|---|---|---|---|
| **P0** | 把「会话摘要 + 本轮资料」前移到 system 之后、历史之前 | A/B：85.8% → 98.7% | 每次少烧 ~900 token（6k prompt 规模） |
| **P0** | 技能库 / 反AI腔规则 / 输出要求全部进 system | 97.9% vs 0% | 技能库从"每次全价"变"永久命中" |
| **P1** | 章节三阶段改单会话追加 | 6772 → ~3900 未命中 | 每章 −42% 输入 |

| **P2** | 头部冻结（契约不含本轮输入、工具集固定、stableCore 不按比例重截断） | HD2：改一行 = 0% | 避免"每次改配置全量归零" |

## 7. 这次实测的局限（必须说明）

1. **只测了硅基流动一家**。`~2048 token 门槛` 和 `128 token 粒度` 是该网关/该模型的表现，官方 `api.deepseek.com` 可能不同（历史上是 64 token 存储单元）。
2. `max_tokens=8` 让回复被截断，不影响 prompt 侧命中判定，但"输出结束处落盘"这条路径没被覆盖。
3. **没有带 tools**。工具 schema 在 prompt 里的位置还没测（协议级实验显示"集合一变全量归零"，但那次是在另一家网关且噪声大，不足以下结论）。
4. 素材取自单个项目，长度分布不代表所有用户。
5. 缓存有预热延迟（秒级）与自动清理（数小时~数天），跨天对比要重新校准。
