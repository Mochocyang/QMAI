# 缓存命中率优化·P1 落地报告（审稿复用写作前缀）

> 2026-10-25
> 前序：`scratch-20261025-缓存优化-P0落地报告.md`（主对话资料前移 + 技能库进 system）
> 本轮：让**审稿**复用**写作**已经落盘的同一份前缀。

---

## 一、问题

写作阶段的前缀是 `buildStableContextPrefix(outlinePrompt, contextPrompt)`，而审稿从自己的
`contextPackToPrompt(pack, undefined, { maxContextSize })` 起头（`review-adapter.ts:143`）。
两者结构、预算、字段顺序都不同 → **字节不同 → 命中率 0%**。

而审稿是单章流程里**单次输入最大**的调用之一，全冷发送代价最高。

## 二、改动

| 文件 | 改动 |
|---|---|
| `src/lib/novel/review-adapter.ts` | ① `ReviewChapterOptions` 新增 `cachePrefix?`；② `buildReviewPrompt` 新增 `cachePrefix` / `extraContext` 两个参数，有前缀时**用它替换**自建上下文段；③ `runReviewStage` 在有前缀时**不再发 system 消息**，改为把审稿人设并进前缀之后的同一 user 消息 |
| `src/lib/novel/deep-chapter-generation.ts` | 4 处 `reviewChapter` 调用（阶段4 全量审稿 + 返修后复审，各含 signal/无 signal 两分支）全部传入 `cachePrefix` |
| `src/lib/novel/review-adapter.spec.ts` | 新增 2 条用例：前缀替换自建上下文段；带前缀时首条消息为 user 且第一块逐字节等于前缀 |

### 为什么必须去掉 system 消息

请求的第 0 个字节决定整条前缀。写作侧发的是 `[user: P + 指令]`，第 0 字节是 P。
如果审稿保留 `[system: 审稿人设][user: …]`，第 0 字节变成审稿人设，与写作错位，
**后面再完全一样也命中不了**。所以有前缀时把审稿人设并进 P 之后。

### 角色光环不能丢

`reviewChapter` 会"用初稿正文重新匹配角色光环"（补齐初稿里新登场的角色）。
前缀替换掉自建上下文后，这份重匹配结果会丢，因此单独作为 `extraContext`
接在前缀之后（`## 初稿新增角色光环（写作阶段之后重新匹配）`）。

## 三、验收

### 单测

```
vitest run src/lib/novel/review-adapter.spec.ts   → 18 passed
vitest run src/lib/novel src/components           → 6057 passed / 1 failed / 6 todo
```
唯一失败是既有环境问题：`ui-test-ai-input.spec.tsx` 读不到
`docs/ai-composer-nowrap-20261007/check-composer.mjs`（夹具缺失，与本次无关）。

### 真机实测（硅基流动 DeepSeek-V4.1-Flash，真实项目素材，P ≈ 9138 字符）

| 请求 | prompt | cached | 命中率 |
|---|---|---|---|
| 写作-初稿（冷启动） | 5928 | 0 | **0.0%** |
| **审稿-复用同一前缀** | 5929 | 5888 | **99.3%** |
| 审稿-旧做法（自建上下文起头） | 780 | 0 | **0.0%** |
| 写作-返修（再复用一次） | 5931 | 5888 | **99.3%** |

结论：写作 → 审稿 → 返修 三段现在共享同一份缓存，**只有各自新增的指令那几十个 token 全价**。

## 四、顺带发现的一条硬约束

上一轮测出「prompt < ~2048 token 完全不缓存」，这次又撞到一次：
第一次用 1699 token 的前缀测，三条请求全是 0%。把素材加到 5928 token 才出现 99.3%。

**含义**：真实章节的审稿 prompt 通常远大于 2k（上下文包 + 3000 字正文），没问题；
但**分段审稿**如果某段正文很短、上下文又被压得很小，整条可能掉到门槛以下 → 白跑。
如果后续把审稿分段改小，要一起校验长度。

## 六、还没做（按实测收益排序）

1. **章节三阶段改单会话追加**：未命中 6772 → ~3900（−42%）。改动面最大（`deep-chapter-generation` 5 处调用 + 多阶段 checkpoint/重试），建议单独一批。
2. **stableCore 固定配额**：现在按"剩余预算平均分配"，实测前段变一行会让稳定块只剩 43.9% 公共前缀。需要先定权重（涉及上下文构成比例，要产品确认）。
3. **合并 2k token 以下的小调用**：低于门槛直接不缓存。
4. **资料章内冻结**：P0 遗留项，避免写入过程中台账变化导致前缀失效一次。
