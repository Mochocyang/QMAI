## 0. 设计目标与非目标

### 目标
1. 用户能在大纲向导里**明确选择「同人」**，而不是靠手填自定义题材。
2. 用户能提供**原作素材**，系统把它编译成一份**落盘、可迭代、受保护的「原作正典」**。
3. 用户能声明**同人模式**与**容许偏离**，让「有意改动」与「写崩了」可区分。
4. 正典在**大纲生成**与**章节生成**两个阶段都被注入，且在 token 预算里**优先于人物状态**（对齐 `AGENTS.md` 的
   「用户指定 > 章节细纲 > 上一章结尾 > **Canon 正史** > 人物状态 > …」）。
5. 不破坏既有核心工作流：草稿隔离、`ingestChapter()` 摄取链、`SECTION_PRIORITY` 顺序、`resolveNovelModel()` 出口。

### 非目标（本轮不做）
- 不做「原作章节自动抓取/爬虫」。
- 不做同人专有的六维审稿新维度（只把正典与模式**接入**现有审稿上下文，新维度另行立项）。
- 不做同人子题材的**逐个子 Skill**（哈利波特 / 火影 / 斗罗…），只做一个通用 `fanfic-derivative`，
  子题材以 `outline-genres.ts` 已有的 14 个标签**展示**，不各自建 Skill。

## 1. 关键设计决策

### D1：同人是「题材」还是「创作类型」？

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 只加题材选项 | 在 `MALE_GENRES`/`FEMALE_GENRES` 各加 `tongren` | 改动最小，但「同人」与「男频/女频」不正交，且无处承载模式与正典 |
| B. 题材 + 独立「同人设定」区块 | 题材列表加 `tongren`，并在向导里增设一组同人专属字段 | 改动中等，**模式/正典/偏离有明确归属**，UI 可按需展开 |
| C. 独立创作入口（照抄 InkOS） | 顶部新增「同人创作」入口 + 独立向导 + 独立意图 | 最贴近 InkOS，但改动面最大，且与现有「大纲向导」双轨 |

**推荐 B**。理由：
- 同人的**受众维度仍然是男频/女频**（同人既可以是男频也可以是女频），把它塞进频道会破坏正交性；
- 模式与正典是**从属于一次生成请求**的参数，放在向导里最自然，也便于走通「同一次生成」的既有链路；
- 保留后续升级到 C 的空间：只要把「同人设定」区块的提升为独立入口即可，**核心链路（正典编译、上下文注入）不必重写**。

### D2：正典存哪儿？

| 方案 | 取舍 |
|---|---|
| A. `wiki/原作正典.md`（混进 wiki，靠 `searchWiki` 命中） | ✗ 会退化成现在的 `canonRules`：模糊、不可靠、可能搜不到 |
| B. `.novel/fanfic-canon.md`（受管资产，**直接按路径读**，不检索） | ✓ 与 `.novel/` 下既有的状态类资产（`character-states.json`、`timeline.json`、`snapshots/`）同构；可被上下文数据源**确定性读取**；可在 UI 里查看/重编译 |
| C. 项目根 `原作正典.md` | ✗ 与「项目目录 = Markdown 章节 + JSON + LanceDB」的既有布局冲突 |

**推荐 B**：`.novel/fanfic-canon.md`。**正典必须按固定路径读取，不经过模糊检索**——这是与现状 `canonRules` 最本质的区别。

### D3：正典在上下文里的优先级？

`context-engine.ts:35-59` 现有 `FIELD_PRIORITY`（数字越小越先保留）：

```
sectionBriefing 0 / task 1 / chapterGoal 2 / mustDo 3 / mustAvoid 4 / soulDoc 5
storyFrameworkBinding 5.5 / outline 6 / recentSummaries 7 / previousChapterEnding 8
characterStates 9 / characterAuras 10 / foreshadowingStates 11 / recentChapterContents 12
revisionDirectives 13 / cognitionStates 14 / timeline 15 / relatedSettings 16
canonRules 17 / nextChapterAdvice 18 / writingStyle 19 / searchResults 20 / graphSearchResults 21
```

`AGENTS.md` 声明的顺序是「… > **Canon 正史** > 人物状态 > 伏笔 > …」，
所以新增的 `sourceCanon` 应插在 **`characterStates(9)` 之前**。

**取值 `4.5`**：紧跟 `mustAvoid(4)` 之后、`soulDoc(5)` 之前。
- 它是**硬约束**（不得违背），理应比可变的 `characterStates` 更早保留；
- 但不该压过 `mustDo/mustAvoid`（那两项是**本次生成**的用户指令，优先级更高）；
- 用 4.5 而不是整数，是为了**不改动任何既有字段的序号**，把对 token 预算与既有测试的影响降到最小
  （与代码里 `storyFrameworkBinding: 5.5` 的既有做法一致）。

### D4：正典怎么进正文提示词？

现状：正文提示词 = `buildStableContextPrefix(outline, contextPrompt)` + skills + 任务书/执行清单
（`deep-chapter-prompts.ts:55-61, 135-148`），其中 `contextPrompt` 来自 `contextPackToPrompt(pack)`。

**推荐：只走 context pack**，不新增 prompt 参数。理由：
- 一次改动同时覆盖任务书阶段、正文阶段、扩写/润色/终稿阶段（它们都吃同一个 `contextPrompt`）；
- 不触碰 `buildDeepChapterBriefPrompt` 等 6 个函数的签名，回归面最小；
- 天然获得 `buildContextPack` 的裁剪/预算保护。

## 3. 数据流（改后）

```
【建书/大纲阶段】
用户在大纲向导选择：创作类型=同人、题材=同人衍生、模式=au、原作=《X》、粘贴原作素材、容许偏离=[时间线改动]
        │
        ├─(1) compileFanficCanon(sourceMaterial, sourceName, mode)   ← resolveNovelModel(...,"extract")
        │       └─ 超长则分片编译 → 固定骨架 Markdown
        │       └─ saveFanficCanon(projectPath) → .novel/fanfic-canon.md
        │       └─ 写 project-meta：fanficMode / fanficSourceName / fanficAllowedDeviations / fanficCanonPath
        │
        └─(2) buildOutlineWizardPrompt(request)
                └─ ## 同人模式：au（架空世界）
                   ## 原作正典素材：<正典全文>
                   ## 容许偏离：时间线改动
                   ## 同人写作硬规则：<六条>
                   ## 本次优先调用 Skill：… fanfic-derivative …
                        │
                        └─→ 大纲会话 → 用户确认 → 写入 大纲/卷纲/章纲/人物小传/设定

【章节生成阶段】
buildContextPack(projectPath, task, chapterNumber)
        └─ sourceCanonDataSource 直接读 .novel/fanfic-canon.md（不检索，8000 字上限）
                └─ ContextPack.sourceCanon（FIELD_PRIORITY = 4.5，高于 characterStates=9）
                        └─ contextPackToPrompt() → 「## 原作正典（不可违背）」
                                └─ buildStableContextPrefix(outline, contextPrompt)
                                        └─ 任务书 / 正文 / 扩写 / 润色 / 终稿 全部继承
```

## 4. 同人写作硬规则（写入 Skill 与提示词，移植自 InkOS）

1. **正典是权威**：已导入的正典对既定角色、关系、世界规则、时间线、角色已知信息、标志性限制具有权威性。
2. **服从所选模式**：`canon` 填补原作未展示的时段或视角；`au` 指明分歧点并严格跟随后果；`ooc` 明确有意偏离的成因与边界；`cp` 让关系变化驱动剧情，不把任一方压扁。
3. **写新线，不复读**：建立新的戏剧线，不重演原作场景；新增配角与事件必须服务新线且能与原作区分。
4. **靠动机/认知/节奏保留声音**：保留角色辨识度不靠抄原句。
5. **无证据就留空或发问**：绝不把猜测写成正典。
6. **压缩素材是证据，不是臆造许可**。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 动 `FIELD_PRIORITY` 影响既有 token 预算 | 用 `4.5` 不改动任何既有字段序号；新增字段默认为空串，**不占预算**；补一条「正典存活」的预算测试 |
| 新增数据源拖慢上下文构建 | `sourceCanon` 是**单文件直接读**，比现有 `canonRules` 的 `searchWiki` 更快 |
| 同人 Skill 缺失时静默降级 | 参照 InkOS 的 `activations.ts`：同人题材命中但 Skill 解析不到时，提示词里**显式写出缺失的 Skill 名**，并在 UI 校验层给出错误（而不是安静走原创技能） |
| 老项目读不到新字段 | `project-meta` 新字段**全部 optional**；`ContextPack.sourceCanon` 为 `""` 时提示词不出现该段 |
| 破坏草稿隔离 | 正典只进**上下文读取**，不写入章节记忆；`ingestChapter()` 完全不改 |
| 正典过大挤掉正文上下文 | 8000 字上限 + 分片编译时**先压缩成证据包**再落盘（移植 InkOS 的 `prepareSourceText`） |
| 侵权/合规 | 正典是**用户自备素材**，软件只做本地编译与本地存储；提示词明确「只保留原作有证据的内容」 |

## 6. 验收标准

1. 大纲向导里能选到「同人衍生」，并能设置模式 / 原作名称 / 原作素材 / 容许偏离。
2. 提交后 `.novel/fanfic-canon.md` 落盘，内容为固定骨架且含模式与素材来源。
3. 生成的大纲提示词里同时出现「同人模式」「原作正典」「容许偏离」「同人写作硬规则」「fanfic-derivative」。
4. `buildContextPack()` 返回的 `pack.sourceCanon` 非空，且 `contextPackToPrompt(pack)` 含「原作正典」段。
5. 在 token 预算被压缩时，`sourceCanon` **先于** `characterStates` 保留（测试断言）。
6. `npm run typecheck`、`npm run typecheck:tests`、`npm run test:mocks` 回到基线（701 文件 / 6610 用例，0 失败）。
7. 原创路径完全不受影响：不选同人时，`sourceCanon` 为空、提示词无该段、既有测试全绿。
