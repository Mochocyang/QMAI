## 1. 软件里怎么跑出有效数据

### 1.1 先确认模型（决定数据可比性）

在 AI 会话的模型选择里，固定用**同一个模型**跑完这一轮测试。
推荐用 `deepseek-v4.1-flash`（硅基流动），因为你历史数据里它最差（5.7%），
改善最明显、最有说服力。

**整个测试过程中不要换模型**——不同模型的缓存互相独立，混在一起统计会互相污染。

### 1.2 跑三类数据（重要，覆盖不同链路）

| 顺序 | 在 AI 会话里发什么 | 覆盖链路 | 说明 |
|---|---|---|---|
| ① | `帮我看一下第20章的章纲有没有问题` | 主对话链路 | 验证 P0（资料前移）。连发 4~5 轮不同问题 |
| ② | `写第21章` | 章节深度生成 | 验证 P1/P3/P6。一次调用内含任务书/草稿/审稿/返修多次请求 |
| ③ | `继续写第22章` | 章节 + 跨章 | 验证 P2/P3 的跨章复用 |

**每一轮之间至少间隔 30 秒**（原因见第 3 节）。

### 1.3 怎么算"有效样本"

- 主对话：**≥ 5 轮**（少了看不出趋势）
- 章节生成：**≥ 2 章**（跨章复用要看两章对比）
- 一次"写第21章"会触发多次 API 调用（任务书、草稿、审稿、返修，可能还有润色），
  所以 2 章就能贡献 8~12 条请求，样本量够了。

### 1.4 别做什么

- ❌ 不要中途切换模型
- ❌ 不要连续快速重发（缓存写入有延迟，见第 3 节）
- ❌ 不要边跑边改设定文件（改了设定，上下文包就变，前缀作废）
- ❌ 不要用"重新生成"覆盖同一轮——那会多出一批相似请求，干扰统计

## 3. 三个必须知道的坑（否则你会误判）

### 坑 1：缓存写入有延迟，别急着重发

实测：同一个前缀间隔 **8 秒**重发，命中仍是 **0%**；间隔 **35 秒**才吃到 **91.2%**。

所以如果你连发两条想"验证命中"，第二条很可能显示 0%，那不是没修好，是 provider 还没落盘。

### 坑 2：不同模型的缓存互相独立

`deepseek-v4.1-flash` 和 `gemini-3.8-flash-high` 的缓存不通用。
测试期间固定一个模型，统计时也按模型看，别只看全局平均值。

### 坑 3：任务书和草稿可能用不同模型

`deep-chapter-generation.ts:553-554`：任务书用「项目默认模型」，草稿用「AI 会话当前模型」。
如果这两个在设置里不一样，任务书与草稿之间缓存不共享，**每章第一个草稿请求必然冷启动**。
这是既有设计（任务书可用便宜模型），不是 bug；但统计前先确认一下两者是否一致，
否则会把"设计使然"当成"没修好"。

## 4. 怎么判断算通过

| 指标 | 改造前（实测基线） | 目标 |
|---|---|---|
| 全局命中率 | 31.4% | **> 70%** |
| 零命中请求占比 | 46% | **< 20%** |
| deepseek-v4.1-flash 命中率 | 5.7% | **> 70%** |

主指标是 **命中率** 和 **零命中占比**。
脚本里那个「指纹重复率」只看趋势，不能当结论——它把 tools / reasoning 也算进去了，
会出现「指纹变了但命中 94.9%」的误报。

## 5. 如果结果不对，怎么定位

按这个顺序看 `--timeline` 的输出：

1. **零命中占比还是很高（>50%）**
   → 前缀仍在被改写。看相邻两条的 `est`（估算 token）是否接近但指纹不同：
   接近且不同 ⇒ 内容被替换而非追加（P0 修过的那类问题）。

2. **同指纹连续两次仍 0%**
   → 间隔是不是太短（坑 1），拉到 35 秒以上再试。

3. **命中率上去了但绝对值低**
   → 前缀太短，低于 provider 的最小可缓存长度（DeepSeek 侧实测约 2048 token）。

4. **章节链路完全没数据**
   → 说明章节生成的请求没走 agent 的 trace 汇总。把这个现象告诉我，我查链路。
