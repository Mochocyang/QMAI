记忆中心单页重构 · 设计

需求原话：「将记忆中心 UI 重构，不再是双栏结构，而是设计为单个页面重新设计」。

经确认，改造范围为两层左右分栏全部拆除（外层「中间栏 ↔ 内容区」与内层「章节列表 ↔ 快照详情」）， 采用顶部标签页 + 全宽内容，并把双栏遗留的状态耦合一并清掉。

1. 现状：嵌套了两层双栏

层分栏实现位置
① 外层中间栏（7 个记忆分类 + 计数）↔ 右侧内容区 sidebar-panel.tsx:1013-1096 的 lint && novelMode 分支
② 内层章节列表（w-48 固定宽，含区间搜索）↔ 快照详情 memory-center-view.tsx:650-764 的 isSnapshotList 分支

读代码时发现的既有缺陷（本次顺带修掉）

大纲快照目前根本打不开。outlineCards（chapterNumber < 0） 只在第 707-713 行被用来显示一个计数「大纲快照：N 条」，从来不渲染成卡片； 而左侧章节列表也只列正数章节（allChapterNumbers 过滤了 > 0）。
真实数据：他，只想活着 = 1 个章节快照 + 10 个大纲快照； 黑雨之下 = 1 个 + 36 个。记忆的绝大多数内容当前无法查看。
那个计数本身还是错的。加载器在 memory-center.ts:319 把卡片列表截断到 RECENT_SNAPSHOT_CARD_LIMIT = 10，而排序是「章节在前、大纲在后」， 所以 1 + 10 的场景下只会剩下 9 个大纲卡片 → 界面显示「9 条」，实际是 10 条。
而这次截断是纯浪费。loadMemoryCenterData 第 268-270 行 已经把全部快照读进内存（listSnapshots 后对每个号 loadSnapshot）， 第 319 行的 slice 只是把已读到的数据丢掉。去掉上限不增加任何 I/O。

计数直接显示在标签文字右侧 —— 这样原中间栏唯一不可替代的职能（一览各分类规模）被保留下来。

自查发现的一处自相矛盾（已修正）：统计条第一格不能叫「章节快照」。 stats.snapshotCount 是章节 + 大纲的总数（真实数据 11）， 而标签页「章节快照」是 chapterCards.length（真实数据 1）。 同一屏上出现两个都叫「章节快照」却分别是 11 与 1 的数字，会直接读作 bug。
因此该格改称 「快照总数」，并在 zh.json 新增键 novel.memoryCenter.stats.totalSnapshots。 注意 stats.snapshots（值「章节快照」）当前无人使用，本次也不复用。
i18n 约束：本项目只有 zh.json 一个语言包，且 i18n-parity.test.ts:142 强制「每个被引用的键都必须存在于 zh.json」。 所以本次新增的键（含上面的 totalSnapshots）必须同步写进 zh.json， 否则该测试会红。反向是安全的：改写后不再使用的 selectPrompt/selectHint 等键留在 zh.json 里不会报错 —— 该测试的孤儿清单（collectScopedOrphanCandidates）只盯 11 个 review.* / novel.outlineGenerator.* 键，不含任何 memoryCenter.*。

标签条：单排，绝不换行

8 个标签在窄窗口下会放不下。这里明确选择横向滚动（overflow-x:auto + 选中项 scrollIntoView），而不是换行。理由：本项目上一轮刚修过「底栏收窄时摆成两排」的缺陷， 用户对无预期的上下结构明确反感；标签条换行会读作「排错了」，横向滚动则是可预期的行为。

章节 / 大纲快照页

  • 顶部一条工具行：区间筛选（起始章 / 结束章 / 清除）与摘要文案，横向排列，不再占左栏。
  • 下方SnapshotCard 全宽纵向堆叠，每张卡内部仍是 md:grid-cols-2 的四组列表（人物状态变化 / 认知变化 / 伏笔变化 / 时间线事件）—— 这是卡片内部的网格，不是分栏。
  • 渐进披露：默认 15 张 + 「显示更多」按钮。因为卡片现在全量在手，分页是纯客户端行为。
  • 卡片动作不变：查看记忆（打开 markdown 详情）、编辑（SnapshotViewer）、删除（确认弹窗）。
  • 大纲快照按标题排序，不再按编号。原因：编号是文件名的哈希 （chapter-ingest.ts:1437，-(hash % 999 + 1)，可到 -817）， 按它排序等于随机顺序。标题即大纲文件名（chapter-ingest.ts:1471 写入 chapterTitle: outlineName）。
  • 大纲卡片标题 = chapterTitle，缺失时回退为「大纲快照 N」（N = Math.abs(number)）， 不再出现「大纲快照(-817)」这种带负号的写法。
大纲快照的「编辑」是安全的。snapshot-viewer.tsx:244 明确处理了 chapterNumber < 0（此时显示 snapshot.chapterTitle）， 且 listSnapshots / loadSnapshot / 路径拼接 （chapter-ingest.ts:698,957,1319）都支持负数 —— 该组件本来就是为大纲快照写的， 只是被记忆中心的死代码挡住而从未被调用。

详情导航：留在页内，不是分栏

打开 markdown 详情（或快照的 markdown）时，标签页内容区整体切换为详情视图，标题行显示详情名并出现 「返回」按钮 —— 这是页面级导航，一行一件，不产生左右分栏。既有的两项体验逐字保留：

  • 关闭详情后恢复原滚动位置与焦点（restoreScrollTop / restoreFocusId）。
  • 从快照卡进入详情后，「返回」回到原来的快照列表（parentView 机制）。

3. 状态架构变更

3.1 中间栏整体退场

项目里已有三次同类迁移的先例 —— ui-test-shell.tsx:111-113 原文注释：

// 技能库、灵魂改为整窗卡片画廊，不再占用左侧目录栏。
const fullWindowViews = … "skillLibrary" … "soul" … "bookAnalysis"

记忆中心加入这个集合即可，顺着项目既有方向走，不是新发明。

坑：lint 这一个 view 被两个功能共用。 content-area.tsx:124：case "lint": {novelMode ? <MemoryCenterView /> : <LintView />}。
novelMode 默认 true，但确实可以为 false（lib/lint.test.ts 就测了 false 分支）， 此时渲染 LintView，而它依赖中间栏的章节树（sidebar-panel.tsx 的 isChapter / inferModeFromPath 机制）。
因此判据必须是 activeView === "lint" && novelMode， 若只写 activeView === "lint"，会把非小说项目的审查视图一起变成整窗、弄掉它的章节树。

3.2 去掉握手字段

selectedMemoryCenterEntry（wiki-store.ts:578,739,805）全项目 只有中间栏写、内容区读，它存在的唯一理由就是这两栏之间通信。两栏并成一个页面后， 这个全局耦合没有存在意义 —— 改为视图内的 useState<MemoryTabKey>。这是本次重构的实质， 而不只是搬 UI。

4. 死代码清理

以下两处在改动前就已不可达，但都带着状态与渲染分支，会让重写后的单页组件更难读，因此一并清掉。

分支为什么不可达清理内容
plot-framework 该 key 根本不在 MEMORY_LABEL_KEYS 里，没有任何路径能写入这个值 frameworkSummary 状态、PlotFrameworkSummaryCard（58 行）及 loadPlotFrameworkLibrary / summarizePlotFrameworkLibrary / PlotFrameworkSummary 导入
dismantling-library 侧栏主动过滤掉了它（filter((key) => key !== "dismantling-library")）， 该分支只是个「若被选中就置空」的空操作 该空操作分支。其意图（拆文库不得出现在记忆中心）由新测试以「标签清单恰好 8 项、不含这两个 key」继续守住
本次不动的地方：memory-center.ts 里的 dismantlingProjects 字段 在改动前就已无人消费（只被赋值并返回，全项目无读取）。它是数据层的历史遗留， 删它属于另一件事，故保留并在文档中记录，不混进这次 UI 重构。

5. 数据层变更（两处，都很小）

  1. 去掉 10 条上限：memory-center.ts:319 的 allSnapshotCards.slice(0, RECENT_SNAPSHOT_CARD_LIMIT) → 返回全部 allSnapshotCards，并删除该常量。零额外 I/O（见 §1），同时修掉大纲计数偏少。
  2. 删除视图中按需加载的残留：selectedChapter / loadedCard / loadingCard 及那段 loadSnapshot effect （memory-center-view.tsx:555-612）—— 卡片既然全量在手，按需加载不再需要。 snapshotNumberFromMarkdownPath 保留（编辑/删除判定仍要用）。
自查发现的第二处遗漏（已补）：上面第 1 条会触碰一个已有的契约测试 —— src/lib/novel/memory-center.test.ts:162-178，测试名就叫 「loadMemoryCenterData 保留最近 10 条章节快照，不会被意外裁成 6 条」， 断言 data.snapshots 长度为 10。
它的夹具恰好是 10 条，所以去掉上限后它仍会通过（10 进 10 出）—— 但这时它已经不再守护任何东西，成了一条会误导人的空断言。
故需按新契约改写：夹具给 12 条，断言 12 条全部返回，并保留「降序、最新的在前」这一条仍然有效的意图。

6. 文件结构

原 memory-center-view.tsx 已 968 行；单页改造会再增大它，因此按职责拆成三个单元。 每个单元都能独立说明「做什么 / 怎么用 / 依赖谁」。

文件职责依赖
memory-center-view.tsx 页面外壳：标题行、统计条、标签条、详情导航、加载/错误/空态、删除弹窗、快照编辑器挂载 下面两个 + store + fs
memory-center-snapshots.tsx SnapshotList / SnapshotCard / SnapshotCollection（章节与大纲共用） 仅 props，无 store
memory-center-tabs.ts 纯配置与计算：标签 key、i18n 键、图标、计数解析（resolveMemoryTabCount） 仅类型，无 React

markdown 详情（EditableMarkdownMemory）体量小，留在 view 内。 标签与图标的定义从 sidebar-panel.tsx 搬到 memory-center-tabs.ts。

8. 风险与不做的事

不做的事：

  • 不删 dismantlingProjects（§4 末），不碰 dismantling.ts。
  • 不改 LintView（非小说项目的审查视图）及其章节树依赖。
  • 不改 loadMemoryCenterData 的读取策略 —— 它本来就读全部快照，本次只停止丢弃。
  • 不新增记忆的写入/提取能力，纯展示层重构。

风险：

  • 删除 selectedMemoryCenterEntry 会同时失效 memory-center-dismantling.spec.ts 的现有断言 —— 已计划按「保留意图、改写断言」处理，而不是删掉测试。
  • sidebar-panel.tsx 是 1203 行的共享文件，删分支前需先确认 memoryData/memoryLoading/memoryError 未被「导入记忆提取" 那条取消路径复用；若被复用则只删渲染分支、保留状态。
  • 单页后一次性渲染的卡片变多（真实数据 1+36 上限），已用「默认 15 张 + 显示更多」控制 DOM 规模。
