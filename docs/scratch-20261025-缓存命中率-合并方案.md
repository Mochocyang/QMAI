## 0. 两版是否相同？—— 判定

**不同。约 40% 重叠、60% 互补，另有 4 处实质冲突。**

两版的分歧不是"谁对谁错"，而是**看的链路不同**：

| | v1（我） | v2（DSH） |
|---|---|---|
| 主战场 | **AI 主对话 / Agent 链路**（chat-panel → runner → context-hub） | **章节深度生成产线**（deep-chapter-generation → review-adapter） |
| 主要证据 | 运行时源码 `dsh-runtime/*.tgz` 解包 | 运行时 README + lib，并实测青木源码 |
| 交付形态 | 断点清单 + 可落地补丁 | 缺陷分级 + 方案性价比排序 |
| 盲区 | 没看章节产线（审稿/多阶段） | 没看主对话链路（历史裁剪/契约/折叠） |

**结论：两者拼起来才是完整地图。** 青木有两条独立的请求链路，只管一条命中率仍然上不去。

## 2. 事实基线（两版合并后）

### 2.1 DeepSeek 的五条硬规则

| 规则 | 依据 | 影响 |
|---|---|---|
| 前缀从第 0 个 token 开始匹配 | 官方 Context Caching | 越靠前越值钱 |
| **每条缓存前缀是独立完整单元，必须完整匹配才命中** | 官方（2026 SWA 版） | `A+B` → `A+C` 这一轮**不命中**；要等公共前缀 `A` 被识别落盘，第三轮起才命中 `A` |
| 落盘点：用户输入结束处、模型输出结束处、公共前缀检测、长输入固定间隔 | 官方 | **追加式对话天然踩点**，这是最优形态 |
| `prompt_cache_key` 不支持；Anthropic 兼容端点的 `cache_control` 被忽略 | 官方 + 实测 | 给 Claude 做的断点对 DeepSeek 零作用 |
| 流式 usage 需 `stream_options.include_usage` | 官方 API | 不开就看不到 `prompt_cache_hit_tokens` |

**由第 2 条推出一条两版都没说透的结论**：
当前章节产线的三个"兄弟请求"（`P+指令A`、`P+指令B`、`P+指令C`）里，
第 1 次 0%、**第 2 次也可能是 0%**，第 3 次起才稳定命中 `P`。
所以 v2 估的"阶段命中率 60~85%"偏乐观；真实情况是**每章前两次调用几乎全冷**。
这恰恰把"改成一个会话语义"的优先级又往上顶了一档。

### 2.2 命中率公式（两版一致）

```
命中率 = 可复用前缀 / 全部输入 = 1 − 本轮增量/总量
```
推论：**只有"历史只追加"能让命中率随轮次单调逼近 100%**。
所有"重排、重截、重折叠"都是在把分子打回 0。

| # | 机制 | 证据 |

## 5. 目标架构（两版合并后的统一模型）

### 5.1 三层前缀

```
┌── L0 应用级（跨会话、跨章、跨项目永久稳定）────────────────┐
│ system: 软件规则 + 反AI腔规则 + 输出硬性要求 + 语言要求      │  ← 新增，当前缺失
├── L1 作品级（同一本书内稳定）─────────────────────────────┤
│ 完整大纲(不含章纲) + 世界观/人物档案/文风画像/硬性规则        │  ← 从 stableCore 拆出
├── L2 章节级（一章之内稳定）───────────────────────────────┤
│ 章纲 + 前情分析 + 人物状态 + 伏笔 + 时间线 + 检索结果        │  ← 从"前缀首位"下沉
├── L3 阶段级（一次调用内稳定）─────────────────────────────┤
│ 任务书 / 初稿 / 审稿意见（上一阶段的输出原样回传）            │
└── L4 本轮增量（唯一 miss）────────────────────────────────┘
```

### 5.2 三条铁律

1. **头部冻结**：L0~L2 一旦发出，会话内不再改。资料变了 → 尾部追加"上下文更新"，只在压缩点重写。
2. **历史只增不改**：进入历史的每条消息字节永久固化（含正文折叠结果、去AI味后处理结果）。要瘦身 → 中段压缩一次。
3. **易变内容全在尾部**：时间、本轮资料、任务契约、工具变更说明。

### 5.3 一条推论（两版都没强调）

**"模型输出 → 回传历史"这一段必须定型化。**
青木对模型输出做了后处理（`stripThoughtDumpFromText`、章节标题规范化、去AI味）。只要后处理规则升级，历史里那条消息就会重渲染 → 前缀变。
所以：**回传的必须是"当时落定的那份字节"，并连同它一起存档**，不能每次重新跑一遍清洗函数。

## 6. 改造路线（合并后按性价比重排）

排序原则：**先能测量 → 再改小刀口 → 最后动结构**。每项都可单独上线、单独回滚。

### 第 0 步：先能测（半天，v1 独有，且是前置条件）

- `llm-providers.ts:953` 条件里加 `isDeepSeekEndpoint(config)`，让 DeepSeek 也带 `stream_options.include_usage`；
- `context-hub-stats-summary.tsx` 去掉 `?? localCacheRate` 的冒充，供应商没报就显示"未提供"；
- 出一份"每章分阶段命中率"报表（复用现成 `LlmRequestCacheTrace.prefixFingerprint`）。

> 不做这步，后面所有改动都是盲改。**v2 的方案 6 方向对，但没发现 DeepSeek 上压根收不到数据。**

### 第 1 步：审稿复用写作前缀（1 天，v2 方案 2）

- `buildReviewPrompt` 的首段改成 `buildStableContextPrefix(outlinePrompt, contextPrompt)`；
- 维度说明、阶段要求、正文片段全部排在后面（现有结构已基本满足）；
- 取消/延后"用初稿重匹配 `characterAuras`"——改为把新角色光环作为**追加段落**放在前缀之后。

收益：审稿从 0% → 80%+，且它是最大单次输入。改动面最小、风险最低。

### 第 2 步：主对话头部稳定（1 天，v1 的 P0-2）

- `taskContract` 改用**会话首条 user 目标**，不再用本轮输入；
- 统一只走尾部注入，删掉"插进 system 块"的分支。

### 第 3 步：历史只增不改三件套（2 天，v1 的 P0-3/P0-4）

- 折叠**定型化**：算一次写回消息，之后不重算；锁定会话创建时的 `readChapterToolAvailable`；
- 取消 `slice(-2)`，改"摘要 + 从固定 floor 起的连续尾部"；
- 裁剪器**只动尾部、不改旧消息**，floor 一旦确定写入会话状态，不再浮动。

### 第 4 步：写作链路补 system（1 天，v2 方案 3）

- 把 `DE_AI_GENERATION_RULES` + 输出硬性要求 + 语言提醒抽到 system；
- 顺序变成 `system(L0) → 前缀(L1+L2) → 阶段指令(L3)`（与现在正好相反）。

> ⚠️ 这一步会再次改变请求头。**必须和第 5 步一起规划、一次上线**，否则改两次、两次全冷。

### 第 5 步：前缀分层 + 章节多阶段单会话化（3~5 天，v2 方案 1+4 + v1 P1-3）

- `pack.outline` 拆成 `fullOutline` / `chapterOutline`，不再 `joinNonEmpty`；
- `## 前情分析` 从前缀首位下沉到 L2；
- `pack.task` 从 prompt 首位移到末尾；
- 章节各阶段改成一条追加式对话：上一阶段输出作为 assistant 消息**逐字节**回传，新指令尾部追加。

```
req1: [L0][L1][L2][指令A]                                   → 任务书
req2: [L0][L1][L2][指令A][A(任务书)][指令B]                    → 初稿
req3: [L0][L1][L2][指令A][A(任务书)][指令B][A(初稿)][指令C]      → 返修
```

### 第 6 步：工具集冻结（半天，v1 P1-4）

- 会话内工具集合与顺序固定；"禁用某工具"改为尾部声明，不从 `tools` 数组里删；
- `toOpenAITools` 输出前按 `name` 排序。

### 第 7 步：护栏 + 看板（1 天）

- `src/lib/__tests__/prefix-stability.spec.ts`：断言同一会话 `req(N+1)` 以 `req(N)` 为前缀（或公共前缀 ≥95%），覆盖普通对话、写章、折叠前后、计划→写作、工具增减；
- 看板：每轮 `cacheReadTokens/inputTokens` + `prefixFingerprint` 是否与前一轮相同（正常应长期相同）。

### 暂缓项

- **会话压缩（中段替换）**：等历史真的长到需要时再做。当前历史被 `slice(-2)` 压得很小，先解决"别砍头"比"会压缩"更急。
- **并行审稿改串行**：时延代价大，等第 1 步验证收益后再评估。

## 7. 对合并稿的二次审查（自我批判）

### 7.1 审查方法

对合并稿逐条做三问：① 有没有代码/官方依据？② 结论是否依赖某个未验证前提？③ 改动之间会不会互相抵消？

### 7.2 通过复核的结论（有硬依据）

- 11 个断点全部落到具体 `file:line`，并已实际打开代码确认（`context-engine.ts:1188` 首段确为 `pack.task`；`mergedOutline` 确含 `chapterOutline`；`review-adapter.ts` 确在重匹配 aura 并 `Promise.all`；写作侧确无 system 消息）。
- DSH 九条机制均有源码或 README 原文。
- `include_usage` 缺失已确认：`llm-providers.ts` 全文只有一处赋值，条件不含 DeepSeek/custom 非 Azure。

### 7.3 判定 v2 不成立或需修正的三条

| v2 论断 | 判定 | 理由 |
|---|---|---|
| "审稿 system 仅 50~100 token，低于 64 最小缓存粒度，等于没缓存" | **论据不成立，结论仍成立** | ① 旧的"64 tokens 存储单元"规则已不在新版官方指南里（改为前缀单元 + 落盘时机描述）；② 实测那句 system（`review-adapter.ts:265-267`，含语言提醒）约 110 字 ≈ 110 token，本身就超过 64。审稿无缓存的真实原因是**前缀与写作不同源**（断点⑧），不是粒度。 |
| "阶段命中率 60~85%" | **偏乐观，需下修** | 按"必须完整匹配前缀单元"规则，兄弟请求第 2 次仍可能 0%，第 3 次起才命中。真实曲线是 `0% → 0% → P命中 → …`。 |
| "你已经有测量能力（已在采集 `prompt_cache_hit_tokens`）" | **不成立** | 解析代码在（`llm-providers.ts:269-285`），但请求没开 `include_usage`，DeepSeek 不会返回 usage 块 → 解析永远不触发。**必须先补第 0 步。** |

### 7.4 判定 v1 需修正的两条

| v1 论断 | 修正 |
|---|---|
| "P0 之后主对话命中率约 65%" | 该估算默认历史能保留 12k tokens。但 `min(4000, 5%窗口)` 的历史预算会把历史压到 4k 以内，实际命中率取决于"system + 4k"。应改为**先修历史预算**再谈 65%。 |
| 只分析主对话链路就下"综合命中率 0~7%" | 章节产线（占写作主要调用量）不在这个口径里。综合应分链路报：主对话、章节产线、审稿。 |

### 7.5 合并后才暴露的三个新风险

1. **第 4 步与第 5 步会互相抵消**：如果先补 system（第 4 步）再改多轮化（第 5 步），期间所有章节请求会各冷一次。必须合并成一次上线，或用开关整体切换。
2. **多轮化推高总 token**：历史里带着任务书 + 初稿（约 3k~6k tokens/章）。命中价 1/10 时仍然划算，但要按"命中量×0.1 + 未命中量×1.0"算总账，不能只看命中率。建议灰度期间同时记录**每章总费用**，而不只是命中率。
3. **定型化与"用户手改历史"冲突**：如果用户编辑了历史消息或重新生成，字节必然变。需要明确规则：**编辑/重新生成 = 主动作废该点之后的前缀**，并在 trace 里标记原因，否则会被误判成"改动没生效"。

### 7.6 仍无法静态确定、必须实测的三件事

1. **DeepSeek 是否对"部分匹配"有更宽的命中**（例如长输入按固定间隔落盘，可能让兄弟请求也吃到一截）。这直接决定第 1 步的收益是 80% 还是 40%。→ 用 3 次顺序请求 + `prompt_cache_hit_tokens` 实测。
2. **审稿单次输入到底多大**（是否 >窗口 50%）。若不是最大单次输入，第 1 步的优先级要下调。
3. **工具 schema 在 DeepSeek 的 prompt 模板里排在消息之前还是之后**。若在之后，断点⑥的危害会小很多。→ 用两次请求只改工具集、不改消息，看 `prompt_cache_hit_tokens` 是否归零。

### 7.7 审查结论

- 合并稿的**机理层**（§2、§3）证据充分，可直接作为设计依据。
- **问题定位层**（§4）11 个断点全部可复现、可定位，建议直接转为 issue 清单。
- **改造路线层**（§6）第 0~3 步低风险、可立即执行；第 4~5 步必须打包上线；第 7 步护栏应在第 2 步之前就落地（先有护栏再改，避免改坏不自知）。
- **收益数字**一律视为待验证估算，以第 0 步实测为唯一口径。

---

## 8. 一页结论

1. **两版不同源、不重复，缺一不可**：v1 管主对话，v2 管章节产线。
2. **共同根因只有一个**：青木在"每轮/每阶段重算并重写过去的内容"，DSH 在"一次定型、只追加"。
3. **两版各有一处硬错误**：v2 以为已经有命中数据（实际 `include_usage` 没开）；v1 只看了主对话就给了综合命中率。
4. **最优路径**：先补测量（0）→ 审稿复用前缀（1）→ 主对话头部冻结（2）→ 历史只增不改（3）→ system 下沉（4）→ 前缀分层 + 单会话化（5，与 4 打包）→ 工具冻结（6）→ 护栏（7，提前到 2 之前）。
5. **目标**：章节阶段 90%+、审稿 85%+、主对话长会话 90%+；单章综合从约 30~50% 提到 88% 以上，账单约为原来的 2~3 折。
