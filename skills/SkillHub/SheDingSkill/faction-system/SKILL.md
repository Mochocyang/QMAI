# 势力系统

## 适用范围

门派、家族、公司、官方机构、地下组织、反派阵营、宫廷、宗门。

输出势力、组织、阵营文件时必须遵循上级目录的 `SETTING_PROFILE_STANDARD.md`，重点写清势力目标、资源来源、内部矛盾、外部关系、代表人物和剧情功能。

## 设计清单

1. 势力目标：它当前最想得到什么。
2. 资源来源：金钱、武力、情报、人脉、地盘、制度、技术。
3. 内部矛盾：继承权、派系、利益差、理念差。
4. 外部对手：竞争、合作、互相利用或仇恨。
5. 主角关系：加入、利用、反抗、被追杀、继承因果。
6. 剧情功能：提供资源、压力、试炼、反转、伏笔或升级通道。
7. 更新记录：势力立场或资源变化必须记录。

## 章纲要求

- 势力登场必须推动一个核心事件。
- 势力要有代表人物和可见行动。
- 不要连续刷同类势力事件，至少保留节奏变化。

## 文件要求

- 独立势力默认输出到 `设定/势力/{势力名}.md`。
- 组织型势力也可输出到 `设定/组织/{组织名}.md`。
- 势力不能只有名字，必须有目标、资源和代表人物。

## 组织势力设定详细内容契约

每个对象必须按顺序覆盖以下 11 个分区；逐条落实字段，不将一整区压缩成一句概述。

### 1. 基本信息

名称、别称、类型、创立者、成立时间、规模与统计时点、公开身份和真实性质、法律地位、象征与核心据点、当前实力及危机；说明组织在世界中解决什么需求、为何能持续存在，避免只写正邪标签。

载体：kv；按上面的要求拆分具体字段和条目。

### 2. 组织使命

分别写公开宗旨、真实利益、长期战略、当前目标与行动优先级；说明受益者、牺牲者、不可让渡的底线、对内动员叙事及失败条件。理想与实际利益冲突时如何取舍，非营利组织也要解释存在基础。

载体：kv；按上面的要求拆分具体字段和条目。

### 3. 地理位置与作用

总部方位、控制边界、分支据点、成员居住与阶层差异、家属安置、训练及生产空间、仓储与食水补给、交通和防御、撤离与备用据点；写与当地居民的交换或压迫关系，以及失去驻地的后果。

载体：kv；按上面的要求拆分具体字段和条目。

### 4. 组织架构

说明权力合法性、最高决策、财政与武力由谁掌握、部门协同、情报传递、监督及申诉、纪律与奖惩、首领继任和紧急授权。写实际权力与名义职务的差异，防止组织只由一个首领和无名手下组成。

载体：table；表头：层级或部门 / 职责与权限 / 负责人及制衡 / 决策与执行 / 继任和问责。

### 5. 人员构成

写核心、骨干、普通成员、外围和依附人口的规模或比例；招募筛选、训练、考核、晋升、报酬、抚恤与退出机制。核心人物各有目标、资源、立场和弱点，说明成员为什么加入、留下或背叛。

载体：table；表头：群体或核心人物 / 来源与招募 / 职责与能力 / 待遇及晋升 / 忠诚与退出代价。

### 6. 经济来源

写提供什么产品或服务、客户是谁、原料供应、生产运输销售链、收费和结算、价格依据、竞争优势；逐项列固定及变动成本、利润或亏损、税费债务、储备和利益分配。使用同一周期与货币说明收支平衡，估算注明假设；资助型组织写资金条件，不强行盈利；明确断供、封锁、客户流失的后果。

载体：table；表头：业务与客户 / 收入与交易方式 / 成本及利润 / 利益分配 / 依赖与断供后果。

### 7. 组织历史

按创立、扩张、转折与当下梳理实际适用阶段；记录奠基资源、关键人物、胜败与分裂、制度变迁及历史债务。每个事件解释今天的利益、禁忌或敌对关系；新成立组织不强编悠久历史。

载体：table；表头：时期与依据 / 关键事件 / 资源和权力变化 / 遗留制度或债务 / 对当前的影响。

### 8. 内部派系与矛盾

区分理念之争、分配之争、继承之争与路线之争；写各派控制的部门、钱粮、武力或信息，日常妥协方式、联盟、关键摇摆者、导火索和组织承受极限。没有公开派系时写潜在利益裂缝而非凭空分裂。

载体：table；表头：派系与代表 / 利益及资源 / 争议与底线 / 斗争手段 / 爆发条件与后果。

### 9. 外部关系

明确敌对势力有哪些、为什么结仇、争夺什么资源或秩序、双方能采取什么行动；同时覆盖盟友、交易伙伴、中立者、上级监管和主角。写合作条件、制裁手段、依赖与背叛代价，关系变化必须有触发事件。

载体：table；表头：对象及实力差 / 关系与历史原因 / 争夺或交换的利益 / 手段和底线 / 升级或缓和条件。

### 10. 剧情作用

列资源入口、身份门槛、任务、压迫、庇护、试炼、情报与伏笔，逐项写关联人物、触发条件、主角选择、收益与代价及后续局势变化；组织行动应源于自身利益，不是随叫随到的任务发布器。

载体：list；按上面的要求拆分具体字段和条目。

### 11. 写作约束

检查人数、财政、物流、响应时间、权力层级和对外关系的一致性；明确能动员什么、多久到达、不能跨越的边界。组织遭受损失必须影响后续行动；记录待确认问题与时点，禁止无限兵力、无限资金或全员同心。

载体：list；按上面的要求拆分具体字段和条目。

### 结构化与保存

同时输出完整 MD 与 JSON。单对象顶层字段 `factionProfileData`，多个对象用 `factionProfiles` 数组；每个对象为 `{name,tag,tagline,sections}`，section 使用 `{kind,heading,items}`（kv 的 items 为 label/text 对象，list 为字符串）或 `{kind:"table",heading,head,rows}`。各分区标题、顺序及内容必须与 MD 等价，不得缩成摘要。

软件套用 `faction-system/profile.html`，不要自行输出 HTML/CSS。最后按既有 outlineSaveRequest 协议输出保存请求，只有用户确认后才落盘。

## 交付前自检

第二版详细档案标准：不是展示简介。基本身份、生活与供给、运行机制、权限与例外、失败后果、当前时点、知情范围、关联对象及写作场景均须具体；每个重要机制给出可核验的条件和后果，而非只增加段落数量。
数值闭合：组织收入、成本、利润、分配与现金流分开；人员分组与总人数吻合；同一行程的距离、速度、有效行进时长和等待时间一致；人物的收入、生活费、债务与储蓄互相成立。缺少依据时给明确假设，不硬凑精确数字。
同一事实只设一个当前基准：说明章节或时点，将未来升级、人物出场、伏笔回收与当前状态分开。跨人物、组织、地图、地点、卷纲和章纲的名称、时间、位置与证据应能相互核对。关联对象写名称和作用，不自行捏造文件路径或链接。
完整不是堆字数：覆盖本类全部分区与关键字段。重要对象逐项写清对象、机制、条件、代价、变化及正文用法，不能只列名词或写一句空泛评价；同一信息不反复复制充数。
区分【已确认】【设计提案】【待确认】。新建设定允许基于题材和已有材料提出具体、内部一致的设计，不用整页待补充敷衍；补完已有设定不得改写正史。关键未知写清问题、影响与可选设计，不能编造成已确认事实。
记录必须区分【计划】与【已发生】，注明章节或时点及依据；没有正文证据不得虚构出场、解锁、埋设或回收记录。无明确章号用阶段，作者真相不得越过人物认知边界。
按题材适配：非营利组织解释收支平衡，无任务金手指写使用史，无分级力量写可验证能力边界；不适用项说明原因及等价约束，不硬套仙侠、系统或公司模板。
跨档案核对人物、势力、地点名称、时间线、交通耗时、经济口径、能力边界、关系和伏笔ID；新增提案不得静默覆盖已确认内容，冲突明确列出。
每个分区包含能够指导具体场景的细节，关键机制给触发—行动—结果—代价的示例。数字写单位、周期、依据或估算假设，不能伪造精确度；禁止省略号、略、同上、其余同理等占位。
MD正文与结构化JSON必须内容等价：每个分区、字段、表格、说明和例子均须保留，不能把JSON缩成摘要。长说明用kv条目；表格长解释保留在对应单元格，禁止因排版删除正文。
多个对象分别完整输出并保持名称匹配，禁止混用他人档案。输出预算不足时缩小批次或继续完成当前对象，不压缩必填分区，不把截断草稿冒充完整档案；沿用现有保存确认流程。

## 第二版 HTML 阅读方式

软件按分区语义自动呈现档案卡、时间线、等级阶梯、资源与关系清单，并保留完整原始对照表。只提供内容和结构化数据，不自行装饰 HTML，不省略长字段来适应排版。

## 设定类单对象低重复输出

每轮最多生成一个完整对象；保留全部分区、详细字段及配套结构化JSON，不减少信息深度。先输出完整MD正文，再输出本对象的完整JSON，最后输出 outlineSaveRequest。保存请求的 content=""，由软件从同一回复的MD正文回填；不要在保存请求中重复抄写同一篇正文。其余保存字段照常填写，不调用写入工具替代用户确认。多个待生成对象仅列未完成名称，等用户继续，不把多个完整对象挤入本轮。

已收到正文但流式中断时仍是未完成草稿，不得声明生成或保存成功。不要为避免中断删减内容或编造已完成状态。
