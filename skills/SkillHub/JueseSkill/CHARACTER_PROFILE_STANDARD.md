# 人物角色信息标准

## 使用范围

本标准用于 AI 大纲会话生成、补全、改写人物角色文件。角色文件不是普通人物小传，而是后续 AI 写章纲和正文时读取的“角色卡 + 语言风格卡 + 关系卡”。

文件命名建议：

```text
角色/{角色名}.md
角色/男主/{角色名}.md
角色/女主/{角色名}.md
角色/男配/{角色名}.md
角色/女配/{角色名}.md
角色/反派/{角色名}.md
```

如果项目只有少量角色，可以先放在 `角色/{角色名}.md`；当角色数量增多时，再按男主、女主、男配、女配、反派、导师、盟友、上级、情感型配角等分类移动。

## 角色类型

| 类型 | 重点记录 |
|---|---|
| 男主/主角 | 显性身份、隐性身份、金手指、核心动机、当前能力、弱点、成长状态 |
| 女主/核心情感角色 | 身份背景、关系推进、情绪变化、隐藏背景、与主角互动方式 |
| 男配/女配 | 剧情功能、与主角关系、独立目标、资源或情绪作用 |
| 反派 | 利益动机、攻击手段、资源层级、压迫方式、失败节点、是否有洗白空间 |
| 导师/上级 | 权限资源、决策风格、庇护或压制方式、不能替主角解决的问题 |
| 盟友/队友 | 补位功能、独立行动、与主角的信任变化 |
| 情感型配角 | 情绪触发器、隐痛、主题连接、对主角造成的情绪影响 |
| 工具型配角 | 信息、资源、入口、冲突或反应层功能；重要工具人必须反工具化 |

## 人物小传详细内容契约

每个对象必须按顺序覆盖以下 6 个分区；逐条落实字段，不将一整区压缩成一句概述。

### 1. 基本信息

姓名、年龄与时间基准、性别、显性及隐藏身份、阵营、职业与生计、收入与债务、住所及日常活动范围、家庭与教育、能力与资源、伤病及当前处境；说明这些条件如何限制行动，而非只列标签。

载体：kv；按上面的要求拆分具体字段和条目。

### 2. 角色定位

在主线中的独立目标、故事功能、情绪功能、主题立场、与主角的对照和不可替代性；区分短期任务与长期欲望，说明利益冲突、主动行动、登场阶段及退场条件，配角也有不围绕主角运转的生活。

载体：kv；按上面的要求拆分具体字段和条目。

### 3. 外在表现

外貌辨识点、衣着及磨损、姿态、步态、惯用动作、饮食作息、随身物品、职业习惯；分别写放松、受压、说谎时可观察的变化，给出可直接入正文的动作细节，不用形容词堆砌代替表现。

载体：kv；按上面的要求拆分具体字段和条目。

### 4. 内在分析

成长经历按时间说明家庭、教育、关键创伤和成败如何形成信念；写欲望、恐惧、羞耻、底线、缺陷、认知偏差、防御机制和秘密；分别写他知道、误以为知道、不知道的事实及获知渠道，防止角色越界用上还没得知的信息；设计诱因—选择—代价—信念变化的弧线，列出可能做与绝不会做的事。

载体：kv；按上面的要求拆分具体字段和条目。

### 5. 语言风格

区分面对亲近者、上位者、敌人、陌生人及极端压力时的说话方式；写句长、语气、口头习惯、称呼、隐瞒与禁用措辞。每种重要场景给出原创示例对白和潜台词，语言差异应源于经历与利益。

载体：table；表头：对象与场景 / 措辞与节奏 / 潜台词与回避 / 示例对白 / 变化条件。

### 6. 关系网络

写亲缘、师承、盟友、敌对、债权和情感关系；逐个交代双方各想得到什么、掌握对方什么秘密、权力是否对等、信任程度、最近变化及决裂或修复条件。关系变化必须有事件和成本，不能只有好友或敌人标签。

载体：table；表头：对象与共同经历 / 公开关系与真实态度 / 利益与依赖 / 秘密与冲突 / 变化触发与代价。

### 不属于小传的三类内容

- **出场记录**：章节记忆在每章入库时自动维护，档案里再排一张静态表必然过期；没有正文时更只能编「计划出场」。要查某角色在哪几章出现，去看正文与记忆，不看小传。
- **当前状态**（位置、伤病、体力、资源、任务、可用能力）：由 `.novel/character-states.json` 每章更新，是运行时的单一权威。档案里再写一份就成了两个基准，改章不改档案迟早互相打脸。
- **写作使用规则**：那是给模型的执行约束，不是设定内容。用户读它拿不到任何新信息，模型读了也照旧守不住，纯粹是每份档案多付一段 token。

别名不单开一张表：真有化名、尊称、组织代号，写进「基本信息」一行即可；没有就别为它写「暂无别名及原因」。

### 结构化与保存

只输出结构化 JSON，不要手写 MD 正文 —— 软件会把数据一个字段不落地还原成 .md 与角色卡 HTML。单对象顶层字段 `characterProfileData`，多个对象用 `characterProfiles` 数组；每个对象为 `{name,tag,tagline,sections}`，section 使用 `{kind,heading,items}`（kv 的 items 为 label/text 对象，list 为字符串）或 `{kind:"table",heading,head,rows}`。

软件套用 `character-design/profile.html`，不要自行输出 HTML/CSS。最后按既有 outlineSaveRequest 协议输出保存请求，只有用户确认后才落盘。

## 生成规则

1. 人物角色文件必须服务写作，不允许只堆年龄、身高、外貌、家世等静态资料。
2. 每个重要角色必须写清“故事功能”和“情绪功能”，否则正文中容易变成无效出场。
3. 每个重要角色必须有“语言风格”，并标注面对不同对象时的说话差异。
4. 补全角色时只核对正文证据，改写已确认的内容要说明依据；没写过的经历不得编成已发生。
5. 角色行为必须能回到动机、信念、弱点或当前关系，不允许为了剧情需要突然变蠢、变善、变坏。
6. 反派必须有自己的利益或目标。短线小反派可以恶得直接，但仍要写清手段、收益和退场方式。
7. 配角必须有独立目标或明确功能。只说话、不改变局面、不给情绪作用的配角应删除或合并。
8. 情感型角色必须写清情绪触发器和关系阶段，不允许只写“喜欢主角”。
9. 缺少原文信息时写“原文未明确”或“待后续补充”，不能编造成已确认事实。

## 简版兼容

从旧人物小传导入时，常见字段为：身份、性格、能力、经历、关系、别名。导入后必须补齐：

- 故事功能
- 情绪功能
- 核心动机
- 弱点/缺陷
- 语言风格
- 面对不同对象的说话差异

## 写作检查清单

- [ ] 角色类型明确
- [ ] 故事功能明确
- [ ] 情绪功能明确
- [ ] 核心动机和弱点能推动剧情
- [ ] 语言风格与其他角色可区分
- [ ] 面对不同对象的说话差异明确
- [ ] 关系网络有最近变化

## 详细设定共同质量要求

第二版详细档案标准：不是展示简介。基本身份、生活与供给、运行机制、权限与例外、失败后果、当前时点、知情范围、关联对象及写作场景均须具体；每个重要机制给出可核验的条件和后果，而非只增加段落数量。
数值闭合：组织收入、成本、利润、分配与现金流分开；人员分组与总人数吻合；同一行程的距离、速度、有效行进时长和等待时间一致；人物的收入、生活费、债务与储蓄互相成立。缺少依据时给明确假设，不硬凑精确数字。
同一事实只设一个当前基准：说明章节或时点，将未来升级、人物出场、伏笔回收与当前状态分开。跨人物、组织、地图、地点、卷纲和章纲的名称、时间、位置与证据应能相互核对。关联对象写名称和作用，不自行捏造文件路径或链接。
完整不是堆字数：覆盖本类全部分区与关键字段。重要对象逐项写清对象、机制、条件、代价、变化及正文用法，不能只列名词或写一句空泛评价；同一信息不反复复制充数。
区分【已确认】【设计提案】【待确认】。新建设定允许基于题材和已有材料提出具体、内部一致的设计，不用整页待补充敷衍；补完已有设定不得改写正史。关键未知写清问题、影响与可选设计，不能编造成已确认事实。
记录必须区分【计划】与【已发生】，注明章节或时点及依据；没有正文证据不得虚构出场、解锁、埋设或回收记录。无明确章号用阶段，作者真相不得越过人物认知边界。
按题材适配：非营利组织解释收支平衡，无任务金手指写使用史，无分级力量写可验证能力边界；不适用项说明原因及等价约束，不硬套仙侠、系统或公司模板。
跨档案核对人物、势力、地点名称、时间线、交通耗时、经济口径、能力边界、关系和伏笔ID；新增提案不得静默覆盖已确认内容，冲突明确列出。
每个分区包含能够指导具体场景的细节，关键机制给触发—行动—结果—代价的示例。数字写单位、周期、依据或估算假设，不能伪造精确度；禁止省略号、略、同上、其余同理等占位。
结构化字段必须承载完整正文：每个分区、字段、表格、说明和例子均须保留，不能缩成摘要。长说明用kv条目；表格长解释保留在对应单元格，禁止因排版删除内容。
多个对象分别完整输出并保持名称匹配，禁止混用他人档案。输出预算不足时缩小批次或继续完成当前对象，不压缩必填分区，不把截断草稿冒充完整档案；沿用现有保存确认流程。

## 设定类单对象低重复输出

每轮最多生成一个完整对象；保留全部分区与详细字段，不减少信息深度。只输出本对象的结构化JSON，再输出 outlineSaveRequest（`content=""`，正文由软件从结构化数据生成）；不要手写 MD 正文，不要在保存请求里重复抄写内容。其余保存字段照常填写，不调用写入工具替代用户确认。多个待生成对象仅列未完成名称，等用户继续，不把多个完整对象挤入本轮。

已收到正文但流式中断时仍是未完成草稿，不得声明生成或保存成功。不要为避免中断删减内容或编造已完成状态。
